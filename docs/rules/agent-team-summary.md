# サブエージェント・エージェントチーム活用ルール（サマリー版）

> 完全版は `docs/rules/agent-team.md`（Haiku 推奨スキル一覧・モデル指定方針の SSOT・プロジェクト固有オブザーバー詳細）。

## 2 協調モードと振り分け（最重要・常駐）

「エージェントチーム / 専門チーム」には実装が **2 つ** あり、混同しやすい。必ず区別する。

| モード | 実体 | 議論 | 既定で使う場面 |
|--------|------|------|--------------|
| **役割分担型 fan-out** | `Agent` ツールの並列サブエージェント（メインが集計） | なし | 内部の自動調査・速度/コスト優先。障害調査（`problem-investigation-protocol.md` Step 3）・定型チェック |
| **議論型（ネイティブ Agent Teams）** | `discussion-review` スキル: メインが lead、参加者は name 付き background `Agent` + `SendMessage` + 共有ホワイトボード | あり（相互に反論・検証） | **ユーザーが明示的に「専門チームを組成して」と指示したとき**・過剰指摘削減が要るレビュー |

**振り分けルール（SSOT・飼い主決定）**

- ユーザーが「専門チームを組成して」「チームで議論して」等と明示したら **議論型（`discussion-review` スキル）が既定**。fan-out で代替してよいのは、コスト/速度優先の明示があるか、議論に値しない軽微なタスクのときだけ（理由を 1 行述べる）
- 議論型の実行前に `discussion-whiteboard-rules.md` を Read し、`discussion-review` スキルの手順に従う
- **障害検出時の内部自動調査は fan-out が既定**（ユーザー明示指示ではないため）
- フォールバック連鎖: ネイティブ失敗 → `tools/run_discussion_review.py`（claude -p 駆動）→ それも失敗なら fan-out。各段の退避をログに残す（サイレントフォールバック禁止）
- 🔴 **`SP-n` スプリント開発・リファインメントの編成の既定は `session-sprint-rules.md` §2 が正本**（単独実行禁止・sp 別の役割数）。本ファイルは汎用の振り分け（議論型 vs fan-out の選び方）のみを扱う

## モデル選択（コスト最適化）

> 🔴 **モデルは「エイリアス」で指定し、厳密バージョン ID を運用ファイルに書かない**（世代交代時の修正が不要になる）。
> 例外は ① API 直叩き ② 料金表など ID をキーにする実装 ③ 意図的なピン留め。SSOT: `agent-team.md`「モデル指定の方針」。

| 用途 | モデル | effort |
|------|--------|--------|
| 知能重視タスク（長文生成・複雑な設計判断） | `opus` | `/effort xhigh`（明示指定。既定は `high`） |
| メインセッション・実装・PR 対応 | `sonnet` | `/effort medium` |
| 調査・検証・チェック（サブエージェント） | `haiku` | — |
| 一区切りに収まらない最難関・超長時間タスク | `fable`（高コスト・既定にしない） | `/effort high`〜 |

**原則**: 迷ったら `sonnet`。`opus` は明確に必要な場合のみ（`.claude/settings.json` の既定が `sonnet` なのは意図的）。コスト削減はまず effort を下げて評価する。詳細は `claude-code-optimization.md`。

## サブエージェント使い分けと並列化

| 状況 | subagent_type | model |
|------|--------------|-------|
| コードベース探索・ファイル検索 | `Explore` | メイン継承（v2.1.198〜）。安くするには `Explore.md` を `model: haiku` で上書き（§F-6） |
| 実装計画・設計 | `Plan` | `sonnet` |
| 実装・API 呼び出し | `general-purpose` | `sonnet` |
| 検証・パターン検索 | `general-purpose` | `haiku` |

- 🔴 **独立した作業は並列で同時実行し、依存があるときだけ逐次にする。その並列化の前提は「設計時点でのファイル非重複分割」**: 委譲する前に、各サブエージェントが書き込むファイル・スコープが **重ならないように分割** する（重なったまま並列起動すると、後勝ちで上書きが消える・整合しない編集が混ざる）。結果のマージ・調整はメインが担う。`isolation: "worktree"` は **メイン ↔ サブの事後隔離** であってこの分割設計を代替しない（分割を怠ったまま worktree を付けても、マージ時に同じ衝突が出るだけ）。Issue / PR / ラベル等の **外部リソースの排他は本項の対象外** で、`session-concurrency-rules.md` の多層防御が担当する
- **層依存があるときの 3 段階**（#112）: ① **契約先行**（型・インターフェース・スキーマだけを 1 体に先に確定させる）→ ② **依存役先行**（その契約に依存する側を起動）→ ③ **並行実行**（契約が固まった以降は非重複分割で同時起動）。契約を決めずに並行起動すると、各役が別々の契約を仮定して整合しない実装が混ざる。**同一ファイルに複数タスクの追記が集中する場合は、そのファイルだけ並列委譲の対象から外して親が集約して書く**（表・索引・enum・スキーマのように **複数役の出力が 1 箇所へ集まる集約先リソース** が対象。委譲前に親が「行 ID とセルの値」を確定させて各役の委譲プロンプトに書く。確定できない場合は集約先の更新を委譲対象から外し、全役の完了後に親が埋めると明示する。設計上の選択として委譲プロンプトか Issue に記録する・#215）
- 🔴 **①の直後・②へ進む前に契約を仕様と突き合わせる**（#174・実測: `retry-after` の判定順を `prd.md` §7 の表と逆に書いた契約で 3 名が並行実装し、Layer 1 セルフレビュー 4 観点が独立に CRITICAL 指摘するまで誰も気づかなかった。実装者は契約を正として作業するため契約の誤りを検知する立場にいない）。**仕様（`prd.md` の該当節）だけを読ませたサブエージェント 1 名** に契約が仕様と一致するか判定させてから②へ進む（追加の役割 1 名・`session-sprint-rules.md` §2 の sp 別役割数を変更するものではない）。`sp:8` は同 §2 の既定どおり `discussion-review` の 1 ラウンドが契約検証も兼ねるため、本項の追加判定は不要
- **委譲前にスコープ重複を機械検査する**（#103・`tools/check_agent_scope_overlap.py`）: 分割設計を確定したら委譲前に実行し、重複が見つかったら逐次実行か分割再設計に切り替える
- **委譲後は完了報告と実 diff を突合する**（#99・`tools/check_agent_diff_claim.py`）: 全サブエージェントの完了報告を受け取ったら実行し、報告と実ファイル状態の食い違い（虚偽報告・報告漏れ）を解消してから次の判断に進む。🔴 **委譲プロンプトには「変更ファイル一覧」を機械可読な明示リストブロック（`CHANGED_FILES:` 行の直後に 1 行 1 パス）で返り値に含めることを必須項目として書く**（#717）。自由文中で「〜は変更していません」等と言及しただけのパスは、ツール側が明示ブロックの外を読まないため claim に混入しない（旧仕様は文字列一致だけで「報告済み」とみなし、否定文脈の言及を誤って claim 扱いし `missing_from_report` を握りつぶす fail-open だった）。明示ブロックが無い報告は全文ヒューリスティックスキャンへフォールバックする（stderr / JSON `fallback_used` で明示・黙って劣化させない）が、新規の委譲プロンプトでは明示ブロック形式を既定にする
- 🔴 **並行実行中は作業ツリー全体を操作する破壊的 git コマンド、および作業ツリーを移動するコマンドを禁止する**（#93 / #768）: 複数役が同時に走っている間、委譲プロンプトで作業ツリー全体を **巻き戻す系**（`git reset --hard` / `git checkout -- .` / `git clean` / `git stash` 等・1 体が巻き戻すと他役の未保存編集ごと消える）だけでなく、**移動する系**（`git checkout <branch>` / `git switch` / `gh pr checkout` 等）も禁じる。実例（#768）: Layer 1 セルフレビューのファインダー 1 体が `gh pr checkout` 相当の操作でブランチを作り `main` へ移動した結果、親セッションの作業ツリーが `main` に切り替わったまま残り、親が「修正した実装が消えている」と誤認した（未コミット変更があれば実際に失われていた）。**コミットは全役の完了後に親がまとめて行う**。⚠️ **Stop フック・PreCompact / PostCompact の WIP 自動コミットは、この規律の外側で動く**（他役が作業中かどうかを知らない）。実装をわざと壊す時間帯を作る作業（変異テスト等）を始める前に `tools/mutation_guard.sh begin` でマーカーを置き、終わったら `end` で外す（TTL 2 時間で自動失効。マーカー中は `stop-git-check.sh` のコミット要求も止まり、`session-start.sh` のクリーンアップは追跡変更をパッチへ退避する）。worktree 分離下の役が `begin` してもリポジトリ全体で共有される。詳細は L-131（`docs/rules/lessons/session-safety.md`）
- サブエージェントは成果物全文でなく **1,000〜2,000 トークンのサマリー** を返す
- 重要な出力（タイトル・設計案等）は Verbalized Sampling（並列候補生成 → 選択）で決める。詳細は `agent-team.md`「サブエージェントの高度な機能」
- `isolation: "worktree"`: 並行して同じファイルを触る変更を隔離する（変更なしなら自動クリーンアップ）
- `run_in_background: true`: 完了時に通知が来る（`sleep` ポーリング禁止）。**push 系を委譲したら必ず `mcp__github__get_file_contents` 等で結果を検証する**（L-080）

## 🔴 並行安全プリアンブル（委譲プロンプトへ貼る実テキスト・SSOT・#816）

サブエージェントは `CLAUDE.md` も `docs/rules/` も自動では読まない。**本節は「読ませる」ためではなく
「貼る」ためのものである**: 委譲元スキルは `Agent` 起動前に本節を Read し、下のコードブロックの中身を
**実テキストのまま委譲プロンプトの先頭へ展開する**。ファイルパスや節名を書いただけでは実行時に
解決されず、サブエージェントには何も届かない（#768 と同型の再発になる）。

```text
親セッションおよび他のサブエージェントが同じ作業ツリーで並行作業している。次の操作は一切禁止する。
- 作業ツリーを巻き戻す系: `git reset` / `git checkout -- <path>` / `git checkout -- .` / `git clean` / `git stash`
- 作業ツリーを移動する系: `git checkout <branch>` / `git switch` / `git worktree` / `gh pr checkout`
- 履歴を進める系: `git commit` / `git push`（コミットは全役の完了後に親セッションがまとめて行う）
ファイルは現在の作業ツリーのまま読み書きする（チェックアウトし直さない・ブランチを切らない）。
差分が要るときは `git diff` / `mcp__github__pull_request_read(method="get_diff")` で取得する。
```

- **役割が読み取り専用のとき**（レビュー・調査・議論）は、貼った直後に `ファイルの編集も禁止する。` を 1 行足す。
  逆に実装役へは足さない（編集は実装役の仕事であり、禁止すると役割そのものが成立しない）
- コードブロックは **短く保つ**（貼る側のプロンプト予算を食うため）。背景・実例・例外の説明はこの上の
  箇条書き（#93 / #768 の行）が持ち、貼るテキストには入れない
- 新しく委譲テンプレートを持つスキルを追加したら、本節への参照と展開手順を必ず書く。再掲漏れは
  `python3 tools/check_delegation_preamble.py` が検知する（`tools/run_checks.sh` に配線済み）
- **`research-runner` は本節の対象外**（#816 の調査表に載りながら完了条件の 4 スキルに含めなかった理由）: 同スキルの並列化は `Agent` ツールでの委譲ではなく `claude -p` サブプロセス（cwd = 一時ディレクトリ）経由であり、親と同一の作業ツリーを共有しないためプリアンブルを貼る先が無い。将来 `Agent` 起動へ拡張したら `tools/check_delegation_preamble.py` の明示リストへ追加する

## 🔴 委譲が「空回答・期待外」になる要因（#367・常駐チェック）

**委譲プロンプトに必ず書く 4 点**: ① 必要なルールを再掲する（`Explore` / `Plan` は **CLAUDE.md を読まない**）
② 返答の言語・形式を明示する（**output style は継承されない** ため `concise-neko` は届かない）
③ 「最終テキストは親への返り値」と伝える（サイレント規律 L-111 の過剰適用で返り値が痩せる）
④ **アプリコードを書かせる場合は「`src/domain/ports/` を確認し、時刻・乱数・キャッシュ・レート制限は既存ポート経由にする（無ければ新設し、既存の抽象を二重に作らない）」を書く**（#91・`architecture-rules.md` §1.5。並列 fan-out では **同じ PR で他役が導入したポートが見えない** ため、書かないと同じ抽象が二重に生まれる）。

**空回答を見たら**: `tools` が background フィルタ（v2.1.198 以降 background が既定）で全滅していないか
（`python3 tools/check_agent_definitions.py`）→ API 打ち切りでないか、の順に切り分ける。フィルタ表と
Agent Teams の制約（teammate から background 不可・nested team 不可・`TeamCreate` 廃止）は
`agent-team.md` §F-1〜F-7。

## 🔴 独立した複数対策を 1 委譲に含めるときはデータフロー干渉を検証させる（#725）

**適用範囲**: 1 体のサブエージェントに **独立した複数の対策**（例: A「変更ファイルを明示ブロックで返す」+ B「巨大入力を先頭 N 文字で切り詰める」）をまとめて委譲するとき。実例（#725）: B の切り詰めを `main()` の先頭で行う実装にしたため、切り詰め位置より後ろにあった A の明示ブロックが消え、A が無効化された。**各対策は単体では self-test 全緑**（切り詰めだけ・明示ブロックだけを検証するテストは通る）で、Layer 1 セルフレビューが実測するまで誰も気づかなかった。

複数の役が別ファイルを分担する契約ずれ（#112 / #174）とは別種の欠陥で、**1 体・1 ファイル内の同一関数を対策同士が同じデータフローで通る順序の見落とし**（入力の完全性・呼び出し順序・共有状態の干渉）が原因。委譲プロンプトに次を書く:

```
このタスクは独立した N 個の対策を含む。実装後、各対策が同じ入力・同じ変数を通る順序を書き出し、
片方が他方の前提を壊していないかを self-test で示すこと（例: 対策 A の効果が対策 B の適用後も残るケース）。
```

- 検証の形は「対策 A の効果が対策 B の適用後も残ることを確かめるテスト」を **1 件以上** 置くこと（各対策の単体テストだけでは不十分）
- 各対策が単体で正しくても、片方が他方の前提（入力の完全性・呼び出し順序・共有状態）を壊すことがある
- 🔴 **委譲プロンプトに `干渉検証: 実施済み（テスト名）` または `干渉検証: 対象外（理由）` の 1 行を返り値へ必須で含めさせる**。親は「委譲後は完了報告と実 diff を突合する」（#99）と同じタイミングでこの行の有無を確認する（書かせるだけでは読み飛ばされたことを親が検知できない）
- 関連: #474（検査ツール委譲の必須項目）・`sprint-development-rules.md` `SD-2` の変異対象選定（#686）は「self-test が緑でも実装の欠落・相互作用・本番経路の未通過を見逃す」という同じ根本問題の別局面

## 🔴 完了報告のタイミングと上限（#375・常駐チェック）

- **結果は「後のターンの完了通知」で届く**（v2.1.211 公式仕様）。委譲直後のターンで結果を語れないのは正常。
  通知前に「完了しました」と書くのは L-113（捏造）、**通知後に統合報告を省くのは L-111 の過剰適用**
  （委譲結果の報告はサイレント対象外・`output-verbosity-rules.md` §3.1）。
- **そのターン内で結果が要るなら `run_in_background: false`**（同期実行）。セッション全体で同期にするなら
  `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`（frontmatter `background: false` は同期化の手段として
  公式定義されていない）。完了済みは `/tasks` に done で残り、`SendMessage` で再開できる。
- **上限**（超過は spawn 失敗）: 同時 20 / ネスト深度 3（v2.1.219〜。v2.1.217〜218 だけ 1 だった）。
  **セッション合計 200 の上限は v2.1.224 で撤廃**（長時間セッションでも新規エージェント作成を拒否しなくなった）。
  詳細と環境変数は `agent-team.md` §F-8〜F-10。

## Haiku サブエージェント向けプロンプト先頭テンプレート

> Haiku は Claude 5 世代ではないため、**明示的な出力ルールを省略しない**（「判断に委ねる」方針の適用外・#326）。

```
# 出力ルール（必ず守ること）
- 箇条書き・要点のみ（詳細説明・前置き・謝辞は省略）
- ファイル全文でなくパスと行番号のみ返す
- 結果は1,000〜2,000トークン以内
- 処理不能（対象が存在しない・データ破損・前提の欠落）と判明したら、弁明や代替案を書かず
  `<CANNOT_COMPLETE: 理由1行>` だけを返して即終了する
```

> 最後の 1 行は **早期撤退マーカー**。親はこれを見たら再委譲せず自分で原因を切り分ける（背景は `agent-team.md`）。

## 🔴 検査ツール・ゲートを直すタスクの委譲プロンプト必須項目（#474）

**適用範囲**: `tools/check_*.py`・hooks・quality gate 等の **検査ロジック** を新設・修正するタスクの委譲に限る（アプリ機能の実装タスクには適用しない）。PR #456 で 2 サイクルのレビュー往復が発生した原因は、いずれの検査も同じ構造的欠陥（見逃し経路の未列挙・入力バリアントの未検証・exit code の未確認）だった。委譲プロンプトに以下 3 点を **必ず** 含める:

1. **失敗経路の列挙**: 「見逃し（miss）」の状態に至りうる経路を全て書き出させる（正規表現の非マッチ・早期リターン・例外の握り潰し等）
2. **症状のバリアント展開**: 同じ症状を起こす入力形を 2〜3 パターン変えて試させる（大文字小文字・改行位置・引用符の有無等）
3. **テストの到達範囲**: エントリポイント（`main()` またはフック起動点）から exit code まで、テストが実際に貫通しているかを確認させる
4. **（`subprocess` を import する検査のみ）fake runner の argv 検証**（#710）: 終了コードだけを差し替える fake は判定結果を固定値に潰す変異（例: `violations = []`）を見逃す。fake に呼び出しコマンドラインを記録させ、意図したサブコマンド呼び出し・危険な省略の有無・`main()` からの実到達を assert させる（完了条件・判定基準の SSOT は `sprint-development-rules.md` §2 完了条件）

いずれか 1 つでも欠けたプロンプトは「検査器・ゲートを直す」タスクの委譲として不十分とみなす。
