# 検査ツール設計基準（Check Tool Design Rules・SSOT）

> **このファイルは `tools/check_*.py`・hooks・quality gate など「検査ツール」の終了コードと
> fail-open / fail-closed の設計基準の唯一の正本（SSOT）である。**（Issue #709）
>
> **射程**: 新規の検査ツールを書くとき・既存の検査ツールを改修するときに参照する基準。
> **非射程**: 既存 39 本（`ls tools/check_*.py | wc -l`・2026-09-03 JST 時点）の一括棚卸しは含まない
> （逸脱を見つけたら改修のついでに寄せる。全件を揃えるための専用スプリントは立てない）。
> **タスク依存ルール**（Hot 層に常駐させない）: 検査ツールを書く / 直すときにだけ Read する。

---

## 0. なぜ基準が要るか（実測された壊れ方）

fail-open な検査は **緑を返しながら何も守っていない**。検査が無い状態より悪い。「検査があるから安心」
という誤った安心感を配布し、レビュアーがその領域を見なくなるためである。

実例（PR #705）: `.gitignore` の再包含行を削除しても PASS する検査が `npm run check` の必須ゲートに
配線された。Layer 1 セルフレビューの 3 観点が独立に検出して初めて判明した。

同じ穴が毎回入るのは、**新規ツールを書くときに参照できる基準が無く、毎回設計から考え直している**
ためである（`docs/rules/lessons/` に個別の教訓はあるが、終了コード軸の基準は本ファイルが初出）。

## 1. 終了コードの標準

| コード | 意味                     | 判定の性質                                                |
| ------ | ------------------------ | --------------------------------------------------------- |
| `0`    | 合格（違反なし）         | **検査が実際に走り、対象を見たうえで違反が無かった**       |
| `1`    | 違反あり                 | 検査が走り、違反を検出した                                 |
| `2`    | 判定不能                 | 検査自体が成立しなかった（入力不在・パース失敗・外部コマンド到達不可） |

🔴 **`2`（判定不能）を `0` に丸めない。** 黙って PASS するのが最も危険な失敗モードである
（`tools/check_deferred_try_jsonl.py` / `tools/check_prod_drift.py` が明文でこの規約を採る）。

### 逸脱してよいケースと、その書き方

標準の 3 値で表せない状態があるときに限り、**追加のコードを足してよい**（既存コードの意味は変えない）。

- 実例: `tools/check_parallel_safety.py` は `3` = `undetermined`（衝突は無いが判定材料が足りない）を持つ。
  `0` にすると「並行可能」と誤読され、`1` にすると衝突していないのにブロックしてしまうため、どちらへも
  丸められない状態として独立させている。
- 実例: `tools/check_datetime_tz.py` は違反（`❌`）と解析不能（`⚠️`）をどちらも非ゼロで返すが、
  **stderr の先頭記号で呼び出し側が切り分けられる** ようにしている（#445）。

逸脱するときの必須要件:

- [ ] docstring の `終了コード` セクションに全コードの意味を書く（呼び出し側が読む唯一の契約）
- [ ] **なぜ標準の 3 値に収まらないか** を 1 行添える（後から標準へ寄せてよいかの判断材料になる）
- [ ] 呼び出し元（`tools/run_checks.sh`・スキル・hooks）が新コードを正しく解釈することを確認する

## 2. 対象 0 件で終わったときの既定は fail-closed

🔴 **「検査対象が 1 件も無かった」を `0`（合格）で返さない。** 検査対象の選択が壊れているのか、
本当に対象が無いのかを終了コードだけでは区別できないためである。

実例（#706・修正済み）: `tools/check_cjk_markdown.py` は `--under DIR` の単独指定を「`--changed`
併用時の絞り込みフィルタ」としてしか実装しておらず、単独指定すると対象 0 件のまま exit 0 を返していた。
**2 名が独立にこれを踏んだ**（絞り込んだつもりで何も検査していない状態が、緑として報告された）。

### 実装の形

- 既定は「対象 0 件 → 非ゼロで終わる（メッセージに『対象の選択が意図どおりか確認せよ』を含める）」
- **例外にしてよいのは「対象 0 件が日常的に起こりうる」検査だけ**（例: 変更ファイル起点の検査で、
  その種類のファイルを 1 つも触っていない PR）。この場合も:
  - [ ] 0 件を許容する条件をコード内コメントに 1 行残す（なぜ日常的なのか）
  - [ ] 「日常的な 0 件」と「選択の壊れによる 0 件」を **入力の与えられ方で区別する**
        （明示指定 / 絞り込みが与えられているのに 0 件なら CRITICAL、無指定で 0 件なら日常）

## 3. 外部コマンドの終了コードは「何を意味しないか」を確認する

`git` 等の外部コマンドの終了コードをそのまま判定に使う前に、**そのコマンドが返す非ゼロが本当に
検査したい事象を意味するか** を確かめる。

- 実例: `git check-ignore` は index を参照するため、**追跡済みファイルには常に 1 を返す**。
  「1 = ignore されていない」と読むと、追跡済みファイルを全て「ignore 対象外」と判定してしまい、
  分岐そのものが到達不能な死に枝になる（PR #705 の初版がこれだった）。
- 実例: `tools/check_deferred_try_jsonl.py` は `git ls-files --error-unmatch` の終了コードを
  **想定した値以外なら `2`（判定不能）へ倒す**（想定外の値を勝手に「合格」と解釈しない）。

必須要件:

- [ ] 使う外部コマンドの終了コードの意味を **公式ドキュメントまたは実測** で確認する（記憶で書かない・CP-2）
- [ ] 想定外の終了コードは `2`（判定不能）へ倒す。`0` にも `1` にも丸めない
- [ ] self-test では **fake runner に argv を記録させ**、意図したサブコマンドが呼ばれていることを assert する
      （終了コードだけ差し替える fake は、判定結果を固定値へ潰す変異を見逃す・#710。完了条件の正本は
      `sprint-development-rules.md` §2 完了条件）

## 4. self-test は「壊すと落ちる」ことを実測してから配線する

本節は規律を再定義しない。**正本は `docs/rules/sprint-development-rules.md` `SD-2`**（変異テストの
進め方・self-test の実効性確認 #430・本番の主コードパスを変異対象に含める #686）。

本ファイルが足すのは 1 点だけ:

🔴 **終了コードを返す経路（`main()` から `sys.exit()` まで）を変異対象に必ず 1 つ含める。**
判定関数だけを変異させると、「判定は正しいが終了コードへ反映されていない」退行を見逃す
（`tools/check_datetime_tz.py` の docstring が同じ趣旨を明記している）。

## 5. 根拠（既存ツールの実測ばらつき・2026-09-03 JST 時点）

本基準は机上ではなく、下記の実測から逆算している。**各ツールの選択にはそれぞれ理由があり、
本基準は「新規に書くときの既定」を定めるものであって、既存の逸脱を一律に矯正するものではない。**

| ツール                            | 終了コード                            | 備考                                                       |
| --------------------------------- | ------------------------------------- | ---------------------------------------------------------- |
| `check_deferred_try_jsonl.py`     | `0` / `1` / `2`                       | 「判定不能を 0 にしない」を docstring で明文化             |
| `check_prod_drift.py`             | `0` / `1` / `2`（fail-closed）        | `check_deploy_gate.py` の規約を踏襲                        |
| `check_cjk_markdown.py`           | `0` / `1` / `2`                       | `--under` 単独の fail-open は #706 で修正済み              |
| `check_parallel_safety.py`        | `0` / `1` / `3`                       | `3` = `undetermined`（「並行可能」と誤読させないため）      |
| `check_datetime_tz.py`            | `0` / 非ゼロ（`❌` と `⚠️` を記号で区別） | 違反と解析不能を stderr の先頭記号で切り分ける（#445）     |

## 6. 「対象 0 件で exit 0」の機械検出は見送る（#709 完了条件の記録）

**結論: 見送る**（本基準はレビュー規律として運用し、機械検査は作らない）。

理由: 「対象 0 件」の表現がツールごとに違う（空リスト・`None`・早期 `return 0`・`argparse` の
既定値経由）ため、静的に検出しようとすると判定が広すぎて全検査ツールで誤検知するか、狭すぎて
黙って素通りする（fail-open な検査を防ぐための検査自体が fail-open になる）。
`sprint-development-rules.md` `SD-2` の「機械検査の可否（#349 完了条件の記録）」と同じ構造の判断である。

代替の担保: 本基準の §2 を Layer 1 セルフレビュー（観点「テスト」「エラーハンドリング」）が見る。
検査ツールを新設・改修する PR では、レビュー時に「対象 0 件で何が返るか」を必ず 1 度確認する。

---

## 7. 完了・成功の定義（検査ツールを新設・改修したとき）

- [ ] docstring に `終了コード` セクションがあり、返しうる全コードの意味が書かれている
- [ ] 判定不能を `0` に丸めていない
- [ ] 対象 0 件のときの挙動を決めており、`0` を返すなら理由がコード内コメントにある
- [ ] 外部コマンドの終了コードを使うなら、その意味を実測またはドキュメントで確認した
- [ ] 変異テストで self-test が FAIL することを実測し、変異対象に `main()` からの終了コード経路を含めた
