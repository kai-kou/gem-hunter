# 検査ツール設計基準（Check Tool Design Rules・SSOT）

> **このファイルは `tools/check_*.py`・hooks・quality gate など「検査ツール」の終了コードと
> fail-open / fail-closed の設計基準の唯一の正本（SSOT）である。**（Issue #709）
>
> **射程**: 新規の検査ツールを書くとき・既存の検査ツールを改修するときに参照する基準。
> **非射程**: 既存の `tools/check_*.py`（本数は `ls tools/check_*.py | wc -l` で数える）の一括棚卸しは含まない
> （逸脱を見つけたら改修のついでに寄せる。全件を揃えるための専用スプリントは立てない）。
> **タスク依存ルール**（Hot 層に常駐させない）: 検査ツールを書く / 直すときにだけ Read する。

---

## 0. なぜ基準が要るか（実測された壊れ方）

fail-open な検査は **緑を返しながら何も守っていない**。検査が無い状態より悪い。「検査があるから安心」
という誤った安心感を配布し、レビュアーがその領域を見なくなるためである。

実例（PR #705）: `.gitignore` の再包含行を削除しても PASS する検査が `npm run check` の必須ゲートに
配線された。Layer 1 セルフレビューの 3 観点が独立に検出して初めて判明した。

同じ穴が毎回入るのは、**新規ツールを書くときに参照できる基準が無く、毎回設計から考え直している**
ためである（`docs/rules/lessons/` に個別の教訓はあるが、終了コード軸の基準は本ファイルが初出）。

## 1. 終了コードの標準

| コード | 意味                     | 判定の性質                                                |
| ------ | ------------------------ | --------------------------------------------------------- |
| `0`    | 合格（違反なし）         | **検査が実際に走り、対象を見たうえで違反が無かった**       |
| `1`    | 違反あり                 | 検査が走り、違反を検出した                                 |
| `2`    | 判定不能                 | 検査自体が成立しなかった（入力不在・パース失敗・外部コマンド到達不可） |

🔴 **`2`（判定不能）を `0` に丸めない。** 黙って PASS するのが最も危険な失敗モードである
（`tools/check_deferred_try_jsonl.py` / `tools/check_prod_drift.py` が明文でこの規約を採る）。

### 逸脱してよいケースと、その書き方

標準の 3 値で表せない状態があるときに限り、**追加のコードを足してよい**（既存コードの意味は変えない）。

- 実例: `tools/check_parallel_safety.py` は `3` = `undetermined`（衝突は無いが判定材料が足りない）を持つ。
  `0` にすると「並行可能」と誤読され、`1` にすると衝突していないのにブロックしてしまうため、どちらへも
  丸められない状態として独立させている。
- 実例: `tools/check_datetime_tz.py` は違反（`❌`）と解析不能（`⚠️`）をどちらも非ゼロで返すが、
  **stderr の先頭記号で呼び出し側が切り分けられる** ようにしている（#445）。

逸脱するときの必須要件:

- [ ] docstring の `終了コード` セクションに全コードの意味を書く（呼び出し側が読む唯一の契約）
- [ ] **なぜ標準の 3 値に収まらないか** を 1 行添える（後から標準へ寄せてよいかの判断材料になる）
- [ ] 呼び出し元（`tools/run_checks.sh`・スキル・hooks）が新コードを正しく解釈することを確認する

## 2. 対象 0 件で終わったときの既定は fail-closed

🔴 **「検査対象が 1 件も無かった」を `0`（合格）で返さない。** 検査対象の選択が壊れているのか、
本当に対象が無いのかを終了コードだけでは区別できないためである。

実例（#706・修正済み）: `tools/check_cjk_markdown.py` は `--under DIR` の単独指定を「`--changed`
併用時の絞り込みフィルタ」としてしか実装しておらず、単独指定すると対象 0 件のまま exit 0 を返していた。
**2 名が独立にこれを踏んだ**（絞り込んだつもりで何も検査していない状態が、緑として報告された）。

### 実装の形

- 既定は「対象 0 件 → 非ゼロで終わる（メッセージに『対象の選択が意図どおりか確認せよ』を含める）」
- **例外にしてよいのは「対象 0 件が日常的に起こりうる」検査だけ**（例: 変更ファイル起点の検査で、
  その種類のファイルを 1 つも触っていない PR）。この場合も:
  - [ ] 0 件を許容する条件をコード内コメントに 1 行残す（なぜ日常的なのか）
  - [ ] 「日常的な 0 件」と「選択の壊れによる 0 件」を **入力の与えられ方で区別する**
        （明示指定 / 絞り込みが与えられているのに 0 件なら CRITICAL、無指定で 0 件なら日常）

## 3. 外部コマンドの終了コードは「何を意味しないか」を確認する

`git` 等の外部コマンドの終了コードをそのまま判定に使う前に、**そのコマンドが返す非ゼロが本当に
検査したい事象を意味するか** を確かめる。

- 実例: `git check-ignore` は index を参照するため、**追跡済みファイルには常に 1 を返す**。
  「1 = ignore されていない」と読むと、追跡済みファイルを全て「ignore 対象外」と判定してしまい、
  分岐そのものが到達不能な死に枝になる（PR #705 の初版がこれだった）。
- 実例: `tools/check_deferred_try_jsonl.py` は `git ls-files --error-unmatch` の終了コードを
  **想定した値以外なら `2`（判定不能）へ倒す**（想定外の値を勝手に「合格」と解釈しない）。

必須要件:

- [ ] 使う外部コマンドの終了コードの意味を **公式ドキュメントまたは実測** で確認する（記憶で書かない・CP-2）
- [ ] 想定外の終了コードは `2`（判定不能）へ倒す。`0` にも `1` にも丸めない
- [ ] self-test では **fake runner に argv を記録させ**、意図したサブコマンドが呼ばれていることを assert する
      （終了コードだけ差し替える fake は、判定結果を固定値へ潰す変異を見逃す・#710。完了条件の正本は
      `sprint-development-rules.md` §2 完了条件）

## 4. self-test は「壊すと落ちる」ことを実測してから配線する

本節は規律を再定義しない。**正本は `docs/rules/sprint-development-rules.md` `SD-2`**（変異テストの
進め方・self-test の実効性確認 #430・本番の主コードパスを変異対象に含める #686）。

本ファイルが足すのは 1 点だけ:

🔴 **終了コードを返す経路（`main()` から `sys.exit()` まで）を変異対象に必ず 1 つ含める。**
判定関数だけを変異させると、「判定は正しいが終了コードへ反映されていない」退行を見逃す
（`tools/check_datetime_tz.py` の docstring が同じ趣旨を明記している）。

## 5. 検査ツールの実行場所を決める（#164）

🔴 **検査ツールは「書いたら終わり」ではない。「どこで実行されるか」を決めて記録するまでが新設・改修の作業である。**
実行場所が決まっていない検査は、緑にも赤にもならないまま死蔵し、レビュアーには「検査がある」とだけ見える
（§0 の fail-open と同じ構造の誤った安心感を配布する）。

### 5.1 3 区分と配線先の決め方

| 区分    | 判定基準                                                           | 本判定の配線先                                             |
| ------- | ------------------------------------------------------------------ | ---------------------------------------------------------- |
| **(a)** | PR 前の品質ゲートとして意味がある（差分に対して毎回走らせて損がない） | `tools/run_checks.sh` に本判定を配線する                    |
| **(b)** | 実行に本番疎通・外部 API・ネットワークが要る                       | 本判定は配線しない（外部要因で全 PR が赤くなるため）。`--self-test` だけを配線する |
| **(c)** | 親が手動で叩く / 特定スキル・フックからのみ起動する運用ツール       | 本判定は配線しない。代わりに **スクリプトへ `# tool-wiring-ok: {理由}` マーカーを書く（必須）**。§5.3 表 A への追記はその併記 |

判定に迷ったら **(a) を既定にする**。「PR ごとに走ると重い / 外部に依存する / 手遅れになる（着手前・委譲前に
効く判定である）」という具体的な理由を 1 行書けないなら、それは (a) である。

### 5.2 🔴 「本判定を配線しない」と「`--self-test` を配線しない」は別の判断である

この 2 つを混同して片方だけ決めると、決めなかった側が死蔵する。**必ず 2 つとも明示的に決める。**

- **本判定**（そのツールが実際に検査対象を見る実行）: どこで走るのか。`run_checks.sh` か、スキルか、フックか、親の手動実行か。
- **`--self-test`**（ネットワーク・実データ非依存のユニットテスト）: ほぼ常に `run_checks.sh` へ配線してよい。
  本判定が (b)(c) で配線されなくても、self-test は PR ごとに走らせる価値がある（回帰を止める唯一の層になる）。

典型的な組み合わせは「本判定は (c) で `run_checks.sh` 非配線・`--self-test` は配線」である。
「両方とも非配線」を選ぶには、**両方について** 理由をマーカーに書く必要がある。

### 5.3 記録済みの決定（全数の一覧ではない）

🔴 **本節の 2 つの表はいずれも「全数記録」ではない。** 本判定を `run_checks.sh` に配線していないスクリプトは
これより多く、その全数が要るときは `python3 tools/check_tool_wiring.py --json` を叩いて実測する
（表に無い＝`run_checks.sh` で走っている、ではない）。

#### 表 A: `# tool-wiring-ok:` マーカーで機械検査から除外しているもの

`tools/check_tool_wiring.py` の除外契約と 1:1 で対応する（マーカーを持つものだけがここに載る）。

| スクリプト                     | 本判定の実行場所                                                            | 配線しない理由                                                                            |
| ------------------------------ | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `check_agent_scope_overlap.py` | 並列委譲の直前に親が手動実行（`docs/rules/agent-team-summary.md` の指示）    | 委譲前に効く判定で、PR 直前の一括検査では手遅れ                                            |
| `check_issue_labels.py`        | Issue 棚卸し時に手動実行（`--self-test` のみ配線済み）                      | 本判定（`--check`）は GitHub API への実疎通が必要（#288 と同じ扱い）                       |
| `check_roadmap_status.py`      | ロードマップ更新時に手動実行（`--self-test` のみ配線済み）                  | 同上（GitHub API への実疎通が必要）                                                        |
| `check_tracked_intent.py`      | 追跡ファイルを投入した時点で `run_checks.sh` へ配線する（現在は `--self-test` のみ配線済み） | 本判定は追跡ファイルが 0 件の間つねに FAIL する（`run_checks.sh` 4.12 節・PR #638 レビュー） |

🔴 **下 3 本は #164 の本文が名指ししていなかった非配線**（`tools/check_tool_wiring.py` の新設で初めて機械検出された）。
いずれも `run_checks.sh` のコメントには実行場所と理由が書かれており、§5 冒頭の定義でいう「死蔵」ではない
（**機械には見えていなかった非配線** である）。「死蔵」の語は実行場所そのものが決まっていないものにだけ使う。

#### 表 B: #164 が名指しした 5 本の実行場所

Issue #164 の完了条件（「5 本すべてに実行場所が記録されている」）を満たすための記録。マーカーの有無とは独立で、
`run_checks.sh` へ配線済みのものも含む。

| スクリプト                       | 本判定の実行場所                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `check_agent_definitions.py`     | `tools/self_review_check.py`（`.claude/agents/` を変更した PR でのみ条件実行）                              |
| `check_claude_code_updates.py`   | `.claude/skills/claude-code-spec-sync/SKILL.md`（定期スロット。ネットワーク必須のため PR ゲートに載せない） |
| `check_datetime_tz.py`           | `tools/run_checks.sh`（本判定・`--self-test` とも配線済み）                                                 |
| `check_pending_pr_reviews.py`    | `tools/pr_review_heartbeat.sh` / `.claude/hooks/session-start.sh` / `pr-review-watcher` ほかセッション復帰系スキル |
| `check_skill_references.py`      | `.claude/skills/skill-audit/SKILL.md`（本判定が現在 exit 1 のため PR ゲートに載せない）                     |

いずれも `--self-test` 側の扱いを独立に決めている（§5.2）。🔴 **正は表ではなく実測である**:
`check_tool_wiring.py` が走査する形の **呼び出し箇所**（§5.4）と **マーカー** の実測が契約であり、
両者と本節の表が食い違ったら **実測に合わせて表を直す**（表に無いことを理由に呼び出し箇所やマーカーを消さない）。
突合は `python3 tools/check_tool_wiring.py --json` で行う。

### 5.4 機械保証の所在

| 軸                | 検査ツール                       | 除外マーカー                     |
| ----------------- | -------------------------------- | -------------------------------- |
| `--self-test` の配線 | `tools/check_selftest_wiring.py` | `# selftest-wiring-ok: {理由}`   |
| **本判定の配線**  | `tools/check_tool_wiring.py`     | `# tool-wiring-ok: {理由}`       |

いずれも **理由が空のマーカーは無効**（除外してよいかを人が判断した形跡を残させるため）。
2 つの検査は独立に走り、片方の除外がもう片方の除外を意味しない（§5.2）。

`check_tool_wiring.py` が **実行場所として認める形** は次のとおり（ここに現れない呼び出しは「未配線」と判定される）。

- `tools/run_checks.sh`
- `.claude/hooks/*.sh`
- `.claude/skills/**/SKILL.md`（再帰）/ `.claude/skills/*/reference.md`
- `.claude/commands/*.md`
- `scripts/*.sh` / `scripts/*.py`
- 他の `tools/*.py` / `tools/*.sh` からの呼び出し
- スクリプト自身の `# tool-wiring-ok: {理由}` マーカー

🔴 **`docs/rules/*.md` は実行場所と認めない。** ルール文書に「実行せよ」と書いても実際には走らない
（それが #164 の教訓そのものである）。ルールに書きたい場合も、実際の起動点はスキル・フック・スクリプトの
いずれかに置く。

### 5.5 新しく `tools/check_*.py` を作ったときにやること

1. **実行場所を決める** — §5.1 の 3 区分に落とす。本判定と `--self-test` を **別々に** 決める（§5.2）
2. **記録する** — (a) なら `tools/run_checks.sh` に配線する。(b)(c) なら該当スクリプトに
   `# tool-wiring-ok: {なぜ本判定を配線しないか}` を書き（**マーカーが必須の記録先**）、実行場所
   （どのスキル・フック・手順から起動するか）を同じ行かその直下のコメントに明記する。§5.3 表 A への
   追記は併記であってマーカーの代わりにはならない（検査は表を読まない）。
   実行場所として認められる形は §5.4 の一覧を参照する（`docs/rules/*.md` への記述は実行場所にならない）
3. **検査が緑になることを確認する** — `python3 tools/check_tool_wiring.py` と
   `python3 tools/check_selftest_wiring.py` を実行し、どちらも PASS することを実測する

## 6. 根拠（既存ツールの実測ばらつき・2026-09-03 JST 時点）

本基準は机上ではなく、下記の実測から逆算している。**各ツールの選択にはそれぞれ理由があり、
本基準は「新規に書くときの既定」を定めるものであって、既存の逸脱を一律に矯正するものではない。**

## 7. 「対象 0 件で exit 0」の機械検出は見送る（#709 完了条件の記録）

**結論: 見送る**（本基準はレビュー規律として運用し、機械検査は作らない）。

理由: 「対象 0 件」の表現がツールごとに違う（空リスト・`None`・早期 `return 0`・`argparse` の
既定値経由）ため、静的に検出しようとすると判定が広すぎて全検査ツールで誤検知するか、狭すぎて
黙って素通りする（fail-open な検査を防ぐための検査自体が fail-open になる）。
`sprint-development-rules.md` `SD-2` の「機械検査の可否（#349 完了条件の記録）」と同じ構造の判断である。

代替の担保: 本基準の §2 を Layer 1 セルフレビュー（観点「テスト」「エラーハンドリング」）が見る。
検査ツールを新設・改修する PR では、レビュー時に「対象 0 件で何が返るか」を必ず 1 度確認する。

---

## 8. 完了・成功の定義（検査ツールを新設・改修したとき）

- [ ] docstring に `終了コード` セクションがあり、返しうる全コードの意味が書かれている
- [ ] 判定不能を `0` に丸めていない
- [ ] 対象 0 件のときの挙動を決めており、`0` を返すなら理由がコード内コメントにある
- [ ] 外部コマンドの終了コードを使うなら、その意味を実測またはドキュメントで確認した
- [ ] 変異テストで self-test が FAIL することを実測し、変異対象に `main()` からの終了コード経路を含めた
- [ ] **本判定の実行場所を決めて記録した**（§5.1 の 3 区分・`run_checks.sh` への配線か `# tool-wiring-ok:` マーカー）
- [ ] **`--self-test` の配線を本判定とは別に決めた**（§5.2・配線しないなら `# selftest-wiring-ok:` マーカー）
- [ ] `python3 tools/check_tool_wiring.py` と `python3 tools/check_selftest_wiring.py` が PASS する
