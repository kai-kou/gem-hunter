## L-128: 認証を足すと「レート枠」だけでなく「データの可視範囲」も広がる（2026-08-19・#142）

**パターン**: レート制限の緩和を目的に外部 API の認証方式を強化・変更した（未認証 → GitHub App の
installation token・`D-20`）ところ、**リポジトリオーナー（ユーザー）から「自分のプライベート
リポジトリが検索対象になっている」という報告があり、それを受けて調査・修正した**。
🔵 **事実関係の限定**: 発覚の契機はユーザー報告であり、こちらで API を叩いて混入を実測・採取した
記録は残していない（「実測で混入を確認した」とは書かない）。
仕様は「GitHub **公開** リポジトリの検索」（`prd.md` §3.1）だったが、それが要件 ID・受け入れ条件・
テストとして落ちておらず、散文でしか書かれていなかったため誰も検出できなかった。

**根本原因**（3 層）:

- **直接原因**: `GET /search/repositories` を installation token（Bearer）で叩き、クエリに公開限定条件を付けていない
- **中間原因**: 「公開のみ」が検証可能な要件（`NFR-n` / `AC-n`）になっておらず、テストが存在しなかった
- **根本原因**: 認証方式の変更を **レート枠・運用コスト・秘密の取り回し** の軸だけで評価し、
  **認証がデータの可視範囲を広げる副作用** を評価しなかった（ADR の比較表にその軸が無かった）

**対策**:

1. 仕様上の範囲（例: 公開のみ）を **アプリ側のクエリとフィルタで明示的に強制する**。認証の権限設定・
   インストール先の運用に委ねない。多層で強制し、1 層欠けても私有データが露出しない構造にする
   （① 利用者キーワード中の修飾子構文（`名前:値` / `-名前:値`）の拒否 ② 検索クエリへの `is:public`
   付与 ③ 結果マッパーでの `private: true` 除外 ④ 詳細応答が `private: true` なら「見つからない」扱い）
   - 🔴 **修飾子を 1 つ足すだけの対策で「範囲が閉じた」と考えない**: GitHub の検索構文は同一修飾子の
     重複指定（`is:private is:public`）を AND として解釈しないため、利用者がキーワードに `is:private`
     や `user:誰か` と書けるままだと `is:public` の付与層は破れる。**利用者入力を検索構文へ素通しする
     経路自体を塞ぐ**（インジェクションとして扱う）
2. その範囲を **検証可能な要件と受け入れ条件に落とす**（本件では `NFR-33` / `AC-12`）。散文で書いて終わりにしない
3. 認証方式を決める ADR の比較表に **「取得しうるデータの可視範囲」の軸を必ず入れる**
   （[ADR 0003](../../adr/0003-github-app-authentication.md) §5.4 に追記済み）

**判定基準**: 「API 呼び出しに認証を追加・変更する PR で、**レスポンスに含まれうるデータの可視範囲の
差分** を確認したか？」 — 未認証／別トークンとの差分（新たに見えるようになるリソースは何か）を
1 行で書けないなら、まだ評価していない。

**禁止パターン / 推奨パターン**:

- ❌ 「権限は `contents:read` だけだから安全」で済ませる（権限の *種類* と可視範囲の *広さ* は別軸）
- ❌ 実測で「公開リポジトリを読めること」を確認して、「公開しか読めないこと」の確認を省く
- ❌ 「クエリに `is:public` を AND 付与したから公開に閉じた」と考える（利用者入力に修飾子構文が
  混ざると破れる。付与とインジェクション遮断は別の層）
- ✅ 認証で広がる可視範囲を洗い出し、仕様の範囲との差分をアプリ側のフィルタで塞ぎ、テストで固定する
