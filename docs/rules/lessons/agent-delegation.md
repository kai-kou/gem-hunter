# Warm 層 教訓 — サブエージェント委譲・Agent Teams（agent-delegation）

サブエージェント / Agent Teams への委譲で「回答が空になる」「期待しない形式で返る」類の教訓を蓄積する。
タスク依存で必要時に Read する（常駐しない）。常駐サマリーは `agent-team-summary.md`、
仕様表の SSOT は `agent-team.md` §「委譲が『空回答・期待外の回答』になる公式要因」。

## L-121: 委譲先が「空回答・期待外の回答」を返すのはハーネス仕様が原因のことが多い（2026-07-29）

**パターン**: サブエージェント / Agent Teams に委譲したのに、返り値が空・極端に短い・英語・
プロジェクト規約を無視した形式で返る。「モデルが怠けた」と解釈して再委譲やプロンプト強化を繰り返すが直らない。

**根本原因（3 層）**:

- **直接原因**: 委譲先に届く前提（ツールプール・コンテキスト・システムプロンプト）が、委譲側の想定と違う。
- **中間原因**: Claude Code の仕様がそれを **エラーなしで** 起こす。
  ① `tools` に書いたツールが 2 段フィルタで **silent に削除** され、全滅すると zero tools（= 空回答）。
  v2.1.198 以降 **background が既定** のため、background 許可リスト外の組み込みツールは常に消える。
  ② `Explore` / `Plan` は **CLAUDE.md を読まない**（公式仕様・変更不可）。
  ③ **output style はサブエージェントに継承されない**（fork を除く）。`concise-neko` の日本語・ねこ規律は届かない。
  ④ API 打ち切り時、**foreground** で出力がツール呼び出しだけだと `Agent terminated early due to an API error`
  （v2.1.199 では **空の partial result**）。**background**（既定）では failed とマークされ、
  終了メッセージにエラー名と最後の出力が含まれる。
- **根本原因**: 「CLAUDE.md とルールに書けば委譲先も従う」という誤った前提でチーム設計をしていた。
  委譲先は **別のシステムプロンプト・別のコンテキスト・別のツールプール** で動く独立実行環境である。

**対策（実装済み）**:

- `agent-team.md` に公式フィルタ表と全制約を F-1〜F-7 として明文化（SSOT）。常駐サマリーを `agent-team-summary.md` に追加。
- `tools/check_agent_definitions.py` が `.claude/agents/*.md` の `tools` を公式フィルタと突合し、
  zero tools（空回答）になる定義を検出する。`tools/self_review_check.py` が `.claude/agents/` 変更時に自動実行する。

**禁止パターン / 推奨パターン**:

```
❌ 「CLAUDE.md に日本語で返すと書いてあるから Explore も従うはず」
✅ Explore / Plan への委譲プロンプトに、必要なルール（言語・形式・除外パス）を毎回再掲する

❌ 空回答を見て「サブエージェントが怠けた」と判断し同じプロンプトで再委譲する
✅ ① tools が全滅していないか（check_agent_definitions.py）② API 打ち切りでないか の順に切り分ける

❌ サイレント規律（L-111）を委譲プロンプトにもそのまま適用する
✅ 「最終テキストは親への返り値。結論・根拠・該当箇所を必ず含める」と明示する（返り値は実況ではない）
```

## L-122: フックが公式スキーマに無いフィールドを読むと、静かに壊れて「偽の観測」を注入する（2026-07-29）

**パターン**: `subagent-stop.sh` が SubagentStop の入力を `is_error` / `result` として読んでいたが、
公式スキーマにこの 2 つは存在しない（正しくは `stop_reason` / `last_assistant_message`）。
`jq` も `.get()` も既定値を返すだけでエラーにならないため、フックは壊れたまま動き続けた。
結果、サブエージェントの異常終了時に **最終出力が常に空の異常報告** をオーケストレータへ注入していた
（`最終出力（末尾）:` の直後が空行）。診断できないうえ、成果が失われたかのような誤った観測になる。

**根本原因（3 層）**:

- **直接原因**: 非実在フィールドを読み、既定値（`false` / `""`）を実データとして扱った。
- **中間原因**: フック入力のフィールド名を公式ドキュメントの **JSON 例（逐語）** と突き合わせず、
  要約・記憶で書いた。フック出力は Claude の観測になるため、誤りが「事実」として下流へ流れる。
- **根本原因**: フックの入力契約に対する機械的・手続き的な検証手段が無く、壊れても誰も気づかない。

**対策（実装済み）**:

- `hook-events-reference.md` §4.5 に「フック入力 JSON のフィールド名は公式スキーマで検証する」と
  Stop / SubagentStop の逐語スキーマを明記。
- `subagent-stop.sh` を `stop_reason` / `last_assistant_message` へ修正し、判定を **fail-safe に反転**
  （既知の異常語を含むときだけ発話し、空・未知の `stop_reason` は無音）。

**禁止パターン / 推奨パターン**:

```
❌ フックの入力フィールド名を記憶や要約から書く（要約経路はフィールド名を取り違える）
✅ 公式 hooks ドキュメントの JSON 例を逐語で確認してから書く（L-113 の姉妹則）

❌ 判定不能なときに「異常」と報告する（Claude の観測を偽情報で汚す）
✅ 異常と断定できるシグナルがあるときだけ発話し、未知・空は無音にする（fail-safe）
```

**姉妹ケース（2026-08-31・PR #730 のレトロ）**: 同じ「識別子を記憶で書く」根から、**MCP ツールの
パラメータ名** でも失敗した。`mcp__github__add_reply_to_pull_request_comment` を `commentID`（大文字 D）
で 5 件連続呼び出し、全て `missing required parameter: commentId` で失敗した（正しくは `commentId`）。
同じセッション内の別ツール `add_comment_to_pending_review` が `pullNumber` を使うため、命名規則を
類推してしまったのが原因。

こちらは fail-closed（即エラー）なので偽の観測は生まれず、実害は往復コストだけで済む。**復旧手順が
確立している点が本エントリの L-122 本体と違う**: `ToolSearch` で `select:<ツール名>` を投げれば
スキーマが返るので、1 回失敗したら記憶で直さずスキーマを取り直す。

```
❌ 別ツールの命名規則から類推してパラメータ名を書く（pullNumber → commentID のような取り違え）
✅ 1 回でも「missing required parameter」が出たら ToolSearch でスキーマを取り直してから再実行する
```

## L-143: 多層防御に対する変異テストは「1 層だけ潰して PASS」を欠陥と読み違える

**症状**: サブエージェントが「防御チェックを削除したら self-test が FAIL した」と報告したのに、親が同じ
変異を再現すると **PASS のまま** になり、報告と実測が食い違う。逆のパターン（1 層だけ潰して FAIL した
のを見て「担保できている」と結論する）も同型。

**実測（PR #743）**: `tools/check_decision_ids.py` の symlink 防御は 2 層構成だった。

```python
if path.is_symlink():                                 # ① リンクそのものを弾く
    continue
resolved = path.resolve()
if not resolved.is_relative_to(resolved_repo_root):   # ② 解決後がリポジトリ配下か検証
    continue
```

| 変異 | self-test | 実害 |
|---|---|---|
| ① のみ無効化 | **PASS** | リポジトリ外 symlink は ② が弾くため **実害なし**（内部 symlink の二重走査が復活するだけ） |
| ①② を同時に無効化 | **FAIL** | 防御が消える |

**① 単独の変異が PASS なのは多層防御として正しい挙動** であり、self-test の欠陥ではない。ところが変異
テストの報告文（「symlink チェックを削除 → FAIL」）だけでは、どの層をどう壊したかが復元できず、親と
担当で結論が割れる。

**対策**:

- **同じ攻撃面に複数の防御層があるときは「全層を同時に潰して落ちるか」を最低ラインにする**。全層を
  潰しても PASS なら、その防御は一切テストされていない
- **単層の変異が PASS だったときは、それを欠陥と結論する前に「どの層が実害を防いだか」を実測で切り分ける**
  （外部リソースを実際に用意して、読まれないことを確認する）
- 変異テストの記録には **壊した箇所を行単位で特定できる形**（関数名 + 条件式）で書く。「〜のチェックを
  削除」だけでは復元できない

```
❌ 「防御チェックを削除 → FAIL」とだけ報告する（どの層かが復元できない）
✅ 「iter_target_files() の is_symlink() と is_relative_to() を同時に無効化 → FAIL」と層を特定して書く
```

**保持理由**: 委譲先の変異テスト報告を親が検証する場面は全スプリントで発生し、食い違いの原因が
「多層防御」だと気づかないと、担当の報告を虚偽と誤認するか、逆に不十分な担保を受け入れるかに倒れる。

## L-146: 変異が源文に当たらないまま「PASS（カバー不十分）」と報告される

**症状**: サブエージェントが変異テストの結果を「一部の分岐は PASS（現在のテストケースでカバー不十分）」
と報告してそのまま完了扱いにする。差し戻して調べると、**変異対象の文字列が源文に存在せず、変異が一度も
適用されていなかった**（置換が 0 箇所ヒットで no-op になり、無変更のまま self-test を走らせて PASS）。

つまり「テストが分岐をカバーしていない」のではなく「**変異テスト自体が実行されていなかった**」。
報告の文面は前者に読めるため、親が「カバー不足なら後で足せばよい」と受け取って見逃す。

**実測（PR #772）**: `tools/check_markdown_table_columns.py` の初版で 4 変異中 2 変異が
「⚠️ PASS: 正規表現（カバー不十分）」「⚠️ PASS: エスケープ保護（カバー不十分）」と報告された。
差し戻し後、担当が harness に「変異が実際に当たったか」の assert を入れたところ、両変異とも
**置換対象が源文に無く未適用** だったと判明した。assert 追加後に回帰ケースを足して再実測すると
7 変異すべてが FAIL を検知した。

**対策**:

- **変異を適用したら「実際に置換が起きたか」を必ず assert する**（`sed` / `str.replace` は対象が
  無くても成功終了する）。Python なら `assert old in src`、シェルなら置換前後の `diff` が非空であること
- **`PASS`（＝ self-test が落ちない）を「カバー不十分」で片付けない**。`SD-2` は「FAIL しない分岐は
  テストされていない」と定めており、回帰ケースを足して FAIL するまでがワンセット
- 委譲プロンプトに「変異が当たったことを確認してから self-test を走らせる」を明記する（#775）

```
❌ 「⚠️ PASS: 正規表現（現在のテストケースでカバー不十分）」で完了報告する
✅ 「変異対象 `^:?-+:?$` が源文に存在することを assert → 置換 → self-test FAIL を確認」まで実測する
```

**保持理由**: 変異テストは `SD-2` の中核だが、no-op の変異は「実施した」という報告だけを残して
検証をゼロにする。L-143（多層防御で単層変異が PASS するのは正常）と症状が似ているため、
**「PASS の理由が多層防御なのか未適用なのか」を切り分けないと、両方向に誤読する**。
