## L-094: ドキュメントと実装が乖離（desync）して「ローカル必須」等の古い前提が残る（2026-06-13）

**パターン**: インフラ・ツールはクラウドで動くように更新されたのに、ドキュメントやスキル手順が
「ローカル実行が必要」「この機能は未対応」と古いまま残り、本来自律実行できる作業をユーザー確認に
回してしまう（CP-6 違反の温床）。逆に、ある処理が SKILL.md 手順で実装されているのかコードで
実装されているのかが曖昧で、二重実装・不整合が起きる。

**根本原因**: ドキュメント（説明）と実装（実体）の更新が同期しておらず、Single Source of
Truth が複数箇所に分散している。

**対策**:
- 「ローカル必須」と書く前に **実際にクラウド実行を試す**（`user-confirmation-minimization.md` §4）
- 実装場所（SKILL.md 手順 / コード）を表に **正確に記載** する（どちらで実装したか明示）
- SSOT を 1 箇所に定め、派生ドキュメントは参照のみにする（独立した重複定義を作らない）
- 機能追加時はドキュメントとコードを同一 PR で更新する

**再発（2026-09-01 JST・PR #747）**: 「散らばりの数え方」を `tools/count_change_scatter.py` の
`categorize()` に実装しながら、同じ PR 内でドキュメント（`.claude/skills/retro-try-handler/reference.md`）には別実装の awk ワンライナーを
残した。両者は同じ入力に対して異なるカテゴリ数を返し（`app/` + `src/` を 1 と数えるか 2 と数えるか等）、
閾値の直上・直下で判定が反転する状態だった。🔴 **スクリプトの docstring 自身が「同じ数え方を 2 か所に
書くと解釈がぶれる」ことを新設理由に挙げていたのに、同じ PR がその状態を再生産した**。
**判定ロジックをコードに実装したら、ドキュメント側には数え方を書き直さず「そのコマンドを呼ぶ」だけにする**
（表を載せる場合は「正本はコード。食い違ったらコードが正しい」と明記する）。検出は Layer 1 の 5 観点が
独立に同じ CRITICAL へ到達して間に合ったが、人手のレビュー依存のままである（機械検出は #699 で検討中）。

## L-145: ドキュメントを正本として機械抽出する実装は、入れ子スコープの一段外側で fail-open を再生産する（2026-09-01）

**パターン**: SSOT を複製しないために「ドキュメントの表をパースして挙動を決める」設計を採ると、
抽出スコープ（文書 → セクション → 行 → 列 → セル内トークン）のうち **絞り込んだ 1 段の外側が
無検証のまま残り**、そこが次の fail-open になる。境界を狭める修正をしても、同じバグクラスが
一段外側へ移動して再発する。

**実測（PR #758・Issue #56 の Cloudflare MCP アローリスト）**: 許可ツール名を
`cloudflare-infrastructure.md` §7.4 の表から抽出する実装で、同型の欠陥が 3 回連続で出た。

| 回 | 検出段階（証跡の所在） | 広すぎたスコープ | 壊れ方 |
| --- | --- | --- | --- |
| 1 | コミット前・コーディネーターの差し戻し（**証跡は PR #758 本文の変異テスト表**「許可集合の抽出を『第 2 列限定』から『行全体』に戻す（当初実装の fail-open）」の行。git 履歴には残らない） | 表の **行全体**（3 列すべて）からバッククォート語を拾う | 第 1 列・第 3 列の英数字のみの語が許可ツール名に混入 |
| 2 | PR 作成後・Layer 1 セルフレビュー（PR #758 のインラインコメント） | 行の特定が **文書全体** への部分文字列一致 | 同じ文言を含む散文を拾い、散文中の `` `d1_database_get` `` が許可になる |
| 3 | 同上（PR #758 のインラインコメント） | 列の特定が **位置決め打ち**（`cut -f3`） | 表に列を 1 つ挿入すると deny 済みツールが許可、正規ツールがブロック |

🔴 **回 1 は最初のコミット（`b316d81`）に入る前に潰れているため、git log を辿っても 3 段階の修正サイクルは見えない**（検証するなら上表の「証跡の所在」を見る）。

**3 回とも self-test は緑だった**（回 1 は 20 ケース / 回 2・3 は 24 ケース）。変異テストも回 2・3 は PR #758 本文に実測表があり、回 1 も実装役が実施を報告している。つまり「テストが実装を撃つか」だけを見る規律では拾えない（撃つべきテスト自体が存在しない段があった）。

**対策**:
- ドキュメントをパースする実装では、**参照する入れ子スコープを列挙** してから書く
  （文書 / セクション / 行 / 列 / セル内トークン）。各段に「その段だけが崩れた」フィクスチャを
  1 件ずつ用意し、**fail-closed に倒れることを実測** する（fail-open に倒れる段があれば CRITICAL）
- 位置（`cut -f3` 等）ではなく **ヘッダの列名から動的に解決** する。解決できなければ fail-closed
- 行の特定は表構造にアンカーする（行頭 `|` + 区分セルの完全一致）。候補行が 0 件でも複数件でも
  fail-closed に倒す（曖昧なら止める）
- 🔴 **ドキュメント側にも同じ文言を書かない**。パーサが探す文字列を散文に複製すると、
  節の並べ替えという無害な編集で挙動が変わる。実例: PR #758 は §7.4 に「本表の『読み取り（許可）』行から
  読み取る」という散文を自分で追記した。**現在の並び順（表が先・散文が後）では発火しない** が、
  散文が表より前に来る編集（説明を先に書く構成へ直す等）に変われば、その散文が拾われて挙動が変わる
- 抽出結果をメッセージ等に出すときも、その場で抽出結果から組み立てる（一覧をハードコードしない）

**関連**: Issue #750（境界の外側の負ケース必須化。本教訓の「外側は 1 段とは限らない」を追記済み）/
`sprint-development-rules.md` `SD-2`（変異テスト）/ `agent-team-summary.md`「検査ツール・ゲートを
直すタスクの委譲プロンプト必須項目」（#474）

## L-147: 検査ツールの `--under` にファイルパスを渡すと、検査対象ゼロのまま素通りする（2026-09-02・PR #805）

**症状**: 変更した 1 ファイルだけを検査するつもりで `--under` にファイルパスを渡すと、検査が 1 件も走らない。

```
$ python3 tools/check_cjk_markdown.py --fix --under docs/rules/github-mcp-fallback-patterns.md
[cjk-md] 警告: --under で指定した配下に .md ファイルが 1 件もありません: [...]
[cjk-md]   → パス指定の誤りがないか確認してください（黙って PASS 扱いにしない）
```

**原因**: `--under` は「そのディレクトリ配下」を意味する **ディレクトリ専用** の引数で、`--changed`（git 変更検知）と組み合わせて範囲を絞るために使う（#85 の並行委譲対策）。ファイルパスを渡すと「配下に .md が 0 件」となる。

**正しい使い方**: 対象ディレクトリを渡し、`--changed` と併用する。

```bash
python3 tools/check_cjk_markdown.py --fix --changed --under docs/rules
python3 tools/check_markdown_table_columns.py --changed --under docs/rules
```

**この失敗が致命傷にならなかった理由**: 本ツールは 0 件を **黙って PASS にせず警告を出す**（fail-loud）設計になっている。同種の検査ツールを作るときはこの設計を踏襲する — 「対象 0 件」と「対象があって全部合格」を出力で区別できないツールは、パス指定を間違えた瞬間から永久に何も検査しなくなる。

**関連**: `CLAUDE.md`「Markdown 出力ルール」/ Issue #85（並行委譲中は `--under` で範囲を絞る）

**再発（2026-09-02・PR #818）**: 同じ firing で `--under docs/rules/token-optimization-rules.md`（ファイルパス）を渡して空振りした。**`--under` はディレクトリ限定**（`walk_md_under()` が `base.is_dir()` でない要素を黙って skip する）。警告文が「配下に .md ファイルが 1 件もありません」としか言わないため、原因（ファイルを渡した）が読み取れない — メッセージに「ファイルパスが渡されました」の分岐を足す改善案は本再発時に検討し、`priority:low` として lessons 記載で完結させた（起票しない）。

## L-148: E2E で「代表要素だけ」を測る検査は、なぜその要素で足りるかを書かないと射程が黙って縮む（2026-09-02・PR #812）

**症状**: `getComputedStyle` で計算後の値を検証する E2E を書くとき、対象を代表要素（例: `p` / `td` の最初の 1 件）に絞るのは実務上妥当だが、**なぜその要素で足りるのかがコメントに無い** と、後から読む人には「全要素を検査しているつもり」に見える。実際には見出し・リスト項目・インライン要素は一度も測られていない。

**なぜ危険か**: 検査の射程が縮んでいることに誰も気づかないまま、「この観点は E2E が担保している」という記述だけがドキュメントに残る（同じファイルの他エントリと同じ desync の型）。テストが緑であることは射程の広さを何も保証しない。

**対策**: 検査対象を絞ったら、**絞った理由を 1 行コメントで残す**（例: 「検索結果・README のコンテンツは本文が主要なので `p` / `td` の実効値で代表させる。見出し・リストは同じカスケードを共有するため個別検査は省く」）。理由を書けないなら、それは「絞ってよいか検討していない」ということなので、対象を広げるか検討そのものを Issue に切り出す。

**関連**: PR #812（SC 1.4.12 Text Spacing の E2E）/ 本ファイル冒頭の desync 系エントリ

## L-157: 構造を持つ文書を正規表現の部分一致で判定する検査は、必ず fail-open へ倒れる（2026-09-04・PR #900）

**症状**: HTML / TSX / JSON など **構造を持つ文書** に対して「この文字列が含まれるか」を正規表現で判定する検査を書くと、クリックできない・実行されない・別の意味を持つ位置に同じ文字列があるだけで **PASS してしまう**。検査は緑のまま、守っているつもりの不変条件が壊れる。

**実測**（`tools/check_site.py` の `check_footer_readme_link` 初版・LP footer → README 本体の導線を守る検査）:

| 入力 | 判定 | なぜ通ったか |
|---|---|---|
| `<footer>README は https://…/README.md にあります</footer>` | PASS | 地の文（リンクではない） |
| `<footer><!-- <a href="…/README.md">…</a> --></footer>` | PASS | コメントアウト |
| `<footer><a href="#top" title="…/README.md">top</a></footer>` | PASS | 別要素の属性値 |
| `<footer><a href="…/README.md.bak">…</a></footer>` | PASS | 前方一致（右境界なし） |

**判定基準**: 「判定対象は **標準ライブラリのパーサがある** 構造化文書か？」（HTML / XML / JSON / TSX の AST / Python の `ast`）→ YES なら正規表現の部分一致で判定しない。

🔴 **Markdown と YAML は別扱い**（標準ライブラリにパーサが無く、外部依存を足す方が害が大きい）。本リポジトリの Markdown 検査（`tools/check_cjk_markdown.py` / `check_markdown_table_columns.py` / `check_rules_sync.sh` など）は行指向の正規表現走査が既定であり、**本エントリはそれらを違反として扱わない**。ただし Markdown を正規表現で走査するときは、**コードフェンス・HTML コメント・引用ブロックを先に除去してから判定する**（除去しない実装は本エントリと同じ fail-open になる。既存実装は `tools/md_fence.py` がフェンス判定を担う）。

**対策**:

- 標準ライブラリのパーサを使う（`html.parser.HTMLParser` / `json` / `ast` 等）。コメントは `handle_comment`、地の文は `handle_data` へ回るので、**実データだけを集める** 構造になる。参照実装は `tools/check_site.py` の `FooterLinkParser`（`<footer>` の入れ子深さを数えて `<a href>` だけを収集し、URL は完全一致——同一文書内アンカー `#…` のみ許容——で判定して `README.md.bak` のような派生パスを弾く）
- self-test の負ケースに「構造上到達不能な位置」（コメント内・地の文・別要素の属性値）と「近似だが別カテゴリ」（`README.md.bak` / 同じディレクトリの別ファイル）を必ず置く。この 2 軸が無いと、判定を最弱まで潰す変異（`re.compile("README")` 相当）でも self-test が PASS する（実測）

**関連**: #590（正規表現で走査する検査ツールの初版に毎回入る欠陥クラス・本エントリはその 5 種類目）/ #896（self-test の負ケースが構造異常に偏る）/ `docs/rules/check-tool-design-rules.md`

## L-161: シェルスクリプトから「名前」を正規表現で抜くと、関数定義の内部実装まで拾って変数プレースホルダが混入する

**症状**（PR #1003・Issue #463 で実測）: `tools/run_checks.sh` から既知チェック名を抽出する
`extract_known_names_ordered()` が、`run_check "名前"` の **呼び出し箇所** だけでなく
`run_check()` / `run_check_timeout()` の **関数定義の内部実装**（`run_check_timeout "$name" ...` /
`RESULTS+=("${name}|...")`）にもマッチし、`${name}` と `$name` の 2 件をチェック名として取り込んでいた
（全 114 件中 2 件）。抽出結果は照合の whitelist として使われるため、偽装表に `$name` の行を並べると
一致率・絶対数のカウンタを無関係な語で押し上げられる（**fail-open**）。

**なぜ self-test で気づけなかったか**: フィクスチャが「呼び出し箇所だけを並べた合成シェルスクリプト」で、
**本番相当の入力（関数定義を含む実ファイル）を代表していなかった**。抽出対象のファイルが自分で定義した
ヘルパー関数を含む場合、その定義本体は「呼び出しと同じ字面」を持つため、呼び出しだけのフィクスチャでは
この経路が一度も通らない。

**対策**:

- 抽出パターンは 3 形式とも **行頭アンカー**（`^\s*`）を揃える。1 つだけアンカーが無いと、その形式だけが
  コメント行・文字列内・関数定義内に一致して非対称な挙動になる
- 捕捉した名前に **シェル展開の文字（`$` / `{` / `}`）が含まれていたら除外する**（プレースホルダは
  「実行時に決まる値」であって固定の名前ではない）
- self-test のフィクスチャに、抽出対象ファイルが実際に持つ **ヘルパー関数の定義本体** を含める。
  「呼び出し側だけ」のフィクスチャは、抽出器がその関数定義を読んでしまう経路を検証しない

**判定基準**: 「この抽出器が読むファイルは、抽出したい構文と同じ字面を **定義側にも** 持っているか？」
→ YES なら、フィクスチャに定義側を含めるまで self-test は本番を代表していない。

**関連**: #463 / PR #1003（Layer 1 セルフレビューの 🟡 指摘・親セッションが `total = 114` /
`['${name}', '$name']` を実測）/ #750（self-test の負ケースに「境界の外側」を含める）/
`docs/rules/check-tool-design-rules.md`
