## 1. SD-1 の詳細（動作確認）

### 1.1. プレビュー環境をいつ確立するか

`D-11` により **プレビュー環境のデプロイ先だけ先行決定** するが、デプロイする対象（アプリの骨格）が存在するのは `SP-1` 以降である。したがって:

| 時期 | 動作確認の手段 |
|---|---|
| `SP-1` 実施中 | **開発サーバー起動で代替してよい**（プレビュー環境の設定 = `E-22` を同スプリント内で確立する） |
| `SP-1` 完了後 | 🔴 **プレビュー URL が必須**（`E-22` が済んでいるため代替を認めない） |

⚠️ `SP-1` が 1 セッションに収まらない場合は、`docs/02_requirements/user-story-map.md` §5.4 の規則に従い **`E-22` + `E-1` を先行スプリントとして分割** する（既存 `SP-n` を詰め直さず末尾に番号を足す）。

### 1.2. `NFR-21` との切り分け（なぜ矛盾しないか）

| 対象 | `NFR-21` の適用 |
|---|---|
| **アプリのランタイム**（`app/` 配下・データアクセス層・キャッシュ実装） | 🔴 **適用する。** Next.js 標準機能の範囲で組み、超える依存が必要になった時点で ADR を起票 |
| **開発フローの道具**（PR ごとの自動プレビューデプロイ・CI 設定） | **適用しない**（`D-11`）。乗り換えてもアプリコードの書き換えが発生しないため |

判定基準: 「**その依存を外したときにアプリのコードを書き換える必要があるか**」→ Yes なら `NFR-21` の対象、No なら道具。

### 1.3. プレビュー URL を出せなかったときの手順（沈黙禁止）

```
1. PR 本文に「プレビュー URL なし」と明記し、理由を 1 文で書く
2. ローカル起動手順を書く（コマンド列 + 必要な環境変数名。値は書かない）
3. 原因を problem-investigation-protocol.md の 5 ステップで調査する
4. 自己解決不可 かつ A-1〜A-6 該当（例: A-6 のアカウント設定）
   → user-notification-triage.md §3 の必須要件を満たして報告する
5. 自己解決不可 かつ A に該当しない → B カテゴリの実装 Issue を起票する
```

🔴 **「URL がないまま黙ってマージ」はしない。**

## 2. SD-2 の詳細（TDD）

### 2.1. `SP-1`〜`SP-3` の緩和（例外の根拠と範囲）

テスト基盤（`E-11`）と CI（`E-12`）が揃うのは `SP-4` である（`docs/02_requirements/user-story-map.md` §5.3）。したがって `SP-1`〜`SP-3` では「コマンド 1 つで全テストが通る」「CI が緑」が **物理的に成立しない**。

| スプリント | TDD の適用 |
|---|---|
| `SP-1`〜`SP-3` | **「テストを書ける対象から書く」に緩和。** テストランナーを導入した時点から Red → Green を始める。E2E・CI ゲートは要求しない |
| `SP-4` | 🔴 **緩和の終点。** ここで基盤を揃え、`SP-1`〜`SP-3` で書けなかった分の回帰テストも書く |
| `SP-5` 以降 | Hot 層 §2 の完了条件を **全項目必須** |

🔴 **この緩和は `SP-4` までの一時措置であり、`SP-5` 以降に持ち越さない。** 「基盤がまだ弱いから」を理由に緩和を延長しない。

### 2.2. 何を単体で、何を E2E で見るか

| 対象 | 層 | 理由 |
|---|---|---|
| エラー種別の判別（`prd.md` §7 の対応表） | 単体 | 入力（ステータス + ヘッダ）→ 出力（種別）の純粋な写像 |
| キャッシュキーの命名規約（`NFR-18`） | 単体 | キーの形が壊れると全キャッシュが無効化されるため、形そのものを固定する |
| API レスポンスの型検証（`NFR-19`） | 単体 | 外部データの想定外形状に対する防御 |
| 検索 → 一覧 → 詳細 → 復帰の通し | **E2E** | 操作レビュー手順と 1 対 1 に対応させる |
| キーボードのみでの完走（`AC-9`） | **E2E** | フォーカス順序と可視性は結合状態でしか検証できない |
| アクセシビリティの自動検出可能な範囲 | **E2E**（axe） | `NFR-26` |

### 2.3. モック化の範囲

- GitHub API（検索・詳細）: **必須**（`NFR-24`）
- OAuth フロー: 必須。ただし **`SP-8` で OAuth 実装と同時に組む**（仕様が固まる前にモックを作ると手戻りになる）
- 時刻依存（レート制限の復帰時刻表示）: 固定値を注入できる形にする

## 3. SD-3 の詳細（確認）

### 3.1. 発火ラインの境界例

| ケース | 判定 | 理由 |
|---|---|---|
| 「表示件数の既定値は 20 か 50 か」 | ✅ 確認 | どちらも筋が通り、成果物（初期表示）が変わる |
| 「詳細から戻ったときページ番号を維持するか先頭に戻すか」 | ✅ 確認 | `AC-6` は「検索条件が保持されている」までしか言っておらず、両解釈が成立する |
| 「i18n ライブラリは `next-intl` か別か」 | ❌ 自律 | 実装手段。仮定を 1 行記録して進める |
| 「テストは Vitest か Jest か」 | ❌ 自律 | 実装手段 |
| 「カードの情報の並び順」 | ❌ 自律 | `prd.md` §13 が「UI/UX 設計は未着手」として開けてある。最も単純な解で進め、記録する |
| 「`localStorage` の代わりに DB を使いたい」 | ❌ **却下**（確認以前） | `D-5` 追補で設計原則として却下済み。`SD-4` により読めば分かる |

### 3.2. 記録の書式（自律判断した場合）

Issue コメントまたは最初のコミットメッセージに 1 行:

```
仮定: {曖昧だった点} → {採用した解釈}（根拠: {最も単純な解 / 既存ルール ID}）
```

## 4. SD-4 の詳細（ドキュメント参照）

### 4.1. 「読めば分かること」の具体例（聞いてはいけない）

| 疑問 | 書いてある場所 |
|---|---|
| Watcher 数はどのフィールドか | `prd.md` §4.1 の `FR-4` 注記（`subscribers_count`） |
| 無限スクロールとページネーションどちらか | `prd.md` §4.1 の `FR-7` 注記（ページネーション） |
| ログインを必須にしてよいか | `inception-deck.md` Q4.2（やらない・`D-6`） |
| 健全性スコアを自作してよいか | `inception-deck.md` Q4.2（やらない・`R-3`） |
| このスプリントで何を作るか | `user-story-map.md` §5.3 |
| リリースしてよい品質の下限 | `project-mission.md`「ドメイン固有の品質ゲート」 |

### 4.2. 矛盾を見つけたときの処理

```
矛盾を検出
  → 権威順で正しい側を決める（ユーザー明示 > 仕様 prd.md > テスト > 現行コード）
  → 誤っている側を修正する（放置しない）
      ├─ 現在のスプリントのスコープ内 → その PR で直す
      └─ スコープ外 → 別 Issue を起票してから次に進む（CP-1 の解決規則）
```

## 5. スプリント実行チェックリスト（毎スプリントで使う）

```
着手
[ ] Issue を作成し status:in-progress を付与（CP-4 の論理ロック）
[ ] Hot 層 §4 の 1〜5 を読み、対象 SP-n のゴール・操作レビュー手順・対応 AC を確認
[ ] 仕様解釈の分岐があれば Hot 層 §3 の書式でまとめて確認（依存しない作業は先に進める）
[ ] PR 本文に書く Sprint Goal / sp:N / Session-Id を決める（session-sprint-rules.md §2）

実装
[ ] Red: 失敗するテストを先に書く（SP-1〜SP-3 は書ける対象から）
[ ] Green: 通す最小の実装
[ ] Refactor: 重複を削る
[ ] 操作レビュー手順を E2E テストに写す（SP-4 以降は必須）

完了前
[ ] テストをコマンド 1 つで実行し、実結果で全通過を確認（SP-4 以降）
[ ] PR を作成し、プレビュー URL と参照要件 ID を本文に記載
[ ] プレビュー URL で操作レビュー手順を自分で完走してから、ユーザーに確認を依頼
[ ] 自律判断した仮定を 1 行記録
[ ] Layer 1 セルフレビュー（pr-review-flow-summary.md）
```
