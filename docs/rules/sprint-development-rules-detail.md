## 1. SD-1 の詳細（動作確認）

### 1.1. プレビュー環境をいつ確立するか

`D-11` により **プレビュー環境のデプロイ先だけ先行決定** するが、デプロイする対象（アプリの骨格）が存在するのは `SP-1` 以降である。したがって:

| 時期 | 動作確認の手段 |
|---|---|
| `SP-1` 実施中 | **開発サーバー起動で代替してよい**（プレビュー環境の設定 = `E-22` を同スプリント内で確立する） |
| `SP-1` 完了後 | 🔴 **プレビュー URL が必須**（`E-22` が済んでいるため代替を認めない） |

⚠️ `SP-1` が 1 セッションに収まらない場合は、`docs/02_requirements/user-story-map.md` §5.4 の規則に従い **`E-22` + `E-1` を先行スプリントとして分割** する（既存 `SP-n` を詰め直さず末尾に番号を足す）。

### 1.2. `NFR-21` との切り分け（なぜ矛盾しないか）

| 対象 | `NFR-21` の適用 |
|---|---|
| **アプリのランタイム**（`app/` 配下・データアクセス層・キャッシュ実装） | 🔴 **適用する。** Next.js 標準機能の範囲で組み、超える依存が必要になった時点で ADR を起票 |
| **開発フローの道具**（PR ごとの自動プレビューデプロイ・CI 設定） | **適用しない**（`D-11`）。乗り換えてもアプリコードの書き換えが発生しないため |

判定基準: 「**その依存を外したときにアプリのコードを書き換える必要があるか**」→ Yes なら `NFR-21` の対象、No なら道具。

### 1.3. プレビュー URL を出せなかったときの手順（沈黙禁止）

```
1. PR 本文に「プレビュー URL なし」と明記し、理由を 1 文で書く
2. ローカル起動手順を書く（コマンド列 + 必要な環境変数名。値は書かない）
3. 原因を problem-investigation-protocol.md の 5 ステップで調査する
4. 自己解決不可 かつ A-1〜A-6 該当（例: A-6 のアカウント設定）
   → user-notification-triage.md §3 の必須要件を満たして報告する
5. 自己解決不可 かつ A に該当しない → B カテゴリの実装 Issue を起票する
```

🔴 **「URL がないまま黙ってマージ」はしない。**

## 2. SD-2 の詳細（TDD）

### 2.1. `SP-1`〜`SP-3` の緩和（例外の根拠と範囲）

テスト基盤（`E-11`）と CI（`E-12`）が揃うのは `SP-4` である（`docs/02_requirements/user-story-map.md` §5.3）。したがって `SP-1`〜`SP-3` では「コマンド 1 つで全テストが通る」「CI が緑」が **物理的に成立しない**。

| スプリント | TDD の適用 |
|---|---|
| `SP-1`〜`SP-3` | **「テストを書ける対象から書く」に緩和。** テストランナーを導入した時点から Red → Green を始める。E2E・CI ゲートは要求しない |
| `SP-4` | 🔴 **緩和の終点。** ここで基盤を揃え、`SP-1`〜`SP-3` で書けなかった分の回帰テストも書く |
| `SP-5` 以降 | Hot 層 §2 の完了条件を **全項目必須** |

🔴 **この緩和は `SP-4` までの一時措置であり、`SP-5` 以降に持ち越さない。** 「基盤がまだ弱いから」を理由に緩和を延長しない。

### 2.2. 何を単体で、何を E2E で見るか

| 対象 | 層 | 理由 |
|---|---|---|
| エラー種別の判別（`prd.md` §7 の対応表） | 単体 | 入力（ステータス + ヘッダ）→ 出力（種別）の純粋な写像 |
| キャッシュキーの命名規約（`NFR-18`） | 単体 | キーの形が壊れると全キャッシュが無効化されるため、形そのものを固定する |
| API レスポンスの型検証（`NFR-19`） | 単体 | 外部データの想定外形状に対する防御 |
| 検索 → 一覧 → 詳細 → 復帰の通し | **E2E** | 操作レビュー手順と 1 対 1 に対応させる |
| キーボードのみでの完走（`AC-9`） | **E2E** | フォーカス順序と可視性は結合状態でしか検証できない |
| アクセシビリティの自動検出可能な範囲 | **E2E**（axe） | `NFR-26` |

### 2.3. モック化の範囲

- GitHub API（検索・詳細）: **必須**（`NFR-24`）
- OAuth フロー: 必須。ただし **`SP-8` で OAuth 実装と同時に組む**（仕様が固まる前にモックを作ると手戻りになる）
- 時刻依存（レート制限の復帰時刻表示）: 固定値を注入できる形にする

### 2.4. アーキテクチャレイヤーと依存方向（正本への参照）

🔴 **層・ディレクトリ構成・依存規則の正本は [`docs/03_design/architecture/application-architecture.md`](../03_design/architecture/application-architecture.md)**（`E-2` / `E-3` / `E-5` / `E-8` / `NFR-16` / `NFR-17` / `NFR-21` の具体形）。実装中に読む要約は [`architecture-rules.md`](./architecture-rules.md)、ドメイン語彙は [`domain-model.md`](../03_design/data-model/domain-model.md)。**本ファイルには構成図を再掲しない**（二重定義すると片方だけ古くなる。実際に旧構成が残置して新 SSOT と矛盾した経緯がある・#47）。

**機械強制**: `tools/check_architecture_boundaries.py`（`ARCH-1`〜`ARCH-7`）を `self_review_check.py` が PR 前に変更ファイルへ実行する。dependency-cruiser 等の追加導入は **必須ではない**（必要になった時点で `E-7` の実装詳細として検討する。新しいイネイブラー ID は作らない）。

⚠️ **用語の注意**: `src/infrastructure/`（アダプタ層）と `infrastructure-design.md` の `INF-n`（運用基盤の契約）は別物（3 層判定境界の正本は `docs/02_requirements/user-story-map.md` §5.2）。

### 2.5. TDD のコミット規約と 2 段検証

**コミット規約**: 本リポジトリの既存慣行（`git log --oneline` で確認済み・`{type}: {何をしたか} (#N)`）と衝突させない。独自マーカー（`red -` / `green -` 等）は件名に埋め込まず、**`test:` を既存 `type` の並びに 1 つ追加するだけ** にする。1 増分を「テストパスのみ変更するコミット（`test:`）」と「非テストパスのみ変更するコミット（`feat:`/`fix:`）」に分ける。

**Tier 1（毎コミット・静的・ゼロコスト）**: `git diff --name-only` によるパス判定のみ（`test:` コミットがテストパス以外を含んでいないか / 直前が `test:` のとき直後が非テストパスのみの `feat:`/`fix:` になっているか）。`tools/self_review_check.py` が `pre-pr-create-check.sh` フック内で実行する（実装内容の詳細は当該ツールの担当）。

**Tier 2（PR ごとに 1 回だけ・CI）**: PR 内の **最初の `test:`/`feat:` ペアのみ** を対象に、`test:` コミット時点を一時 worktree でチェックアウトして該当テストだけ実行し **非 0 終了（Red）を実測** する。その後 HEAD で全テストを実行し 0 終了を確認する（これは `NFR-25`/`SD-2` が元々要求する「コマンド 1 つで全テスト成功」そのものであり、追加コストではない）。

**なぜ全コミット worktree 実行にしないか**: 増分数 × PR 数に比例して CI 時間が線形に膨張するため（1 firing あたりの増分数が読めない自律ルーティン運用では予算超過のリスクが高い）。PR あたり最初の 1 ペアだけを実測する定数コストに抑える。

**強制ではなくゲートである**: `git commit` に割り込むフックは存在しないため、リアルタイム強制はしない。違反は `pre-pr-create-check.sh`（PR 作成前ゲート）が Tier 1 で検出し、PR 前チェックリスト（本ファイル §5）の完了条件を満たせない形で止める。是正は `git rebase -i` でコミットを分け直すだけでよく、ローカル完結・CI 消費ゼロ。

**§2.1（`SP-1`〜`SP-3` の緩和）との関係**: テストランナー（`E-11`/`E-12`）が無い期間は Tier 1（コミット分離）のみを求め、Tier 2（Red の実測）は `SP-4` 以降に限る。この緩和は `SP-4` で終端し、`SP-5` 以降へは持ち越さない。「基盤がまだ弱いから」で延長しないことは、`sprint-cycle-router` スキルの Step 4-0 ハードゲート（`SP-4` が未 Closed のまま `SP-5` 以降へ進めない）が機械的に保証する。

### 2.6. E2E の命名規約と実行対象の切り替え

E2E フレームワークは Playwright を採用する（この環境は `PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers` で導入済み。`playwright install` を実行しない）。

**命名規約**: `e2e/sp-{n}.spec.ts` に **SP 単位で 1 ファイル 1 `test()`** を置き、`user-story-map.md` §5.3 の操作レビュー手順の **番号と文言をそのまま `test.step()` に写す**（複製ではなく実行可能化）。手順が増えたら `test.step()` も増やす、が `SD-2`「操作レビュー手順を E2E テストに写す」の実行手段になる。

**個別 `test()` に分割しない理由**: 操作レビュー手順は状態を共有する 1 連の操作（検索 → 選ぶ → 戻る、のように前段の結果に依存する）であり、分割すると各 `test()` が前提状態を再構築するための重複セットアップが必要になり、手順との 1 対 1 対応がかえって崩れる。

**実行対象**:

| 時期 | 実行対象 |
|---|---|
| 既定（`E-22` 確立後） | プレビュー URL（`E2E_BASE_URL` を CI が注入） |
| `E-22` 確立前（`SP-1` 実施中） | ローカルビルド（`npm run build && npm start`）。§1.1 の代替を E2E にもそのまま適用する |
| `SP-8` のみ | 🔴 **例外**。`infrastructure-design.md` §8.1 はプレビュー環境の OAuth を無効化するため、`SP-8` の操作レビュー手順（ログイン導線）自体がプレビュー URL 上に描画されず、ネットワークモックでも救えない。`SP-8` の spec のみ **ダミー OAuth 設定を注入したローカルビルド** に対して実行し、OAuth コールバックだけ `route.fulfill` でモックする |

モックの範囲（GitHub API・OAuth・時刻依存）は §2.3 を参照する（本節では再掲しない）。

## 3. SD-3 の詳細（確認）

### 3.1. 発火ラインの境界例

| ケース | 判定 | 理由 |
|---|---|---|
| 「表示件数の既定値は 20 か 50 か」 | ✅ 確認 | どちらも筋が通り、成果物（初期表示）が変わる |
| 「詳細から戻ったときページ番号を維持するか先頭に戻すか」 | ✅ 確認 | `AC-6` は「検索条件が保持されている」までしか言っておらず、両解釈が成立する |
| 「i18n ライブラリは `next-intl` か別か」 | ❌ 自律 | 実装手段。仮定を 1 行記録して進める |
| 「テストは Vitest か Jest か」 | ❌ 自律 | 実装手段 |
| 「カードの情報の並び順」 | ❌ 自律 | `prd.md` §13 が「UI/UX 設計は未着手」として開けてある。最も単純な解で進め、記録する |
| 「`localStorage` の代わりに DB を使いたい」 | ❌ **却下**（確認以前） | `D-5` 追補で設計原則として却下済み。`SD-4` により読めば分かる |

### 3.2. 記録の書式（自律判断した場合）

Issue コメントまたは最初のコミットメッセージに 1 行:

```
仮定: {曖昧だった点} → {採用した解釈}（根拠: {最も単純な解 / 既存ルール ID}）
```

### 3.3. 無人実行モードでの SD-3

`SD-3` は `AskUserQuestion` による確認を求めるが、**ルーティン起動の無人セッションには答えるユーザーがいない**。対話セッションと無人セッションでは、確認が発火したときに取れる行動が異なるため、実行モードの差を明示的に扱う。

🔴 **既定は「待つ」**: `status:waiting-user` Issue に **推奨案付き**（選択肢は最大 2 つ・各 1 行の判断材料・推奨を先頭に明示）で積み、そのスプリントは着手せず次の Ready な `SP-n` へフォールスルーする（Issue 1 件のためにルーティン全体を止めない）。

**例外的に続行してよい 3 条件**（すべて満たすときのみ、推奨案を採用して実装を続行してよい）:

- [ ] 変更が単一 Issue のスコープに閉じている（後続 `SP-n` がこの解釈に依存しない）
- [ ] 画面に見える挙動・API 契約・データモデル・キャッシュキー命名に触れない（内部実装の細部に限る）
- [ ] 差し戻しコストが `sp:1`〜`sp:2` 相当（数十行・単一ファイル）に収まる

続行した場合は次の書式を Issue コメントと PR 本文の両方に記録する:

```
仮定: {曖昧点} → {採用した解釈}（無人実行のため推奨案を採用。ユーザー判断で訂正可）
```

🔴 **`discussion-review` の結論を「ユーザーの答え」の代わりにしない**（`D-12` は「成果物が変わる分岐はユーザーが決める」という決定であり、Claude 内部の別エージェント同士の議論はユーザーではない。これを代替にするとルールを Claude の都合で書き換えることになる）。

**判断根拠（被害の非対称性）**:

| | 誤って「待つ」を選んだ場合 | 誤って「続行」を選んだ場合 |
|---|---|---|
| 性質 | 線形・有界・可逆（Issue が滞留するだけ。次に飼い主が来た firing で即答すれば復帰） | 複利・無界（誤った解釈の上に後続スプリントが積み上がり、剥がすコストが増え続ける） |

待つ側の誤判定コストは安価で回復可能、続行側の誤判定コストは高価かつ悪化し続ける。この非対称性が「既定は待つ」の根拠であり、3 条件を **すべて** 満たす極小のケースに限って続行を許す。

> この節は 2026-08-18 の飼い主の明示確認（`AskUserQuestion` 回答）で確定した内容である。

### 4.2. 矛盾を見つけたときの処理

```
矛盾を検出
  → 権威順で正しい側を決める（ユーザー明示 > 仕様 prd.md > テスト > 現行コード）
  → 誤っている側を修正する（放置しない）
      ├─ 現在のスプリントのスコープ内 → その PR で直す
      └─ スコープ外 → 別 Issue を起票してから次に進む（CP-1 の解決規則）
```

## 5. スプリント実行チェックリスト（毎スプリントで使う）

```
着手
[ ] Issue を作成し status:in-progress を付与（CP-4 の論理ロック）
[ ] Hot 層 §4 の 1〜5 を読み、対象 SP-n のゴール・操作レビュー手順・対応 AC を確認
[ ] 仕様解釈の分岐があれば Hot 層 §3 の書式でまとめて確認（依存しない作業は先に進める）
[ ] PR 本文に書く Sprint Goal / sp:N / Session-Id を決める（session-sprint-rules.md の「スプリントプランニング」節）

実装
[ ] Red: 失敗するテストを先に書く（SP-1〜SP-3 は書ける対象から）
[ ] Green: 通す最小の実装
[ ] Refactor: 重複を削る
[ ] 操作レビュー手順を E2E テストに写す（SP-4 以降は必須）

完了前
[ ] テストをコマンド 1 つで実行し、実結果で全通過を確認（SP-4 以降）
[ ] PR を作成し、プレビュー URL と参照要件 ID を本文に記載
[ ] プレビュー URL で操作レビュー手順を自分で完走してから、ユーザーに確認を依頼
[ ] 自律判断した仮定を 1 行記録
[ ] Layer 1 セルフレビュー（pr-review-flow-summary.md）
```

### 5.1. 中断時チェックリスト（firing の途中で中断するとき）

無人ルーティンはスプリントを複数 firing にまたがって進めてよいが（`session-sprint-rules.md`「1 セッション = 1 スプリント」は 1 firing への完走を要求しない）、**何を満たしていれば安全に中断してよいか** が未定義だと「終わったつもり」の壊れた状態が積み上がる（L-113）。firing を終える前に以下をすべて満たす。

```
[ ] 直前のコミットが壊れた状態を含まない（Red で止まるのは可。Green の途中で止めない）
[ ] Issue を Close していない・完了ラベルを付けていない（status:in-progress のまま）
[ ] Issue コメントに「進捗: {SD ステップ名} まで完了。次は {次にやること}」の 1 行がある
[ ] PR がある場合はタイトルに [WIP] が付き、自動マージ対象になっていない
```
