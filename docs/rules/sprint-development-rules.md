# スプリント開発ルール（Sprint Development Rules・Hot 層サマリー）

> **このファイルは「スプリントをどう回すか」の 4 規律の唯一の正本（SSOT）である。**（飼い主の明示決定・Issue #13）
> 詳細（背景・例外の扱い・実行チェックリスト全文・フォールバック手順）は `docs/rules/sprint-development-rules-detail.md`（Warm 層）。
> `session-sprint-rules.md` が **スプリントの単位と見積もり**（1 セッション = 1 スプリント・`sp:N`）を、
> 本ファイルが **1 本のスプリントの中でどう作るか** を定める。スプリントの中身（`SP-n` の一覧・操作レビュー手順）の
> 正本は `docs/02_requirements/user-story-map.md` §5。

## 0. 4 規律（すべて必須・省略不可）

| ID | 規律 | 一言でいうと |
|---|---|---|
| **SD-1** | **動作確認できる状態で終わる** | スプリントの PR には **開けるプレビュー URL** が貼られている |
| **SD-2** | **TDD 主体・常に動作担保** | テストを先に書く。操作レビュー手順は E2E に写す |
| **SD-3** | **曖昧点を残さない** | 仕様解釈が分岐したら聞く。実装手段は聞かずに決める |
| **SD-4** | **ドキュメントを読んで自律的に動く** | 書いてあることを聞かない。読んだ ID を記録する |

🔴 **`SD-1` と `SD-2` は「スプリント完了の定義」に入る。** コードが書けたことを完了条件にしない
（`docs/02_requirements/user-story-map.md` §7 運用ルール 2）。

## 1. SD-1: 動作確認できる状態で終わる

- スプリントの PR 本文に **プレビュー URL を貼る**。ユーザーはリンクを開くだけで確認できる状態にする
- あわせて `docs/02_requirements/user-story-map.md` §5.3 の該当スプリントの「操作レビュー」手順を **ID で参照** する（本文へコピーしない）
- 前スプリントまでの経路も同じ URL で触れること（回帰の目視確認を兼ねる）
- **出せない場合は PR 本文に理由とローカル起動手順を書く**（沈黙禁止）
- PR 本文に **`Team:` トレーラー**（例 `Team: fan-out(3)`）を必ず含める（チーム編成の既定は `session-sprint-rules.md` §2 が正本）

🔴 **本規律のためにプレビュー環境のデプロイ先だけ先行決定する**（`D-11`）。本番デプロイ先とキャッシュ基盤は引き続き未決（`D-5` / `D-7`）。`NFR-21`（特定 PaaS 固有機能への依存を最小化）は **アプリのランタイムに対する制約として維持** し、**プレビューのためにアプリコードへ PaaS 固有 API を持ち込まない**（持ち込みたくなったら ADR を起票）。

⚠️ **プレビュー環境は `SP-1`（`E-22`）で確立する。** それ以前および `SP-1` 実施中は「開発サーバー起動」で代替してよい（詳細版 §1）。

### 完了条件

- [ ] PR 本文に開けるプレビュー URL がある（または上記の代替が書かれている）
- [ ] その URL で該当スプリントの操作レビュー手順を **完走できる**
- [ ] 前スプリントの経路が壊れていない

## 2. SD-2: TDD 主体・常に動作担保

```
Red（失敗するテストを書く） → Green（通す最小の実装） → Refactor（重複を削る）
```

🔴 **実装を先に書いてテストを後から足す順序を取らない。**

🔵 **道具・層分担・二重ループ・フレームワーク由来の制約は [`docs/04_development/testing-strategy.md`](../04_development/testing-strategy.md)（SSOT・`R-11` の回答）に従う。**
本節は規律だけを定め、制約の中身は再掲しない（片方だけ古くなるため）。

| 層 | 対象 | 対応要件 |
|---|---|---|
| **単体 / 結合** | データアクセス層・エラー判別・キャッシュキー・型検証・UI コンポーネント | `NFR-23` / `NFR-24` |
| **E2E** | 🔴 **`user-story-map.md` §5.3 の「操作レビュー」手順そのもの** | `NFR-23` / `AC-10` |

🔵 **操作レビュー手順と E2E テストを一致させる**（手順を増やしたら E2E も増やす）。手動確認が自動テストに写っていれば、以降のスプリントで壊れたときに自動で気づける。外部 API は必ずモック化する（`NFR-24`）。

### 🔴 やってはいけないこと

- 仕様と矛盾するテストを通すために正しいコードを黙って書き換える（`intent-gate-rules.md`・権威順は ユーザー明示 > 仕様 > テスト > 現行コード）
- テストをスキップ・無効化・quarantine して緑にする
- 実際にテストを走らせずに「動作担保されている」と報告する（実結果でのみ断定・L-113）

### 完了条件

> ⚠️ **`SP-1`〜`SP-3` は例外**（テスト基盤が揃うのは `SP-4`）。この期間は下記を **「テストを書ける対象から書く」に緩和** し、`SP-4` 以降は全項目を必須とする。緩和の根拠と範囲は詳細版 §2。

- [ ] 追加した振る舞いに **先行して書かれたテスト** がある
- [ ] 該当スプリントの操作レビュー手順が E2E テストとして存在する（`SP-4` 以降）
- [ ] コマンド 1 つで全テストが通る（**実行結果を確認済み**・`SP-4` 以降）
- [ ] CI が緑（`SP-4` 以降）。🔴 **Actions 制限中の読み替え**: CI が無いため「`bash tools/run_checks.sh` が緑（`SP-4` 以降）」に読み替える（結果を PR 本文に貼る手順は `pr-review-flow-summary.md`「PR 作成時の必須事項」）。制限解除後はこの読み替えを外し元の文言に戻す

## 3. SD-3: 曖昧点を残さない（確認の発火ライン）

### 🔴 発火ライン（飼い主の明示決定・`D-12`）

> **仕様解釈が 2 通り以上あり、どちらを選ぶかで成果物が変わるとき** に確認する。それ以外は確認しない。

| 判定 | 例 | 行動 |
|---|---|---|
| ✅ **確認する** | 「表示件数の既定値は 20 か 50 か」「戻ったときページ番号も戻すのか維持するのか」— どちらでも筋が通り、選択で成果物が変わる | `AskUserQuestion` で確認する |
| ❌ **確認しない** | 実装手段・ライブラリ選定・命名・ファイル分割・テストの書き方 | **自律実行し、採用した仮定を Issue コメントか最初のコミットメッセージに 1 行記録する** |

🔴 **これは `user-confirmation-minimization.md` の「確認してよい 2 系統」のうち第 2 系統である**（第 1 系統は §1 の A-1〜A-6）。同ファイル §0 / §1 / §3 item 0 (c) / item 2 が本規律を明示的に受けている。`CP-6` と A-1〜A-6 の扱いは **変わらない**。

聞き方は `user-confirmation-minimization.md` §3 item 8 に従う（**選択肢は最大 2 つ / 各 1 行の判断材料 / 推奨を先頭に置き `（推奨）` を付ける**）。

🔴 **答えに依存しない作業を先に全部終わらせてから、まとめて聞く。** 曖昧点 1 つで手を止めない。

## 4. SD-4: ドキュメントを読んで自律的に動く

### スプリント着手時に読む順序

| # | 読むもの | 何を取り出すか |
|---|---|---|
| 1 | `docs/02_requirements/user-story-map.md` §5.3 の該当 `SP-n` | ゴール / 含む `US-n` `E-n` / 操作レビュー手順 / 対応 `AC` |
| 2 | `docs/02_requirements/prd.md` の参照要件 ID と §6 の該当 `AC-n` | 受け入れ条件（**ここが正本。他所の再掲を信じない**） |
| 3 | `docs/02_requirements/prd.md` §13 | そのスプリントに関わる **未決事項** |
| 4 | `docs/00_concept/inception-deck.md` Q4 | やらないこと / 今は決めないこと（スコープの侵食防止） |
| 5 | `docs/project-mission.md` | 品質ゲート・判断基準 |
| 6 | `docs/03_design/ui-ux/ui-ux-guidelines.md`（**UI を触るスプリントのみ**） | 技術スタック・デザイントークン・状態表現・a11y の実装指針 |
| 7 | 🔴 `docs/rules/architecture-rules.md`（**アプリコードを書くスプリントは必読**） | 層の判定・依存規則 7 項目・DDD で守る 3 点・TDD の最低ライン（各 SSOT への入口） |
| 8 | 🔴 `docs/03_design/data-model/domain-model.md` §4（**値オブジェクト・エンティティを実装する前に必読**） | 値オブジェクトの実装の型（ブランド型 + スマートコンストラクタ）。入口は #7 の `architecture-rules.md`、値オブジェクトの実装形はこちら（`domain-model.md` §4）が正本 |

🔴 **`SD-3` の確認は「ドキュメントを読んでも決まらないこと」にのみ発火する。** 読めば分かることを聞くのは `CP-6` 違反。

ドキュメント間が矛盾していたら権威順（**ユーザー明示 > 仕様（`prd.md`）> テスト > 現行コード**・`intent-gate-rules.md`）で解決し、**矛盾自体を修正する**（放置しない）。

### 完了条件

- [ ] Issue / PR に参照した要件 ID（`US-n` / `E-n` / `AC-n` / `NFR-n` 等）が書かれている
- [ ] スコープ外（`inception-deck.md` Q4.2）の項目を混ぜていない
- [ ] 見つけたドキュメントの矛盾を修正したか、別 Issue を起票した
- [ ] （アプリコードを触った場合）`python3 tools/check_architecture_boundaries.py` が PASS し、新しいドメイン語を導入したなら `domain-model.md` を同じ PR で更新した
