# スプリント開発ルール（Sprint Development Rules・SSOT）

> **このファイルは「スプリントをどう回すか」の 4 規律の唯一の正本（SSOT）である。**（飼い主の明示決定・Issue #13）
> `session-sprint-rules.md` が **スプリントの単位と見積もり**（1 セッション = 1 スプリント・`sp:N`）を定めるのに対し、
> 本ファイルは **1 本のスプリントの中でどう作るか** を定める。スプリントの中身（`SP-n` の一覧・操作レビュー手順）の
> 正本は `docs/02_requirements/user-story-map.md` §5。

---

## 0. 4 規律（すべて必須・省略不可）

| ID | 規律 | 一言でいうと |
|---|---|---|
| **SD-1** | **動作確認できる状態で終わる** | スプリントの PR には **生きたプレビュー URL** が貼られている |
| **SD-2** | **TDD 主体・常に動作担保** | テストを先に書く。操作レビュー手順は E2E に写す |
| **SD-3** | **曖昧点を残さない** | 仕様解釈が分岐したら聞く。実装手段は聞かずに決める |
| **SD-4** | **ドキュメントを読んで自律的に動く** | 書いてあることを聞かない。読んだ ID を記録する |

🔴 **`SD-1` と `SD-2` は「スプリント完了の定義」に入る。** コードが書けたことを完了条件にしない
（`docs/02_requirements/user-story-map.md` §7 運用ルール 2）。

---

## 1. SD-1: 動作確認できる状態で終わる

### 1.1. 要件

- スプリントの PR 本文に **プレビュー URL を必ず貼る**。ユーザーはリンクを開くだけで確認できる状態にする。
- あわせて **`docs/02_requirements/user-story-map.md` §5.3 の該当スプリントの「操作レビュー」手順を ID で参照** する（本文へコピーしない）。
- 前スプリントまでの経路も同じ URL で触れること（回帰の目視確認を兼ねる）。

### 1.2. 🔴 `D-7`（デプロイ先未決）との関係

**本規律により、プレビュー環境のデプロイ先だけは先行して決定する**（`D-11`）。

- **本番デプロイ先とキャッシュ基盤は引き続き未決**（`D-5` / `D-7`）。決めるのは「PR プレビューをどこに出すか」だけ。
- `NFR-21`（特定 PaaS 固有機能への依存を最小化する）は **アプリのランタイムに対する制約** として維持する。
  **プレビュー機能（PR ごとの自動デプロイ）への依存は許容する** — これは開発フローの道具であり、
  アプリのコードが特定 PaaS に縛られるわけではない。
- 🔴 **プレビューのためにアプリのコードへ PaaS 固有 API を持ち込まない。** 持ち込みたくなったら ADR を起票する。

### 1.3. 出せなかったときの扱い（沈黙禁止）

プレビュー URL を出せない場合は、**PR 本文にその理由と、ローカルで起動する手順（コマンド列と必要な環境変数）を書く**。
「URL がないまま黙ってマージ」はしない。理由が環境要因（A-6 相当）なら `user-notification-triage.md` §3 の要件を満たして報告する。

### 1.4. 完了条件

- [ ] PR 本文に開けるプレビュー URL がある（または §1.3 の代替が書かれている）
- [ ] その URL で該当スプリントの操作レビュー手順を **完走できる**
- [ ] 前スプリントの経路が壊れていない

## 2. SD-2: TDD 主体・常に動作担保

### 2.1. サイクル

```
Red（失敗するテストを書く） → Green（通す最小の実装） → Refactor（重複を削る）
```

🔴 **実装を先に書いてテストを後から足す順序を取らない。** 新しい振る舞いには **先にテストを書く**。

### 2.2. テストの層と分担

| 層 | 対象 | 対応要件 |
|---|---|---|
| **単体 / 結合** | データアクセス層・エラー判別・キャッシュキー・型検証・UI コンポーネント | `NFR-23` / `NFR-24` |
| **E2E** | 🔴 **`docs/02_requirements/user-story-map.md` §5.3 の「操作レビュー」手順そのもの** | `NFR-23` / `AC-10` |

🔵 **操作レビュー手順と E2E テストを一致させる。** 手動で確認する手順が自動テストに写っていれば、
以降のスプリントで壊れたときに自動で気づける（`SD-1` の回帰確認を機械化する）。手順を増やしたら E2E も増やす。

- 外部 API は必ずモック化する（`NFR-24`）。ネットワーク状況に依存させない。
- テストはコマンド 1 つで実行でき、CI で自動実行される（`NFR-25`）。

### 2.3. 🔴 やってはいけないこと

- **仕様と矛盾するテストを通すために、正しいコードを黙って書き換える**（`intent-gate-rules.md`・L-113 姉妹則）。
  権威順は ユーザー明示 > 仕様（`prd.md`）> テスト > 現行コード。不一致は surface する。
- **テストをスキップ・無効化・quarantine して緑にする。**
- **「動作担保されている」と報告する前に、実際にテストを走らせていない**（実結果でのみ断定する・L-113）。

### 2.4. 完了条件

- [ ] 追加した振る舞いに **先行して書かれたテスト** がある
- [ ] 該当スプリントの操作レビュー手順が E2E テストとして存在する
- [ ] `npm test` 相当のコマンド 1 つで全テストが通る（**実行結果を確認済み**）
- [ ] CI が緑

> ⚠️ テスト基盤そのものが揃うのは `SP-4`（`docs/02_requirements/user-story-map.md` §5.3）。
> `SP-1`〜`SP-3` は基盤構築期のため、TDD の適用は「テストを書ける対象から書く」に留め、`SP-4` 以降は全面適用する。

## 3. SD-3: 曖昧点を残さない（確認の発火ライン）

### 3.1. 🔴 発火ライン（飼い主の明示決定・`D-12`）

> **仕様解釈が 2 通り以上あり、どちらを選ぶかで成果物が変わるとき** に確認する。それ以外は確認しない。

| 判定 | 例 | 行動 |
|---|---|---|
| ✅ **確認する** | 「表示件数の既定値は 20 か 50 か」「戻ったときページ番号も戻すのか維持するのか」— どちらでも筋が通り、選択で成果物が変わる | `AskUserQuestion` で確認する |
| ❌ **確認しない** | 実装手段・ライブラリ選定・命名・ファイル分割・テストの書き方 | **自律実行し、採用した仮定を Issue コメントか最初のコミットメッセージに 1 行記録する** |

これは `user-confirmation-minimization.md` §3 item 0 の 4 分岐のうち **(c) の適用範囲を仕様解釈に限って広げたもの** であり、
`CP-6`（ユーザー介入最小化）は維持される。A-1〜A-6（既約境界外）の扱いは **一切変わらない**。

### 3.2. 聞き方（`user-confirmation-minimization.md` §3 item 8 に準拠）

- **選択肢は最大 2 つ**。3 つ以上に割るのは判断の丸投げ
- **各選択肢に 1 行の判断材料**（何が変わるか / 何を失うか）
- **推奨案を先頭に置き `（推奨）` を付ける**

### 3.3. 聞くタイミング

🔴 **答えに依存しない作業を先に全部終わらせてから、まとめて聞く。** 曖昧点 1 つで手を止めない
（依存しない実装・テスト・調査は先に進める）。

### 3.4. 完了条件

- [ ] 仕様解釈の分岐が残っていない（確認済み、または「どちらでも成果物が変わらない」と判定済み）
- [ ] 自律判断した仮定が Issue / コミットメッセージに記録されている

## 4. SD-4: ドキュメントを読んで自律的に動く

### 4.1. スプリント着手時に読む順序

| # | 読むもの | 何を取り出すか |
|---|---|---|
| 1 | `docs/02_requirements/user-story-map.md` §5.3 の該当 `SP-n` | ゴール / 含む `US-n` `E-n` / 操作レビュー手順 / 対応 `AC` |
| 2 | `docs/02_requirements/prd.md` の参照要件 ID と §6 の該当 `AC-n` | 受け入れ条件（**ここが正本。他所の再掲を信じない**） |
| 3 | `docs/02_requirements/prd.md` §13 | そのスプリントに関わる **未決事項**（決めるべきか、開けたままか） |
| 4 | `docs/00_concept/inception-deck.md` Q4 | やらないこと / 今は決めないこと（スコープの侵食防止） |
| 5 | `docs/project-mission.md` | 品質ゲート・判断基準 |

### 4.2. 🔴 ドキュメントに書いてあることを聞かない

`SD-3` の確認は「**ドキュメントを読んでも決まらないこと**」に対してのみ発火する。読めば分かることを聞くのは `CP-6` 違反。

ドキュメント間が矛盾していたら、権威順で解決して **矛盾自体を修正する**（放置しない）:
**ユーザー明示 > 仕様（`prd.md`）> テスト > 現行コード**（`intent-gate-rules.md`）。

### 4.3. 完了条件

- [ ] Issue / PR に、参照した要件 ID（`US-n` / `E-n` / `AC-n` / `NFR-n` 等）が書かれている
- [ ] スコープ外（`inception-deck.md` Q4.2）の項目を混ぜていない
- [ ] 見つけたドキュメントの矛盾を修正したか、別 Issue を起票した

## 5. スプリント実行チェックリスト（毎スプリントで使う）

```
着手
[ ] Issue を作成し status:in-progress を付与（CP-4 の論理ロック）
[ ] §4.1 の 1〜5 を読み、対象 SP-n のゴール・操作レビュー手順・対応 AC を確認
[ ] 仕様解釈の分岐があれば §3 の書式でまとめて確認（依存しない作業は先に進める）

実装
[ ] Red: 失敗するテストを先に書く
[ ] Green: 通す最小の実装
[ ] Refactor: 重複を削る
[ ] 操作レビュー手順を E2E テストに写す

完了前
[ ] テストをコマンド 1 つで実行し、実結果で全通過を確認
[ ] PR を作成し、プレビュー URL と参照要件 ID を本文に記載
[ ] プレビュー URL で操作レビュー手順を自分で完走してから、ユーザーに確認を依頼
[ ] 自律判断した仮定を 1 行記録
```
