## 0. 4 規律（すべて必須・省略不可）

| ID | 規律 | 一言でいうと |
|---|---|---|
| **SD-1** | **動作確認できる状態で終わる** | スプリントの PR には **開けるプレビュー URL** が貼られている |

## 1. SD-1: 動作確認できる状態で終わる

- スプリントの PR 本文に **プレビュー URL を貼る**。ユーザーはリンクを開くだけで確認できる状態にする
- あわせて `docs/02_requirements/user-story-map.md` §5.3 の該当スプリントの「操作レビュー」手順を **ID で参照** する（本文へコピーしない）
- 前スプリントまでの経路も同じ URL で触れること（回帰の目視確認を兼ねる）
- **出せない場合は PR 本文に理由とローカル起動手順を書く**（沈黙禁止）
- PR 本文に **`Team:` トレーラー**（例 `Team: fan-out(3)`）を必ず含める（チーム編成の既定は `session-sprint-rules.md` §2 が正本）

🔴 **本規律のためにプレビュー環境のデプロイ先だけ先行決定する**（`D-11`）。本番デプロイ先とキャッシュ基盤は引き続き未決（`D-5` / `D-7`）。`NFR-21`（特定 PaaS 固有機能への依存を最小化）は **アプリのランタイムに対する制約として維持** し、**プレビューのためにアプリコードへ PaaS 固有 API を持ち込まない**（持ち込みたくなったら ADR を起票）。

⚠️ **プレビュー環境は `SP-1`（`E-22`）で確立する。** それ以前および `SP-1` 実施中は「開発サーバー起動」で代替してよい（詳細版 §1）。

🔴 **新しい入力経路を追加するスプリント、および入力の解釈ロジック（正規表現・パーサ・バリデータ・トークナイザ）を変更するスプリントは、入力境界表を作り実機に敵対的入力を投げる**（`SP-19` レトロ・実装もテストも正しいのに落ちる欠陥は自動テストでは検出できず実測でしか見つからないため・#448 / #719）。ここでいう「新しい入力経路」とは **ユーザー・外部システムが値を選べる新規パラメータ**（URL クエリパラメータ・ポート引数・外部 API/JSON のフィールド・フォーム入力等）を指し、値域が固定の boolean フラグや内部専用の設定値は対象外とする。表には型・実データの最頻値 / 最大値・設けた上限・異常形式で起きることを書く（表に無い境界は「未検討」として PR に残し、黙って通さない）。あわせて実データを扱う機能は **実装と同じ関数でコーパス全件を数え直し**、分布の尾（最大値・上位 N・0 件率・欠損率）を PR に貼る（サンプル 1 件の動作確認では代替にならない）。

🔴 **入力の解釈ロジックを変更する場合は書式が別**（#719）: 「新規入力経路」の表（型・最頻値/最大値・上限・異常形式）とは中身が異なるため混同しない。**「変更前後で解釈が変わる入力の実例」** を列挙し、列は **変更前の出力 / 変更後の出力 / それが `fail-open`（見落とし方向）と `fail-closed`（誤検知方向）のどちらへ倒れるか** の 3 列にする。既存の入力経路だから安全という思い込みが検証を薄くする（実例: 正規表現の文字クラスを 1 つ拡張しただけで、隣接連結・先頭省略等の実データが誤って融合・誤抽出された・#719 本文）。書式・実行手順の詳細は `sprint-development-rules-detail.md` §1.4。

### 完了条件の書き方

完了条件は **計測手段ではなく「満たすべき事実」** で書く。手段を名指しすると、その手段が使えなくなった時点で条件が自動的に未達扱いになり、達成判定が後付けの裁量に落ちる。代替証拠がある場合は **起票時に格を先に決める**（例: **本命** `wrangler tail` p95 CPU / **代替可** ローカル V8 計測値 + プレビュー CPU 超過ゼロ）。代替で充当した場合はスプリントレビューで ✅ ではなく **🟡 代替証拠で充当** と区別し、本命が取れなかった理由を併記する。

### 完了条件

- [ ] PR 本文に開けるプレビュー URL がある（または上記の代替が書かれている）
- [ ] その URL で該当スプリントの操作レビュー手順を **完走できる**
- [ ] 前スプリントの経路が壊れていない
- [ ] （新しい入力経路を追加した場合）入力境界表を作成し、各行の極端値をプレビュー実機に投げて応答コード・所要時間を記録した
- [ ] （新しい入力経路を追加し、かつ実データを扱う場合）実装と同じ関数でコーパス全件を数え直し、分布の尾（最大値・上位 N・0 件率・欠損率）を PR に貼った
- [ ] （入力の解釈ロジック（正規表現・パーサ・バリデータ・トークナイザ）を変更した場合）「変更前後で解釈が変わる入力の実例」表（変更前の出力 / 変更後の出力 / fail-open か fail-closed か）を作成し、実機で検証した（#719）

⚠️ **このプレビュー URL はスプリント完了後に退役（本番と同じビルドへ張り替え）される**（`cloudflare-infrastructure.md` §8.2.1 が SSOT）。当時の成果物を後から確認したいときは、この URL ではなく PR の差分か当時の version ID を使う。

## 2. SD-2: TDD 主体・常に動作担保

```
Red（失敗するテストを書く） → Green（通す最小の実装） → Refactor（重複を削る）
```

🔴 **実装を先に書いてテストを後から足す順序を取らない。**

🔵 **道具・層分担・二重ループ・フレームワーク由来の制約は [`docs/04_development/testing-strategy.md`](../04_development/testing-strategy.md)（SSOT・`R-11` の回答）に従う。**
本節は規律だけを定め、制約の中身は再掲しない（片方だけ古くなるため）。

| 層 | 対象 | 対応要件 |
|---|---|---|
| **単体 / 結合** | データアクセス層・エラー判別・キャッシュキー・型検証・UI コンポーネント | `NFR-23` / `NFR-24` |
| **E2E** | 🔴 **`user-story-map.md` §5.3 の「操作レビュー」手順そのもの** | `NFR-23` / `AC-10` |

🔵 **操作レビュー手順と E2E テストを一致させる**（手順を増やしたら E2E も増やす）。手動確認が自動テストに写っていれば、以降のスプリントで壊れたときに自動で気づける。外部 API は必ずモック化する（`NFR-24`）。

### 🔴 「実装が効いている」を実効値で確かめる（#349）

テストを先に書いただけでは足りない。**そのテストが実装の欠落を本当に検知するか** を確かめてからマージする（PR #337 は「README が読める」と報告してマージしたが書式が一切当たっておらず、#348 で足した最初の E2E も見出しスケールを丸ごと消して緑のままだった）。

- **見た目・スタイルに関わる変更は、計算後の値（`getComputedStyle`）で検証する**。「クラス名が付いているか」「タグがあるか」で終わらせない（クラスは付くが CSS が当たっていない状態を素通りさせるため）
- **設計値があるなら相対比較だけでなく固定値でも検証する**。相対比較（`h1 > h2` 等）だけだと、スケールを丸ごと失っても既定値の大小関係が偶然一致して通り抜ける
- 🔴 **変異テストで赤くなることを確認してからマージする**: 該当実装を一時的に外し、追加したテストが **実際に落ちること** を実測する。落ちなければそのテストは何も担保していない
- **何を壊して何が落ちたかを PR 本文に 1 行で記録する**（例: `変異テスト: globals.css の見出しスケール宣言を削除 → e2e/readme.spec.ts の font-size アサーションが FAIL することを確認`）

#### 変異テストの進め方（手順の SSOT は `tools/mutation_guard.sh`）

**サブコマンド・TTL 既定値などの手順の正本は `bash tools/mutation_guard.sh` のヘッダコメントと `usage`**（ここに転記しない）。本節が定める規律は次の 3 点:

- 壊し始める **前に** マーカーを置く（置かないと、壊している最中に Stop / PreCompact フックの WIP 自動コミットが走り、意図的な破壊がコミットされる・L-131）
- 変異を戻すときに 🔴 **`git checkout -- <path>` を使わない**（未コミットの実装ごと消える・L-133）。`git stash push -- <変異ファイル>` か、変異前に控えたパッチで戻す
- 終えたらマーカーを外す（外し忘れても TTL で自動失効する）

> **機械検査の可否（#349 完了条件の記録）**: 「スタイル変更があるのに計算後値の検証が無い」を `tools/self_review_check.py` / `pre-pr-create-check.sh` で警告するのは **見送る**。理由: 差分から「スタイル変更」を判定するには CSS ファイル・Tailwind クラス・inline style・CSS-in-JS を横断して検出する必要があり、判定が広すぎれば全 UI PR で誤検知し、狭くすれば黙って素通りする（fail-open）。本規律は上の「PR 本文への 1 行記録」で運用し、記録の有無は Layer 1 セルフレビュー（観点「テスト」）が見る。

### 🔴 やってはいけないこと

- 仕様と矛盾するテストを通すために正しいコードを黙って書き換える（`intent-gate-rules.md`・権威順は ユーザー明示 > 仕様 > テスト > 現行コード）
- テストをスキップ・無効化・quarantine して緑にする
- 実際にテストを走らせずに「動作担保されている」と報告する（実結果でのみ断定・L-113）

### 完了条件

> ⚠️ **`SP-1`〜`SP-3` は例外**（テスト基盤が揃うのは `SP-4`）。この期間は下記を **「テストを書ける対象から書く」に緩和** し、`SP-4` 以降は全項目を必須とする。緩和の根拠と範囲は詳細版 §2。

- [ ] 追加した振る舞いに **先行して書かれたテスト** がある
- [ ] 該当スプリントの操作レビュー手順が E2E テストとして存在する（`SP-4` 以降）。**手順文に書かれた観測対象**（「一部のカードにバッジが出ており」等）が、テスト内で実際に 1 件以上観測されていること（手順文の名詞がアサーションに現れていなければ写せていない・`testing-strategy.md` §7 の不変条件テストの禁止事項と対）
- [ ] コマンド 1 つで全テストが通る（**実行結果を確認済み**・`SP-4` 以降）
- [ ] CI が緑（`SP-4` 以降）。🔵 **二層で確認する**（`D-42`・Issue #543）: ① `.github/workflows/quality-checks.yml`（Prettier / ESLint / 型 / ユニット）が緑であること ② **E2E と Lighthouse a11y ゲートは CI に含まれない** ため、`bash tools/run_checks.sh` を実行して緑であることを確認し、結果を PR 本文へ貼ること（手順は `pr-review-flow-summary.md`「PR 作成時の必須事項」）
- [ ] （見た目・スタイルに関わる変更をした場合）**計算後の値**（`getComputedStyle`）で検証する E2E があり、設計値は固定値でも検証している（#349）
- [ ] （同上）**変異テストで赤くなることを実測し**、何を壊して何が落ちたかを PR 本文に 1 行記録した（#349・進め方は本節「変異テストの進め方」）
- [ ] （`tools/check_*.py` 等の検査ツールを新設・改修した場合）**self-test の実効性を変異テストで確認した**（#430）: self-test を書いた直後に、検査対象の重要な条件分岐を 1 つずつ壊して（正規表現の alternation から 1 語削る・条件分岐を緩める・閾値定数をずらす等）、self-test が **FAIL するか** を機械的に確認する。FAIL しない分岐は「テストされていない」ので、その分岐に対する回帰ケースを足す（到達不能な分岐・早期リターンで実行されないテストを緑のまま見逃さないため。実例は #430 本文）
- [ ] 🔴 **変異対象に「本番の主コードパス」を必ず 1 つ含める**（#686）: 「自分が意識して作ったガード」だけでなく **CLI の入口から副作用の発生点まで** を変異対象に選び、self-test は **本番の入口（`bash "$0"` / `main()`）を経由** させて副作用を検証する（内部関数の直呼びは入口の回帰を見逃すため不可）。選定基準の表・実例・判定の問いは `sprint-development-rules-detail.md` §2.7
- [ ] （パス・文字列で分岐する分類・判定ロジックを新設・改修した場合）**self-test に「境界の外側」の負ケースを含めた**（#750）: 「正しい入力に対する正解」だけを固めた self-test は、`str.startswith()` 等が前方一致へ退行し判定範囲が広がる方向の欠陥（例: `path.startswith("docs/rules")` が `docs/rules-old/x.md` まで誤って同一カテゴリに縮約する）を構造的に見逃す。少なくとも 1 件は「近似だが別カテゴリであるべき入力」を正ケースと対にして書く（見本: `tools/count_change_scatter.py` self-test セクション `1-b`）。変異テスト（本節冒頭の規律）で実際に FAIL することを確認する
- [ ] （`subprocess` を import する検査ツールを新設・改修した場合）**self-test の fake runner が受け取った argv を記録・検証した**（#710）: 終了コードだけを差し替える fake は、判定結果を空リスト等に固定する変異（例: `violations = check_gitignored(path)` → `violations = []`）を見逃す。fake runner に呼び出しコマンドライン全体を記録させ、① 意図したサブコマンドが呼ばれている ② 危険な省略が無い（pathspec の `--`・`timeout` 等、リポジトリの既存慣行に沿った引数が付いている）③ **本判定の経路（`main()`）から実際に呼ばれている** の 3 点を assert する。「外部コマンドを呼ぶ検査かどうか」は実装者判断に委ねず、**`subprocess` を import した時点で該当** とみなす。委譲プロンプト側の必須項目は `agent-team-summary.md`「検査ツール・ゲートを直すタスクの委譲プロンプト必須項目（#474）」に統合済み（本項が SSOT・そちらは参照）

## 3. SD-3: 曖昧点を残さない（確認の発火ライン）

### 🔴 発火ライン（飼い主の明示決定・`D-12`）

> **仕様解釈が 2 通り以上あり、どちらを選ぶかで成果物が変わるとき** に確認する。それ以外は確認しない。

| 判定 | 例 | 行動 |
|---|---|---|
| ✅ **確認する** | 「表示件数の既定値は 20 か 50 か」「戻ったときページ番号も戻すのか維持するのか」— どちらでも筋が通り、選択で成果物が変わる | `AskUserQuestion` で確認する |
| ❌ **確認しない** | 実装手段・ライブラリ選定・命名・ファイル分割・テストの書き方 | **自律実行し、採用した仮定を Issue コメントか最初のコミットメッセージに 1 行記録する** |

🔴 **これは `user-confirmation-minimization.md` の「確認してよい 2 系統」のうち第 2 系統である**（第 1 系統は §1 の A-1〜A-6）。同ファイル §0 / §1 / §3 item 0 (c) / item 2 が本規律を明示的に受けている。`CP-6` と A-1〜A-6 の扱いは **変わらない**。

聞き方は `user-confirmation-minimization.md` §3 item 8 に従う（**選択肢は最大 2 つ / 各 1 行の判断材料 / 推奨を先頭に置き `（推奨）` を付ける**）。

🔴 **答えに依存しない作業を先に全部終わらせてから、まとめて聞く。** 曖昧点 1 つで手を止めない。

## 4. SD-4: ドキュメントを読んで自律的に動く

### スプリント着手時に読む順序

| # | 読むもの | 何を取り出すか |
|---|---|---|
| 1 | `docs/02_requirements/user-story-map.md` §5.3 の該当 `SP-n` | ゴール / 含む `US-n` `E-n` / 操作レビュー手順 / 対応 `AC` |
| 2 | `docs/02_requirements/prd.md` の参照要件 ID と §6 の該当 `AC-n` | 受け入れ条件（**ここが正本。他所の再掲を信じない**） |
| 3 | `docs/02_requirements/prd.md` §13 | そのスプリントに関わる **未決事項** |
| 4 | `docs/00_concept/inception-deck.md` Q4 | やらないこと / 今は決めないこと（スコープの侵食防止） |
| 5 | `docs/project-mission.md` | 品質ゲート・判断基準 |
| 6 | `docs/03_design/ui-ux/ui-ux-guidelines.md`（**UI を触るスプリントのみ**） | 技術スタック・デザイントークン・状態表現・a11y の実装指針 |
| 7 | 🔴 `docs/rules/architecture-rules.md`（**アプリコードを書くスプリントは必読**） | 層の判定・依存規則 7 項目・DDD で守る 3 点・TDD の最低ライン（各 SSOT への入口） |
| 8 | 🔴 `docs/03_design/data-model/domain-model.md` §4（**値オブジェクト・エンティティを実装する前に必読**） | 値オブジェクトの実装の型（ブランド型 + スマートコンストラクタ）。入口は #7 の `architecture-rules.md`、値オブジェクトの実装形はこちら（`domain-model.md` §4）が正本 |

🔴 **`SD-3` の確認は「ドキュメントを読んでも決まらないこと」にのみ発火する。** 読めば分かることを聞くのは `CP-6` 違反。

ドキュメント間が矛盾していたら権威順（**ユーザー明示 > 仕様（`prd.md`）> テスト > 現行コード**・`intent-gate-rules.md`）で解決し、**矛盾自体を修正する**（放置しない）。

### 完了条件

- [ ] Issue / PR に参照した要件 ID（`US-n` / `E-n` / `AC-n` / `NFR-n` 等）が書かれている
- [ ] スコープ外（`inception-deck.md` Q4.2）の項目を混ぜていない
- [ ] 見つけたドキュメントの矛盾を修正したか、別 Issue を起票した
- [ ] （アプリコードを触った場合）`python3 tools/check_architecture_boundaries.py` が PASS し、新しいドメイン語を導入したなら `domain-model.md` を同じ PR で更新した
