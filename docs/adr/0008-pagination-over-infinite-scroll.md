# ADR 0008: `FR-7` でページネーションを選び、無限スクロールを採らない

- **状態**: **承認**
- **日付**: 2026-08-20 JST
- **対応要件**: `FR-7` / `AC-7` / `NFR-2` / `NFR-10` / `NFR-11` / `Q-8`
- **関連**: [`minimum-requirements.md`](../02_requirements/minimum-requirements.md) §3 / [`prd.md`](../02_requirements/prd.md) §4.1 / [UI/UX ガイドライン](../03_design/ui-ux/ui-ux-guidelines.md) §4.5 / [ADR 0006](0006-nextjs16-app-router.md) / [ADR 0007](0007-no-database-client-side-state.md)

---

## 1. 文脈

与件（[`minimum-requirements.md`](../02_requirements/minimum-requirements.md) §3・`FR-7`）は「検索結果が多数となる場合に備え、**ページネーションまたは無限スクロールを実装する**」として選択制にしている。要件定義フェーズでこの選択を確定させ、`prd.md` `FR-7` は「🔴 ページネーションを採用する（無限スクロールは採らない）」と決めた（`open-questions.md` `Q-8` 従属事項）。本 ADR はこの決定の理由と、無限スクロールを却下した具体的根拠を記録する。

`Q-8` は WCAG 2.2 レベル AA を目標に掲げており（`NFR-10`）、Lighthouse Accessibility = 100 を CI ゲート化している（`NFR-27`）。`FR-7` の選択は、この a11y 方針と両立する側を選ぶ必要があった。

## 2. 決定

**ページネーションを採用し、無限スクロールは実装しない。**

- 検索結果一覧は「現在ページ + 前後ページへのリンク」で構成する（`src/ui/pagination.tsx`）
- 現在ページ・表示件数（`perPage`）は **URL（`searchParams`）に反映する**（`NFR-2`。[ADR 0007](0007-no-database-client-side-state.md) §2.2）
- GitHub 検索 API が返せる最大件数（1,000 件）と実際の表示件数（`perPage`）から到達可能な最終ページを `maxPageFor(perPage)` として算出し（`src/domain/model/page-number.ts`）、これを超えるページへはリンクを出さない（`AC-7`）。あわせて `totalCount` から算出した実際の最終ページも尊重し、結果が尽きた次ページへもリンクを出さない（`src/ui/pagination.tsx`）
- `<nav aria-label="検索結果のページ">` でラップし、現在ページはリンクにせず `aria-current="page"` を付与する（[UI/UX ガイドライン](../03_design/ui-ux/ui-ux-guidelines.md) §4.5）
- 件数を明示する（「157 件中 26〜50 件を表示」等）UI とし、上限に達した場合はその旨を明示する

## 3. 理由

`FR-7` の注記（`prd.md` §4.1）が整理した、無限スクロールを不利とする 4 点を実装判断の根拠として維持する。

1. **キーボード操作でフッターに到達できなくなる**: 無限スクロールはスクロール位置に応じて新しいコンテンツを動的に追加し続けるため、キーボードで下方向へ移動し続けてもページ末尾（フッター等）に到達できない、または到達までに要する操作回数が読めない。`NFR-11`（キーボード操作での到達性）に反する
2. **スクリーンリーダーで「どこまで読んだか」が提示できない**: 無限スクロールは明確なページ境界を持たないため、スクリーンリーダー利用者が「今どの範囲を読んでいるか」「あと何件残っているか」を把握する手段が乏しい。ページネーションは「157 件中 26〜50 件」のように現在位置を明示できる
3. **フォーカス管理が複雑になり、戻り時に位置を復元しにくい**: 詳細ページから一覧へ戻ったとき（`FR-6` / `AC-6`）、無限スクロールでは「戻る前にどこまでコンテンツを読み込んでいたか」を再現する必要があり、フォーカス位置の復元（WCAG 2.2 の 3.3.7 Redundant Entry）が複雑になる。ページネーションなら「戻り先のページ番号」という単一の値を URL に保持するだけで復元できる
4. **現在ページを URL に反映できず、`NFR-2`（URL 状態）と衝突する**: 無限スクロールは「今どこまで読み込んだか」という連続的な状態を持ち、これを URL のクエリパラメータのような離散値へ素直に落とし込めない。本プロジェクトは DB を持たず状態を URL に寄せる設計原則（[ADR 0007](0007-no-database-client-side-state.md)）を採っており、ページネーションの「ページ番号」という離散値は URL 状態と自然に整合する

これらはいずれも本プロジェクトが独自に課した非機能要件（`NFR-2` / `NFR-10` / `NFR-11`）との整合性から導かれる判断であり、与件そのものは無限スクロールを禁止していない。**「選択の余地があるところで、自ら課した a11y・URL 状態の方針に合う側を選んだ」** という位置づけである。

### 3.1. GitHub Search API の上限との相性

GitHub 検索 API は 1 クエリあたり最大 1,000 件（`page × per_page` の到達可能範囲）までしか結果を返さない。ページネーションは「最終ページ」という明確な境界を持つため、この上限を **`maxPageFor(perPage)`** として型システムで表現し、上限を超えるページ番号は `PageNumber`（`src/domain/model/page-number.ts`）のスマートコンストラクタで弾ける（`domain-model.md` §4 のブランド型 + スマートコンストラクタの型）。無限スクロールでは「1,000 件目まで読み込んだらそれ以上読み込まない」という同種の上限処理を独自にスクロール監視ロジックへ実装する必要があり、UI 側の実装が複雑になる。

### 3.2. 実装済みの歯止め

`src/ui/pagination.tsx` の `Pagination` は、`maxPageFor(current.perPage)` と `totalCount` から算出した最終ページの **両方** を尊重し、いずれかに達した時点で「次へ」リンクを出さない（`AC-7`）。ページ番号自体も `PageNumber`（`src/domain/model/page-number.ts`）が `1〜MAX_PAGE` の範囲外を例外にし、URL 改変で不正な値が渡っても `tryPageNumber` が既定ページへフォールバックする（500 にしない・`domain-model.md` §4）。

## 4. 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **無限スクロール** | §3 の 4 点（キーボード到達性・スクリーンリーダーでの位置把握・フォーカス復元・URL 状態との衝突）により、本プロジェクトが課した `NFR-2` / `NFR-10` / `NFR-11` と両立しない |
| **ページネーション + 無限スクロールの併用（表示切替可能にする）** | 選択制 UI を追加すると、無限スクロール側の a11y 上の弱点（§3）がそのまま残ったまま実装コストだけが増える。`FR-7` は「いずれかを実装する」であり両方を要求していないため、a11y 上優位な一方に絞る |
| **「もっと見る」ボタン方式（クリックで追加読み込み、スクロール位置は自動監視しない）** | 無限スクロールの自動読み込みほどではないが、それでも「現在何ページ目相当を見ているか」を URL に落とし込めず、`FR-6` の戻り時復元（`AC-6`）でページネーションと同じ複雑さが残る。ページネーションで `AC-7` を確実に満たせる以上、追加のトレードオフを負う理由がない |
| **無限スクロールを採用しつつ URL にオフセットだけ反映する** | オフセットを URL に反映しても、§3 の 1〜3（キーボード到達性・スクリーンリーダー・フォーカス復元）は解決しない。URL 状態の問題（§3 の 4）だけを部分的に緩和しても、a11y 上の弱点は残る |

## 5. 結果（この決定がもたらすもの）

### 良い方向

- キーボードのみで 検索 → 一覧 → 詳細 → 一覧復帰 を完走できる（[UI/UX ガイドライン](../03_design/ui-ux/ui-ux-guidelines.md) §7.3 のチェックリスト項目）
- 現在ページが URL に反映されるため、共有・リロード・ブラウザバックのいずれでも同じ結果を再現できる（`NFR-2`）
- GitHub 検索 API の 1,000 件上限を `PageNumber` 型で機械的に強制でき、上限超過のページ番号を実行時エラーにせず既定ページへフォールバックできる（`AC-7`）
- ページ番号という離散値のみを状態として扱えばよく、DB レス原則（[ADR 0007](0007-no-database-client-side-state.md)）と自然に整合する

### 受け入れる代償

| 代償 | 緩和策 |
|---|---|
| 無限スクロールに比べ、次ページを見るための操作（クリック/タップ）が都度必要になる | ページ番号ボタンを `--size-control-xs` 以上のタップ領域で提供し、モバイルでは前後ボタン中心に簡略化する（[UI/UX ガイドライン](../03_design/ui-ux/ui-ux-guidelines.md) §4.5） |
| 「際限なくスクロールして眺める」体験は提供できない | 本プロジェクトの主要フローは「検索して絞り込み、詳細を確認する」ことであり、際限のない閲覧体験は目的に含まれない（`prd.md` §1.1） |
