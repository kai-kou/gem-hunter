# ADR 0001: UI スタックに Tailwind CSS v4 + shadcn/ui（Radix UI 明示指定）を採用する

- **状態**: 承認
- **日付**: 2026-08-17 JST
- **対応要件**: `TR-5`（UI コンポーネントライブラリの採否）/ `NFR-3` / `NFR-10` / `NFR-27` / `NFR-28`
- **関連**: Issue #16 / [UI/UX リサーチ](../03_design/ui-ux/20260817-ui-ux-research.md) / [UI/UX ガイドライン](../03_design/ui-ux/ui-ux-guidelines.md)

---

## 1. 文脈

`TR-5` は「UI コンポーネントライブラリの採否は問わない（使わない構成も可）」として未決のまま開いていた。一方で本プロジェクトは以下を同時に満たす必要がある。

- **Lighthouse Accessibility = 100 を CI ゲート化**（`NFR-27`）/ WCAG 2.2 レベル AA を目標（`NFR-10`）
- **Server Components を基本とし `use client` はインタラクションが必要な箇所に限定**（`NFR-3`）
- 初期 JS バンドルサイズを抑える（`NFR-28`）
- 主目的は選考課題・ポートフォリオであり、**MVP 時点で正式リリースと遜色ない UI/UX** にしたい

## 2. 決定

以下を採用する。

| 層 | 採用 |
|---|---|
| CSS | **Tailwind CSS v4**（CSS-first 設定。`tailwind.config.js` を作らない） |
| コンポーネント | **shadcn/ui** |
| 基盤プリミティブ | 🔴 **Radix UI を明示指定する**（`npx shadcn init -b radix`） |
| テーマ切替 | **next-themes** |
| フォント | **next/font**（可変フォント・`display: 'optional'`） |

## 3. 🔴 shadcn/ui の既定（Base UI）に逆らって Radix を選ぶ理由

2026-07 の公式アナウンスで、shadcn/ui の新規プロジェクト既定は Radix UI から **Base UI** に変更された（Radix は非推奨化されておらず `-b radix` で選択可能）。それでも Radix を選ぶ。

**理由: アクセシビリティ保証の一次情報の有無。**

| | Radix UI | Base UI |
|---|---|---|
| a11y 保証の一次情報 | ✅ WAI-ARIA Authoring Practices 準拠、NVDA / JAWS / VoiceOver でテスト済みと **公式が明記** | ⚠️ **確認できず**（shadcn 公式アナウンス本文にはアクセシビリティを直接保証する記述がない。第三者記事のみ） |

本プロジェクトは **Lighthouse Accessibility = 100 を CI ゲートにしており、ここが落ちると実装がブロックされる**（`NFR-27`）。基盤プリミティブのアクセシビリティ品質は、この CI ゲートを通せるかを直接左右する。

> **判断基準**: 「品質保証が一次情報で明文化されているか」。Base UI が劣るという証拠はないが、**確認できていないものを、CI ゲートの前提には置かない。**

## 4. 「UI ライブラリを使わない」を採らない理由

`TR-5` は「使わない構成も可」としており、`NFR-28`（バンドルサイズ）の観点では素の Tailwind のみが最小になる。それでも採らない。

- Dialog / Combobox / Popover 等の **フォーカストラップ・ロービングタブインデックス・ARIA 属性・Escape 処理を自前実装** する必要があり、`Lighthouse Accessibility 100` と WCAG 2.2 AA を **安定して** 満たす工数が明確に増える
- 本プロジェクトのトレードオフスライダーは **`S-4`（アクセシビリティ ↔ 実装速度）をアクセシビリティ寄りに、`S-6`（UI の作り込み ↔ 速度）を速度寄りに** 置いている（[インセプションデッキ](../00_concept/inception-deck.md) Q9）。a11y を自前実装で担保しにいくのはこの配分に反する

## 5. 結果（この決定がもたらすもの）

### 良い方向

- **`use client` 境界を PR レビューで目視確認できる。** shadcn/ui はコード生成方式で、生成物が `node_modules` ではなく自リポジトリに残るため、`NFR-3` を機械的に守れる
- 未使用コンポーネントを持ち込まないため、ライブラリ全体の import コストが発生しない（`NFR-28`）
- Tailwind v4 は **ランタイム JS ゼロ**（ビルド時に静的生成）
- `next/font` の既定挙動だけで CLS 対策の大半が入る（`NFR-1`）

### 受け入れる代償

- **shadcn/ui の既定構成から外れる**（`-b radix` の指定を忘れると Base UI が入る）。導入手順を [ガイドライン §1](../03_design/ui-ux/ui-ux-guidelines.md) に明記して防ぐ
- shadcn/ui のインタラクティブ系コンポーネントは必然的に Client Component になる。**その分は Client Bundle に載る**
- Radix が将来 shadcn/ui のサポート対象から外れた場合、本 ADR を見直す必要がある

## 6. 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **shadcn/ui + Base UI（既定のまま）** | アクセシビリティ保証が一次情報で確認できない（§3）。CI ゲートの前提にできない |
| **UI ライブラリ不使用（Tailwind のみ）** | a11y を自前実装する工数がトレードオフ配分に反する（§4） |
| **React Aria（Adobe）** | WCAG 準拠の厳密さは評価が高いが、shadcn/ui エコシステムとの統合実績が薄く、作り込み済み UI 資産を自前で組む工数が増える。DB なし・軽量アプリという本プロジェクトの規模に対してオーバースペック |
| **CSS-in-JS 系（styled-components 等）** | ランタイムを持ち `NFR-28` と `NFR-3` の双方に不利 |
