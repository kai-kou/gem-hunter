# ADR 0012: 任意の GitHub OAuth ログインを、与件が対象外とした認証に上乗せする

- **状態**: **承認**
- **日付**: 2026-08-20 JST
- **対応要件**: `AR-5` / `D-6` / `D-20` / `NFR-30` / `AC-11` / `NFR-33`
- **関連**: [PRD](../02_requirements/prd.md) §0.3 / §3.2（エラー種別） / §12 / [決定ログ](../02_requirements/open-questions.md) `D-6`「D-6 の決定から従属的に確定する事項」 / [ADR 0003](./0003-github-app-authentication.md)（サーバー側の GitHub App 認証・`D-6` 6 で本 ADR の前提を変更しないと確認済み） / `src/infrastructure/github/oauth.ts`

---

## 1. 文脈

与件（[`minimum-requirements.md`](../02_requirements/minimum-requirements.md) §1.2）は認証を明示的に「対象外」としている。一方で `D-6`（2026-08-17）は、サーバー側の GitHub API 認証を単一の資格情報（現在は [ADR 0003](./0003-github-app-authentication.md) の GitHub App installation token）に決めた時点で、検索の律速枠（30 req/分）をアプリ全体で共有する構成が確定した。共有枠は利用者数が増えるほど個々の体感速度が悪化し、`NFR-7`（レート制限耐性）を長期的に満たせなくなる。

`D-9`（[PRD](../02_requirements/prd.md) §0.3）は `P1-MVP` の定義を 2 要素に分けている。

1. 与件の受け入れ基準 11 項目を満たす最小集合（必達の下限）
2. **後から入れると既存コードの書き換えが発生する上乗せ要件** — ロケール基盤（`D-4`）/ キャッシュ抽象（`D-5`）/ **任意 OAuth（`D-6`）**

任意 OAuth はこの②に分類されている。認証を後付けすると、セッション管理・ログイン導線・エラー体験（レート制限到達時の案内文言）・トークンの保管方式など複数レイヤーへ手が入り、MVP 後に追加するよりも今 MVP に含める方が書き換えコストが低いと判断されていた。本 ADR は、この判断（`D-6` のログイン設計部分）を **なぜ採ったか / 何を捨てたか** の記録として ADR 化する。

---

## 2. 決定

**未ログインでも全機能を使える前提を維持したまま、任意の GitHub OAuth ログインを `P1-MVP` に含める。**

| # | 決定 |
|---|---|
| 1 | ログインは完全に任意。**ログインで変わるのはレート枠だけ**（未ログイン = アプリ共有枠、ログイン = 各自の 30 req/分）。機能差を作らない（`AR-5`） |
| 2 | OAuth スコープは要求しない（no scope）。公開リポジトリの検索・閲覧しか行わないため追加権限は不要 |
| 3 | ユーザーの GitHub アクセストークンは暗号化した httpOnly Cookie（セッション）にのみ保持し、サーバー側ストア（DB）を持たない（`D-5` の DB レス原則と整合。実装は `src/infrastructure/platform/session-cookie.ts`） |
| 4 | CSRF 対策として OAuth の `state` パラメータを必須にする。ログアウト（Cookie 破棄）も要件に含める |
| 5 | callback URL は環境変数（`GITHUB_OAUTH_CALLBACK_URL`）で外部注入し、デプロイ先が未定の段階でも構成を壊さない |
| 6 | レート制限エラー（403/429 かつ `x-ratelimit-remaining: 0`）の案内文に **ログインで枠を増やせる旨** を含め、ログイン導線として機能させる |
| 7 | 資格情報（`GITHUB_OAUTH_CLIENT_ID` / `GITHUB_OAUTH_CLIENT_SECRET` / `GITHUB_OAUTH_CALLBACK_URL`）が揃っていない環境では、ログイン導線自体を静かに無効化する（`installation-token.ts` の `readCredentials()` パターンを踏襲・`src/infrastructure/github/oauth.ts` の `oauthCredentialsConfigured()`） |

🔴 **本 ADR は認証方式そのもの（GitHub App installation token）を扱わない**。サーバー側の認証方式選定は [ADR 0003](./0003-github-app-authentication.md) が正本であり、同 ADR §2 決定 6 は「`D-6` のうち任意 OAuth ログイン・機能差を作らない原則は変更しない」と明記して本決定を引き継いでいる。本 ADR は「与件が対象外とした認証を、なぜ・どういう設計で上乗せしたか」の記録に限定する。

---

## 3. 理由

### 3.1. なぜ与件の「対象外」を破ってよいと判断したか

与件 §1.2 の「対象外」は「実装しなくてよい」であって「実装してはならない」ではないと解釈した。`D-2`（要件の上乗せは自由・与件の下限を割らない限り制約されない）に沿う限り、与件が要求していない機能を追加すること自体は与件違反にならない。ただし **解釈を書き残さないと「要件を読んでいない」と誤読されうる** ため、この上乗せの理由を README・PRD・本 ADR の複数箇所に明記することを完了条件に含めた（`NFR-30` / `AC-11`）。

### 3.2. なぜ後付けせず `P1-MVP` に含めたか（`D-9` の②）

認証を後から追加すると、以下のレイヤーへの手戻りが発生する。

- **セッション管理**: MVP 後に追加すると、既に DB レスで確定させた状態設計（`D-5` 追補）へ「サーバー側ストアを持たない」制約を保ったままセッションを差し込む必要があり、Cookie 方式を選ぶこと自体は変わらないが、検証・実装のやり直しが発生する
- **エラー体験**: レート制限到達時のエラー文言（§3.2「レート制限エラーがログイン導線になる」設計）は、ログイン機能の有無を前提に文言を設計している。後から足すと文言・導線を作り直す
- **秘密情報の取り回し**: OAuth クライアントシークレットを読んでよい層を 1 ファイルに限定する設計（`ARCH-5` / `NFR-22`）は、後から差し込むよりも他の秘密情報（GitHub App の秘密鍵）と並行して最初から設計した方が一貫性を保ちやすい

これらは「後から入れると既存コードの書き換えが発生する」という `D-9` ②の基準に該当するため、`P1-MVP` に含めた。

### 3.3. なぜ機能差を作らないか（`AR-5` の核）

未ログインでも全機能が使える前提を崩すと、`D-6` の目的（不特定多数が気軽に使える）が壊れる。ログインを「レート枠を各自のものに切り替えるだけ」の手段に限定することで、認証を上乗せしたこと自体が既存のミッション（個人開発者が気軽に使える検索）と矛盾しないようにしている。

### 3.4. なぜ OAuth スコープを要求しないか

本プロダクトは他人の公開リポジトリの検索・閲覧のみを行い、Issue 作成・Webhook 購読・書き込み系の操作を一切行わない（[ADR 0003](./0003-github-app-authentication.md) §2 決定 6 で明記済み）。追加スコープを要求しないことで、利用者が同意する権限を最小化し、「最小権限」を設計として実証する。

### 3.5. なぜレート制限エラーをログイン導線にするか

任意ログインは機能的な必然性がないため、案内なしでは存在に気づかれにくい。レート制限に到達した瞬間（＝ログインの価値が最も伝わる瞬間）に案内を出すことで、機能差を作らずに導線を成立させる。

## 4. 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **認証を必須にする（ログインしないと使えない）** | `D-6` の目的（不特定多数が気軽に使える）と矛盾する。「実際に使われている OSS を見つけられるようにする」というミッションの間口を自ら狭める |
| **認証を一切入れない（与件どおり対象外のまま）** | サーバー側認証の共有レート枠（30 req/分）がアプリ全体の律速になり、利用者が増えるほど体感速度が悪化する。`NFR-7` を長期的に満たせない |
| **PAT（Personal Access Token）を利用者に手入力させる** | 利用者に GitHub の PAT 発行という技術的ハードルを課す。与件が想定する「個人開発者が気軽に使える」体験に反する。加えて利用者が発行した任意スコープのトークンをサーバーが預かることになり、`NFR-9`（秘密の取り回し）の観点でも OAuth（no scope・GitHub 側で権限管理）より劣る |
| **ユーザーの OAuth トークンをサーバー側の既定認証に使う** | 未ログインで全機能が使えるという `D-6` の原則が壊れる。サーバー側の既定認証は GitHub App installation token のまま維持する（[ADR 0003](./0003-github-app-authentication.md) §6） |
| **複数トークン（PAT 等）のローテーション** | レート制限の回避とみなされる恐れがある。`D-6` / [ADR 0003](./0003-github-app-authentication.md) で既に不採用（本 ADR でも維持） |
| **ライブラリ（Auth.js 等）で OAuth を実装する** | `fetch` と Web Crypto のみに依存する自前実装を採用し、追加ライブラリは導入しない（whiteboard `content/discussions/sp8-auth-i18n-20260819/whiteboard.md` 争点 A/C の決定。Cloudflare Workers ランタイムとの親和性・プレビュー無効化方針との相性を理由とする） |

---

## 5. 結果（この決定がもたらすもの）

### 良い方向

- 未ログインの利用者体験（与件の下限）を一切損なわずに、レート枠が逼迫した利用者へ緩和手段を提示できる
- OAuth スコープを要求しないことで、認証の追加が招く権限リスクを最小化できる
- セッションを暗号化 httpOnly Cookie に限定し、`D-5`（DB レス原則）を崩さずに認証状態を持てる

### 受け入れる代償

| 代償 | 緩和策 |
|---|---|
| 与件の対象外項目に手を入れたことの説明責任が生じる | README・PRD・本 ADR の複数箇所に上乗せ理由を明記する（`NFR-30` / `AC-11`。本節が完了条件） |
| OAuth 資格情報（3 環境変数）が実行環境に必要になる | 未設定でも機能を静かに無効化し（`oauthCredentialsConfigured()`）、未ログイン体験を壊さない設計にする |
| **認証を追加した以上、データの可視範囲（プライベートリポジトリの混入）を明示的に評価する責務を負う** | [ADR 0003](./0003-github-app-authentication.md) §5.4 が定めた 4 層の公開限定強制（`NFR-33` / `AC-12`）をアプリ側に実装する。認証を上乗せする決定は、レート枠・実装コストだけでなく可視範囲の変化も同じ表で評価すべきという教訓（`L-128`）は本 ADR の対象領域にも当てはまる |

---

## 6. 撤回条件

以下のいずれかを観測したら本決定を見直す。

1. サーバー側の共有レート枠（30 req/分）が実運用で十分（同時利用者数が少ない・キャッシュヒット率が高い）と判明し、ログイン機能を維持するコスト（実装・保守）が見合わないと判断された場合
2. ログインしないと使えない機能を求めるユーザーからの要望が強く、`AR-5` の「機能差を作らない」原則自体を見直す必要が生じた場合（`D-6` の目的そのものの再検討を要するため、単独の ADR 追補では済まない）
