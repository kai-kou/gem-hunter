# ADR 0010: 複数トークンのローテーションを採用しない

- **状態**: **承認**
- **日付**: 2026-08-20 JST
- **対応要件**: `D-6` / `D-20` / `NFR-7` / `NFR-9` / [PRD](../02_requirements/prd.md) §3.2「やらないこと」/ [`inception-deck.md`](../00_concept/inception-deck.md) Q4.2
- **関連**: [ADR 0003](0003-github-app-authentication.md)（サーバー側認証方式） / [`open-questions.md`](../02_requirements/open-questions.md) `D-6` / `D-20`

---

## 1. 文脈

GitHub API のレート制限（[PRD](../02_requirements/prd.md) §2.2）は本プロダクトの律速要因である。検索 API は認証済みでも 30 req/分、Core API は認証済みで 5,000 req/h（Fine-grained PAT 時点。GitHub App では 8,800 req/h・[ADR 0003](0003-github-app-authentication.md)）と、上限が固定である。

レート枠を広げる技術的な選択肢の 1 つに「複数のトークン（PAT / installation token）を用意し、リクエストごとに使い分けて枠を合算する」ローテーションがある。この選択肢は要件定義の初期段階（`D-6`・2026-08-17）で既に検討され、[`inception-deck.md`](../00_concept/inception-deck.md) Q4.2「やらないこと」に「複数トークンのローテーション」として明記済みだった。GitHub App 方式への改訂（`D-20`・[ADR 0003](0003-github-app-authentication.md)・2026-08-18）でも、この不採用判断は明示的に維持事項として引き継がれている。

`NFR-32`（技術的意思決定を ADR として記録する）は本主題を「記録すべき ADR」の主題 7 として指定している（[PRD](../02_requirements/prd.md) §12）。本 ADR はこれまで複数の決定ログに分散していた不採用理由を 1 箇所にまとめて記録する。

---

## 2. 決定

**GitHub API のレート枠を広げる手段として、複数トークンのローテーションを採用しない。**

レート枠の拡大は、代わりに以下の 2 手段で対応する。

| # | 手段 | 詳細 |
|---|---|---|
| 1 | **サーバー側の既定認証を GitHub App の installation token にする** | [ADR 0003](0003-github-app-authentication.md)。Core 枠が Fine-grained PAT の 5,000 req/h から 8,800 req/h に拡大する（実測。ただし律速である検索枠 30 req/分は変わらない） |
| 2 | **任意の GitHub OAuth ログイン**（`AR-5`） | ログイン時はアプリ共有枠ではなく利用者自身の 30 req/分を使う。機能差は作らず、変わるのはレート枠だけ |

---

## 3. 理由

### 3.1. レート制限の回避とみなされる恐れがある

`D-6`（2026-08-17）の決定時点から一貫して記録されている不採用理由は、**複数トークンを使い分ける行為自体が、GitHub のレート制限機構を意図的に迂回する運用とみなされうる**という懸念である（[`open-questions.md`](../02_requirements/open-questions.md) `D-6` 従属事項・[`inception-deck.md`](../00_concept/inception-deck.md) Q4.2・[ADR 0003](0003-github-app-authentication.md) §6）。

⚠️ **本 ADR は GitHub の利用規約・AUP の該当条項をリポジトリ内の一次情報として確認していない**（`R-8`「GitHub 利用規約・法務の一次確認」は [`open-questions.md`](../02_requirements/open-questions.md) §4 で **第三者へ公開する時点** の実施と定義されており未了）。したがって本 ADR で断定できるのは「懸念があるとして 3 回の決定ログにわたり一貫して不採用と判断されてきた」という事実であり、GitHub 側の規約文言そのものの引用ではない。裏付けの取れる範囲でのみ理由を記述する。

### 3.2. 秘密情報の管理面が増える

トークンを複数保持すると、秘密として管理する対象が増える。[ADR 0003](0003-github-app-authentication.md) §3.2 が明示するとおり、`INF-4`（定常運用ゼロ）は「人手の定常作業を発生させない」ことを求めており、GitHub App の installation token を選んだ決め手も「保持する秘密を署名鍵 1 つに閉じ、有効期限の更新作業を発生させない」ことだった。複数トークンのローテーションは、この方向性と逆行する。

- 保持する秘密（署名鍵 or PAT）の数が増えるほど、`NFR-9`（秘匿情報をクライアントへ露出させない）の実装面での監視対象・漏洩時の影響範囲が広がる
- 各トークンの発行元アカウント・権限・有効期限をそれぞれ管理する必要があり、`INF-4` が禁じる人手の定常作業（更新・失効監視）が複数系統に増える

### 3.3. 帰属不能な呼び出しになる

GitHub App の installation token は、単一の App インストールに紐づき、監査ログ上の呼び出し元が一意に特定できる（[ADR 0003](0003-github-app-authentication.md) §3.3）。複数トークンをリクエストごとに切り替える設計は、この一意性を崩し、どのリクエストがどのトークンで行われたかの追跡・説明可能性を損なう。`project-mission.md` の優先順位（説明可能性）とも整合しない。

### 3.4. 運用複雑度が実利に見合わない

律速要因は検索 API の 30 req/分であり、これは GitHub App でも Fine-grained PAT でも変わらない固定枠である（[ADR 0003](0003-github-app-authentication.md) §3.1・§6.2「決め手にならなかった軸」）。複数トークンのローテーションで Core API 枠（詳細取得側）を合算できたとしても、**アプリ全体のスループット上限を規定している検索枠には効かない**。実装・運用コストに見合う実利が乏しい。

---

## 4. 却下した選択肢（＝本 ADR の主題そのもの）

| 選択肢 | 却下理由 |
|---|---|
| **複数の Fine-grained PAT をラウンドロビンで使い分ける** | レート制限の回避とみなされる恐れ（§3.1）。秘密情報の管理対象が PAT の本数分増える（§3.2） |
| **複数の GitHub App installation を用意し、リクエストごとに切り替える** | 同上に加え、呼び出し元の帰属が崩れ説明可能性を損なう（§3.3） |
| **利用者ごとの OAuth トークンをアプリ共有枠の補助として無断で再利用する** | `AR-5` は「ログインで変わるのは自分自身のレート枠だけ」という原則を明記しており、他の利用者の検索処理に流用すると機能差の透明性が崩れる（[PRD](../02_requirements/prd.md) §4.2 `AR-5` の設計原則と矛盾） |

---

## 5. 結果（この決定がもたらすもの）

### 良い方向

- 保持する秘密が「App の署名鍵 1 つ」に閉じ、`INF-4`（定常運用ゼロ）・`NFR-9`（秘匿情報の露出防止）の実装面がシンプルなまま保たれる
- 全リクエストの呼び出し元が単一の App インストールに一意に帰属し、説明可能性が保たれる
- GitHub 側から見た本プロダクトの API 利用パターンが、レート制限機構を迂回しようとしていないことを明示できる

### 受け入れる代償

| 代償 | 緩和策 |
|---|---|
| 検索 API の 30 req/分がアプリ全体の実効上限として残り続ける | キャッシュ・request coalescing・GitHub API 呼び出しの直列化・`x-ratelimit-remaining` 監視による degraded 表示で緩和する（`D-6` 従属事項・[ADR 0005](0005-cache-port-yagni-exception-and-ttl.md)） |
| 同時利用者数が増えた場合、共有枠の逼迫が早まる | 任意 OAuth ログイン（`AR-5`）で自分のレート枠に切り替えられることを、レート制限エラー時の案内として利用者に提示する（[PRD](../02_requirements/prd.md) §7 エラー種別の判別仕様） |
