# ADR 0014: キーワード非依存の発見面を日次の有限ダイジェストとして実装する

- **状態**: **承認**
- **日付**: 2026-08-20 JST
- **対応要件**: `AR-9` / `AR-10` / `US-30`〜`US-33` / `D-27`〜`D-29` / `AC-9`
- **関連**: [`decisions.md`](../../content/discussions/post-mvp-strategy-20260820/decisions.md)（本 ADR の決定源） / [ディープリサーチ](../../content/research/20260820-zero-query-discovery_deep_research.md) / [補完リサーチ](../../content/research/20260820-zero-query-discovery_supplement.md) / [ADR 0008](0008-pagination-over-infinite-scroll.md)（無限スクロール不採用の既存決定） / [ADR 0009](0009-hidden-gem-score-definition.md)（`Gem Index` の算出方法・本 ADR は再定義しない）

## 1. 文脈

MVP（`M-2` / `S-1`）は `SP-11`（#212）で達成済みで、検索窓にキーワードを入力する動線のみが実装されている。飼い主の意向（`decisions.md` §0）により **`M-5`（Phase 2 着手判断ゲート）を「着手する」で通過** させ、`S-3`（Phase 2）を構想から実装対象へ格上げした。

初期コンセプト [`initial-concept.md`](../00_concept/initial-concept.md) が志向していた「キーワード入力だけでなく、リマインド的なリストアップができてもよい」という要望を実装するには、(1) 発見面をどこに置くか (2) 更新頻度・再現性をどう設計するか (3) 「リマインド」の実体を何にするか、を確定させる必要がある。飼い主は専門チームの議論に先立ち `AskUserQuestion` で仕様分岐 1〜3（`decisions.md` §2）に回答済みで、本 ADR はその回答と専門チームの議論（`decisions.md` §3）を実装可能な設計として確定させるものである。

ディープリサーチ（[本体](../../content/research/20260820-zero-query-discovery_deep_research.md)・[補完](../../content/research/20260820-zero-query-discovery_supplement.md)）は 3 票制の敵対的検証を通しており、本 ADR は **検証済み所見（§2 F-1〜F-14）と補完リサーチの一次確認済み事実のみを根拠に使う**。反証・不支持となった主張（deep_research §4）は一切引用しない。

## 2. 決定

🔴 **frontmatter の `対応要件` にある `AC-9` について**: 本 ADR が追加する機能は上乗せ要件（`AR-9` / `AR-10`）であり、`user-story-map.md` の `SP-14` / `SP-15` が明記するとおり **新しい `AC-n` を作らない**（両スプリントとも「対応 `AC`: なし」）。ただし既存の `AC-9`（キーボードのみで完走できる）は全画面に適用される横断要件であり、本 ADR が追加する発見面もこれを当然に満たす（§3.1・操作レビュー手順 5「Tab と Enter だけで一覧から詳細まで完走できる」）。frontmatter の `AC-9` はこの横断適用を指しており、`SP-14` 固有の新規受け入れ条件ではない。

### 2.1. 発見面をトップページ（`/{locale}`）に置き、日次の有限ダイジェストとして実装する

- キーワードを入力しない発見面（`A-8`）を **トップページ（`/{locale}`）** に置く。開いた瞬間に「今日の Gem」が見える。検索窓は同じページ上部に残し、MVP の検索動線（`A-2` 以降）は変更しない。
- 提示形式は **有限件数（既定 5 件）の日次ダイジェスト**。無限フィード・無限スクロールは採らない。

### 2.2. 生成は日付を唯一のシードとする決定論的生成とし、サーバー側に状態を持たない

- 並び順は **UTC 日付文字列（例 `YYYYMMDD`）を唯一のシード** として決定論的に生成する。同じ日は全ユーザーで同じ並びになり、リロードしても再現し、日付が変わると入れ替わる。
- 候補データ（`Gem Index` 済みの静的 JSON・`D-28`）はバッチ生成済みのものをそのまま配信し、ランキング自体の並べ替え計算は **クライアント側** で行う（[補完リサーチ §2.3](../../content/research/20260820-zero-query-discovery_supplement.md)）。Worker は静的配信 + エッジキャッシュに徹し、Cloudflare Workers Free の CPU 予算（10ms/リクエスト）を消費するサーバー側計算を持たない。
- サーバーはリクエストごとの個人化状態を一切持たない（`D-6` / `D-14` を維持）。
- 🔴 **日付シードはクエリパラメータ `?date=YYYYMMDD` で外部から上書きできる**。プレビュー URL を開いた人間が「翌日まで待つ」ことなく `SP-14` 操作レビュー手順 4（日付を進めると顔ぶれが入れ替わる）を完走できるようにするための決定であり、サーバー状態を持たないまま（`D-6` / `D-14` 維持）検証可能にする。URL 共有だけで同じ画面を再現できる副次的な利点もある（`SD-1`: プレビュー URL 上で操作レビューを完走できる必要がある）。**入力値は日付として厳密に検証し、不正値（存在しない日付・形式不一致等）は既定の当日（UTC）にフォールバックする**（本番の挙動をパラメータ未指定時と同一に保つ）。E2E テスト用の時刻モックのみで完結させる案（本番の URL 表面積を増やさない）は、プレビュー URL 単体で操作レビューを完走できないため本 ADR では採らない（§4）。

### 2.3. 無限フィードを採らない（ADR 0008 の延長）

[ADR 0008](0008-pagination-over-infinite-scroll.md) は検索結果一覧について無限スクロールを不採用と決定済みである。本 ADR は同じ判断を発見面にも適用し、**今回新たに得られた根拠のみ** を追加する（ADR 0008 §3 の 4 点は再論証しない）。

### 2.4. 前回訪問からの差分は上乗せ機能とし、フォールバックを必須要件にする

- 「前回訪問以降に入れ替わった候補がわかる」（`US-32`）は **上乗せ機能** として実装する（コア体験である日次ダイジェスト自体の前提にしない）。
- Safari の ITP 仕様により、当該サイトでの操作なしに Safari を 7 日間使用すると `localStorage` を含むスクリプト書き込み可能ストレージが全削除される（§3 参照）。したがって **前回訪問タイムスタンプが失われている場合、エラーや空画面を出さず「初回として全件を表示する」フォールバックを必須要件とする**（任意対応にしない）。

### 2.5. RSS 配信を採用し、メール / push 通知は採らない

- 「ダイジェストを購読できる」（`US-33` / `AR-10`）は **RSS**（Pull 型・購読者リストをサーバーに持たない）で実現する。
- **メール通知・push 通知は不採用** とする。配信先リストの永続化が `D-14`（サーバーに個人データを持たない）・`D-18`（永続ストアを採用しない）に正面から抵触するため。

### 2.6. Gem Index の算出方法は再定義しない。母集団はエコシステム内で閉じて計算する

`Gem Index`（被依存数パーセンタイル順位 − star パーセンタイル順位・2 軸非合算）は [ADR 0009](0009-hidden-gem-score-definition.md) が確定済みであり、本 ADR はこれをそのまま採用する。

- **母集団はエコシステムごとに閉じて計算する**（npm の中で完結、PyPI の中で完結。**両者を混ぜて 1 つの母集団にしない**）。これは `D-10`（`docs/02_requirements/open-questions.md`）に従属する整理として既に記録されている考え方であり、本 ADR は矛盾なくそのまま採用する（`decisions.md` §3.3）。
- **対象エコシステムは `D-10` のとおり npm + PyPI**。本 ADR はこの決定を変更しない。
- 🔴 **`SP-14`（最初のスプリント）のスコープだけを npm 1 エコシステムに限る**。PyPI は後続スプリントで同じ仕組みをそのまま適用する（新たな設計判断を要しない）。
- 🔴 **不変条件**: 「薄いスライス」とは **対象エコシステムを 1 つに絞る**（`SP-14` = npm のみ）という意味であり、**npm の中をさらにサンプリングすることではない**。母集団（npm 全量）を絞ると残差の分散が消え `R-2` 違反（GitHub Trending の劣化コピー）につながる（`decisions.md` §3.3 の母集団取り違え禁止）。

## 3. 理由

### 3.1. 無限フィードではなく有限ダイジェストを選ぶ理由

[A] NN/g は無限スクロールが適するのは「特定のタスクや目標を持たずに同質なアイテムを閲覧する」状況に限られるとし、逆に (a) 特定のものを探す (b) 長いリスト内のアイテムを比較する (c) 上位数件だけを検分する、という用途では非推奨としている。gem-hunter の「提示された OSS を比較検討して 1 つ選ぶ」という利用目的行為はまさに (b)(c) に該当する。

[A] 同記事はさらに、無限スクロールがキーボードのみのユーザーにとって、1 ページに大量のコンテンツが載るためリンクを 1 つずつ tab 移動せざるを得ず操作を複雑化すると述べる。本プロジェクトは Lighthouse Accessibility = 100 とキーボードのみでの完走（`AC-9`）を必須ゲートとしており（[ADR 0008](0008-pagination-over-infinite-scroll.md) が既に同じ理由で検索結果一覧の無限スクロールを退けている）、発見面だけ無限フィードを採用すると a11y ゲートに抵触する。

- 出典: https://www.nngroup.com/articles/infinite-scrolling-tips/ （ディープリサーチ F-1 / F-2、票 3-0）

### 3.2. 日付シードの決定論的生成を選ぶ理由

[A] 時間トリガー型の定期ダイジェストには実例がある。Hugging Face Daily Papers は日次でキーワード入力なしに新着が提示される仕組みを稼働させている。ただし現行の Subscribe（メール購読）は `/login?next=%2Fpapers` へ遷移しログインを要求するため、gem-hunter の「ログイン不要」制約とは正面から衝突する（[ディープリサーチ F-3](../../content/research/20260820-zero-query-discovery_deep_research.md)、票 3-0）。この制約衝突が §2.5 で RSS を採り、メール購読を採らない理由になっている。

[A] 時間帯単位のシャッフル（Product Hunt が 2026-03-27 の単日イベント「Randomized Leaderboard Day」で実施した、30 分周期のうち 25 分ランダム・5 分通常ランク順という時間分割方式）は実在の前例である（ディープリサーチ F-4、票 3-0）。**開いている間に内容が動く実装は、ユーザーが操作していないのにコンテンツが変化し続ける点で WCAG 2.2.2（Pause, Stop, Hide）に抵触するリスクがある** ため、独立機能としては採らない。日付シードという「1 日単位の離散値」に内部実装を留めることで、この前例が示す「ランキング固定化への対処としての時間区切り」という発想だけを、a11y リスクなしに取り込む。

### 3.3. 「今回新たに得た根拠」— 無限フィード不採用の追加論拠（ADR 0008 の延長）

ADR 0008 は検索結果一覧について「キーボード到達性・スクリーンリーダーでの位置把握・フォーカス復元・URL 状態との衝突」の 4 点を根拠に無限スクロールを退けている。発見面については、上記 3.1 の NN/g 所見（比較・検分用途での非推奨）と、時間トリガー型シャッフルを独立機能にした場合の WCAG 2.2.2 リスク（3.2）が、ADR 0008 にはなかった **発見面固有の追加根拠** である。両 ADR の結論（無限フィードを採らない）は一致するため重複論証はしない。

### 3.4. 前回訪問差分をフォールバック必須の上乗せ機能にする理由

[A] Safari は当該サイトでのユーザー操作なしに Safari を 7 日間使用すると、`localStorage` を含むスクリプト書き込み可能ストレージを全削除する（WebKit 公式ブログの逐語: *"deleting all of a website's script-writable storage after seven days of Safari use without user interaction on the site"*）。対象には IndexedDB・sessionStorage・Service Worker のキャッシュも含まれる（[補完リサーチ §2.1](../../content/research/20260820-zero-query-discovery_supplement.md)）。

この制約は設計で消せない — サーバーに状態を持たない（`D-14` / `D-18`）という原則を維持する限り、前回訪問の記録先はクライアントストレージ以外に選択肢がなく、週 1 未満のアクセス頻度の Safari ユーザーでは記録自体が失われる。したがって「差分表示」をコア体験の前提にすると、対象ユーザー層で機能が壊れる。**上乗せ機能に格下げし、ストレージ喪失時は全件表示へ自然に劣化するフォールバックを必須要件にする** ことで、ITP の影響範囲を「便利機能が使えない」に留め、「壊れる・空白が出る」を防ぐ。

### 3.5. メール / push 通知・ログイン限定パーソナライズを採らない理由

[A] Hugging Face Daily Papers のメール購読はログイン必須であることが実取得で確認された（3.2 と同一出典）。gem-hunter がこの経路を模倣してメール配信を行うには、配信先リスト（メールアドレス）をどこかに永続化する必要があり、`D-14`（サーバーに個人データを持たない）・`D-18`（永続ストアを採用しない）に正面から抵触する。push 通知も購読先の永続化を要する点で同じ制約に触れる。ログイン限定のパーソナライズは `D-6`（ログインで機能差を作らない）に抵触する。RSS は購読者リストをサーバー側に持たない Pull 型のため、`D-14` / `D-18` を維持したまま「定期的に新着を受け取る」という体験だけを実現できる。

### 3.6. Gem Index を単一スコアに合算しない設計とセレンディピティ研究の整合

[A] セレンディピティの定義には研究上のコンセンサスが存在せず、Kaminskas & Bridge（ACM TiiS 2016）の surprise + relevance の 2 成分説と、Kotkov ら（Knowledge-Based Systems 2016）の relevance + novelty + unexpectedness の 3 成分説が併存する（ディープリサーチ F-10、票 3-0）。単一スコアへの潰し込みは、少なくとも UMAP '25 の枠組み（fortuitous / refreshing / enriching の 3 成分・単純加算を明示的に批判）では不適切とされる（ディープリサーチ F-8、票 3-0）。

これは [ADR 0009](0009-hidden-gem-score-definition.md) が既に「`Gem Index`（過小評価度）と `criticality_score`（健全性）を 1 つのスコアに合算しない」と決めていることと独立に整合する。本 ADR はこの設計を **再定義せず、そのまま踏襲する**（`decisions.md` §3.3）。

### 3.7. 被依存数を主軸に据える設計への実証的裏付け（データ基盤の妥当性）

[A] star を水増しされた 738 パッケージのうち **70.46% が依存パッケージ数ゼロ、77.50% が依存リポジトリ数ゼロ** であることが ICSE 2026 採択論文で報告されている（[補完リサーチ §1.1](../../content/research/20260820-zero-query-discovery_supplement.md)）。star は購入・水増しが可能だが被依存数は構造的に操作が難しく、「被依存数（実利用）を起点にする」という ADR 0009 の設計と、日次ダイジェストで被依存数由来の `Gem Index` を並び順に使う本 ADR の設計の両方に実証的な裏付けを与える。

- 出典: https://arxiv.org/html/2412.13459v2（Six Million (Suspected) Fake Stars on GitHub, ICSE 2026）

## 4. 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **無限フィード / 無限スクロール** | NN/g 基準で「比較・検分」用途に非推奨（§3.1 F-1）。キーボードのみのユーザーの操作を複雑化し `AC-9` / Lighthouse A11y 100 と衝突（§3.1 F-2）。[ADR 0008](0008-pagination-over-infinite-scroll.md) が検索結果一覧について既に下した判断と同一方向 |
| **時間帯シャッフルを独立機能にする（Product Hunt 型の常時稼働版）** | 実在の前例はある（§3.2 F-4）が、開いている間に内容が動く実装は WCAG 2.2.2（Pause, Stop, Hide）に抵触するリスクがある。日付シードという内部実装の一部としてのみ温存する |
| **メール / push 通知** | 配信先リストの永続化が `D-14`（サーバーに個人データを持たない）・`D-18`（永続ストアを採用しない）に正面から抵触する（§3.5）。RSS（Pull 型）に置き換える |
| **ログイン限定のパーソナライズ** | `D-6`（ログインで機能差を作らない）に抵触する（§3.5） |
| **日付シードを E2E テスト用の時刻モックのみで上書きする（クエリパラメータを設けない）** | 本番の URL 表面積は増やさないが、プレビュー URL を開いた人間が `SP-14` 操作レビュー手順 4（日付を進めると顔ぶれが入れ替わる）を「翌日まで待つ」以外の方法で確認できず、`SD-1`（プレビュー URL 上で操作レビューを完走できる）を満たさない（§2.2） |
| **`package.json` 貼り付けによる文脈入力** | 🔵 **却下ではなく今回のスコープ外**。クライアント完結の解析パターン（`FileReader` + URL ハッシュ保持・サーバー送信なし）は前例があり（[補完リサーチ §2.2](../../content/research/20260820-zero-query-discovery_supplement.md)）、プロダクト価値の観点で捨てる理由がないため、別 Issue として起票する対象に留める |

## 5. 未確定事項（着手時に潰す前提・`decisions.md` §6）

🔴 **本 ADR で確定した事項（未確定ではない）**: **対象エコシステム** は `D-10` のとおり npm + PyPI で決定済み（`SP-14` は npm のみに範囲を限定・§2.6）。**パーセンタイルの母集団の切り方** は本 ADR で「エコシステム内で閉じて計算する（混ぜない）」と確定済み（§2.6）。この 2 点を以下の表に含めない。

🔴 **以下は未確定であり、実データを見てから `SP-14` / `SP-15` 着手直後に確定させる**（`decisions.md` §6 の転記）。

| # | 未確定事項 | 何が必要か |
|---|---|---|
| 1 | しきい値・足切り基準の具体値 | `Gem Index` のどの範囲を「隠れた名品」として提示するかの具体値は未定。npm の実データ（S3 ダンプ）を見てから `SP-14` 着手直後に決定する |
| 2 | 配信件数 | §2.1 の「既定 5 件」は暫定値。実データのボリューム・パーセンタイル分布を見てから確定する |
| 3 | S3 ダンプの集計フィールド未検証 | Ecosyste.ms の S3 バルクダンプに `dependent_packages_count` / `rankings` 等の集計フィールドが含まれるかを着手直後に実ファイルで確認する。含まれない場合はパーセンタイルの自前計算または API 併用に切り替わり、見積もりが変わる |
| 4 | `criticality_score` の鮮度未確認 | 最終 push が 2025-12-02 で cron の稼働継続が未確認（[補完リサーチ §4.6](../../content/research/20260820-zero-query-discovery_supplement.md)）。健全性フィルタに使う前に実測し、停止していれば OpenSSF Scorecard へ寄せる |
| 5 | Safari ITP の 7 日キャップは設計で消せない | フォールバック（§2.4）は任意機能ではなく必須要件として実装する（これ自体は確定済みの制約だが、実装漏れを防ぐため着手時チェック項目として残す） |
