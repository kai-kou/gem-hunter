# ADR 0007: DB を持たない設計原則と、状態をクライアント側へ寄せる判断

- **状態**: **承認**
- **日付**: 2026-08-20 JST
- **対応要件**: `NFR-2` / `D-5` / `D-5` 追補 / `D-13` / `D-14` / `AR-7` / `AR-8`
- **関連**: [`open-questions.md`](../02_requirements/open-questions.md) `D-5` / `D-5` 追補 / [`prd.md`](../02_requirements/prd.md) §5.2 / §7.2 / [アプリケーションアーキテクチャ](../03_design/architecture/application-architecture.md)

---

## 1. 文脈

与件（[`minimum-requirements.md`](../02_requirements/minimum-requirements.md) §1.2）は認証・お気に入り・独自スコアリング・通知・課金を対象外としており、DB の要否には直接言及していない。要件定義フェーズで「GitHub API 直参照か、自前 ETL + DB か」（`D-5`）を検討した結果、**MVP は GitHub API 直参照で動かし DB は持たない** と決定し（`open-questions.md` `D-5`）、さらに「MVP の都合ではなく設計原則に格上げする」（`D-5` 追補）として、状態を `localStorage` / Cookie / URL に寄せる方針を Phase 2 まで可能な限り貫くことを決めた。

本 ADR は、この決定が実際に何を実装として意味するか（状態の置き場所を要素ごとにどう振り分けたか）と、DB を持たないことで **捨てたもの** を記録する。

## 2. 決定

### 2.1. サーバー側ストアを持たない

サーバー側に永続ストア（DB・KV・Durable Objects 等）を一切持たない。実行モデルは **サーバーレス関数前提**（`D-13`）で、インスタンスが使い捨てである前提で設計し、プロセス内メモリにも状態を持たせない（唯一の例外は [ADR 0005](0005-cache-port-yagni-exception-and-ttl.md) の `CachePort`＝TTL 付きの再計算可能なキャッシュであり、失っても正しさが壊れない一時データに限る）。

### 2.2. 状態の置き場所（要素ごとの振り分け）

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 検索キーワード・ページ・ソート・表示件数 | **URL（`searchParams`）** | リロード・共有で同じ結果を再現できる（与件 §4.3・`NFR-2`）。サーバー側で誰の状態かを識別する必要がない |
| ロケール（言語） | **URL のパスセグメント** | 共有時に言語が保たれる（`D-4`） |
| セッション（任意 OAuth ログイン時） | **暗号化した httpOnly Cookie** | サーバー側にセッションストアを持たずにログイン状態を維持できる。ユーザーの OAuth トークンをクライアントへ露出させない（`NFR-9`と同じ原則をユーザートークンにも適用） |
| UI 設定・検索履歴・お気に入り（`AR-7` / `AR-8`・`P1-積み上げ`） | **`localStorage`**（実装は積み上げフェーズ） | サーバー不要で実現できる。端末間で同期しないことを UI 上で明示する制約を受け入れる |

### 2.3. サーバー側ログの制約

アプリケーションからは個人と結びつきうる情報を一切ログ出力しない。IP・User-Agent・検索キーワード・閲覧対象・GitHub ユーザー識別子・トークンを記録せず、出力してよいのはエラー種別コード・HTTP ステータス・レート残量・処理時間に限る（`D-14`）。匿名集計もサーバー側には持たない。

## 3. 理由

### 3.1. なぜ DB を持たない設計を「原則」に格上げしたか

要件定義フェーズの当初は「MVP はデータ基盤を先に固めなくても書ける最小スコープ」という消極的な理由で GitHub API 直参照を選んでいた（`open-questions.md` `D-5`）。しかし実装が進むにつれ、DB を持たないことが単なる MVP の簡略化ではなく、以下の複数の要件を同時に満たす **設計上の要石** になっていることが明らかになったため、`D-5` 追補として原則に格上げした。

- **`D-13`（サーバーレス関数前提）との整合**: インスタンスが使い捨てである以上、プロセス内状態は次のリクエストで失われる。DB を持たない設計はこの制約と自然に整合する
- **`D-14`（個人情報非保持）との整合**: そもそもサーバー側にストアがなければ、個人と結びつく情報を誤って永続化するリスクの多くが構造的に発生しない
- **`D-15`（運用の手離れ）との整合**: DB を持つと、スキーマ移行・バックアップ・容量監視という定常運用作業が生まれる。単一開発者 + AI 自律運用（`sprint-cycle-router` が 1 時間ごとに自走）という体制では、これらの定常作業を見る人間がいない
- **`NFR-9`（サーバー側の GitHub 認証トークン非露出）との相性**: DB を挟まずに GitHub API を直接叩く構成は、トークンの流通経路をサーバー側の 1 箇所（composition root → インフラ層）に閉じやすい

### 3.2. なぜ状態をクライアント側（URL / Cookie / `localStorage`）へ寄せるか

DB を持たないと決めた時点で、「検索条件をどう次のリクエストへ引き継ぐか」という問題が残る。従来の Web アプリであればサーバー側セッション（DB 保存）で解決するところを、本プロジェクトは **状態の性質ごとに URL / Cookie / `localStorage` へ振り分ける**（§2.2）ことで解決した。

- **URL**: 検索条件は「誰の状態か」を識別する必要がなく、かつ与件 §4.3 がリロード・共有時の再現性を要求している。URL に載せることで、サーバー側の識別なしに同じ結果を再現でき、`NFR-2` を満たす
- **httpOnly Cookie**: セッションのように「サーバーだけが読めればよく、改ざんされてはならない」状態は、暗号化 Cookie で持てば DB を経由せずにステートレスに検証できる（`D-6` の任意 OAuth ログインと矛盾しない。むしろセッションストアを立てる選択肢自体を消すため、DB レス原則を強化する方向にある）
- **`localStorage`**: お気に入り・検索履歴のように「その端末のその利用者だけが使う、失われても致命的でない」状態は、サーバーを経由せずクライアント側だけで完結できる

## 4. 捨てたもの（この判断が禁じるもの）

DB を持たない・状態をクライアント側へ寄せるという判断は、以下の機能・実装方針を **意図的に取らない**。

| 捨てたもの | 理由 |
|---|---|
| **サーバー側ユーザーデータ**（お気に入り・検索履歴・プロフィールをサーバーに永続化し、端末をまたいで同期する） | DB レス原則に正面から反する。`AR-7` / `AR-8` は `localStorage` 実装（端末間非同期）に限定し、サーバー同期版は範囲外とする |
| **通知・アラート・週刊ダイジェスト（配信）**（`Q-5`） | 配信には「誰に何を送るか」を永続化する常駐処理が必要で、DB レス原則と正面から衝突するため、Phase 1 の対象に含めない。Phase 2 でも静的データ配信（`GR-5` / `GR-7`）による代替を優先候補とし、DB 導入は最後の手段とする |
| **サーバー側セッションストア**（Redis 等によるセッション管理） | 暗号化 httpOnly Cookie によるステートレスセッションで代替できるため、原則を破ってまで導入する理由がない |
| **利用実績のサーバー側集計・分析基盤** | `D-14` によりサーバー側で個人と結びつく情報を記録しないため、分析基盤自体の入力データが存在しない。KPI は完成度 KPI に限定する（`Q-11`） |
| **Phase 2 の自前スコアリング結果の恒久保存**（DB での随時更新） | `GR-5` / `GR-7` はバッチ生成した静的データの配信を第一候補とする。動的な DB 更新は「最後の手段」であり、まず静的配信で成立するかを検証してから検討する |

## 5. 結果（この決定がもたらすもの）

### 良い方向

- スキーマ移行・バックアップ・容量監視という定常運用作業が発生しない（`D-15` の「運用の手離れ」に直結）
- 個人情報を誤って永続化するリスクの大半が構造的に排除される（`D-14`）
- URL に検索条件を持たせることで、キャッシュキー生成（`NFR-18`）・共有 URL・ブラウザバックのいずれも同じ状態表現で扱える
- サーバーレス関数前提（`D-13`）の実行モデルと矛盾なく整合する

### 受け入れる代償

| 代償 | 緩和策 |
|---|---|
| `localStorage` は端末間で同期されず、ブラウザのデータ削除で消え、容量上限（数 MB 程度）がある | UI 上で「この端末のみ保存」であることを明示する。同期が必要になった時点で初めて DB を検討する（`minimum-requirements.md` §4） |
| 通知・週刊ダイジェストのような「配信」系機能を持てない | Phase 2 では静的データ配信（`GR-5` / `GR-7`）で代替する方針を先に用意している |
| 将来サーバー側ユーザーデータが必要になった場合、DB 導入という原則の転換が要る | 転換する場合は本 ADR を supersede する新しい ADR を書く（`D-5` 追補の格上げと対称の扱い） |

## 6. 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| **自前 ETL + DB（`D-5` の検討時点の対抗案）** | 被依存数などの実データを継続収集するバッチ基盤とスキーマ管理が要り、単一開発者 + AI 自律運用という体制では定常運用コストが見合わない（`D-15`） |
| **お気に入り・検索履歴をサーバー側 DB に保存する** | 端末間同期という利便性は得られるが、DB レス原則（`D-5` 追補）を破る。`localStorage` で実現できる範囲に留める（`Q-5`） |
| **セッションを DB 保存のサーバーサイドセッションで実装する** | 暗号化 httpOnly Cookie で同じ目的（ステートレスなログイン維持）を達成でき、DB を追加する理由がない |
| **検索条件をサーバー側セッションに保持する** | URL で十分に再現でき、かつ与件 §4.3（リロード・共有で同じ結果）を満たすには URL の方が直接的。セッション経由は共有 URL で状態が再現できなくなる |
| **通知・週刊ダイジェストを DB 導入の口実にする** | 原則を崩す前に、まず静的データ配信（`GR-5` / `GR-7`）で成立するかを検証する順序を優先する |
