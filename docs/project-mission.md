# プロジェクトミッション（CP-5 の実体）

> `core-principles.md` の CP-5 は本ファイルを参照する形で汎用化されている。判断に迷ったら
> 本ファイルのミッションに最も貢献する選択をする。
>
> 本ファイルの内容は [`docs/02_requirements/open-questions.md`](./02_requirements/open-questions.md) の
> 決定ログ（`D-n` / `Q-n`）に基づく。決定を変更する場合は両方を同時に更新する。

## ミッションステートメント

**star の多さでは埋もれてしまう「実際に使われている OSS」を、個人開発者が見つけられるようにする。**

star は注目度の指標であって利用実績ではない。約 600 万個の偽 star が観測されている現状（`competitive-analysis.md`）では、star 順に並べるほど「本当に役立つが知られていないもの」は見えなくなる。gem-hunter は **被依存数（実利用）に対して star（注目度）が不釣り合いに小さいもの** を Gem と定義し、注目度ではなく実利用を起点に発見できる状態をつくる。

## KPI / 成功指標

> `Q-11` の決定により、**完成度 KPI のみを置く**。利用実績 KPI（訪問数・検索実行数・再訪率）は、
> 運用を開始する判断をした時点で追加する（現時点では計測基盤を持たない）。

| 指標 | 目標 | 計測方法 |
|------|------|---------|
| 与件受け入れ基準の充足 | 11 / 11 項目 | [`minimum-requirements.md`](./02_requirements/minimum-requirements.md) §7 のチェックリスト |
| Lighthouse Accessibility | 100 | CI ゲート（決定論的に判定されるため満点を要求） |
| Lighthouse Performance | 90 以上 | CI ゲート（複数回実行の中央値・スロットリング固定） |
| Core Web Vitals | LCP 2.5s 以下 / INP 200ms 以下 / CLS 0.1 以下 | ローカル計測（Google の "good" 境界を引用） |
| 主要フローのテスト | 全て存在し CI で成功 | CI |
| 技術的意思決定の ADR 化 | 決定ログの主要決定に漏れがない | `docs/adr/` と `open-questions.md` 決定ログの突合 |

## ミッションに基づく判断基準

| 判断場面 | ミッション指向の選択 |
|---------|-------------------|
| 与件と上乗せ要件が衝突した | **与件を優先する**（`D-2`。与件は必達の下限であり、上乗せがそれを侵してはならない） |
| 新機能を足すか、積み上げ基盤を整えるか | **基盤を優先する**（`D-9`。回帰を検知できない状態で機能を積むと、積むほど壊れる） |
| DB が必要に見えてきた | **まずクライアント保持（`localStorage` / Cookie / URL）と静的データ配信を検討する**（`D-5` 追補。DB 導入は最後の手段） |
| 差別化機能を思いついた | **GitHub 純正検索で再現できないかを先に確認する**（`R-2`。`stars:` `topic:` 等で 1 行で書けるものは差別化にならない） |
| スコアや指標を自作したくなった | **OpenSSF（criticality_score / Scorecard）で代替できないかを先に確認する**（`R-3`。再実装ではなく依存で解く） |
| ログイン必須にしたくなった | **却下する**（`D-6`。ログインはレート枠の切替のみで、機能差を作らない） |
| Gem のランキングに健全性スコアを合算したくなった | **却下する**（`Q-1`/`Q-2`。合算すると「健全だが有名」が上位に戻り、star 追随ランキングに退化する） |
| 迷ったとき | **説明できる方を選ぶ**（`D-3` の主目的は「与件充足 + 設計判断の説明可能性」） |

## 優先順位付け（迷ったとき）

1. **与件（`minimum-requirements.md`）の充足** — 割ってよい項目はない
2. **積み上げ可能性の確保** — テスト / CI / データアクセス層の分離 / ルーティングとキャッシュ境界
3. **説明可能性** — 技術的意思決定を ADR に残す
4. **差別化機能**（Gem Index） — Phase 2
5. ドキュメント・運用改善

## ドメイン固有の品質ゲート

**これを下回ったらリリースしない**:

- 与件チェックリスト（`minimum-requirements.md` §7）を **1 項目でも満たさない** 状態
- Lighthouse Accessibility が **100 未満**
- 主要フロー（検索 → 一覧 → 詳細 → 復帰）のテストが **失敗している**
- キーボードのみで検索から詳細閲覧まで **完走できない**
- GitHub API のトークンなど秘匿情報が **クライアントへ露出している**

**これを守る**:

- 挙動を変える変更には ADR か Issue を紐づける（「なぜ変えたか」を残す）
- `P1-MVP` の要件を削る判断は行わない（削るのは `P1-積み上げ` 以下のみ）
- Lighthouse Performance ゲートが原因で実装が 2 回以上ブロックされたら、**ゲートの設定自体を見直す**（ゲート遵守を目的化しない）

## SP 工程別標準値（session-sprint-rules.md §3.2 の実体）

> `session-sprint-rules.md` §3.1 のベーススケール + §3.1.5 Dynamic 補正を、本プロジェクトの工程に
> 当てはめた **暫定値**。実測（`content/analytics/sprint/` の tokens/sp・分/sp 中央値）が 4 週分
> 貯まったら @owner が較正する（§6）。

| 工程 | ベース SP | 備考 |
|------|-----------|------|
| 文言修正・設定値変更・1 行修正 | `sp:1` | 機械的変更 |
| 単一コンポーネントの軽微改修・ドキュメント軽微更新 | `sp:2` | 単一ファイル |
| 単一画面・単一 API クライアント関数の実装 + テスト | `sp:3` | 標準タスク |
| 複数ファイル横断（キャッシュ層・エラー処理・i18n 基盤等）・ADR を伴う設計判断 | `sp:5` | 要件定義書との同期を伴う |
| 新規フェーズ着手（Phase 2 のデータパイプライン等）・アーキテクチャ変更 | `sp:8` | 分割を検討（§3.1） |

**Dynamic 補正（横断適用・+1〜2 SP）**: 要リサーチ・仕様未確定・新規領域・clarification 見込みが高い場合に加算する。SP は離散値（1/2/3/5/8）なので、加算結果は最も近い上位スケールに丸める。

- 例: 「Next.js 16 の `use cache` の実挙動確認を伴うキャッシュ層実装」= 複数ファイル横断（`sp:5`）+ Dynamic（+1・一次確認が必要）→ `sp:8` に丸める。
- **上限**: ベース + Dynamic が `sp:8` を超える場合はキャップせず、タスクを分割する（8 超のラベルは付けない）。

> **較正の約束（gaming 防止・§7）**: 本表は実測（tokens/sp）に基づき更新するが、velocity（done_sp）や
> tokens/sp 自体を目標値・ノルマにはしない。あくまで「見積もり精度を上げる」ためだけに使う観測値。
