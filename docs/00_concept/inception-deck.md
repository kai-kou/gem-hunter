# 前半：なぜここにいるのか

## Q1. 我々はなぜここにいるのか

### 目的（2 層構造）

| 層 | 内容 | 根拠 |
|---|---|---|
| **主目的** | **選考課題 / ポートフォリオ。** 与件を確実に満たし、設計判断を説明できる状態にする | `D-3` |
| **副次目標** | **有用であればそのまま運用を継続したい。** 運用継続を阻害しない設計にする（無料枠に収まる / レート制限で破綻しない / 規約違反をしない） | `D-3` |

### 🔴 この 2 層が衝突したときの解決規則

**主目的が勝つ。** 「運用継続に有利だが与件を侵す」選択は採らない（`D-2`：与件は必達の下限）。

ただし **「後から入れると既存コードの書き換えが発生するもの」だけは例外的に先に入れる**（`D-9`）— ロケール基盤（`AR-4`）/ キャッシュ抽象（`NFR-17`）/ 任意 OAuth（`AR-5`）。これは副次目標のためではなく、**積み上げ速度を落とさないため** の判断である。

### なぜ「star ではないもの」で探すのか

star は注目度の指標であって利用実績ではない。約 600 万個の偽 star が観測されており、star 順に並べるほど「実際に使われているが知られていないもの」は見えなくなる（詳細は [`lean-canvas.md`](./lean-canvas.md) §2）。

## Q2. エレベーターピッチ

> **「実際に使われている OSS を見つけたい」個人開発者向けの、**
> **`gem-hunter` というプロダクトは、GitHub リポジトリ検索 Web アプリケーションです。**
> **これは star の多さでは埋もれてしまう「実利用の多い OSS」を発見することができ、**
> **GitHub 純正の検索とは違って、**
> **被依存数に対する star の不足（残差）で並べ替える機能が備わっています。**

### 🔴 このピッチには重大な但し書きがある

**上記は Phase 2 まで含めた完成形のピッチであり、Phase 1 の成果物はこのピッチを実現しない。**

| フェーズ | ピッチのどこまでを満たすか |
|---|---|
| **Phase 1**（実装対象） | 「GitHub リポジトリ検索 Web アプリケーションです」まで。**差別化部分（残差での並べ替え）は含まない** |
| **Phase 2**（構想のみ・実装しない） | 「GitHub 純正とは違って〜」以降 |

したがって **Phase 1 の完了報告でこのピッチを使わない。** Phase 1 のピッチは次のとおり：

> **`gem-hunter` Phase 1 は、キーワードで GitHub リポジトリを検索・閲覧できる Web アプリケーションであり、**
> **Phase 2 で「実利用に対する注目度の不足」による並べ替えを載せるための土台です。**

この区別を曖昧にすると、「与件を満たした」ことと「課題を解いた」ことが混同される（[`lean-canvas.md`](./lean-canvas.md) §9.1）。

### 4.2. やらないこと

| 項目 | やらない理由 | 根拠 |
|---|---|---|
| **ユーザー認証を必須にすること** | ログインは任意であり、機能差を作らない。ログインで変わるのはレート枠だけ | `D-6` / 与件 §1.2 |
| **DB を持つこと** | 状態は URL / Cookie / `localStorage` に寄せる。**MVP の都合ではなく設計原則** | `D-5` 追補 |
| **通知・アラート・週刊ダイジェストの配信** | 永続化と常駐処理が必要で、DB レス原則と衝突する | `Q-5` |
| **課金・サブスクリプション（Pro 機能という枠組みごと）** | 収益化を目的としない | `D-3` / `Q-5` |
| **目的別タグの自前生成（LLM 分類・人手キュレーション）** | 維持コストが運用継続と両立しない。GitHub topics の活用に絞る | `Q-4` |
| **健全性スコアの自作** | OpenSSF が既にある。再実装ではなく依存で解く | `R-3` / `GR-2` |
| **エージェント向け API / MCP の提供** | 不採用と決定済み | `D-1` |
| **GitHub App 化・Webhook 受信** | 他人の公開リポジトリを読むだけで、監視対象リポジトリが存在しない | `Q-6` |
| **複数トークンのローテーション** | レート制限の回避とみなされる恐れがある | `D-6` |
| **無限スクロール** | WCAG 2.2 AA 目標と衝突し、URL 状態保持とも噛み合わない | `Q-8` / `FR-7` 注記 |
| **Phase 2（Gem Index）の実装** | 🔴 **構想として記述するが Phase 1 では実装しない** | `D-3` / `D-1` |
| **GitHub 由来データの機械翻訳** | リポジトリ説明文・topics・言語名は原文のまま。正確性を損なう | `AR-4` 詳細 |
| **獲得チャネルの設計（GTM）** | 運用開始を判断した時点で扱う | `D-3` / [`lean-canvas.md`](./lean-canvas.md) §6 |

# 後半：どうやって実現するのか

## Q6. 解決案を描く（アーキテクチャ概要）

```
       ブラウザ
          │  URL に検索条件を保持（キーワード / ページ / ソート / 件数 / ロケール）
          ▼
  ┌─────────────────────────────────────────────┐
  │  Next.js 16 (App Router)                    │
  │  ┌───────────────────────────────────────┐  │
  │  │ UI 層（Server Components 基本）        │  │
  │  │  - 一覧 / 詳細 / エラー・空・読込中    │  │
  │  └───────────────┬───────────────────────┘  │
  │                  │ 🔴 UI から API を直接呼ばない（NFR-16）
  │  ┌───────────────▼───────────────────────┐  │
  │  │ データアクセス層                       │  │
  │  │  - 直列化 / request coalescing / ETag  │  │
  │  │  - レート残量監視 → degraded 表示      │  │
  │  └───────┬───────────────────┬───────────┘  │
  │          │                   │              │
  │  ┌───────▼────────┐   ┌──────▼───────────┐  │
  │  │ Cache Port     │   │ 認証             │  │
  │  │ get/set/invalidate │ 共有 PAT         │  │
  │  │ + TTL のみ     │   │ + 任意 OAuth     │  │
  │  └───────┬────────┘   │ (httpOnly Cookie)│  │
  │          │            └──────────────────┘  │
  └──────────┼─────────────────────────────────┘
             │           🔴 DB は持たない
             ▼
      GitHub API（検索 30 req/分 = 律速 / Core 5,000 req/h）

  ─── Phase 2 で追加（実装しない・接続点だけ確保）───────
      Ecosyste.ms（被依存数） / OpenSSF（健全性）
      → データアクセス層の背後に差し込む（UI を触らない）
```

### 中核となる 5 つの設計原則

| 原則 | 内容 | 根拠 |
|---|---|---|
| **DB を持たない** | 状態は URL / Cookie / `localStorage` へ | `D-5` 追補 |
| **インフラを決め打たない** | キャッシュ基盤・**本番** デプロイ先は未決。特定 PaaS 固有機能への依存を最小化。⚠️ **プレビュー環境のデプロイ先は先行して決める**（`D-11`・Q4.4 参照） | `D-5` / `D-7` / `D-11` / `NFR-21` |
| **データアクセスを 1 箇所に隔離する** | Phase 2 のデータ源追加時に UI を触らずに済む | `NFR-16` |
| **積み上げ可能性を先に確保する** | 後付けコストが高いもの（i18n ルーティング・キャッシュ境界・OAuth）を MVP に含める | `D-9` |
| **既存のものを再実装しない** | 健全性スコアは OpenSSF に依存する | `R-3` |

⚠️ **Cache Port は YAGNI の意図的な例外**（`NFR-17`）。面積を `get` / `set` / `invalidate` + TTL のみに絞り、汎用キャッシュライブラリを自作しない。理由を ADR に残す。

## Q8. 期間を見極める

### 🔴 前提：期日は存在するが未確定（`D-9`）

したがって **絶対日付でスケジュールを引かない。** 代わりに「到達順序」を固定する。

```
  ┌────────────┐   ┌──────────────┐   ┌─────────┐
  │ P1-MVP     │→→ │ P1-積み上げ   │→→ │  期日   │
  │ 最短で到達 │   │ 順次追加      │   │（未確定）│
```

|---|---|---|
| **`P1-MVP`** | ① 与件の受け入れ基準 11 項目を満たす最小集合 + ② 後付けコストが高い上乗せ（`AR-4` / `AR-5` / `NFR-17`） | 🔴 **①は削らない。**②のうち①を割らないものだけが削減候補 |

| **`P2`** | Gem Index（`GR-1`〜`GR-7`） | そもそも Phase 1 では実装しない |

## Q9. 何を諦めるのか（トレードオフスライダー）

> `project-mission.md` の優先順位（① 与件充足 → ② 積み上げ可能性 → ③ 説明可能性 → ④ 差別化）を、判断可能な形へ射影したもの。

### 9.1. スライダー

`◆` が現在位置。**同じ位置に 2 つ置かない**（全部が最優先なら優先順位が存在しないのと同じ）。

| # | 軸 | 位置 |
|---|---|---|
| **S-1** | **与件の充足** ←→ 上乗せ機能の量 | `与件 ◆──────────── 上乗せ` |
| **S-2** | **積み上げ基盤**（テスト / CI / 層分離 / 境界） ←→ 機能数 | `基盤 ─◆─────────── 機能数` |
| **S-3** | **説明可能性**（ADR / README） ←→ 実装速度 | `説明 ──◆────────── 速度` |
| **S-4** | **アクセシビリティ** ←→ 実装速度 | `A11y ───◆───────── 速度` |
| **S-5** | **運用継続可能性**（無料枠 / レート耐性 / 規約遵守） ←→ 機能リッチさ | `運用 ─────◆─────── リッチ` |
| **S-6** | **UI の作り込み** ←→ 実装速度 | `作り込み ─────────◆─ 速度` |
| **S-7** | **差別化（Gem Index）** ←→ 与件の完成度 | `差別化 ──────────◆ 完成度` |

### 9.2. 各スライダーの読み方（＝ 迷ったときの決定規則）

| # | この位置が意味すること | 根拠 |
|---|---|---|
| **S-1** | 🔴 **与件と上乗せが衝突したら、常に与件を採る。** 上乗せは与件を侵さない範囲でのみ足す | `D-2` |
| **S-2** | **機能を 1 つ足すより、回帰を検知できる状態を優先する。** 検知できない状態で積むと、積むほど壊れる | `D-9` |
| **S-3** | **「なぜそうしたか」を残す時間を実装時間から削らない。** ただし ADR は主要決定に絞る（`prd.md` §12 の 8 件） | `D-3`（説明可能性が主目的の一部） |
| **S-4** | **Accessibility は決定論的に判定できるので満点を要求する**（Lighthouse 100）。Performance は揺れるので同じ厳しさで扱わない | `Q-7` / `Q-8` |
| **S-5** | **中庸。** 運用継続は副次目標であり、主目的を侵さない範囲で確保する。ただし「無料枠を超える」「規約に触れる」選択は採らない | `D-3` |
| **S-6** | 🔵 **UI の装飾性そのものは要件としない。** 見やすさ・操作しやすさを満たせば十分（与件 §3.1）。⚠️ ただし **`NFR-13`（配色）だけは先に確定させる**（後戻りコストが高い） | 与件 §3.1 / `NFR-13` |
| **S-7** | 🔴 **差別化機能（Gem Index）は Phase 1 では一切実装しない。** 与件の完成度を優先する。Phase 2 を **阻害しない設計** にとどめる | `D-3` / `D-1` |

### 9.3. 🔴 スライダーを動かしてよい条件

- **S-1 / S-7 は動かさない**（`D-2` / `D-3` の決定そのもの。動かすなら決定ログの更新が先）
- **S-4 を「速度」側へ動かすのは、`NFR-27` の撤退条件（Lighthouse ゲートが 2 回以上ブロック）に該当した場合のみ**
- その他は期日確定時（Q8）に再検討してよい

## Q10. 何がどれだけ必要か

### チーム編成

| 役割 | 担当 |
|---|---|
| プロダクトオーナー / 意思決定 | 開発者本人 |
| 設計・実装・レビュー・ドキュメント | 開発者本人 + Claude Code（自律運用ハーネス） |
| レビュー | **Layer 1 セルフレビュー**（観点別フレッシュ文脈）で完結。外部 AI レビュアーは使わない |

🔴 **実質 1 人体制である。** したがって「レビュー待ちで止まる」時間は存在しない代わりに、**独立した第三者の目が入らない**。これを補うのが ADR（`NFR-32`）と CI の機械ゲート（`NFR-25`〜`NFR-27`）である。

### コスト

| 項目 | 見積もり |
|---|---|
| インフラ | **無料枠内を前提**（⚠️ 未試算・`R-6`） |
| 外部サービス利用料 | なし（GitHub API / Ecosyste.ms / OpenSSF はいずれも無料枠を使う） |
| 🔴 **実質的な制約** | **金銭ではなく GitHub API のレート枠**（検索 30 req/分）。詳細は [`lean-canvas.md`](./lean-canvas.md) §8 |

### 必要な環境（外部から注入するもの）

`prd.md` §10 が正本。GitHub アクセストークン / OAuth クライアント ID・シークレット / コールバック URL / セッション暗号化キー / 既定ロケール / キャッシュ接続情報。🔴 **いずれも `NEXT_PUBLIC_` 接頭辞を付けない**（`NFR-9`）。
