|---|---|
| ✅ **検証済み** | 一次情報で確認した（出典を併記する） |
| ⚠️ **未検証** | 一次情報にあたっていない。反証されうる |
| 🔒 **決定事項** | 検証の対象ではなく、`D-n` / `Q-n` で意思決定した前提 |

## 2. ① 課題（Problem）

### 2.1. 上位 3 つの課題

| # | 課題 | 検証状況 |
|---|---|---|
| **P-1** | **star が利用実績の代理指標として機能していない。** star は注目度の指標であり、約 600 万個の偽 star が観測されている（He et al., ICSE 2026・[競合調査](../01_research/market/20260817-github-repo-search-competitive-analysis.md)） | ✅ 検証済み（一次文献） |
| **P-2** | **star 順に並べるほど、実際に使われているが知られていない OSS が沈む。** 実例として `debug_inspector` は 25 star でありながら 111,000 以上の OSS プロジェクトから依存されており、既存のどの検索手段でも上位に現れない | ✅ 検証済み（実例で確認） |
| **P-3** | **「自分のプロダクトにちょうどよく、活発にメンテナンスされているライブラリ」を探す手段がない。** 巨大フレームワークは学習コストが高く、かといって無名リポジトリは信頼性の判断材料がない | ⚠️ **未検証（`R-1`・n=0）**。著者の仮説 |

🔴 **`P-3` だけ性質が違う。** `P-1` / `P-2` は外部データで裏が取れているが、`P-3` は「ユーザーがそう感じている」という主張であり一次情報がない。**プロダクトの価値の源泉は `P-1` / `P-2` に置き、`P-3` に依存させない。**

### 2.2. 既存の代替手段（Existing Alternatives）

課題を抱えた人が **いま実際に取っている行動**。

| 代替手段 | どこまで解けているか | 残るギャップ |
|---|---|---|
| **GitHub 検索**（`stars:10..500 pushed:>...` 等） | 🔴 **相当部分が再現できてしまう**（`R-2` で実測・n=1） | star の範囲は指定できるが、**被依存数を条件にできない**（データが API に存在しない） |
| grep.app（コード検索） | コード断片からの到達 | リポジトリの健全性・利用実績が見えない |
| OSS Insight（統計分析） | マクロなトレンド可視化 | 個別のニッチな要件に合致するリポジトリの発見には不向き |
| Libraries.io / Ecosyste.ms | 被依存数そのものは取得できる | **検索体験ではない**。「探す」用途に最適化されていない |
| awesome-* リスト / X・Reddit の口コミ | 人手のキュレーションによる信頼 | 網羅性がなく、更新が止まる。検索できない |

🔴 **`R-2` の含意**: 「star が少なくて活発なリポジトリ」は GitHub 純正検索の 1 クエリで書けてしまう。**したがって「star 範囲での絞り込み」は差別化にならない。** 差別化は被依存数（純正で書けない軸）を使うところにしか存在しない（`Q-1` / `Q-2`）。

## 3. ② 顧客セグメント（Customer Segments）

### 3.1. ターゲット

**個人開発者・インディーハッカー・フリーランスエンジニア。**

「車輪の再発明はしたくないが、巨大なフレームワークは学習コストが高い。自分のプロダクトにちょうどよく、活発にメンテナンスされているライブラリが欲しい」というニーズを持つ層（`initial-concept.md` §3.1 由来）。

### 3.2. アーリーアダプター

上記のうち、**新しい依存を入れる判断を自分ひとりで下せる** 人。組織の技術選定プロセス（稟議・セキュリティレビュー）を経由しないため、「知名度が低いが実利用の多いライブラリ」を実際に採用できる。

### 3.3. ⚠️ 検証状況：未検証（`R-1`）

- **一次情報にあたっていない**（`docs/01_research/user/` は空）。ペルソナもペインも著者の仮説である
- 検証手段（`R-1` の記載）: HN / Reddit / X の既存スレッド収集（デスクリサーチ）で代替可能。5〜10 人へのヒアリングができれば理想
- 🔴 **現時点でこの仮説を根拠に要件を追加しない。** 要件の追加根拠は与件（`minimum-requirements.md`）か、検証済みの `P-1` / `P-2` に置く

## 4. ③ 独自の価値提案（Unique Value Proposition）

### 4.1. UVP

> **star の多さでは埋もれてしまう「実際に使われている OSS」を、個人開発者が見つけられるようにする。**

（[`project-mission.md`](../project-mission.md) のミッションステートメントと同一。ミッションの正本は同ファイル）

### 4.2. ハイレベルコンセプト

> **star を分子ではなく分母として使う検索。**

既存の検索は「注目度が高い順」に並べる。gem-hunter は「実利用に対して注目度が **不足している** 順」に並べる。star を水増ししても順位は上がらず、むしろ下がる。

### 4.3. なぜこれが「独自」と言えるか

| 根拠 | 内容 | 出典 |
|---|---|---|
| **純正検索で書けない** | 被依存数は GitHub API に存在しないため、`stars:` `topic:` 等の検索構文では原理的に再現できない | `Q-1` / `Q-2` / `R-2` |
| **既存スコアの再実装ではない** | OpenSSF `criticality_score` は「重要度の絶対値」を測る。Gem Index が測るのは **重要度に対する注目度の不足（残差）** であり別物 | `Q-1` / `Q-2` / `R-3` |
| **偽 star に構造的に頑健** | star を水増しすると Gem Index は下がり、ランキングから外れる | `prd.md` §1.4 |

### 4.4. ⚠️ この UVP の弱点（先に認識しておく）

- 🔴 **Phase 1 では UVP を提供しない。** Phase 1 は与件どおりのキーワード検索であり、Gem Index は Phase 2（`D-3` により Phase 1 では実装しない）。**したがって Phase 1 の成果物は UVP の検証にならない**
- 「実際に使われている」の操作的定義を **被依存数** に置いているが、被依存数はライブラリ以外（CLI ツール・アプリケーション・ドキュメント）には効かない。**カバー範囲がライブラリに偏る**

## 5. ④ ソリューション（Solution）

上位 3 課題への対応。**要件の詳細は [`prd.md`](../02_requirements/prd.md) が正本であり、ここでは対応関係のみ示す。**

| 課題 | ソリューション | フェーズ | 要件 ID |
|---|---|---|---|
| `P-1` / `P-2` | **Gem Index**（被依存数のパーセンタイル順位 − star のパーセンタイル順位）による並べ替え | Phase 2 | `GR-1` |
| `P-1` / `P-2` | **健全性による足切り**（OpenSSF `criticality_score` / Scorecard に依存し、自作しない） | Phase 2 | `GR-2` |
| `P-3` | **topics 絞り込み × Gem Index 並べ替え** の組み合わせ | Phase 2 | `GR-4`（🔴 検索結果への適用は `D-32`・2026-08-21 により撤去済み。詳細は [`open-questions.md`](../02_requirements/open-questions.md) `D-32`） |
| （基盤） | **キーワードによる GitHub リポジトリ検索 Web アプリケーション** | Phase 1 | `FR-1`〜`FR-7` / `AR-1`〜`AR-8` |

🔴 **2 軸を 1 つのスコアに合算しない**（`Q-1` / `Q-2`）。合算すると「健全だが有名」なリポジトリが上位に戻り、否定したはずの star 追随ランキングに退化する。

🔴 **Phase 1 と Phase 2 の関係**: Phase 1 は UVP を提供しないが、**Phase 2 を阻害しない設計** であることが要件になっている（データアクセス層の隔離 `NFR-16`、ソート UI の拡張余地 `AR-2`）。

## 8. ⑦ コスト構造（Cost Structure）

### 8.1. 金銭コスト

**無料枠に収まることを制約として課す**（`D-3` の副次目標「運用継続を阻害しない設計」）。

⚠️ **未試算**（`R-6`）。競合調査のコスト試算は埋め込み・ベクトル DB 中心で、MVP（埋め込み不要）のコストは算出していない。

### 8.2. 🔴 実質的な制約は金銭ではなくレート枠

**GitHub 検索 API のレート枠がアプリ全体の律速であり、キャッシュなしの公開運用は成立しない。** 🔴 **具体値の正本は [`prd.md`](../02_requirements/prd.md) §2.2**（外部事実であり変わりうるため、本書では複製しない）。

⚠️ **必要枠の逆算が未実施**（`R-5`）。「1 検索あたりの API 呼び出し回数 × 想定利用者数 × キャッシュヒット率」の試算がないため、**何 DAU まで捌けるかが未知**。

この制約が要件を直接規定している: キャッシュ（`NFR-5` / `NFR-17`）・request coalescing・直列化・ETag・残量監視（`NFR-7`）・任意 OAuth ログインによるレート枠切替（`AR-5`）。

### 8.3. 運用継続の前提コスト（Phase 2）

Ecosyste.ms のデータは CC BY-SA 4.0 であり、**出典表示の義務が運用時に発生する**（`GR-6`）。金銭コストではないが、継続的に負う義務としてここに記録する。

## 10. ⑨ 圧倒的な優位性（Unfair Advantage）

### 10.1. 現時点の結論：**持たない**

リーンキャンバスの慣例どおり、ここは **空欄のままにする勇気を持つ** ブロックである。虚偽の優位性を書くと、実在しない堀を前提に意思決定してしまう。

「Gem Index = 被依存数の順位 − star の順位」という定義自体は **公開されており、模倣可能** である。データ源（Ecosyste.ms・OpenSSF）も公開 API であり、誰でも同じものを作れる。

### 10.2. 参入障壁の所在（優位性ではないが、構造的な壁）

| 壁 | 内容 | 誰に対して効くか |
|---|---|---|
| **被依存数が GitHub API に存在しない** | GitHub 純正の検索構文では原理的に再現できない（`Q-1` / `Q-2`） | 🔵 **GitHub 自身が実装するまでは効く**。ただし GitHub が実装したら消える |
| **名前解決の泥臭さ** | リポジトリ URL ↔ パッケージ名の対応（モノレポ・URL 未設定・古い URL）。ここが甘いと Gem Index の分母が壊れる（`prd.md` §11） | 後発の実装者。**技術的な参入コストとして効く** |
| **母集団定義の妥当性** | パーセンタイルの母集団をどう切るかで値の意味が変わる。ここに説明可能な根拠を持つこと | 同上 |

### 10.3. 将来的に優位性になりうるもの（現時点では **ない**）

- 名前解決の対応表そのもの（作り込むほど模倣コストが上がる資産になる）
- 「どの母集団でパーセンタイルを取るか」の較正済みパラメータ

🔴 **これらを「持っている」と書かない。** いずれも未着手であり、Phase 2 の実装を経て初めて資産になる。
