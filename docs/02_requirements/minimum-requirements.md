# 最低要件定義（MVP）

> 本ドキュメントは、GitHubリポジトリ検索Webアプリケーションとして本プロジェクトが**最低限満たすべき要件**を定義する。ここに記載のない拡張機能（Gem Score、目的別タグ、レコメンド等の構想は [`docs/00_concept/initial-concept.md`](../00_concept/initial-concept.md) を参照）は本要件のスコープ外とし、本要件を満たしたうえで段階的に追加する。

## 1. 目的とスコープ

### 1.1. 目的

利用者がキーワードでGitHub上のリポジトリを検索し、検索結果から任意のリポジトリを選択して、その基本情報を確認できるWebアプリケーションを提供する。

### 1.2. スコープ

| 区分 | 内容 |
|---|---|
| 対象 | リポジトリ検索、検索結果一覧表示、リポジトリ詳細表示 |
| 対象外 | ユーザー認証、お気に入り・リスト管理、独自スコアリング、通知、課金 |

## 2. 技術要件

| 項目 | 要件 | 必須/推奨 |
|---|---|---|
| フレームワーク | Next.js v16以降 | 必須 |
| ルーティング | App Routerを使用する（Pages Routerは使用しない） | 必須 |
| データソース | GitHub API のリポジトリ検索エンドポイント（`GET /search/repositories`） | 必須 |
| UIコンポーネントライブラリ | 任意のライブラリ（shadcn/ui等）を使用してよい。使用しない構成も可 | 任意 |
| 言語 | TypeScript | 推奨 |

## 3. 機能要件

| ID | 要件 | 受け入れ条件 |
|---|---|---|
| FR-1 | キーワード入力による検索 | 検索フォームに任意のキーワードを入力し、検索を実行できる |
| FR-2 | 検索結果の一覧表示 | GitHub APIのリポジトリ検索結果を一覧で表示する。各項目にオーナーアイコンとリポジトリ名を表示する |
| FR-3 | 検索結果からの詳細遷移 | 一覧の任意の項目を選択すると、該当リポジトリの詳細画面へ遷移する |
| FR-4 | 詳細情報の表示 | 詳細画面にリポジトリ名・オーナーアイコン・プロジェクト言語・Star数・Watcher数・Fork数・Issue数を表示する |
| FR-5 | 詳細画面のページ化 | 詳細はモーダルではなく**独立したページ**として実装し、固有のURLを持つ（URL直接アクセス・リロード・共有が可能） |
| FR-6 | 一覧への復帰 | 詳細画面から検索結果一覧（トップページ）へ戻る導線を提供する |
| FR-7 | 大量結果への対応 | 検索結果が多数となる場合に備え、ページネーションまたは無限スクロールを実装する |

### 3.1. 画面構成

#### 3.1.1. トップページ（検索・一覧）

| 要素 | 仕様 |
|---|---|
| ヘッダー | アプリケーションタイトルを表示 |
| 検索入力欄 | キーワードを入力するテキストフィールド。未入力時はプレースホルダで入力を促す |
| 検索実行 | 検索ボタン、およびキーボード操作（Enter）で実行できる |
| 結果リスト | 1件を1カードとして縦に並べる。カード内にオーナーアイコンとリポジトリ名を表示し、カード全体が詳細への遷移操作の対象となる |
| 追加読み込み | ページネーションまたは無限スクロールにより、2ページ目以降の結果を取得できる |

#### 3.1.2. 詳細ページ

| 要素 | 仕様 |
|---|---|
| ヘッダー | アプリケーションタイトルを表示。トップページへ戻る導線を含む |
| リポジトリ概要 | オーナーアイコン、リポジトリ名、プロジェクト言語を表示 |
| 統計情報 | Star数・Watcher数・Fork数・Issue数を、項目名と数値の対で並べて表示 |

> 画面レイアウトの詳細は、見やすさ・操作しやすさを満たす限り自由とする。装飾性そのものは要件としない。

### 3.2. 状態ごとの表示要件

以下の状態を利用者が判別できるようにUIへ反映する。

| 状態 | 要件 |
|---|---|
| 初期状態（未検索） | 検索を促すことがわかる表示とする |
| 読み込み中 | 検索・追加読み込み・詳細取得の各処理中であることを示す |
| 結果0件 | 該当するリポジトリが存在しないことを明示する |
| エラー | 通信失敗・APIエラー・レート制限超過を区別して伝え、再試行手段を提供する |
| 該当リポジトリなし（詳細） | 存在しないリポジトリのURLへアクセスした場合、Not Found相当の表示を行う |

## 4. 非機能要件

プロダクション運用を想定した実装とする。

### 4.1. 信頼性・エラーハンドリング

- API呼び出しの失敗を握りつぶさず、利用者に伝えたうえでアプリケーションを継続利用可能な状態に保つ。
- GitHub APIのレート制限（未認証時は上限が低い）を考慮し、超過時に適切なメッセージを表示する。必要に応じてアクセストークンによる認証済みリクエストを利用できる構成とする。
- APIトークン等の秘匿情報はクライアントへ露出させず、環境変数およびサーバーサイドで扱う。

### 4.2. パフォーマンス

- 入力のたびに無条件でAPIを呼ばない（デバウンス、明示的な検索実行等による抑制）。
- App Routerのサーバーコンポーネント／キャッシュ機構を活用し、不要な再取得とクライアントバンドルの肥大化を避ける。
- 画像（オーナーアイコン）は最適化して配信する。

### 4.3. ユーザビリティ・アクセシビリティ

- スマートフォンからデスクトップまでのレスポンシブ対応を行う。
- キーボードのみで検索から詳細閲覧まで操作できる。
- フォーム・ボタン・画像に適切なラベルおよび代替テキストを付与する。
- 検索条件（キーワード、ページ）はURLに反映し、リロードおよび共有時に同じ結果を再現できるようにする。

### 4.4. 保守性

- ディレクトリ構成・命名・責務分割に一貫性を持たせ、API呼び出し・表示ロジック・UIを分離する。
- APIレスポンスの型を定義し、型安全に扱う。
- Lint／フォーマッタを導入し、規約を機械的に検証できる状態にする。

## 5. テスト要件

- テストコードを記述する。
- 少なくとも以下を対象とする。
  - 検索実行から結果一覧が表示されるまでの主要フロー
  - 一覧から詳細ページへの遷移および詳細情報の表示
  - 読み込み中・0件・エラーの各状態表示
- 外部APIへの依存はモック化し、ネットワーク状況に依存せずテストが再現可能であること。
- テストはコマンド一つで実行でき、CIで自動実行できる状態とする。

## 6. ドキュメント要件

- READMEに以下を記載する。
  - セットアップ手順（依存インストール、必要な環境変数、起動・テスト実行コマンド）
  - 設計上の判断、工夫した点、こだわったポイント
  - 開発にAIを利用した場合は、その利用方法と範囲
- 重要な技術的意思決定は [`docs/adr/`](../adr) にADRとして記録する。
