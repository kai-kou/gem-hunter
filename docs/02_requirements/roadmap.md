### 0.2. 🔴 前提: 期日は存在するが未確定である（`D-9` / `RK-6`）

したがって本書は **絶対日付でスケジュールを引かない**。あわせて **工数（人日・週数）の見積もりも書かない**（根拠のない数字になるため・`D-9` の従属事項）。

代わりに、期日がなくても **今すぐ確定できる 3 つ** で時間軸を表現する。

| # | 本書が確定させるもの | 理由 |
|---|---|---|
| 1 | **到達順序**（どのマイルストーンを、どの順で通るか） | 期日が決まっていなくても順序は決まる。順序が決まれば「次に何をするか」は一意になる |

| 3 | **期日が確定したときの記入手順**（§5） | 期日が来たときに何をどこへ書くかを先に決めておく |

🔵 **「未確定」は「無期限」ではない。** 日付だけが未定であり、順序・判定・削減順序は本書で確定している。

## 6. スコープ調整の規則（削る順序）

期日が想定より早い / 進捗が想定より遅いと判明したときは、**次の順序でのみ** 削る。

```
① M-3 の下位項目から削る（§3 の着手順序の下から）
        ↓ それでも足りない場合
② M-3 を丸ごと落とす（M-2 到達で与件は満たされている）
        ↓ それでも足りない場合
③ 🔴 ここで止まる。M-1 / M-2 は削らない
```

⏸ **削減順序 ② を援用済み（`D-41`・2026-08-24）。** `M-3` を丸ごと落とす判断を実際に行った。⚠️ ただし発動理由は本節冒頭の条件（期日・進捗の逼迫）ではなく、与件充足済み + `M-3` に通過判定が無いことである（詳細は §3 `M-3` の注記）。

🔴 **`M-1` / `M-2` を削らない理由**: `M-2` は与件（必達の下限・`D-2`）であり、`M-1` はその到達に必要な境界確定である。`M-1` を削ると `M-2` が「後から全体を書き換える作業」に化けるため、短縮どころか遅くなる（`D-9`）。

⚠️ **`M-1` / `M-2` の内部で削れるものはない、という意味ではない。** `prd.md` §0.3 のとおり、`P1-MVP` のうち **②（後付けコストが高い上乗せ）で、削っても①（与件充足）を割らないもの** は理屈のうえでは削減候補になる。ただし ② は「後から入れると既存コードを書き換える」という理由で MVP に置かれているため、**削ると `M-3` 以降の速度が落ちる**。削る場合は理由を決定ログ（`open-questions.md`）に残す。

🔵 **`M-6`（`P2`）は実装・通過済みなので、本節の削減順序の射程外である**（2026-08-24・#569 で通過判定を実測検証済み）。本節が定めるのは **これから作るスコープをどの順で落とすか** であり、既に動いているものを消す規則ではない。`M-2` 到達時点で確定した本節の順序に `D-27` 由来の `M-6` が入っていないのは、そのためそのままでよい。

⚠️ **実装済みの機能を事後に撤去する判断は、本節ではなく個別の決定として記録する。** 前例は `D-33`（`SP-16` の `sort=gem-index`・2026-08-21）と `D-34`（`SP-15` の RSS）で、いずれも「使われ方の実測を見て落とす」判断であり、期日・進捗の逼迫を理由とする本節の削減とは発動条件が違う。
