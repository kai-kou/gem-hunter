## 1. プロダクト概要

### 1.1. 解決する課題

GitHub の検索では有名なリポジトリが上位を占めやすい一方、**star は注目度の指標であって利用実績ではない**。約 600 万個の偽 star が観測されており（He et al., ICSE 2026・[競合調査](../01_research/market/20260817-github-repo-search-competitive-analysis.md)）、star 順に並べるほど「実際に使われているが知られていないもの」は見えなくなる。

実例として、`debug_inspector` は 25 star でありながら 111,000 以上の OSS プロジェクトから依存されている。この種のリポジトリは、既存のどの検索手段でも上位に現れない。

### 1.2. ミッション

**star の多さでは埋もれてしまう「実際に使われている OSS」を、個人開発者が見つけられるようにする。**

（KPI・判断基準・品質ゲートは [`project-mission.md`](../project-mission.md) が正本）

### 1.3. ターゲットユーザー

個人開発者・インディーハッカー・フリーランスエンジニア。「車輪の再発明はしたくないが、巨大なフレームワークは学習コストが高い。自分のプロダクトにちょうどよく、活発にメンテナンスされているライブラリが欲しい」というニーズを持つ。

> ⚠️ **このペルソナは未検証である**（`R-1`）。一次情報にあたるユーザーリサーチは実施しておらず、初期コンセプトの仮説をそのまま引き継いでいる。要件の優先順位付けにあたっては、この点を割り引いて扱う。

### 1.4. Hidden Gem の定義（本プロダクトの中核）

> **Gem とは、「実際に使われている度合い（被依存数）」に対して「注目度（star 数）」が不釣り合いに小さいリポジトリである。**

判定は **2 軸を役割分担させて** 行う（`Q-1` / `Q-2`）。

| 軸 | 指標 | 役割 |
|---|---|---|
| ① 過小評価度 | `Gem Index` = エコシステム内での「被依存数のパーセンタイル順位」−「star のパーセンタイル順位」（`Q-3`） | **並び順**（ランキング） |
| ② 健全性 | OpenSSF `criticality_score` / Scorecard（自作しない） | **足切り**（フィルタ） |

🔴 **2 軸を 1 つのスコアに合算しない。** 合算すると「健全だが有名」なリポジトリが上位に戻り、否定したはずの star 追随ランキングに退化する。

この定義を採る理由（`Q-1` / `Q-2` の決定ログに詳細）:

1. star を分子ではなく **分母** として使うため、star 単純ランキングにならない
2. **被依存数は GitHub API に存在しない** ため、GitHub 純正検索では原理的に再現できない
3. `criticality_score`（重要度の絶対値）の再実装ではなく、**重要度に対する注目度の不足（残差）** を測る別物である
4. **偽 star に構造的に頑健**（star を水増しすると Gem Index は下がり、ランキングから外れる）

### 1.5. フェーズ構成

| フェーズ | 内容 | 本書での扱い |
|---|---|---|
| **Phase 1** | GitHub リポジトリ検索 Web アプリケーション | 実装対象。`FR-n` / `AR-n` / `NFR-n` |
| **Phase 2** | Gem Index による発見機能 + キーワード非依存の発見体験（日次ダイジェスト） | **`D-27` により `M-5`（Phase 2 着手判断ゲート）を通過し、実装対象へ格上げ**（スライス `S-3`）。`GR-n` / `AR-9` / `AR-10` / `US-30`〜`US-33`。🔴 `D-3` は変更しない（理由は [`open-questions.md`](./open-questions.md) `D-27` 参照） |

## 2. 前提と制約

### 2.1. 事業上の位置づけ

主目的は **選考課題 / ポートフォリオ**。ただし **有用であればそのまま運用を継続したい**（副次目標・`D-3`）。したがって次の 2 つを同時に満たす。

- 与件を確実に満たし、設計判断を説明できること（主目的）
- 運用継続を阻害しない設計であること（副次目標）— 無料枠に収まる / レート制限で破綻しない / 規約違反をしない

収益化は現時点で目的としない。

### 2.2. 技術的制約（一次情報で確認済み・2026-08-17 JST）

| 制約 | 値 | 影響 |
|---|---|---|
| GitHub 検索 API のレート制限 | 認証済み **30 req/分** / 未認証 10 req/分 | **アプリ全体の律速**。キャッシュなしの公開運用は成立しない |
| GitHub Core API のレート制限 | 認証済み 5,000 req/h / 未認証 60 req/h | 詳細取得はボトルネックにならない |
| 二次レート制限 | 100 並行リクエスト / 900 ポイント毎分 / **直列実行を推奨** | 並行リクエストを避ける設計が必要 |
| 条件付きリクエスト | **304 が返る場合は primary rate limit を消費しない** | 詳細取得で有効（検索結果は変動するため 304 になりにくい） |
| 検索結果の総数上限 | 1 クエリあたり最大 1,000 件 | ページネーションの上限になる |
| `watchers_count` の実体 | **star 数のミラー**。真の Watcher 数は `subscribers_count` | `FR-4` の実装に直結（§4.1 参照） |
| 被依存数 | **GitHub API では取得できない** | Phase 2 で外部 API（Ecosyste.ms）が必須になる |

### 2.3. アーキテクチャ上の設計原則

| 原則 | 内容 | 根拠 |
|---|---|---|
| **DB を持たない** | 状態は URL / Cookie / `localStorage` に寄せ、サーバー側ストアを持たない | `D-5` 追補 |
| **インフラを決め打たない** | ✅ **デプロイ先はプレビュー・本番とも Cloudflare Workers に確定した**（`D-16`・2026-08-18）。キャッシュ基盤も HTTP `Cache-Control` + Workers Caching に確定し、永続ストアは未採用（`D-18`）。🔴 **原則そのものは維持する**: 特定 PaaS 固有機能への依存は最小化し、事業者固有バインディングへのアクセスは `src/infrastructure/platform/` 配下に限定する（`NFR-21`） | `D-5` / `D-7` / `D-11` / `D-16` / `D-18` |
| **サーバー側に個人情報を持たない** | 利用者の識別子・行動履歴・IP・検索キーワードをサーバー側に記録しない。実行モデルはサーバーレス関数前提とする | `D-13` / `D-14` |
| **データアクセスを 1 箇所に隔離する** | GitHub API 呼び出しは専用層に閉じ込め、UI 層から直接呼ばない | `D-5` / `D-9` |
| **積み上げ可能性を先に確保する** | 後から入れると既存コードの書き換えが発生するものを MVP に含める | `D-9` |
| **既存のものを再実装しない** | 健全性スコアは OpenSSF に依存する | `Q-1` / `Q-2` / `R-3` |

### 2.4. 状態の置き場所

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 検索キーワード・ページ・ソート・表示件数 | **URL（`searchParams`）** | リロード・共有で同じ結果を再現する（`NFR-2`） |
| ロケール | **URL のパスセグメント** | 共有時に言語が保たれる |
| ログインセッション（OAuth トークン） | **暗号化 httpOnly Cookie** | サーバー側ストア不要。クライアント JS から読めない |
| UI 設定・検索履歴・お気に入り | **`localStorage`** | サーバー不要で実現できる |
| API レスポンス | **キャッシュ層（破棄可能）** | 永続ストアではない |

#### 2.4.1. URL クエリパラメータの契約（`US-9` / `AC-2` / `NFR-2`）

> 🔴 **本表が名前・既定値・許容値の正本である。** 実装（`src/ui/url/search-params.ts` の `SEARCH_PARAM_KEYS` と `src/domain/model/` の値オブジェクト）は本表の実装であり、**先に本表を変えてからコードを変える**。共有された URL は外部から参照され続けるため、名前と既定値の変更は後方互換の破壊にあたる（`NFR-2`）。

| パラメータ名 | 意味 | 既定値（省略時） | 許容値・制約 | 不正値のとき |
|---|---|---|---|---|
| `q` | 検索キーワード | `''`（未入力） | 1〜256 文字。GitHub 検索修飾子（`stars:` 等）・論理演算子（`AND` / `OR` / `NOT`。**大文字トークンのみ拒否** し、小文字の `and` / `or` / `not` は通常語として許可する）は受け付けない | 未入力として扱う（画面側はエラー表示のために生値も参照する） |
| `page` | ページ番号 | `1` | 🔴 **1〜50 の整数**（`1000 ÷ 既定表示件数 20` に由来する **固定値**。`per_page` の実値では再計算しない） | 既定値へ丸める |
| `sort` | 並び順 | `relevance` | `relevance` / `stars` / `updated`（🔴 `gem-index` は `D-33`（2026-08-21）により撤去。候補プールの被覆率が低く一般語でほぼ一致しないため機能として成立しなかった。旧 URL の `sort=gem-index` は不正値として既定値へ丸める。再導入条件は [`open-questions.md`](./open-questions.md) `D-33`） | 既定値へ丸める |
| `per_page` | 表示件数 | `20` | `20` / `50` / `100` | 既定値へ丸める |

- **既定値はクエリに載せない**（既定と同じ値を URL から省略でき、共有リンクが短くなる）
- **不正値で 404 やエラー画面にしない**（丸めて表示を続ける）。ただし `q` だけは「未入力」と「不正な入力」を画面上で区別する
- 🔴 **`page` の上限は二層になっている**（`AC-7`）。URL のパース時は上表の固定値（1〜50）だけで判定し、`per_page` に応じた到達可能上限（`floor(1000 / per_page)`）はページ送りリンクを出すかどうかの判定にのみ使う。したがって `per_page=100&page=40` のように **リンクを辿らず URL を直接書き換えた場合は丸められず**、GitHub 検索 API の 1,000 件上限超過エラーになりうる（既知の制約）
- ロケールはクエリではなく **パスセグメント** に置く（上表「状態の置き場所」）

⚠️ **受け入れる制約**: `localStorage` の内容は端末間で同期されず、ブラウザのデータ削除で消え、容量上限（数 MB 程度）がある。同期が必要になった時点で初めて DB を検討する。

## 3. スコープ境界

### 3.1. Phase 1 の対象

キーワードによる GitHub 公開リポジトリの検索、検索結果の一覧表示、リポジトリ詳細の表示、およびそれらを支える非機能要件。

### 3.2. 対象外（やらないこと）

> 🔴 **本節は「要件レベルのスコープ境界」だけを示す。やらないことの完全な一覧の正本は [`inception-deck.md`](../00_concept/inception-deck.md) Q4.2 である**（`D-8`）。同 Q4 には本節に載らない項目（DB を持つこと・健全性スコアの自作・無限スクロール・Phase 2 の実装・GitHub 由来データの機械翻訳・獲得チャネルの設計）と、**「今は決めないこと」**（Q4.4）も含まれる。**両者が食い違ったらインセプションデッキが優先する。**

| 項目 | 理由 |
|---|---|
| ユーザー認証を **必須** にすること | 与件 §1.2。ログインは任意であり、機能差を作らない（`D-6`） |
| お気に入り・リスト管理 | 与件 §1.2 では対象外。ただし `localStorage` で実現可能なため `P1-積み上げ` に置く（`Q-5`） |
| メール / push 通知 | 配信先リストの永続化が必要で、`D-14`（サーバーに個人情報を持たない）・`D-18`（永続ストア不採用）に正面抵触する（`Q-5`） |
| 課金・サブスクリプション | `D-3` により目的としない |
| 目的別タグの自前生成（LLM 分類・人手キュレーション） | 維持コストが運用継続と両立しない。GitHub topics の活用に絞る（`Q-4`） |
| エージェント向け API / MCP の提供 | `D-1` で不採用 |
| GitHub App の **Webhook 受信・イベント購読** | 本プロダクトは他人の公開リポジトリを読むだけで、監視対象リポジトリが存在しない（`Q-6`）。⚠️ **GitHub App を「サーバー側の認証方式」として使うことは採用済み**（`D-20`）。ここで不採用なのは Webhook を受けて常駐処理を行う形態であり、両者を混同しない |
| 複数トークンのローテーション | レート制限の回避とみなされる恐れがある（`D-6`） |
| プライベートリポジトリの検索・表示 | 対象は公開リポジトリのみ（§3.1）。⚠️ **サーバー側の認証（`D-20`）を入れると、トークンから見えるプライベートリポジトリが API 応答に現れうる**。認証設定に委ねずアプリ側で公開限定を強制する（`NFR-33` / `AC-12`） |

🔵 **静的な日次ダイジェストと RSS（`AR-9` / `AR-10`・§11）は対象内**: 上表のメール / push 通知と異なり、購読者リストを持たない Pull 型のため `D-5`（DB を持たない）の撤回は不要（`D-27`）。

| **FR-4** | 詳細情報の表示（リポジトリ名・オーナーアイコン・言語・Star 数・Watcher 数・Fork 数・Issue 数・🔵 概要（description）・🔵 最終更新日（`pushed_at`）・🔵 README） | `P1-MVP` | 🔴 **「Watcher 数」には `subscribers_count` を用いる**（下記の注記参照）。🔴 **対象が公開リポジトリでない場合は「見つからない」として扱う**（`NFR-33` / §7 の 404）。🔵 概要・最終更新日・README は Issue #334（F-3 / F-4）により追加（専門チームの議論は[議論記録](../../content/discussions/feedback334_detail_readme_20260821/whiteboard.md)を参照）。最終更新日は一覧の `AR-1` と同じ `pushed_at` 由来（欠落時は `updated_at`）。README は取得・表示に失敗しても詳細ページ全体を落とさず代替リンクへ縮退する（`NFR-9`） |
| **FR-5** | 詳細をモーダルではなく独立ページとして実装し、固有 URL を持つ | `P1-MVP` | URL 直接アクセス・リロード・共有が可能であること |
| **FR-6** | 詳細画面から一覧（トップページ）へ戻る導線 | `P1-MVP` | 戻り先で検索条件が保持されること（URL 状態・§2.4） |
| **FR-7** | 大量結果への対応 | `P1-MVP` | 🔴 **ページネーションを採用する**（無限スクロールは採らない・下記の注記参照） |

#### 🔴 FR-4 の注記: 「Watcher 数」の実体

GitHub の REST API では、`watchers_count` および `watchers` は **star 数のミラー** であり、Watcher（通知購読者）の数ではない。真の Watcher 数は **`subscribers_count`** である（GitHub 公式ドキュメントで確認済み・2026-08-17 JST）。

- `watchers_count` を使うと、画面上に **star と同じ数字が 2 つ並ぶ**。
- **`subscribers_count` は検索結果のレスポンスには含まれず、`GET /repos/{owner}/{repo}` でのみ得られる。** これにより §4.3 の取得方式が技術的に確定する。

#### 🔴 FR-7 の注記: ページネーションを選ぶ理由

与件は「ページネーション **または** 無限スクロール」を選択制としているが、`Q-8`（WCAG 2.2 AA を目標）を採る以上、無限スクロールは次の 4 点で不利であり、ページネーションを採用する（理由は ADR に記録する）。

1. キーボード操作でフッターに到達できなくなる
2. スクリーンリーダーで「どこまで読んだか」が提示できない
3. フォーカス管理が複雑になり、戻り時に位置を復元しにくい
4. 現在ページを URL に反映できず、`NFR-2`（URL 状態）と衝突する

#### AR-4 の詳細（i18n）

- **URL 形式**: 全ロケールにプレフィックスを付ける（`/ja/...` / `/en/...`）。プレフィックスなしの `/` は既定ロケールへリダイレクトする。
- **既定ロケール**: `ja`（ユーザー決定）
- 🔴 **ルーティング設計は実装の最初に確定させる**。後から locale セグメントを足すと既存 URL がすべて変わり、共有リンクが壊れる。
- **翻訳対象は自前の UI 文言のみ**。GitHub 由来のデータ（リポジトリ説明文・topics・言語名）は原文のまま表示する（機械翻訳は正確性を損なう）。

#### AR-5 の詳細（OAuth）

- **OAuth スコープは要求しない（no scope）**。公開リポジトリの検索・閲覧しか行わないため追加権限は不要。
- **セッションは暗号化した httpOnly Cookie で保持する**（DB を持たないため）。ユーザーの OAuth トークンをクライアントへ露出させない。
- **CSRF 対策として `state` パラメータを必須** とする。ログアウト（Cookie 破棄）も提供する。
- **callback URL は環境変数化する**（`D-16` でデプロイ先は Cloudflare に確定したが、環境変数化の方針自体は事業者非依存かつプレビュー URL が PR ごとに変わるため維持する）。
- **与件との関係**: 与件 §1.2 は認証を「対象外」としているが、これは「実装しなくてよい」であって禁止ではないと解釈し、**レート枠という技術的必然を根拠に上乗せする**。🔴 **この解釈と理由を README にも明記する**（書き残さないと「要件を読んでいない」と誤読されるため）。
- **認証を足したことを口実に、与件が対象外とした他の項目（お気に入り・通知・課金・独自スコアリング）を MVP に入れない。**

### 4.3. データ取得方式

呼び出してよい GitHub API エンドポイントは以下の一覧に **限定する**（`TR-4` / `NFR-16` の ACL 制約）。新規エンドポイントの追加は本表への追記を伴う。

| 用途 | エンドポイント | 備考 |
|---|---|---|
| 検索 | `GET /search/repositories` | 律速（30 req/分）。`AR-2` のソート、`AR-3` の件数、ページをパラメータで渡す。🔴 **利用者キーワードに検索修飾子の構文が含まれていたら送信せずエラーにし、クエリに公開限定条件（`is:public`）を付与する**（`NFR-33`。付与だけでは公開に閉じない） |
| 詳細 | `GET /repos/{owner}/{repo}` | 🔴 **常に単独で呼ぶ**（検索結果のデータを引き回さない）。🔴 **応答が `private: true` なら「見つからない」として扱う**（`NFR-33`） |
| 🔵 README | `GET /repos/{owner}/{repo}/readme`（`Accept: application/vnd.github.html+json` で GitHub レンダリング済み HTML を取得） | Issue #334（F-4）により追加。詳細の `findDetail` が private / 404 と判定した場合は呼ばない（`NFR-33` / `AC-12` のゲートを usecase 層で先に通す）。取得した HTML はサニタイズしてから表示する（実装の正本は [application-architecture.md](../03_design/architecture/application-architecture.md)） |

**詳細を単独取得する理由**（`Q-10`）:

1. `FR-4` の「Watcher 数」= `subscribers_count` は **検索結果に含まれない** ため、単独取得が技術的に必須
2. `FR-5`（URL 直接アクセス可能な独立ページ）を満たすには、いずれにせよ単独取得の経路が要る
3. 2 経路（引き回し / 単独取得）を持つと、遷移元によって表示内容が変わりうる
4. Core API は 5,000 req/h で余裕があり、**ETag が効く**（304 は枠を消費しない）

#### 🔴 NFR-27 の注記: CI ゲートの偽陽性対策

これを付けずにゲート化すると、`D-9` の「積み上げ速度」を落とす。

- 本番相当のビルドに対して計測する（開発サーバーでは測らない）
- **複数回実行の中央値** を採る。単発の結果でゲートしない
- CPU / ネットワークのスロットリング設定を固定する
- Accessibility と Performance を **同じ厳しさで扱わない**（前者は決定論的、後者は揺れる）
- ⚠️ **撤退条件**: Lighthouse ゲートが原因で実装が **2 回以上ブロックされたら、ゲートの設定自体を見直す**。ゲート遵守を目的化しない

| **NFR-32** | 技術的意思決定を ADR として記録する | `P1-MVP` | 「なぜその選択をしたか / 何を捨てたか」を残す。最低限 §12 の一覧 |

### 5.8. セキュリティ・プライバシー

| ID | 要件 | 優先度 | 内容 |
|---|---|---|---|
| **NFR-33** | 認証トークンを用いても、取得対象を公開リポジトリに限定する | `P1-MVP` | 🔴 **認証はレート枠だけでなく、トークンから見えるデータの可視範囲も広げる**。サーバー側の認証（GitHub App の installation token・`D-20`）では、App のインストール先に含まれるプライベートリポジトリが検索・詳細の応答に現れうる。本プロダクトの対象は公開リポジトリのみ（§3.1）であるため、**可視範囲の限定を App の権限設定や運用に委ねず、アプリ側で多層に強制する**: ① 利用者が入力したキーワードに **検索修飾子の構文（`名前:値` / `-名前:値`）が含まれる場合は検索を行わずエラーとして扱う**（検索クエリへのインジェクション遮断）② 検索クエリに公開限定条件（`is:public`）を付与する ③ 検索結果のマッピングで `private: true` の項目を除外する ④ `GET /repos/{owner}/{repo}` の応答が `private: true` なら「見つからない」として扱う（§7 の 404 と同じ提示）。いずれか 1 層が欠けても私有データが露出しない構造にする。🔴 **`is:public` の付与だけで公開に閉じるとは考えない**: GitHub の検索構文は同一修飾子の重複指定（`is:private is:public`）を AND として解釈せず、利用者がキーワードに `is:private` や `user:誰か` と書けるままだと ② の層は破れる。① を前提に置き、GitHub 側の構文解釈に安全性を依存させない。🔵 **検索でも認証は維持する**（未認証検索へ切り替えるとレート枠が 30 req/分 → 10 req/分に下がり `NFR-7` が悪化するため）。🔵 **`private: true` を除外しても、応答の `totalCount` は GitHub が返した値のまま保つ**（総件数とページングの整合を崩さないため。表示件数との差分は許容する）。検証は `AC-12` |

## 6. 主要フローの受け入れ基準

> 与件の受け入れ基準 11 項目（`AC-1`〜`AC-11`）に対応する。Given/When/Then はそのままテストケースに写せる粒度で書く。
> `AC-12` 以降は **与件由来ではなく本書で追加した受け入れ基準**（削ると与件は割らないが、`P1-MVP` として必達に置く）。

### AC-1: Next.js v16 以降 + App Router で構築されている

- **Given** リポジトリのソースコード
- **When** 依存とディレクトリ構成を確認する
- **Then** Next.js が v16 以降であり、`app/` ディレクトリによる App Router を使用している（`pages/` によるルーティングを使用していない）

### AC-2: キーワード検索で結果が一覧表示される

- **Given** トップページを開いている
- **When** 検索欄にキーワードを入力し、検索を実行する（ボタン押下または Enter）
- **Then** GitHub API の検索結果が一覧として表示される
- **And** 検索キーワードが URL に反映されている

### AC-3: 一覧項目にオーナーアイコンとリポジトリ名が表示される

- **Given** 検索結果が表示されている
- **When** 任意の 1 件を確認する
- **Then** オーナーアイコンとリポジトリ名が表示されている
- **And**（`AR-1`）説明文・主要言語・star 数・最終更新日・topics も表示されている

### AC-4: 一覧項目の選択で、独立した URL を持つ詳細ページへ遷移する

- **Given** 検索結果が表示されている
- **When** 任意のカードを選択する
- **Then** 詳細ページへ遷移する
- **And** そのページは **モーダルではなく独立したページ** であり、固有の URL を持つ
- **And** その URL を直接開いても、リロードしても同じ内容が表示される

### AC-5: 詳細ページに所定の情報が表示される

- **Given** 任意のリポジトリの詳細ページを開いている
- **When** 表示内容を確認する
- **Then** リポジトリ名・オーナーアイコン・プロジェクト言語・**Star 数**・**Watcher 数（`subscribers_count`）**・Fork 数・Issue 数・🔵 概要（description・存在する場合のみ）・🔵 最終更新日（`pushed_at`）・🔵 README（存在する場合。取得失敗時は「GitHub で読む」への代替リンク）が表示されている
- **And** Star 数と Watcher 数が同じ値になっていない（`watchers_count` を誤用していないことの検証）

### AC-6: 詳細ページからトップページへ戻れる

- **Given** 検索結果から詳細ページへ遷移している
- **When** 戻る導線を使用する
- **Then** 検索結果一覧へ戻る
- **And** 直前の検索条件（キーワード・ページ・ソート・件数）が保持されている

### AC-7: ページネーションで 2 ページ目以降を閲覧できる

- **Given** 検索結果が 1 ページに収まらない件数である
- **When** 次のページへ移動する
- **Then** 2 ページ目以降の結果が表示される
- **And** 現在のページが URL に反映されている
- **And** 総件数が 1,000 件を超える場合でも、取得可能な範囲（1,000 件）を超えるページを要求しない

### AC-8: 読み込み中・0 件・エラーの各状態が判別できる

- **Given** トップページを開いている
- **When** 未検索の状態を確認する / 検索を実行して結果を待つ / 該当 0 件のキーワードで検索する / API がエラーを返す
- **Then** それぞれ「検索を促す表示」「読み込み中の表示」「該当なしの明示」「エラーの内容と再試行手段」が表示される
- **And** いずれの状態変化も `aria-live` で支援技術に伝えられる（`NFR-12`）
- **And** エラーは種別ごとに区別されている（§7 の対応表）

### AC-9: レスポンシブ対応およびキーボード操作が可能

- **Given** 任意の画面幅（スマートフォン相当〜デスクトップ相当）
- **When** 検索 → 一覧 → 詳細 → 一覧への復帰を **キーボードのみ** で操作する
- **Then** すべての操作が完了でき、フォーカスが常に可視である
- **And** 200% 拡大時にもレイアウトが破綻しない

### AC-10: 主要フローのテストコードが存在し、実行して成功する

- **Given** リポジトリのソースコード
- **When** 単一のコマンドでテストを実行する
- **Then** `AC-2` / `AC-4` / `AC-5` / `AC-8` に対応するテストが存在し、すべて成功する
- **And** 外部 API はモック化されており、ネットワーク状況に依存しない

### AC-11: README にセットアップ手順と設計上の判断が記載されている

- **Given** リポジトリの README
- **When** 内容を確認する
- **Then** セットアップ手順（依存インストール・必要な環境変数・起動・テスト実行）が記載されている
- **And** 設計上の判断・工夫した点が記載されている（`AR-5` の上乗せ理由を含む）
- **And** AI を利用した範囲と方法が記載されている

### AC-12: 認証済みでもプライベートリポジトリが表示されない（上乗せ・`NFR-33`）

- **Given** サーバーがプライベートリポジトリを参照できる認証情報（GitHub App の installation token・`D-20`）を持って動作している
- **When** そのトークンから見えるプライベートリポジトリに一致するキーワードで検索する
- **Then** GitHub へ送る検索クエリに公開限定条件（`is:public`）が含まれている
- **And** 検索結果に `private: true` のリポジトリが 1 件も含まれない
- **When** キーワードに検索修飾子の構文（例: `is:private`・`user:誰か`・`-is:public`）を含めて検索する
- **Then** 検索は GitHub へ送られずエラーとして提示され、プライベートリポジトリは 1 件も表示されない
- **When** `private: true` の項目が除外された検索結果を表示する
- **Then** 総件数（`totalCount`）は GitHub が返した値のまま保たれ、ページング（総ページ数・移動導線）が結果件数の増減で崩れない
- **When** そのプライベートリポジトリの詳細ページ URL を直接開く（`FR-5` の経路）
- **Then** 「見つからない」として扱われ（§7 の 404 と同じ提示）、リポジトリ名・説明・統計情報のいずれも表示されない

## 7. エラー種別の判別仕様

> 与件 §3.2 の「通信失敗・API エラー・レート制限超過を区別して伝える」を、機械的に判定可能な形へ落としたもの（`Q-9`）。

| 判別条件 | 種別 | 利用者への提示 |
|---|---|---|
| fetch 自体が失敗 | ネットワーク到達不可 | 「接続できません」+ 再試行手段 |
| 403 / 429 かつ `x-ratelimit-remaining: 0` | 一次レート制限 | `x-ratelimit-reset` から復帰時刻を算出して提示 + 🔵 **ログインで枠を増やせる案内**（`AR-5`） |
| 403 / 429 かつ `retry-after` あり | 二次レート制限 | `retry-after` 秒後に再試行可能と提示 |
| 401 / 403（上記以外） | 認証・権限の問題 | **内部情報を出さず汎用エラー** として扱う（サーバー設定の問題であり利用者は対処できない） |
| 422 | 検索クエリが不正 | 入力の修正を促す |
| 404（詳細ページ） | 対象なし | Not Found 表示 |
| 5xx | GitHub 側の障害 | 再試行を提示 |

🔵 **レート制限エラーがログイン導線になる。** `AR-5` の存在価値がエラー体験の中で自然に伝わる設計とする。

### Phase 2 のユーザーストーリー（`US-30`〜`US-34`）

キーワード非依存の発見体験（日次ダイジェスト・`AR-9` / `AR-10`・§4.2）を実現するユーザーストーリー `US-30`〜`US-33`（実装単位は `SP-14` / `SP-15`）の **定義は [`user-story-map.md`](./user-story-map.md) §2 が正本**（`D-8`）。本書は要件 ID（`AR-2` / `AR-9` / `AR-10` / `GR-n`）のみを持ち、内容をここに再掲しない。🔴 **`US-34`（検索結果を Gem Index 順に並べ替える・実装単位は `SP-16`）は `D-33` により撤去済み**。定義・撤去の経緯は同じく `user-story-map.md` §5.3 `SP-16` を参照（履歴として節ごと残す）。🔴 **`US-33`（ダイジェストの RSS 配信・実装単位は `SP-15` の一部）は `D-34` により撤去済み**。経緯は [`open-questions.md`](./open-questions.md) `D-34` を参照。

### Phase 2 の中核課題（先に認識しておくもの）

- **名前解決**（リポジトリ URL ↔ パッケージ名）。🔵 **Ecosyste.ms の API が双方向の対応付けを提供している** ことが一次確認で判明した（パッケージ側に `repository_url`、リポジトリ側に `purl`）ため、負担は大幅に軽くなった。ただし 1 リポジトリが複数パッケージを公開する（モノレポ）、パッケージのリポジトリ URL が未設定・古い、といった **例外処理は残る**（出典は[補完リサーチ](../../content/research/20260820-zero-query-discovery_supplement.md) §4.4）
- **パーセンタイルの母集団定義**。母集団が変われば値が変わるため、「どの範囲を 100% とするか」を決めずにパーセンタイルを出すと数値の意味が定義できない
- **データ源が 3 系統になる**（被依存数 = Ecosyste.ms / star = GitHub API / 健全性 = OpenSSF）
