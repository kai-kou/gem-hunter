## 1. バックボーン（ユーザーの行動の流れ）

```
              ┌──→  A-2           A-3            A-4          A-5           A-6            A-7
              │  ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌──────────┐   ┌──────────┐
 A-1          │  │条件を  │→→ │結果を    │→→ │候補を  │→→ │一覧へ  │→→ │つまずき  │   │見つけた  │
┌──────┐      │  │組み立て│   │見渡す    │   │見極める│   │戻って  │   │から復帰  │   │ものを    │
│到達  │→→ ───┤  │る      │   │絞り込む  │   │        │   │比べる  │   │する      │   │残す      │
│する  │      │  └────────┘   └──────────┘   └────────┘   └────────┘   └──────────┘   └──────────┘
└──────┘      │       ↑                                     ↑ 全工程で         ↑ P1-積み上げ
              │       │ 合流                                   起こりうる
              │  ┌──────────┐
              └→→│きっかけ  │
                 │なく出会う│
                 │  (A-8)   │
                 └──────────┘
```

| ID | アクティビティ | ユーザーの目的 |
|---|---|---|
| **A-1** | 到達する | アプリを開き、自分の言語で使える状態にする |
| **A-2** | 条件を組み立てる | 探したいものをキーワードと並び順で表現する |
| **A-3** | 結果を見渡す・絞り込む | 一覧をざっと見て、詳細を開く価値のある候補を選別する |
| **A-4** | 候補を見極める | 1 件の詳細を見て、採用可否を判断する |
| **A-5** | 一覧へ戻って比べる | 元の検索条件のまま次の候補へ移る |
| **A-6** | つまずきから復帰する | 何も出ない・失敗したときに、原因を理解して次の手を打つ |
| **A-7** | 見つけたものを残す | 後で見返せるようにする |
| **A-8** | きっかけなく出会う | キーワードを入力せずに、その日の候補と出会う（`A-1` の直後、`A-2` と並列の入口・`D-27`） |

> **A-6 は他と性質が違う。** 時系列上の 1 ステップではなく、A-1〜A-5 のどこでも発生しうる。ただし「復帰する」という独立したユーザー体験があるため、バックボーン上に置いて可視化する。
>
> 🔴 **`A-8` は ID の数字と図の並び順が一致しない。** `A-1`〜`A-7` を確定させたあとに `D-27` で新設したため末尾の番号を振った（§0.2 の「一度振った ID は変更・再利用しない」規約）。バックボーン上の位置は図のとおり `A-1` の直後・`A-2` と並列の入口であり、`A-2` を必ず通っていた現行構造を「検索から入る経路」と「きっかけなく出会う経路」の 2 入口に変える。両経路は `A-3`（結果を見渡す・絞り込む）へ合流する。

## 5. スプリント単位への分割（操作してレビューできる増分）

### 5.1. なぜこの節が必要か

§4 のリリーススライスは **粒度が粗すぎてスプリントの単位にならない**（特に `S-1` は `AC-2`〜`AC-11` をまとめて満たす 1 塊で、1 セッション = 1 スプリントの運用に載らない）。また §3 の横断イネイブラーは技術単位で並んでいるため、そのまま着手すると **「動くものが増えないスプリント」** が生まれる。

そこで本節は、スライスを **スプリント（`SP-n`）へ縦に割り直す**。分割の基準はただ 1 つ。

> 🔴 **スプリント終了時に、ユーザーが実際に触って「前より何が変わったか」を確認できること。**

### 5.2. スプリントが「レビュー可能」であるための 5 条件

新しいスプリントを切るとき、以下を **すべて** 満たすこと。1 つでも欠けたら割り方が間違っている。

| # | 条件 | 満たさない例 |
|---|---|---|
| **C-1** | **操作して確かめられる振る舞いが変わる**（できることが増える / 速度・API 消費・失敗時の挙動が変わる、のいずれか） | 「型定義を整備する」だけのスプリント — 触っても何も変わらない |
| **C-2** | 🔴 **デモ手順が 5 行以内で書ける**（何を開き、何を入力し、何が見えれば成功か） | 「レート制限対策を実装する」— どう操作すれば確認できるかが書けない |
| **C-3** | **前スプリントの経路を壊さない**（回帰はテストで検知できる状態にある） | テスト基盤がないまま機能だけ積む |
| **C-4** | **単独で `sp:8` 以内に収まる**（超えるなら分割する・`session-sprint-rules.md` §3） | 「MVP を完成させる」 |
| **C-5** | **1 つの `SP-n` は 1 つの GitHub Issue として起票する。同一 `SP-n` を技術レイヤー（フロントエンドだけ・バックエンドだけ等）で複数 Issue に分割しない** | 「SP-6 のフロントエンド分」「SP-6 のバックエンド分」に分けて起票する |

🔴 **`C-2` が実質的なゲートである。** イネイブラー（`E-n`）だけで構成されたスプリントを作ってよいのは、**`C-2` を満たせる場合に限る**（例: キャッシュは「同じ検索を 2 回実行してレート残量が減らないこと」で確認できる／テスト基盤は「コマンド 1 つでテストが通ること」で確認できる）。`C-2` を書けないイネイブラーは **単独スプリントにせず、それが観測可能になる機能スプリントへ同梱する**。

🔴 **デモ手順に他スプリントの成果物を前提として書かない。** 書いてしまうと、そのスプリント単独では完了判定ができなくなる（§5.5 の依存関係を必ず確認する）。

🔴 **`C-5` は `C-2` の複製ではない。** レイヤー単独の Issue（例: 「バックエンドだけ」）は、それ単独では `C-2`（デモ手順が 5 行以内で書ける = 操作して確かめられる）を満たせない。分割の禁止は、この不成立を **起票段階で先回りしてガードする** ものであり、`C-2` とは判定タイミングが異なる（`C-2` は実装後の振り返り、`C-5` は起票時の予防）。

**3 層（インフラ / バックエンド / フロントエンド）の判定境界**:

| 層 | diff に含まれるか判定する対象 | 対応する既存 ID |
|---|---|---|
| フロントエンド | `app/**/page.tsx` / `app/**/layout.tsx` / `src/ui/**` | `E-8` / `NFR-3` |
| バックエンド | `app/**/route.ts` / `src/usecases/**` / `src/domain/**` / `src/infrastructure/**` / `src/composition/**` / `src/shared/**` | `E-2` / `E-5` / `TR-4` |
| インフラ | `.github/workflows/**` / プレビューデプロイ設定 / `.env.example` 等の環境変数宣言 / `next.config.*` のランタイム契約部 | `E-12` / `E-22` / `E-6` / `INF-6`〜`INF-14` |

⚠️ **層の定義とディレクトリ構造の正本は [アプリケーションアーキテクチャ](../03_design/architecture/application-architecture.md) §1**（本表は 3 層判定のための写し）。「インフラ」は運用基盤の契約（`INF-n`）であって、クリーンアーキテクチャ用語の `src/infrastructure/`（アダプタ層）ではない。`src/infrastructure/` と `src/shared/` はバックエンド層の一部として数える。混同しないこと。**

**適用範囲（飼い主が確定・2026-08-18）**: `C-5` 違反（技術レイヤー別の分割 Issue）は **全スプリントで blocking**。加えて `SP-1` のみ **3 層すべてに diff が無ければ blocking**。`US-n` を含む機能スプリントは **3 層中 2 層以上に触れていなければ warning**（block しない）。イネイブラー単独スプリント（Issue の `含む` が `E-n` のみ）は **exempt**（操作レビュー手順が書けることが条件）。この適用範囲は `AskUserQuestion` による飼い主の明示確認を経て確定した（`content/discussions/sprint-cycle-design-20260818/whiteboard.md` round 3）。

機械検証は `tools/self_review_check.py`（PR 前チェック）と `tools/sprint_backlog_sync.py`（Issue 起票時）が行う。

## 7. 本書の使い方（運用ルール）

> 🔴 **スプリントの回し方（TDD・プレビュー URL・確認の発火ライン・ドキュメント参照順）の正本は [`sprint-development-rules.md`](../rules/sprint-development-rules.md)**（`SD-1`〜`SD-4`）。本節は本書の使い方に限る。

1. **実装着手時**: 🔴 **着手単位は §5 の `SP-n`**（スライス `S-n` ではない）。スプリント 1 本を 1 セッションで回し、Issue には **`SP-n` / `US-n` / `E-n` と参照要件 ID を書き、受け入れ条件は `AC-n` を参照する**（本文へコピーしない）
2. **スプリント完了時**: §5 の該当スプリントの **「操作レビュー」手順を、PR に貼ったプレビュー URL 上で上から実際になぞる**（`SD-1`）。なぞれない項目が 1 つでもあればそのスプリントは **未完了** とする（コードが書けたことを完了条件にしない）
3. **操作レビュー手順は E2E テストに写す**（`SD-2`）。手順を増やしたら E2E も増やす。手動確認と自動テストを一致させておくことで、以降のスプリントで壊れたときに自動で気づける
4. **スプリントを新しく切るとき**: §5.2 の 5 条件（`C-1`〜`C-5`）をすべて満たすか確認する。**イネイブラーだけのスプリントを作らない**
5. **スコープ調整時**: 削るのは S-2 から。🔴 **S-0 / S-1 は削らない**（`prd.md` §0.3）
6. **要件が変わったとき**: 先に `prd.md` を更新し、次に本書の参照を合わせる。**逆順にしない**（正本が後追いになると ID の意味が壊れる）
7. **新しいストーリーを足すとき**: 既存 ID を詰めず、末尾に新しい番号を振る
8. **期日が確定したとき**: 本書は時間軸を持たない。日付の記入は [`roadmap.md`](./roadmap.md) §5 の手順で行う（本書の `SP-n` は既に同 §2 / §3 でマイルストーン `M-n` へ束ねられている）
9. **`SP-n` の Ready の定義（着手可能条件）**: 以下 5 条件をすべて満たしたとき、その `SP-n` は次のルーティン firing で着手可能（Ready）とする。**これは「着手してよい条件」であって「着手後にやること」ではない**（着手後の規律は `sprint-development-rules.md` の `SD-1`〜`SD-4`）。
   - [ ] `labels` に `type:feature` + `sp:{N}` + 優先度ラベルが付与されている
   - [ ] `body` が本書 §5.3 の該当 `SP-n` セクションを **ID で参照** している（本文をコピーしない・§0.1 の正本規律）
   - [ ] §5.5 の順序制約上、先行する `SP-n` の Issue がすべて **Closed**。🔴 **判定基準は Issue が Closed かどうかであり、PR のマージ状態ではない**（PR がマージされても操作レビューが未完なら下記 10 に従い Issue は open のまま＝ Ready にならない）
   - [ ] 🔵 着手中（`status:in-progress`）の `SP-n` は Closed ではないため、上記条件によって自動的にブロックされる（**1 スプリント進行中に次のスプリント Issue を積まない**・CP-4 の論理ロックと整合）
   - [ ] `C-5` に違反する分割 Issue になっていない
   - [ ] `status:blocked` が付いていない
10. **`SP-n` → GitHub Issue への変換**: タイトルは `SP-{n}: {ゴール}`（正規表現 `^SP-(\d+):` で機械判定する）。ラベルは `type:feature` + `sp:{N}` + 優先度（`SP-1`〜`SP-11` は `P1-MVP`、`SP-12` 以降は `P1-積み上げ`）。本文は **ID 参照のみ**（§0.1 の正本規律。操作レビュー手順や `AC-n` の本文をコピーしない）。**未起票の次の 1 件だけ起票する**（先読みで積まない。CP-4 の Issue 論理ロックと相性が悪いため）。着手順序は **未 Closed の最小 `SP-N`（数値昇順）**（§5.5 の依存グラフは番号が既に体現しているため、毎回パースし直さない）。Issue のクローズ条件は **操作レビュー手順の全項目を PR のプレビュー URL 上でなぞれた状態でマージされたときのみ**（`SD-1`。コードがマージされただけでは閉じない）。実行は `tools/sprint_backlog_sync.py`（`sprint-cycle-router` スキル Step 3.5 から呼ばれる）。

    > 🔵 **設計ドキュメントが指定する固有ゲート**（例: `cloudflare-infrastructure.md` §5.3 の Workers Free 実測ゲート）は、**別トラックの独立 Issue として追跡し、`SP-n` Issue の close 判定には含めない**。close 条件は本項の文言（操作レビュー手順の完走）が正本であり、他ドキュメントのゲートで上書きしない（`intent-gate-rules.md` の権威順）。
11. **在庫が尽きたとき（`M-3` 到達）**: `S-2`（`SP-12` 以降）は有限であり、いずれ `SP-n` は尽きる。尽きたら `[Milestone] M-3 到達` Issue を **1 回だけ** 起票して通知する（A-5 相当。`docs/rules/user-notification-triage.md` §3 の必須要件を満たす）。以後は `self-improvement-loop` の消化モードへ主従を切り替える（ルーティンは止めない）。**通知が無いと改善消化で動き続けるため「プロダクトが完成したこと」に誰も気づかず、`M-4`（公開判断ゲート）が永久に先送りされる**。
