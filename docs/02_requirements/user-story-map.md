## 1. バックボーン（ユーザーの行動の流れ）

```
 A-1          A-2           A-3            A-4          A-5           A-6            A-7
┌──────┐   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌──────────┐   ┌──────────┐
│到達  │→→ │条件を  │→→ │結果を    │→→ │候補を  │→→ │一覧へ  │→→ │つまずき  │   │見つけた  │
│する  │   │組み立て│   │見渡す    │   │見極める│   │戻って  │   │から復帰  │   │ものを    │
│      │   │る      │   │絞り込む  │   │        │   │比べる  │   │する      │   │残す      │
└──────┘   └────────┘   └──────────┘   └────────┘   └────────┘   └──────────┘   └──────────┘
                                                                    ↑ 全工程で         ↑ P1-積み上げ
                                                                      起こりうる
```

| ID | アクティビティ | ユーザーの目的 |
|---|---|---|
| **A-1** | 到達する | アプリを開き、自分の言語で使える状態にする |
| **A-2** | 条件を組み立てる | 探したいものをキーワードと並び順で表現する |
| **A-3** | 結果を見渡す・絞り込む | 一覧をざっと見て、詳細を開く価値のある候補を選別する |
| **A-4** | 候補を見極める | 1 件の詳細を見て、採用可否を判断する |
| **A-5** | 一覧へ戻って比べる | 元の検索条件のまま次の候補へ移る |
| **A-6** | つまずきから復帰する | 何も出ない・失敗したときに、原因を理解して次の手を打つ |
| **A-7** | 見つけたものを残す | 後で見返せるようにする |

> **A-6 は他と性質が違う。** 時系列上の 1 ステップではなく、A-1〜A-5 のどこでも発生しうる。ただし「復帰する」という独立したユーザー体験があるため、バックボーン上に置いて可視化する。

## 4. リリーススライスのまとめ

> 🔴 **スライスはスプリントの単位ではない**（`S-1` だけで `AC-2`〜`AC-11` を含み、1 セッション = 1 スプリントに収まらない）。**実際の着手単位は §5 の `SP-n`** を使うこと。

### S-0：歩く骨格（`P1-MVP`）

> **達成条件**: 「キーワードを入れて検索し、一覧から詳細ページへ行き、一覧へ戻る」が **端から端まで細く通っている**。表示項目は最小でよいが、**検索結果と詳細レスポンスが実際にキャッシュされている** こと（`E-3`。キャッシュキーの形を実物で確定させるため、抽象だけ作って未適用にしない）。

`US-1` / `US-6` / `US-9` / `US-11` / `US-16` / `US-17` / `US-20`
`E-1` / `E-2` / `E-3` / `E-4` / `E-5` / `E-6` / `E-7` / `E-8` / `E-9` / `E-11` / `E-12`

🔴 **このスライスの目的は動くデモではなく、「後から変えると全体を書き換える境界」を先に固定すること**（`D-9`）— URL 設計・ロケールのルーティング・キャッシュキー・データアクセス層の位置・配色。

## 5. スプリント単位への分割（操作してレビューできる増分）

### 5.1. なぜこの節が必要か

§4 のリリーススライスは **粒度が粗すぎてスプリントの単位にならない**（特に `S-1` は `AC-2`〜`AC-11` をまとめて満たす 1 塊で、1 セッション = 1 スプリントの運用に載らない）。また §3 の横断イネイブラーは技術単位で並んでいるため、そのまま着手すると **「動くものが増えないスプリント」** が生まれる。

そこで本節は、スライスを **スプリント（`SP-n`）へ縦に割り直す**。分割の基準はただ 1 つ。

> 🔴 **スプリント終了時に、ユーザーが実際に触って「前より何が変わったか」を確認できること。**

### 5.2. スプリントが「レビュー可能」であるための 4 条件

新しいスプリントを切るとき、以下を **すべて** 満たすこと。1 つでも欠けたら割り方が間違っている。

| # | 条件 | 満たさない例 |
|---|---|---|
| **C-1** | **操作して確かめられる振る舞いが変わる**（できることが増える / 速度・API 消費・失敗時の挙動が変わる、のいずれか） | 「型定義を整備する」だけのスプリント — 触っても何も変わらない |
| **C-2** | 🔴 **デモ手順が 5 行以内で書ける**（何を開き、何を入力し、何が見えれば成功か） | 「レート制限対策を実装する」— どう操作すれば確認できるかが書けない |
| **C-3** | **前スプリントの経路を壊さない**（回帰はテストで検知できる状態にある） | テスト基盤がないまま機能だけ積む |
| **C-4** | **単独で `sp:8` 以内に収まる**（超えるなら分割する・`session-sprint-rules.md` §3） | 「MVP を完成させる」 |

🔴 **`C-2` が実質的なゲートである。** イネイブラー（`E-n`）だけで構成されたスプリントを作ってよいのは、**`C-2` を満たせる場合に限る**（例: キャッシュは「同じ検索を 2 回実行してレート残量が減らないこと」で確認できる／テスト基盤は「コマンド 1 つでテストが通ること」で確認できる）。`C-2` を書けないイネイブラーは **単独スプリントにせず、それが観測可能になる機能スプリントへ同梱する**。

🔴 **デモ手順に他スプリントの成果物を前提として書かない。** 書いてしまうと、そのスプリント単独では完了判定ができなくなる（§5.5 の依存関係を必ず確認する）。

### 5.5. 順序の制約（入れ替えてよい範囲）

```
SP-1 → SP-2 → SP-3 → SP-4 → SP-5   ← S-0。この順序は固定
                                  ↓
        SP-6 ─┐
        SP-7 ─┼→（自由に入れ替え可）
       SP-10 ─┘
        SP-8 → SP-9                ← 🔴 この依存だけは固定
                                  ↓
                               SP-11（最後）
```

| 制約 | 理由 |
|---|---|
| 🔴 **`SP-1`〜`SP-5` の順序は固定** | 骨格が通り、境界が確定し、回帰を検知できる状態になるまで機能を積まない |
| 🔴 **`SP-8` は `SP-9` より前** | `US-25`（レート制限時のログイン導線）の確認にログイン機能が要る |
| 🔴 **`SP-11` は最後** | 受け入れ基準 11 項目の通し確認を行うため |
| 🔵 **`SP-6` / `SP-7` / `SP-10` は自由に入れ替えてよい** | 相互に依存しない |
| ⚠️ **`SP-10`（アクセシビリティ）を最後に回さない** | 後から直すと全画面のマークアップに波及する（`NFR-13` の配色を `SP-2` に置いたのと同じ理由） |

## 7. 本書の使い方（運用ルール）

> 🔴 **スプリントの回し方（TDD・プレビュー URL・確認の発火ライン・ドキュメント参照順）の正本は [`sprint-development-rules.md`](../rules/sprint-development-rules.md)**（`SD-1`〜`SD-4`）。本節は本書の使い方に限る。

1. **実装着手時**: 🔴 **着手単位は §5 の `SP-n`**（スライス `S-n` ではない）。スプリント 1 本を 1 セッションで回し、Issue には **`SP-n` / `US-n` / `E-n` と参照要件 ID を書き、受け入れ条件は `AC-n` を参照する**（本文へコピーしない）
2. **スプリント完了時**: §5 の該当スプリントの **「操作レビュー」手順を、PR に貼ったプレビュー URL 上で上から実際になぞる**（`SD-1`）。なぞれない項目が 1 つでもあればそのスプリントは **未完了** とする（コードが書けたことを完了条件にしない）
3. **操作レビュー手順は E2E テストに写す**（`SD-2`）。手順を増やしたら E2E も増やす。手動確認と自動テストを一致させておくことで、以降のスプリントで壊れたときに自動で気づける
4. **スプリントを新しく切るとき**: §5.2 の 4 条件（`C-1`〜`C-4`）をすべて満たすか確認する。**イネイブラーだけのスプリントを作らない**
5. **スコープ調整時**: 削るのは S-2 から。🔴 **S-0 / S-1 は削らない**（`prd.md` §0.3）
6. **要件が変わったとき**: 先に `prd.md` を更新し、次に本書の参照を合わせる。**逆順にしない**（正本が後追いになると ID の意味が壊れる）
7. **新しいストーリーを足すとき**: 既存 ID を詰めず、末尾に新しい番号を振る
8. **期日が確定したとき**: 本書の **スプリント（`SP-n`）** を日付へ射影し、**ロードマップを別途起こす**（本書は時間軸を持たない）
