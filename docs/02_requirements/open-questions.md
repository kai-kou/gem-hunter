## 2. 決定が必要な論点（`D-n`・ユーザー判断）

> 私（Claude）が仮定で決めると成果物が根本から変わってしまうもの。**`D-1` が全体の分岐点** で、他はそれに従属する。

### D-1【最重要】どの製品の要件定義書を書くのか

既存ドキュメントは **3 つの異なる製品** を指している。

| 候補 | 出典 | 内容 | 主要リスク |
|---|---|---|---|
| **(a) 検索 Web アプリ（素朴版）** | `minimum-requirements.md` | キーワード検索 → 一覧 → 詳細ページ。認証・DB・スコアリングなし | 差別化がない（GitHub 純正で足りる）。ただし確実に完成する |
| **(b) IndieGems（B2C ディスカバリー）** | `initial-concept.md` | Gem Score・目的別タグ・週刊ダイジェスト・Pro 課金 | データ基盤（ETL・永続化・スコア計算）が必須で MVP 規模を大きく超える |
| **(c) エージェント向けライブラリ選定 API / MCP** | `competitive-analysis.md` の Recommendations | 意図ベース検索 + 信頼シグナル（Scorecard / deps.dev / Socket）でリランクして MCP で返す | UI を持たない B2D 製品。コンセプトの B2C 像とペルソナが別物になる |

**推奨**: (a) を **Phase 1 の確定スコープ** として要件定義書を書き、(b)/(c) は「将来拡張として要件定義書の付録に方向性だけ書く」。理由は、(a) が唯一「完成」を定義できるスコープであり、(b)(c) はどちらもデータ基盤の設計判断（`D-5`）を先に固めないと要件が書けないため。

> ⚠️ これは「(b)(c) を諦める」という意味ではなく、**1 つの要件定義書に 3 製品を混ぜない** という提案。

### D-2 `minimum-requirements.md` は「不変の与件」か「自分たちの暫定案」か

同ドキュメントは、受け入れ基準チェックリスト形式・「Star 数 / Watcher 数 / Fork 数 / Issue 数」の表示項目指定・「開発に AI を利用した場合はその利用方法と範囲を README に記載」といった記述から、**外部から与えられた課題仕様（技術選考課題等）の体裁** を持っている。

- **(a) 外部与件（変更不可）** の場合 → 要件定義書は「与件を満たすことを保証する構造」で書き、独自要件は与件を侵さない追加分としてのみ足す。受け入れ基準はそのままトレーサビリティ表になる。
- **(b) 自分たちの暫定案（変更可）** の場合 → コンセプト・競合調査の知見を反映して要件そのものを組み替えられる。

**この違いで要件定義書の書き方が根本から変わる** ため、最初に確定させたい。

### D-3 事業目的（何のために作るか）

- ポートフォリオ / 学習 / 選考課題 → 「完成度と説明可能性」が最優先。運用コスト・法務リスクは軽視してよい。
- 実際に公開して収益化する → GitHub の利用規約・スクレイピング可否（`R-8`）、運用コスト（`R-6`）、継続的な鮮度維持が要件に入る。

**推奨**: 現時点では前者を前提に要件を書き、後者に必要な項目は「Phase 3 の前提条件」として分離しておく。

### D-4 ターゲットと UI 言語

コンセプトの GTM は Product Hunt / X での世界展開（＝英語圏）だが、既存ドキュメントは全て日本語。UI を日本語にするか英語にするか、i18n を要件に含めるかが未定。

**推奨**: MVP は **UI 英語・ドキュメント日本語**（対象が世界中の OSS 開発者であり、i18n 基盤は MVP では持たない）。

### D-5 データアーキテクチャ（GitHub API 直参照 か 自前 ETL + DB か）

これは (b)(c) を目指す場合の **最大の技術的分岐**。

| 方式 | 実現できること | 制約 |
|---|---|---|
| **GitHub Search API 直参照**（`minimum-requirements.md` の前提） | キーワード検索・詳細表示 | 1 クエリ最大 1000 件・検索 30 req/分（認証時）・「dependents 数」「コミット密度」等は取得不可 |
| **GH Archive / BigQuery でバッチ ETL + 自前 DB** | Gem Score・活性度の時系列・偽 star 検出・目的別タグ | BigQuery $5/TB スキャン、DB 運用、鮮度維持の継続コスト。MVP 要件の「DB なし」と両立しない |

**Gem Score・活性度予測・依存数ランキングは、GitHub Search API 単体では原理的に実装できない**（`competitive-analysis.md` §3 の制約と一致）。この事実を要件定義書に明記した上で、Phase 境界をどこに引くかを決める必要がある。

**推奨**: Phase 1 は API 直参照、Phase 2 で ETL 導入。ただし Phase 1 の段階で「API 呼び出しを 1 箇所に隔離する（データアクセス層の分離）」を非機能要件に入れ、Phase 2 の差し替えコストを下げる。

### D-6 GitHub API の認証方式

| 方式 | レート制限 | 適性 |
|---|---|---|
| 未認証 | 60 req/h（検索 10 req/分） | 実質不可。デモですら詰まる |
| Fine-grained PAT（サーバー側で保持） | 5,000 req/h（検索 30 req/分） | **MVP に最適** |
| GitHub App | インストール単位で枠を確保 | 一般公開・多ユーザー運用時に必要 |

**推奨**: MVP は **サーバーサイド保持の Fine-grained PAT**（`minimum-requirements.md` §4.1 の「秘匿情報をクライアントへ露出させない」と整合）。GitHub App は D-3 が「実運用・収益化」の場合のみ Phase 2 以降で検討。

### D-7 デプロイ先

`nextjs16-architecture-research.md` は Vercel と AWS/GCP 等を両論併記のまま。Cache Components / ISR / Image Optimization の挙動と運用コストがここで変わる。

**推奨**: **Vercel**（Next.js 16 の機能を追加設定なしで使え、MVP 規模なら無料枠で収まる）。

### D-8 要件定義書の体裁と粒度

| 候補 | 向いている場面 |
|---|---|

**推奨**: **PRD（§1〜3）+ SRS 風の機能要件表（§4 以降）のハイブリッド**。既存 `minimum-requirements.md` の FR-ID 体系をそのまま引き継ぎ、上位にプロダクト文脈を足す形にする（既存資産を捨てずに済む）。

## 3. 不明瞭・矛盾している点（`Q-n`・要明確化）

> ユーザー判断が要るとは限らないが、**放置すると要件定義書が自己矛盾する** 箇所。

### Q-1【重大】コンセプトのコア機能を、自プロジェクトの競合調査が否定している

`initial-concept.md` のコア機能「マイクロ・スイートスポット検索（star 数 10〜500 に限定）」に対し、`competitive-analysis.md` は次の 2 点を報告している。

1. **star は品質シグナルとして崩壊している**: 約 600 万個の偽 star が検出され（He et al., ICSE 2026）、2024 年 7 月ピーク時は 50 star 超リポジトリの 16.66% が偽 star 活動に関与。同調査の「やめるべきこと」に **「star 単純ランキング（差別化不能）」** が明記されている。
2. **star レンジ絞り込みは GitHub 純正で 1 行で書ける**: 検索構文 `stars:10..500` で同等のフィルタが可能。**「star レンジで絞る」こと自体は差別化にならない。**

→ **「Hidden Gem とは何か」を star 以外の観測可能な指標で再定義しない限り、プロダクトの存在理由が成立しない。** 要件定義の前に決着が必要。

### Q-2 「Hidden Gem」の操作的定義が存在しない

コンセプトは「過小評価された名作」と述べるが、機械的に判定できる定義がない。候補となる指標と、その入手可否は以下。

| 候補指標 | 入手元 | GitHub Search API 単体で取得可能か |
|---|---|---|
| 被依存数（dependents） | deps.dev / Ecosyste.ms / Libraries.io | **不可**（外部 API 必須） |
| コミット密度・最終更新 | GitHub API / GH Archive | 一部可（`pushed_at` のみ） |
| Issue クローズ率・応答時間 | GitHub API（追加リクエスト）/ GH Archive | 一部可（コスト大） |
| README の構造品質 | Contents API + 解析 | 可（ただし解析ロジックは自作） |
| セキュリティ健全性 | OpenSSF Scorecard API | **不可**（外部 API 必須） |
| star 増加率 | GH Archive（時系列が必要） | **不可**（スナップショットのみ） |

→ 「注目度（star）に対して実利用（被依存数）が不釣り合いに大きいものが Gem」という定義は筋が良いが、**被依存数が GitHub API から取れない** ため、`D-5` の判断と不可分。

### Q-3 Gem Score が式レベルで未定義

`initial-concept.md` §3.3 は 3 つの構成要素（Maintenance / Doc Quality / Dependency Signal）を挙げるのみで、重み・正規化方法・スコアレンジ・再計算頻度・欠損値の扱いが未定。**このままではテスト可能な受け入れ条件が書けない。**

### Q-4 「目的別タグ付け（#決済 #CLI軽量化）」の生成方法が未定

人手キュレーション / GitHub topics の流用 / LLM による自動分類 のいずれかで、コスト・精度・鮮度・要件の複雑度がまったく変わる。タグ体系（オントロジー）の管理主体も未定。

### Q-5 MVP 要件とコンセプトの「対象外」範囲が食い違う

`minimum-requirements.md` §1.2 は、認証・お気に入り・独自スコアリング・通知・課金を **すべて対象外** としている。これは `initial-concept.md` の Pro 機能（アラート・お気に入り・分析レポート）と週刊ダイジェストを丸ごと外すことを意味する。「MVP で意図的に落とした」のか「別製品として書かれた」のかが不明。

### Q-6 技術リサーチ 2 本の適用範囲が MVP と乖離している

`github-api-research.md` の結論は「GitHub をイベントソースとするアプリを作れ（GitHub App + Webhook 中心）」だが、MVP は **他人の公開リポジトリを検索するだけで、Webhook を受ける対象リポジトリが存在しない**。同様に GraphQL / Octokit / Queue / ETag の各章も MVP には過剰。**どの章を採用し、どの章を将来用として棚上げするかの仕分けが未了**（`nextjs16-...md` にある「本プロジェクトへの適用メモ」に相当する表が、GitHub API 側には存在しない）。

### Q-7 非機能要件が定性的で検証できない

`minimum-requirements.md` §4 は「不要な再取得を避ける」「見やすさ・操作しやすさ」等の定性表現に留まる。数値目標（LCP / INP の予算、検索応答の目標時間、レート制限到達時の具体的挙動、同時利用者数の想定）が未定のため、**受け入れ判定ができない**。

### Q-8 アクセシビリティの達成基準レベルが未定

「キーボード操作可能」「代替テキスト付与」とあるが、WCAG のどのレベル（A / AA）を満たすのかが未定義。テスト要件（axe 等の自動チェックを CI に入れるか）にも未接続。

### Q-9 エラー種別の切り分け要件が実装可能性と未照合

§3.2 は「通信失敗・API エラー・レート制限超過を区別して伝える」と要求するが、GitHub API のレート制限は **403 と 429 の両方で返り、`x-ratelimit-remaining` / `retry-after` ヘッダの読み取りが必要**。二次レート制限（secondary rate limit）は別扱いになる。要件として書くなら、この判別ロジックを仕様に落とす必要がある。

### Q-10 詳細ページの取得方式が未定義

FR-4 の表示項目（Watcher 数など）は `GET /search/repositories` の結果にも含まれるが、詳細ページを **URL 直打ちで開ける**（FR-5）ためには `GET /repos/{owner}/{repo}` を個別に呼ぶ必要がある。検索結果からの遷移時にデータを引き回すのか毎回取得するのかで、キャッシュ設計とレート消費が変わる。

> 補足: GitHub の `watchers_count` は実際には star 数と同値を返し、真の Watcher 数は `subscribers_count` である（REST API の既知の仕様）。要件で「Watcher 数」と書く場合、どちらを指すかの明記が必要。

### Q-11 プロジェクトミッション（`docs/project-mission.md`）が未記入

CP-5 の実体が空のため、判断に迷ったときの優先順位・KPI・品質ゲートが存在しない。要件定義書の「成功指標」節と表裏一体なので、同時に埋めるべき。

### Q-12 リポジトリ名（`gem-hunter`）とプロダクト名（`IndieGems`）が不一致

READMEでは両方併記されているが、正式名称が未確定。ドメイン取得可否も未調査。

### R-2: GitHub 純正検索での代替可能性（実測）

`mcp__github__search_repositories` で以下のクエリを実行した。

```
pdf parser language:python stars:10..500 pushed:>2026-05-01 archived:false
```

**結果: `total_count = 31`。** 「Python の PDF パーサで、star 10〜500、直近 3 ヶ月以内に更新、アーカイブ済みでない」という条件が、**このドメインでは GitHub 純正検索の 1 クエリで完全に再現できた**（上位は py-pdf-parser 426★ 等、いずれも妥当な候補）。

> ⚠️ **サンプル数 n=1・要追試**。実行したのは 1 ドメインのみで母数も 31 件と小さい。言語・分野を変えた 3〜5 ドメインでの追試を `R-2` の残タスクとする。ただし後述の Hidden Gem 定義の主要根拠は「被依存数が GitHub API に存在しない」という **API 仕様側の事実** であり、本サンプル数とは独立に成立する。

### Q-1 / Q-2 の推奨解: 「Gem = 実利用に対する注目度の不足（残差）」

上記 3 点から、Hidden Gem の操作的定義として以下を推奨する。

> **Gem とは、「実際に使われている度合い（被依存数）」に対して「注目度（star 数）」が不釣り合いに小さいリポジトリである。**
>
> `Gem Index = 実利用シグナルの順位 − 注目度シグナルの順位`（または対数回帰の残差）

この定義を推す根拠は以下の 4 点。

1. **star 単純ランキングを回避できる**（`competitive-analysis.md` の「やめるべきこと」に抵触しない）。star は分子ではなく **分母** として使う。
2. **GitHub 純正検索で原理的に再現できない**（被依存数は GitHub API に存在しない）。`R-2` で判明した差別化の欠如を、**唯一直接的に解決する軸**。
3. **`criticality_score` の再実装にならない**。criticality は「重要度の絶対値」、Gem Index は「重要度に対する注目度の不足＝残差」。**既存に同等品が見当たらない**。むしろ criticality_score を実利用シグナルの入力としてそのまま利用できる。
4. **偽 star に対して構造的に頑健**。star を水増しすると Gem Index は **下がる**（＝ランキングから外れる）ため、`competitive-analysis.md` が指摘した偽 star 問題が攻撃面にならない。

**この定義から導かれる要件上の制約（重要）**:

- 被依存数はパッケージレジストリ単位でしか取得できないため、**Phase 2 の対象は「パッケージとして公開されているリポジトリ」に限定される**（アプリ・設定集・学習用リポジトリは対象外になる）。これは同時に、`initial-concept.md` が排除したがっていたノイズ（チュートリアル・課題提出用リポジトリ）を **自動的に除外できる** という利点でもある。
- 対象エコシステムの選定（npm / PyPI / crates.io / Go 等のどれから始めるか）が新たな決定事項になる（→ `D-10` として追加）。
- **Phase 1（検索 Web アプリ）はこの定義を実装しない**。与件（`D-2`）のスコープを侵さず、Phase 2 の中核として設計する。

### D-10（追加）Phase 2 の対象エコシステム

**推奨**: **npm と PyPI の 2 つから開始**（Ecosyste.ms のカバレッジが厚く、`initial-concept.md` のペルソナ＝個人開発者の利用言語と一致するため）。

- 積み上げ側の各項目に **「入れると何が良くなるか / 落とすと何を失うか」を 1 行** 添える（期日が見えた時点で切る判断ができるように）。
- 🔴 **「積み上げていける状態」は要件そのものになる**。以下を `P1-MVP` に含める（後から入れると既存コードの書き換えが発生し、積み上げ速度がそこで落ちるため）:
  - **データアクセス層の分離**（`D-5` の推奨と同一。API 呼び出しを 1 箇所に隔離し、Phase 2 の ETL 差し替え時に UI 層を触らない）
  - **テストと CI の土台**（回帰を検知できない状態で機能を積むと、積むほど壊れる。与件 §5 のテスト要件がそのまま土台になる）
  - **型定義と Lint / フォーマッタ**（与件 §4.4 に既にある）
  - **後付けコストが高い構造の先行確保**: ルーティング設計（locale セグメント含む・`D-4`）とキャッシュ境界。これらは後から変えると全 URL / 全データ取得箇所に波及する
- 逆に **後からいくらでも足せるもの**（表示項目の追加・フィルタ UI・ソート順・Gem Index）は MVP に入れない。

### D-4 の決定から従属的に確定する事項

- **ロケールを URL に含める**（`/[locale]/...`）。与件 §4.3 の「検索条件（キーワード・ページ）を URL に反映する」と同じ URL 設計上で解決するため、**ルーティング設計を実装の最初に確定させる**（後から locale セグメントを足すと既存 URL がすべて変わり、共有リンクも壊れる）。
- **MVP で入れるのはロケール基盤まで**: ルーティング・ロケール検出・メッセージカタログの仕組み・UI 文言のハードコード禁止（すべてカタログ経由）。**日本語カタログの完成度は積み上げフェーズで上げる**。
- **翻訳対象は自前の UI 文言のみ**。GitHub 由来のデータ（リポジトリ説明文・topics・言語名）は翻訳せず原文表示とする（機械翻訳は正確性を損ない、`D-3` の「説明可能性」に反する）。
- **テスト要件への影響**: 主要フローの E2E は **既定ロケール 1 つで実行** し、ロケール切替そのものを独立したテストケースとして 1 本持つ（全フローを 2 ロケール分回すとテスト時間が倍になり、積み上げ速度を落とす）。
- ライブラリは `next-intl` を第一候補とするが、Next.js 16 App Router での最新の推奨構成を実装着手時に一次確認する（`R-7` に統合）。

### D-5 / D-7 の決定から従属的に確定する事項

**「決めない」を成立させるために、決めておくべきこと**（先送りは無条件では成立しない）:

- 🔴 **キャッシュ抽象（Cache Port）を設ける**。MVP は Next.js のキャッシュ機構（`use cache` / Data Cache）を実装として使い、外部キャッシュ（Upstash Redis 等）へ差し替えられるインターフェースを挟む。
  - ⚠️ **YAGNI の意図的な例外**: CLAUDE.md は「1 箇所しか使わない抽象化を先回りで追加しない」を禁じている。本件は **「インフラを決めない」という決定を成立させるための必要条件** であるため例外とし、その理由を ADR に記録する。ただし **抽象の面積は最小に絞る**（`get` / `set` / `invalidate` + TTL 指定のみ。汎用キャッシュライブラリを自作しない）。
- 🔴 **キャッシュキーの命名規約を先に確定させる**。キー設計は後から変えると全キャッシュが無効化され、外部キャッシュへの移行時にも移植できない。最低限、検索結果（クエリ + ページ + ソート条件）と単一リポジトリ（`owner/repo`）で名前空間を分ける。
- 🔴 **TTL 方針を要件として明記する**。検索結果と詳細情報で更新頻度の要求が異なるため、TTL は 1 つの値に統一せず用途ごとに定める（具体値は `R-5` のレート制限逆算と合わせて実装着手時に決定）。
- **特定 PaaS 固有機能への依存を最小化する**。デプロイ先が未定である以上、Vercel 固有の機能に強く依存すると選択肢を狭める。Next.js 標準機能（App Router / `use cache` / `next/image`）の範囲で組み、それを超える依存が必要になった時点で ADR を起票する。
- **DB は MVP で持たない**（`P2` 送り）。Gem Index（`Q-1`/`Q-2`）はバッチ集計と永続化を要するため、DB の導入判断は Phase 2 の着手時に、そのとき決まっているインフラ前提のもとで行う。
- **環境変数の一覧を要件定義書に持つ**。インフラが後から決まる以上、「何を外部から注入する必要があるか」（GitHub トークン・OAuth クライアント情報・キャッシュ接続情報・ロケール既定値）を先に列挙しておかないと、移行時に漏れる。

### D-6 の決定から従属的に確定する事項

**根拠となる実測値**（GitHub 公式ドキュメントで確認済み・2026-08-17）:

| 枠 | 認証済み | 未認証 |
|---|---|---|
| 検索 API | **30 req/分** | 10 req/分 |
| Core API（詳細取得） | 5,000 req/h | 60 req/h |
| 二次制限 | 100 並行リクエスト / 900 ポイント毎分 / 直列実行を推奨 | 同左 |

- **304 が返る条件付きリクエストは primary rate limit を消費しない**（公式明記）。ただし検索結果は変動しやすく 304 になりにくいため、**ETag が効くのは詳細取得側**。
- 律速は **検索の 30 req/分**（単一 PAT ではこれがアプリ全体の上限）。詳細取得（5,000 req/h）は実質ボトルネックにならない。

**ログイン設計**:

- 🔴 **ログインは完全に任意で、機能差を作らない**。ログインで変わるのは **レート枠だけ**（未ログイン = アプリ共有枠、ログイン = 各自の 30 req/分）。「ログインしないと使えない機能」を作った瞬間、`D-6` の目的（不特定多数が気軽に使える）が壊れる。
- 🔴 **OAuth スコープは要求しない（no scope）**。公開リポジトリの検索・閲覧しか行わないため、追加権限は不要。「最小権限」を実証できる設計判断として ADR に残す。
- 🔴 **セッションは暗号化した httpOnly Cookie で持つ**（`D-5` で DB を持たないため）。ユーザーの OAuth トークンを **クライアントへ露出させない**（与件 §4.1 と同じ原則をユーザートークンにも適用する）。
- **CSRF 対策として OAuth の `state` パラメータを必須にする**。ログアウト（Cookie 破棄）も要件に含める。
- **OAuth の callback URL はデプロイ先に依存する** ため、`D-5`/`D-7`（インフラ未定）と直結する。**必ず環境変数化** し、ホスティング先が決まっていなくても構成が壊れないようにする。

**与件との整合（明示的に説明する）**:

- 与件 §1.2 は認証を「対象外」としているが、これは「実装しなくてよい」であって禁止ではないと解釈し、**レート枠という技術的必然を根拠に上乗せする**（`D-2` の「上乗せは自由」に沿う）。
- ただし **解釈を書き残さないと「要件を読んでいない」と誤読されうる** ため、README と要件定義書の双方に「与件では対象外だが、なぜ入れたか」を明記することを完了条件に含める。
- **認証を入れても、与件が対象外とした他の項目（お気に入り・通知・課金・独自スコアリング）は MVP に入れない**。ログインを足したことを口実にスコープを広げない。

**キャッシュ・レート対策の要件化**（`D-5` の Cache Port 上に実装する）:

- 同一クエリのキャッシュ、同時同一クエリの request coalescing、GitHub API 呼び出しの直列化、詳細取得での ETag 利用、`x-ratelimit-remaining` 監視による degraded 表示（キャッシュのみ返す / 混雑を明示）。
- 🔴 **複数トークンのローテーションは採用しない**（レート制限の回避とみなされる恐れがあるため）。この判断も ADR に残す。

**テスト要件への影響**: OAuth フローは外部依存のためモック化する（与件 §5「外部 API はモック化」と同じ扱い）。未ログイン / ログイン済みの両方で主要フローが成立することを検証対象に含める。

### D-5 追補（DB レス原則）の決定から従属的に確定する事項

- ✅ **`D-6` と矛盾しない**。暗号化 httpOnly Cookie によるステートレスセッションは、まさに「サーバー側ストアを持たない」ための定石であり、本原則を **強化する** 方向にある（セッションストアを立てる選択肢が消える）。
- **状態の置き場所を要件として明示する**:

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 検索キーワード・ページ・ソート | **URL**（`searchParams`） | 与件 §4.3 の「リロード・共有で同じ結果」を満たす |
| ロケール | **URL のパスセグメント**（`D-4`） | 共有時に言語が保たれる |
| ログインセッション（OAuth トークン） | **暗号化 httpOnly Cookie** | サーバー側ストア不要。クライアント JS からは読めない |
| UI 設定・検索履歴・お気に入り | **`localStorage`** | サーバー不要で実現できる。端末ローカルで完結 |
| API レスポンス | **キャッシュ層（Cache Port）** | 永続ストアではなく破棄可能なキャッシュとして扱う |

- 🔵 **副次的な発見**: 与件 §1.2 が対象外とした「お気に入り・プライベートリスト管理」は、**`localStorage` なら DB なしで実現できる**。積み上げバックログの有力候補として要件定義書に記録する（`P1-積み上げ`）。
- 🔵 **Phase 2 の Gem Index も DB レスで貫ける可能性がある**: バッチで事前計算した結果を **静的データ（JSON 等）として配信** すれば、クエリ時に DB を必要としない。「対象を上位 N 件に絞る」前提と相性が良い。**Phase 2 の第一候補案として要件定義書に記録し、DB 導入は最後の手段とする**。
- ⚠️ **受け入れる制約を明記する**（後から「できない」と言わないため）: 端末間で同期されない / ブラウザのデータ削除で消える / `localStorage` の容量上限（数 MB 程度）。これらを許容する旨を要件に書き、同期が必要になった時点で初めて DB を検討する。
- 🔵 **副次効果**: サーバーに個人データを保持しないため、プライバシー・データ保護上の考慮が最小化される。これも説明可能な設計判断として ADR に残す。

### D-8 の決定から従属的に確定する事項

**要件定義書が正本として持つもの**: 要件 ID・要件内容・受け入れ条件（主要フローは Given/When/Then）・優先度ラベル・要件間の依存関係・スコープ境界。

**派生ドキュメントとの責務境界**（同じ事実を 2 箇所に書かず、必ず ID 参照で結ぶ）:

| ドキュメント | そこが正本として持つ情報 | 要件定義書との関係 |
|---|---|---|
| **要件定義書**（本体） | 要件 ID / 内容 / 受け入れ条件 / 優先度 / 依存関係 | **正本**。他はここを参照する |
| リーンキャンバス | 課題・価値提案・顧客セグメント・主要指標（事業仮説） | 要件定義書の「目的・ペルソナ・成功指標」節は **ここを要約参照** する |
| インセプションデッキ | やらないことリスト・トレードオフスライダー・リスク・エレベーターピッチ | 要件定義書の「スコープ外」節は **ここを参照** する |
| ユーザーストーリー | 実装単位への分解（1 要件 → 1〜n ストーリー） | **必ず要件 ID を参照する。受け入れ条件を再掲しない**（重複するとドリフトする） |
| ロードマップ | 時間軸・リリース単位 | 要件定義書の優先度ラベルを時間軸へ射影したもの |
| ADR | 技術的意思決定の理由と却下案 | 要件定義書からは ADR 番号を参照するだけにする |

**ID 体系の規約**（正本である以上、ID の安定性が最重要）:

- `FR-n`: 与件由来の機能要件（`minimum-requirements.md` の番号を **そのまま引き継ぐ**）
- `NFR-n`: 非機能要件
- `GR-n`: Gem 系の上乗せ要件（Phase 2 中心）
- `AC-n`: 与件の受け入れ基準 11 項目（トレーサビリティ用）
- 🔴 **一度振った ID は変更・再利用しない**（欠番が出ても詰めない）。派生ドキュメントからの参照が壊れるため。
- 各要件に **`P1-MVP` / `P1-積み上げ` / `P2`** の優先度ラベルを付ける（`D-9`）。

**ドキュメント作成順の推奨**: 要件定義書（正本）→ インセプションデッキ（やらないことの明文化）→ ユーザーストーリー（実装単位）→ ロードマップ（時間軸）。リーンキャンバスは要件定義書の前後どちらでもよいが、`initial-concept.md` と `competitive-analysis.md` から抽出できるため **要件定義書と並行** で作れる。

### Q-8 の決定から従属的に確定する事項

- 🔵 **与件 FR-7 の選択に答えが出る**。与件は「ページネーション **または** 無限スクロール」を選択制にしているが、**AA 目標を採るならページネーションが明確に有利**（無限スクロールはキーボード操作・スクリーンリーダー・フォーカス管理・「現在位置」の提示すべてで不利。加えて `D-4` の URL 状態保持とも噛み合う）。**ページネーションを採用し、その理由を ADR に残す**。
- 🔴 **配色はデザイン着手時に確定させる**（コントラスト比 4.5:1）。色を後から変えると全画面に波及するため、`D-4` のルーティングと同様「後付けコストが高い先行確保項目」に含める（`D-9`）。
- **状態表示（与件 §3.2）とアクセシビリティを接続する**: 読み込み中・0 件・エラーは視覚表現だけでなく **`aria-live` で支援技術にも伝える**。与件の「利用者が判別できる」を、支援技術利用者にも適用する。
- **画像（オーナーアイコン）の代替テキスト方針を決める**: リポジトリ名が隣接して読み上げられる文脈では、アイコンは装飾として `alt=""` にする方が冗長にならない。この判断も明文化する。
- **テスト要件に追加**: axe による自動チェックを CI に組み込む（`@axe-core/playwright` 等。実装着手時に構成を確認 → `R-11` に統合）。
- **手動チェックリストを `docs/` に持つ**: キーボードのみでの検索 → 一覧 → 詳細 → 復帰の完走、フォーカスの可視性と順序、見出し階層とランドマーク、200% 拡大時の破綻有無。

### Q-7 の決定から従属的に確定する事項

**採用する数値目標**:

| 指標 | 目標値 | 根拠 |
|---|---|---|
| LCP | 2.5 秒以下 | Google が定める Core Web Vitals の "good" 境界（外部基準の引用） |
| INP | 200ms 以下 | 同上 |
| CLS | 0.1 以下 | 同上 |
| Lighthouse Accessibility | **100**（ゲート） | axe ベースで決定論的に判定されるため、閾値化しても揺れない |
| Lighthouse Performance | **90 以上**（ゲート） | 下記の安定化条件とセットで運用する |
| キャッシュ TTL | 検索結果と詳細で別値（**暫定**: 検索は分オーダー / 詳細は時間オーダー） | 具体値は `R-5`（レート枠の逆算）と合わせて実装着手時に確定する |

🔴 **CI ゲートの偽陽性対策**（これを付けずにゲート化すると、`D-9` の「積み上げ速度」を落とす）:

- **本番相当のビルドに対して計測する**（開発サーバーでは測らない）。
- **複数回実行の中央値を採る**（Lighthouse CI の複数実行機能を使う）。単発の実行結果でゲートしない。
- **CPU / ネットワークのスロットリング設定を固定する**（実行環境差を減らす）。
- **Accessibility と Performance を同じ厳しさで扱わない**。Accessibility は決定論的なので満点ゲート、Performance は 90 のゲートに留め、**しきい値近傍の揺れで頻繁に落ちるようなら warn 運用へ落とす**（この判断基準もあらかじめ要件に書いておく）。
- **静的指標（バンドルサイズ）を併用する**。Lighthouse の揺れに左右されない補助指標として、初期 JS バンドルサイズの推移を CI で可視化する（ゲート化は必須としない）。
- ⚠️ **サーキットブレーカー**: Lighthouse ゲートが原因で実装が 2 回以上ブロックされたら、ゲートの設定自体を見直す（ゲートを守ることが目的化しないように、この撤退条件を要件に明記する）。

### D-10 の決定から従属的に確定する事項

- **エコシステムは設定値として扱う**（コードに npm / PyPI を直書きしない）。追加が「対象リストへの追記 + バッチ再実行」で済む構造にする。
- 🔴 **名前解決（リポジトリ URL ↔ パッケージ名）が Phase 2 の中核課題**。1 リポジトリが複数パッケージを公開する（モノレポ）、パッケージのリポジトリ URL が未設定・古い、といったケースの扱いを構想段階で明記する。**ここを甘く見ると Gem Index の分母が壊れる**。
- **エコシステムをまたいだ順位の比較可否を決める必要がある**。npm と PyPI では被依存数の絶対値のスケールが異なるため、**順位はエコシステム内で正規化してから統合する**（`Q-3` の正規化方法と直結）。
- 静的データ配信案（`D-5` 追補）の実現可能性は **上位何件を配信するかで決まる**。件数は Phase 2 着手時に、実データのサイズを測ってから決定する。

### Q-3 の決定から従属的に確定する事項

- 🔵 **スコアをそのまま UI に出さず、パーセンタイルを言葉で提示する**。「Gem Score 73 点」より **「被依存数では上位 5%、star では下位 40%」** の方が、根拠が読み手に伝わる。パーセンタイル方式を採った利点をそのまま UI に活かす（`D-3` の説明可能性と整合）。
- **`D-10` のスケール差問題が同時に解ける**。パーセンタイル化はエコシステム内で閉じるため、npm と PyPI の絶対値の違いが指標に混入しない。
- **母集団の定義を要件に明記する**（パーセンタイルは母集団が変われば値が変わるため）。「どの範囲のリポジトリを 100% とするか」を決めずにパーセンタイルを出すと、数値の意味が定義できない。
- **決めきらない事項を明示する**（実データ待ち）: 母集団のサイズ、Gem と見なす差のしきい値、健全性フィルタの足切り基準、被依存数ゼロ・欠損の扱い。要件定義書には **「実データで決定する」と明記** し、決めたつもりにしない。
- **偽 star 耐性の根拠を書き添える**: star のパーセンタイルが上がると Gem Index は下がるため、star の水増しはランキングから外れる方向に働く（`competitive-analysis.md` の偽 star 問題への構造的な回答）。

### Q-4 の決定から従属的に確定する事項

- ⚠️ **差別化軸は Gem Index 1 本に集約される**。topics 単体は GitHub 純正検索の `topic:` 修飾子で代替できるため、それ自体は差別化にならない（`R-2` と同じ構図）。**価値は「topics で絞る × Gem Index で並べる」の組み合わせにあり、この点を要件定義書に明記する**（純正検索は Gem Index を持たないため、この組み合わせは再現できない）。
- 🔵 **topics は追加コストなしで使える**。GitHub の検索・詳細レスポンスに既に含まれるため、追加リクエストが発生しない。**Phase 1 の一覧カード・詳細ページに表示する案は `P1-積み上げ` の有力候補**（`D-9`）。
- **表記揺れの正規化は最小限に留める**（`cli` / `command-line` / `command-line-tool` 等）。シノニム辞書は人手メンテになるため、**上位の頻出タグに限って手当てし、網羅を目指さない**。網羅しようとした時点で「人手キュレーション」に戻ってしまう。
- 🔴 **スコープ外を明記する**: `initial-concept.md` の「#決済 #CLI軽量化」のような **独自語彙・日本語の目的タグは提供しない**。コンセプトからの意図的な後退であり、その理由（自前タグ体系の維持コストが運用継続と両立しない）をインセプションデッキの「やらないことリスト」に記録する。
- **topics が付いていないリポジトリの扱い** を要件に含める（付与率は高くない）。タグで絞り込めない対象が一定数残ることを前提に、キーワード検索との併用を保証する。

### Q-5 の決定から従属的に確定する事項（コンセプト機能の再配置）

`D-3` で収益化しないと決めたため、「無料 / Pro」という区分自体が消える。`initial-concept.md` の Pro 機能は以下へ再配置する。

| コンセプトの機能 | 再配置先 | 理由 |
|---|---|---|
| お気に入り・プライベートリスト | **`P1-積み上げ`** | `localStorage` で DB なしに実現できる（`D-5` 追補）。与件では対象外だが、上乗せ要件として無理なく足せる |
| 詳細なリポジトリ分析レポート | **Phase 2 に吸収** | Gem Index の内訳表示（パーセンタイル提示・`Q-3`）がこれに相当する。独立機能として持たない |
| カスタムアラート（Discord / Slack 通知） | **`P2` かつ条件付き** | 通知には常駐処理か外部サービスが要り、**DB レス原則（`D-5` 追補）と正面から衝突する**。原則を崩す判断をした場合にのみ着手する |
| 週刊ダイジェスト | **`P2` かつ条件付き** | 同上（配信先の管理に永続化が要る）。静的な「今週の Gem 一覧ページ」であれば DB レスで可能なので、**そちらを代替案として記載する** |
| Pro サブスクリプション（課金） | **スコープ外** | `D-3` により目的としない |

### Q-6 の決定から従属的に確定する事項（GitHub API リサーチの適用範囲）

| 区分 | 該当する内容 |
|---|---|
| **Phase 1 で採用** | REST を基本とする / Octokit / Pagination / Rate Limit（一次・二次）/ ETag・条件付きリクエスト / Retry 戦略 / API バージョンの明示 / Secret 管理・最小権限 |
| **Phase 2 で採用** | GraphQL の併用（複数リポジトリのバッチ取得で効く）/ Cache 設計の作り込み |
| **不採用** | GitHub App / Webhooks / Idempotency / Queue / Mutation の作法 / AI Code Review アーキテクチャ |

- **不採用の理由を 1 行で書く**: 本プロダクトは **他人の公開リポジトリを読むだけ** で、監視対象リポジトリもイベント購読関係も存在しない。したがって同リサーチの中心命題「GitHub をイベントソースとするアプリを作れ」は、**本プロダクトの形には当てはまらない**。
- この表は `nextjs16-architecture-research.md` が持つ「本プロジェクトへの適用メモ」と同じ役割を果たす（GitHub API 側には無かったもの）。

### Q-9 の決定から従属的に確定する事項（エラー判別の仕様）

| 判別条件 | 種別 | 利用者への提示 |
|---|---|---|
| fetch 自体が失敗 | ネットワーク到達不可 | 「接続できません」+ 再試行 |
| 403 / 429 かつ `x-ratelimit-remaining: 0` | 一次レート制限 | `x-ratelimit-reset` から復帰時刻を算出して提示 + **ログインで緩和できる案内**（`D-6`） |
| 403 / 429 かつ `retry-after` あり | 二次レート制限 | `retry-after` 秒後に再試行可能と提示 |
| 401 / 403（上記以外） | 認証・権限の問題 | **内部情報を出さず汎用エラー** として扱う（サーバー設定の問題であり利用者は対処できない） |
| 422 | 検索クエリが不正 | 入力の修正を促す |
| 404（詳細ページ） | 対象なし | Not Found 表示（与件 §3.2） |
| 5xx | GitHub 側の障害 | 再試行を提示 |

- 🔵 **レート制限エラーがログイン導線になる**。`D-6`（任意 OAuth）の存在価値が、エラー体験の中で自然に伝わる設計にする。
- 与件 §3.2 の「通信失敗・API エラー・レート制限超過を区別して伝える」は、この表で機械的に判定可能になる。

### Q-10 の決定から従属的に確定する事項

- 🔴 **技術的に単独取得が必須である** ことが確認できた: 与件 FR-4 が求める「Watcher 数」の実体は **`subscribers_count`** であり、**これは検索結果のレスポンスには含まれず `GET /repos/{owner}/{repo}` でのみ得られる**（GitHub 公式ドキュメントで確認済み・2026-08-17）。`watchers_count` / `watchers` は star 数のミラーであり Watcher 数ではない。
- したがって **「検索結果のデータを引き回して詳細を描画する」案は成立しない**。FR-5（URL 直接アクセス可能な独立ページ）とも整合し、経路によって表示内容が変わる問題も起きない。
- **レート影響は軽微**: 詳細取得は Core API（5,000 req/h）で、律速の検索枠（30 req/分）とは別枠。加えて **ETag が効く** ため、304 が返る限り枠を消費しない（`D-6`）。
- **要件定義書には `subscribers_count` を使う旨を明記する**。与件が「Watcher 数」としか書いていないため、**どちらを指すかの解釈を残さないと実装者が誤る**（`watchers_count` を使うと star と同じ数字が 2 つ並ぶ）。
