# project_truth R2: rebuttal / concession

## 1. 争点 D の ADR 選定を 1 本に決着させる

**結論（3 枠を確定する）**: `ADR 0009 + D-33`（Gem Index 撤去）／`ADR 0007`（DB レス）／`ADR 0003`（GitHub App 認証の判断軸）。**dev_audience の ADR 0002・ADR 0005 は不採用ではなく「(g) の 3 枠から (d)/(e) へ配置転換」**という形で両者の指摘を活かす。理由を名指しで裁定する。

### ADR 0009 + D-33 → 全員一致。確定。

### ADR 0002 +「実際に踏んだ罠」→ **(g) ではなく (e) に置く。dev_audience の提案は section 違いとして採用**

dev_audience 自身が R1 §4「ADR 単体というより (e) 技術スタックと合体させて語るのが効果的」と書いており、かつ dev_audience の枚数配分表（R1 §1）では (e) に既に「スタック表 1 + 実際に踏んだ罠 1」の**専用枠が確保済み**。つまりこれは (g) の 3 枠と競合しない別予算である。私が §2 で「候補4は E との重複が大きいため (g) では割愛」と書いたのは、その時点でこの内容の裏取りができていなかったための保留であり、下記§2の裏取り結果を受けて **(e) に確定配置**とする（(g) の 3 枠には数えない）。

### ADR 0005（Cache Port YAGNI 例外）→ **(g) の独立枠にしない。(d) の `W-1〜W-3` に短く合流させる**

内容は精査した（`docs/adr/0005-cache-port-yagni-exception-and-ttl.md` §2.3・§4、本ラウンドで実読）。実測に基づく失敗談（`AsyncLocalStorage` で HIT/MISS を Worker エントリから SSR 内部へ運ぶ案を `wrangler dev --local` + スタブ API で実機検証したが `getStore()` が常に `undefined` で不成立、8 件の却下案）は事実の豊富さで ADR 0009 に匹敵する。**それでも (g) の 3 枠から外す**理由は「持ち帰れるか」の広さで劣後するため: `AsyncLocalStorage` が Workers/OpenNext の内部継続を越えられないという事象は **Cloudflare Workers + OpenNext を触る開発者にしか再現しない、環境固有の罠**であり、0007（DB レス設計）や 0003（認証方式の選定軸）のような「サーバーレス全般／認証設計全般」に効く汎用性を持たない。dev_audience が R1 で自ら「(d) アーキテクチャの `W-1〜W-3` と地続きなので合流させると相乗効果がある」と書いている通り、**(d) の 2 枚のうち 1 枚に「キャッシュ層は実装した上で単体テストの壁にぶつかり撤回した観測手段がある」を 1〜2 行だけ添える**のが正しい重さ。独立スライドにすると (g) が Cloudflare 固有の実装トラブル 2 件（0002 由来のパス罠＋0005 由来のキャッシュ観測罠）に偏り、争点 D の選定基準②「普遍的トレードオフ」から外れる。

## 2. `L-129` / `L-130` の実在確認（dev_audience の「実際に踏んだ罠」の裏取り元）

**実在する。出典を確定する。** `docs/rules/lessons/cloud-environment.md` を本ラウンドで実読した。

- **`L-129`**（201〜227 行目付近・見出し原文「OpenNext Cloudflare のパス処理で踏んだ罠（redirects の path-to-regexp 検証 / 拡張子付きパスの 404・2026-08-19・`SP-2`〜`SP-3`）」）: ① `redirects()` の `destination` に `:path` を含めると **Cloudflare プレビューでのみ**（ローカル `next start` では再現しない）500 になる。原因は OpenNext のルーティング層が `path-to-regexp` の `compile()` を `validate: true` で呼ぶため（Next.js 本体は `validate: false`）。対策は PR #96 で適用済み・回帰テストあり。② 拡張子付きパスの 404 実測表: `/repos/foo/user.github.io` → 307（正常）／`/repos/angular/angular.js` → **404**／`/ja/repos/angular/angular.js` → 200（ロケール付きなら正常）。PR #106 のプレビュー実測。
- **`L-130`**（240〜263 行目付近・見出し原文「本番デプロイ（`wrangler deploy`）は auto mode classifier にブロックされることがある」）: 実測表はブロック 5 回・成功 2 回（内訳・日時・Issue #288/#300 まで記載）。これは私が round 1 で ADR 0002 §「候補4」として引用した内容と完全一致し、二重に裏が取れている。

**結論**: dev_audience の「実際に踏んだ罠」は実在し、しかも両方とも**数値・再現条件（プレビューのみ／ロケール有無で結果が割れる／5対2）付き**で記録されている。§1 の通り (e) スライドに使ってよい。**ただし出典は `CLAUDE.md` 冒頭の "This is NOT the Next.js you know" 警告文言そのものではない**（あれは Next.js の破壊的変更への一般的注意書きで、gem-hunter 固有の実測とは別物）。narrative_design/dev_audience が両者を同一視して 1 枚に混ぜると出典の性質が異なるものを混同することになるため、**警告文言は導入のフックとして 1 行だけ使い、本体は L-129/L-130 の実測データで構成する**ことを申し送る。

## 3. narrative_design 16 枚案・dev_audience 17 枚配分案の横断点検（混入検出）

### 3.1. (b) アウトカムスライドに「Gem Index が検索結果に効いている」と読める混入がある — **検出・要修正**

narrative_design R1 のスライド一覧 No.2（148〜178行目の表）: 「検索結果 UI のスクリーンショット… / **Gem Score バッジの見え方** / 『これが今日話す全て』の一言」。

これは round 1 で私が明示した禁止事項に抵触する: 「書いてはいけないこと: 検索結果が Gem Index 順に並ぶ（`D-33` で撤去済み）」。`D-33`（`open-questions.md` 344 行目）は撤去範囲を明記している: 「`repository-list.tsx` の `gemFacets` 経路を撤去する」。**検索結果一覧のカードに Gem Score バッジは現在表示されない。** 「検索結果 UI」と「Gem Score バッジ」を同一スライドの並列要素として書くと、聴衆は両者が同じ画面に同時に存在すると読む。

**代わりに書ける正確な文言**: No.2 のスライドを 2 系統に分離する。
- (b)-1「検索結果 UI のスクリーンショット」→ 要素からは **Gem Score バッジを外す**（基本検索・一覧・詳細という MVP の姿だけを見せる）
- (b)-2（別スライドまたは同スライドの別セクションとして明示分離）「トップページの『今日の Gem』日次ダイジェスト」→ ここでのみ Gem Index/Gem Score の可視化に触れてよい。ただし見出し・キャプションに **「検索結果ではなくトップページの日次ダイジェストです」と明示**する一言を入れる。

visual_assets R1 の判定表（インフォグラフィック 10・gem-score を「(b) 何ができるのか＝アウトカムの核」「むしろ冒頭 (b) の主役候補」と位置づけている箇所）も同じ罠に片足を踏み入れている。インフォグラフィック 10 自体は Gem Index の**算出ロジック**（定義）を説明する図であり、それ自体は正確（`docs/adr/0009` が定義そのものは維持と明記）。**ただし visual_assets への申し送り**: この画像を (b) で使う場合、キャプションは「検索で使われる」ではなく「**日次ダイジェスト『今日の Gem』が使うロジック**」と明記すること。画像そのものは変更不要、隣接テキストの書き方だけの問題。

### 3.2. (f) 開発プロセスで規範と実績の混同が 1 箇所ある — **検出・要修正**

narrative_design のスライド No.9 タイトル案（171 行目）: 「**1セッション＝1スプリントで、人が待つ時間をなくす**」。

「人が待つ時間をなくす」は効果・アウトカムの断定であり、round 1 で私が指摘した「規範（ルールがある）と実績（効果が出ている）の混同」そのものに該当する。1 セッション=1 スプリントという**運用ルールの存在**（`docs/rules/session-sprint-rules.md` §1）は事実だが、それが「人が待つ時間をなくした」という**効果**を検証したデータは存在しない（round 1 §3「N倍速い」系と同カテゴリの断定）。

**代わりに書ける正確な文言**: 「1セッション＝1スプリントで、確認なしに実装からマージまで自律進行する」（ルール・メカニズムの記述に留め、効果を断定しない）。

一方、dev_audience R1 §1 の (f) 配分理由「**実際に回っているフロー図**」という表現は、単独では効果断定に見えるが、**§4 で確定する数値（マージ済み PR 90 件）を併記すれば正確な事実表現になる**ため、この表現自体は不採用にしない。「フロー図＋『この運用で PR 90 件をマージ済み』という実績数値」の組み合わせで初めて「実際に回っている」と言い切ってよい、という条件付き採用にする。

## 4. (f) を具体的な数字に落とす — lead 提供の数値を採用する

**採用する。** 3 点とも「効果・速度の断定」ではなく「運用の実在証跡」として使える数値であり、round 1 で私が禁止した「N 倍速くなった」類とは性質が異なる（比較対象を伴わない絶対数の事実であるため）。

| 数値 | 出典 | 使ってよい文言 |
|---|---|---|
| マージ済み PR = **90 件** | lead 実測（`mcp__github__search_pull_requests`, `repo:kai-kou/gem-hunter is:merged`, `total_count=90`・取得日 2026-08-22） | 「この自律フローで PR 90 件をマージ済み（2026-08-22 時点）」 |
| Issue/PR 番号 = **#363 まで到達** | round 1 で私が確認した直近マージコミット中の `#358` `#361`（`git log --oneline -5`・本セッション実測）と整合。#363 到達自体は lead 提供値として採用 | 「Issue/PR は #363 まで到達」 |
| `npm run check` = **20 項目**（lint / tsc / vitest / playwright / Lighthouse a11y / 依存規則 / UI 寸法 / コントラスト / ADR 記載検査 ほか） | lead が PR #361 本文の結果表から確認。私は本ラウンドで独立再確認していないが、具体的な検査項目名を伴う特定的な数値であり、README.md の `npm run check` = 「Lint/型/vitest/E2E 等をまとめて実行」という記述（round 1 で確認済み）と矛盾しない | 「PR 前に `npm run check` が 20 項目を機械検証（lint・型・単体/結合・E2E・a11y・アーキテクチャ境界 ほか）」 |

**禁止する使い方（念押し）**: この 3 つの数字から「1 PR あたり平均◯分」「1 日◯PR」等の **速度・生産性を逆算しない**。90 件は「累積の実在証跡」としてのみ使い、分母（経過日数・投入トークン等）と組み合わせた比率化は行わない。理由は round 1 で確定させた通り shallow clone のため活動開始日を正確に特定できておらず、分母が確定しない状態で比率を出すと再び「裏取り不能な速度主張」に逆戻りするため。

**round 1 の shallow clone 指摘は維持する**: `git log --oneline | wc -l` = 50 を総コミット数として使わない、という判定は変更しない。90（マージ済み PR）と 50（shallow clone のコミット数）は別の指標であり、90 の方が信頼できる（GitHub API 側の集計であり shallow clone の影響を受けない）。**スライドには 90 のみを使い、50 は使わない。**
