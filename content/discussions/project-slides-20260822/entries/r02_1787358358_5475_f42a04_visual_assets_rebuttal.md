**決定**: (b) の2枚は **実UIスクリーンショットを採用し、new-01（star vs Gem の概念図・gpt-image-2生成）は撤回する。** 理由は3つ:
1. narrative_design が推す Hightower 流「show don't tell」は「本物を見せる」ことが眼目であり、AI生成の概念図で代替すると効果が薄れる。

3. R1で自分が書いた懸念（"実装済みUIと乖離するモックは誤解を招く"）を、実スクショなら根本的に解消できる。

## 2. dev_audience の可読テキスト上限（全角150字/箇条書き4点）と密画像7〜8枚全面貼りの衝突 → **一部撤回し、narrative_design の5枚案に合わせて絞る**

「読ませない画像を貼るのは聴衆を裏切る」という指摘は正当だと認める。**R1の「7〜8枚流用」は撤回し、以下の条件で再設計する。**

- **上限150字/4点の適用範囲を切り分ける**: dev_audienceの上限は「スライド自身のテキストレイヤー（タイトル・タイプ入力の箇条書き・表）」に適用する。画像に埋め込まれた既存インフォグラフィックの文字は、この150字カウントに **含めない** 代わりに、次の3条件を必達にする独立枠として扱う。
  1. **スライドタイトル（assertion型・narrative_design案）が「読まなくても分かる1メッセージ」を担う**（画像を読まなくてもスライドの主張が伝わる）。
  2. **発表者が口頭で拾う点数は最大3点まで**（dev_audienceの要求どおり明文化する）。
  3. **この形式のスライドはデッキ全体で最大5枚まで**（narrative_designのR1確定16枚案が既に 08→スライド5・07→スライド6・10→スライド8・13→スライド9・11→スライド10 の **5枚** を割り当て済み。これを上限として追認し、それ以上増やさない）。
- **結果として不採用にする既存流用**: R1で「使う」とした 06（ロードマップ）・12（Cloudflare構成）は narrative_design の16枚案に割当先がなく、上記5枚上限も使い切っているため **不使用**（06はロードマップの情報価値が(c)のドキュメント相関図と重複、12はCloudflare詳細を(e)技術スタックのテキスト1行に格下げすれば足りるとdev_audienceの「退屈なので削る」判断とも整合）。
- **投影時可読性への留保**: 既存13枚は1536×864・要素20〜35個という「ドキュメントを近くで読む」密度で作られており、**大会場でのプロジェクター投影では細部が読めない可能性がある** ことは事実として認める（実測なし・確認できていない）。この密度のまま使う5枚は「細部を読ませる」用途ではなく「全体の構造を一瞥で見せ、口頭で3点だけ拾う」用途に限定する、という条件を明文化することで dev_audience の懸念に応える。

## 3. narrative_design の見出し文字数（新規24字/流用32字）と自分の「新規10〜14要素」の整合 → **矛盾なし。統合して確定する**

narrative_designの「見出し」文字数と自分の「1画像あたりの総テキスト要素数」は別軸（前者はタイトル1項目の文字数、後者は画像内の全項目数）なので **両立する**。統合ルールとして確定:

- 新規gpt-image-2生成画像: タイトル ≤24字（2行）+ その他要素（ラベル・短句）を合わせて **総10〜14要素以内**
- 既存流用画像の外側テキストレイヤー（PPTX側の見出し）: ≤32字
- 既存流用画像そのものの内部文字数: 上記§2の独立枠（20〜35要素、5枚上限）

**Gem Score見出し27字→短縮案（narrative_designへの回答）**:

> 「Gem Score＝被依存数とstarの残差」（22字）

「Score」を残しつつ数式的な言い切りにすることで、開発者に「定義そのもの」として刺さりやすくした。「で測る」を落として「＝」にすることで4字短縮している。24字制約を満たす。

## 4. new-02（ADR採用/却下）: 1枚に3件は不可 → **1 ADR = 1 画像に分割する**

自分の「新規画像は10〜14要素以内」制約から機械的に判定する。ADR 1件を「採用/却下/根拠」の3ブロックで表現すると最低でも タイトル1+却下見出し1+却下項目1〜2+採用見出し1+採用項目2〜3+チップ1〜2 = **概ね8〜10要素** かかる（後述の具体例で実測）。これを3件分1枚に詰めると **24〜30要素** になり、上限を2倍以上超過し、かつ§2で自分が撤回した「密画像は口頭3点まで」の原則にも反する（1画像で3 ADR×根拠を全部読ませることになり、まさに"聴衆を裏切る"画像になる）。

**決定**: **1 ADR = 1 スライド = 1 新規画像**（narrative_designの12〜14番のスロット割り当てと自然に一致）。共通確定済みの ADR 0009 + `D-33` を具体例として仮組みする（他候補が確定していなくても同じテンプレートを使い回せることを示す）。

**new-02a（ADR 0009 + D-33）Text elements（10要素・24字制約チェック済み）**:
```
タイトル（banner・assertion型・19字）:
「作った差別化機能を、実測で撤去した」

左ボックス見出し:「却下」
左ボックス項目1:「候補227件・一般語ヒット率0〜8%」
左ボックス項目2:「候補拡大はバンドル3MB上限を超過」

右ボックス見出し:「採用」
右ボックス項目1:「sort=gem-index を検索結果から撤去」
右ボックス項目2:「検索速度 3〜8秒→0.5〜1秒に短縮」
右ボックス項目3:「Gem Index は『今日のGem』に限定継続」

チップ:「ADR-0009」「D-33」
```
合計10要素・タイトル19字。残り2枠（project_truth案のADR0007/0003 or dev_audience案のADR0002+OpenNext/0005）が確定次第、同一テンプレート（却下2項目+採用2〜3項目+チップ2）で同様に組む。**争点Dの決着待ちで自分から候補を選ばない**（越権を避ける）。

## 5. 既存13枚の01 vs 03 → **どちらも不使用に修正**

R1では「01 or 03 のどちらか1枚」としたが、§2の5枚上限（既に07/08/10/11/13で使い切り）と、project_truthの指摘（01はGTM/マネタイズ/収益化を含み開発者聴衆に無関係、実装スコープは与件が主で初期コンセプトは従）を踏まえて撤回する。

- **01（初期コンセプト）不使用**: GTM/収益化ブロックが開発者聴衆に無関係という dev_audience・project_truth の指摘に同意。課題認識（star埋没・偽star）は project_truth が裏取り済みの一次数値（`lean-canvas.md` P-1/P-2）をテキストで引用すれば足り、密画像を追加で使う必要はない。
- **03（インセプションデッキ）不使用**: Q1〜Q10グリッドも同じく寄せ集め型で、narrative_designの16枚確定案がそもそも01/03のどちらにもスロットを割り当てていない（スライド4は「インフォグラフィック01 or 02の一部」を"任意"としているのみ）。5枚上限を使い切っている以上、追加しない。
- 視覚的フックがどうしても欲しい場合の代替: 01の「課題」ボックスだけを **部分クロップ** して小さく添える案はあるが、任意・低優先度（§2の5枚上限には数えない軽微な補助素材として扱うなら許容、ただし推奨はしない）。
