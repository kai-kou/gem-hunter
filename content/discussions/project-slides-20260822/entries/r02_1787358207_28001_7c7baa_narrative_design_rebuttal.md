# narrative_design R2: rebuttal / concession

## 1. dev_audience との導入順の差 → **dev_audience の順序（課題1行フック→アウトカム）を採用し、自説を撤回する**

自分（R1）: 2枚目=アウトカムUI冷たく見せる → 3枚目で課題に巻き戻す。
dev_audience: 2枚目=課題1行フック → 3〜4枚目=アウトカム。

**dev_audience 側を採る。** 理由は自分自身が争点Bで根拠にした Alley の assertion-evidence 構造との **内的整合性** にある: assertion-evidence は「見出し（主張）が先、視覚証拠（画像）が後」という順序をスライド単位で要求する。これは1枚のスライド内の話だが、**導入の2〜4枚目という「ミニ・アセンションブロック」でも同じ論理が効く**: 主張（star数では良いOSSは見えない）を1行提示してから、証拠として検索画面のデモを見せる方が、いきなり画面を見せるより「何がどう違うのか」が伝わる。自分の R1 案は Hightower の show-don't-tell に寄せすぎて、Alley（B の根拠）と矛盾する構成を A に持ち込んでいた。**自分の中の矛盾を dev_audience の指摘で気づいた**、これは concession として明記する。

**負けた側（自説）の懸念の吸収**: 自分が懸念していたのは「市場分析込みの重い初期コンセプトを冒頭に持ってくると開発者が離脱する」という点。これは dev_audience 案でも解消済み — 2枚目は **1行のみ**（初期コンセプトの市場分析・ペルソナ・GTM は一切載せない、後述§2で内容も確定）。冷たいデモ直行のインパクトが弱まる懸念は、visual_assets の new-01（star検索 vs Gem Hunter の左右対比画像）を2枚目の課題フックと **同一画像として使う** ことで吸収する: 1枚の画像の中に「課題（左＝star偏重でグレーアウト）」と「解決の予告（右＝コーラルで強調）」を同時に描かせれば、"1行assertion + 対比図" が1枚で完結し、demoへの落差も最小化できる。つまり2枚目自体を「課題文 + アウトカムの片鱗」のハイブリッド1枚にでき、3〜4枚目でアウトカムを本格的に展開する流れが最も強い。

## 2. project_truth の重大指摘（初期コンセプト≠与件、主従関係）→ **全面的に受け入れる（concession）**

自分の R1 スライド3〜5は「初期コンセプトの課題認識」と「ミッション」を並べていたが、**"与件が主・初期コンセプトが従"という主従関係を明示していなかった**。これは修正する。

- スライド2（課題フック）: `P-1`（約600万個の偽star、He et al. ICSE 2026）**のみ** を使う。市場比較表・ペルソナ・GTM・マネタイズは一切載せない（元々そのつもりだったが、project_truthの指摘で「初期コンセプト＝与件」という誤読リスクがあった前提を正した）。
- スライド5（旧: ミッション/検討全体像スライドに統合）: `project-mission.md` のミッションステートメント + `P-2`（`debug_inspector` 実例）を主役にし、**「初期コンセプト（IndieGems）というアイデアが先にあり、外部与件（選考課題の下限要件）でスコープをくるみ直した」という1文をこのスライドの1要素として必ず入れる**。これで「与件ありきではなく初期コンセプトをベースに」というユーザー指示（時系列としては正しい）と、project_truthが指摘する実装スコープの主従関係の両方を、開発者に誤解させずに満たせる。
- **与件（選考課題）の存在自体は語る**。理由: `inception-deck.md` Q1 が「主目的=選考課題/ポートフォリオ」と明記しており、これを隠すと「なぜ認証や課金が無いのか」「なぜGem Indexが検索結果に反映されないのか」を開発者が誤解する（実際に反映されないのはD-33の技術的判断だが、与件の存在を知らないと「未完成」に見えてしまうリスクがある）。1文で十分。

## 3. `P-3`（未検証）の混入チェック → **自分のR1原稿に直接の引用はないが、表現レベルで危険な箇所があったので修正する（concession）**

R1のスライド4「ミッション/Hidden Gemの定義」の要素案に「ニーズ」という言葉は使っていなかったため `P-3` の直接引用はない。ただし、争点A の説明文中で「開発者が『自分にちょうどいいものが欲しい』というニーズ」的なニュアンスを暗黙に前提していた箇所があり、これは `lean-canvas.md` が明示的に未検証（n=0）とする `P-3` の言い換えに近い。**スライド本文には検証済みの `P-1`/`P-2` のみを使い、「ニーズ」「求めている」のような聴衆の欲求を断定する表現は禁止する**、という制約を lead への申し送りとして明記する。

## 4. visual_assets の設計との整合 → **矛盾なし。基準を数値レベルで統一する**

- 既存インフォグラフィック流用スライド: 見出し(assertion型)がタイトル行で1メッセージを担い、画像は根拠(20〜35テキスト要素の詳細)として下に添える、という自分のB決定と visual_assets の設計は **完全に一致** している。見出し文字数上限は自分の R1 案どおり32字を維持（reused画像側からの反論なし）。
- 新規生成画像（new-01/new-02）: visual_assets は画像全体のテキスト予算を10〜14要素に設定。自分のR1では新規画像の見出しを24字以内としていたが、**dev_audience の「画面上の可読テキスト総量150字以内・見出し20字以内」の方が厳しく安全** なので、**新規画像の見出しは20字を基本、上限22字まで** に下方修正する（24字から短縮。concession）。この見出し1要素 + visual_assets の対比ボックス短句4〜8個（8〜16字/個、visual_assets実測値）で合計10〜14要素に収まり、3者の基準は数値的に整合する。
- R1で指摘した「Gem Score見出し27字」の超過は、20字上限のもとで再度短縮が必要: 「Gem Score＝star の伸び残差で測る」(18字) に修正する。
