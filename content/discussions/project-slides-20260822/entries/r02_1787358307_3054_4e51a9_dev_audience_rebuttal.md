# dev_audience R2: rebuttal / concession

## 1. 導入順の決着 — narrative_design 案を採用（自分の R1 案を撤回）

**結論: 2 枚目=アウトカム UI（narrative_design 案）を採用する。** 自分の「2 枚目=課題フック 1 行 → 3〜4 枚目=アウトカム」は撤回する。

理由: 自分が R1 で立てた核心の主張は「開発者は動くものを先に見たい／技術説明はアウトカムに紐づいて初めて入る」だった。だが自分の案は 2 枚目に**文字のフック**を置いており、これは Hightower の "show don't tell"（narrative_design 出典）に照らすと結局「言ってから見せる」構造で、自分自身の主張と矛盾している。narrative_design の「2 枚目 = 検索結果 UI のスクリーンショットそのもの」は文字ゼロで即座に "star 順ではない" ことが視覚的に伝わり、自分の主張をより純粋な形で実現している。

ただし 1 点だけ条件を付ける: 2 枚目のタイトル行（narrative_design 案「star 順では出てこない OSS を、検索できる」）が assertion 型見出しとして機能する限り、自分が言いたかった「1 行フック」は**独立スライドではなくタイトル行に統合済み**であり、追加のフックスライドは不要。これで自分の懸念は解消される。3 枚目で課題（star 埋もれ問題）に巻き戻す narrative_design の変則 Sparkline 構成を全面採用する。

## 2. 150 字上限と既存インフォグラフィック全面貼り（visual_assets 21〜35 要素）の裁定

**「読ませない画像を貼るのは聴衆を裏切らないか」を本気で立てる**: 60〜70 秒のスライドに 20〜35 テキスト要素の画像を貼ると、聴衆は「これは重要そうだから読まなければ」と反射的に目を走らせるが、時間内に読み切れず、結局「読めなかった」という不満だけが残る。これは visual_assets が自分で書いた「1 画像 1 ドキュメント全体」という指摘そのものが、実は**聴衆の可読性への裏切り**でもあることを意味する。「タイトルが 1 メッセージを担うから画像内テキストは読ませなくてよい」という visual_assets の理屈は、**画像が単一テーマで密度が低い場合にのみ**成立する。

**裁定（自分の 150 字上限の適用範囲を確定する）**:

- **150 字上限は「画像内テキストを含む、聴衆が実際に読むことを期待される全テキスト」に適用される。画像だから別枠、という免除はない。** ただし「読むことを期待しない」画像（背景の質感・雰囲気としてのみ機能する低密度画像）は例外として **カウント対象外**にできる。
- 例外が成立する条件: ① 単一テーマである ② タイトル 1 行だけで聴衆が意味を理解できる ③ 画像内の細部を聴衆が読まなくても話が成立する。この 3 条件を満たすのは visual_assets の判定表でいう **06（roadmap）/ 07（design）/ 08（doc-relations）/ 10（gem-score）/ 11（testing-strategy）/ 12（cloudflare）の 6 枚のみ**。この 6 枚は全面貼りかつ 150 字カウント対象外を認める。
- **09（ADR マップ）と 13（ops-rules）は例外条件を満たさない**。09 は visual_assets 自身が「却下案が載っていない」と認めており、13 は要素数最多（約 35）かつ「CP/A/SD framework + 開発フロー」という**複数テーマの混在**（自分の R1 の "属性寄せ集め型" 判定基準に一致）。visual_assets の「条件付き＝全面貼り＋口頭は 3 点に絞る」提案を**却下する**。この 2 枚は**部分トリミング必須**（09 は争点 D で選んだ ADR 2〜3 件の帯だけ切り出す。13 は「1 セッション=1 スプリント」「TDD」「PR 自律運用」の 3 ブロックだけ切り出す）。トリミング後の要素数は new-01/new-02 と同じ **10〜14 要素以内**に揃える（visual_assets が新規画像に課した上限を、トリミングにも遡及適用することで基準を一本化する）。
- **01/02/03/05 は自分の R1 判定を維持**: 01 or 03 のどちらか 1 枚を選ぶとしても全面貼りせず、該当ブロックのみトリミング（visual_assets の「属性寄せ集め型」認定と一致するので争いはない）。02 は不使用で全員一致。

**結論**: 「画像が語ればテキスト予算を消費しない」という自分の R1 の立場は**単一テーマ・低密度の 6 枚に限定して有効**、それ以外は 150 字ルールの脱法手段として使わせない。

## 3. ADR 争点 D: project_truth 案（0007 / 0003）への賛否

**結論: project_truth の 3 件（0009 / 0007 / 0003）に乗り換える。自分の R1 案（0002+OpenNext / 0005）は D 枠から撤退させる。**

- **ADR 0007（DB レス設計）— 賛成、採用を推す**: 「Web アプリなのに DB を一切持たない」という判断は直感に反する分だけ聴衆の食いつきが強く、かつ URL/Cookie/localStorage への状態分散という具体的な設計パターンは他プロジェクトへそのまま転用できる。自分が R1 で推した ADR 0005（Cache Port YAGNI 例外）とテーマが隣接（どちらも「レイヤーを増やさない判断」）するため、両方を D に入れると印象が重複する。**0007 の方が「サーバーレス web アプリで DB ゼロ」という主張の強さで上回るため、0005 は D 枠から降格し (d) アーキテクチャの W-1〜W-3 の脚注に格下げする**（完全に消さず、口頭の 1 行補足として残す）。
- **ADR 0003（GitHub App 認証 + 6 軸判断フレームワーク）— 強く賛成、自分の R1 推薦を上回る評価に格上げする**: project_truth が指摘した「§6.1 に "次に同じ選定をするときに見る判断軸" 6 項目があり、軸 2・軸 4 が拒否権を持つという一般化まで書かれている」という点は、自分が R1 で ADR 0005 に対して使った評価基準（「汎用的なエンジニアリング判断の型として持ち帰れる」）を**ADR 15 本の中で最も厳密に満たす**。単一の決定の記録ではなく再利用可能なチェックリストそのものであり、開発者が自分のプロジェクトに帰ってすぐ使える形になっている。**争点 D の中で最も「持ち帰れる」1 件として最優先で推す。**
- **自分の元の ADR 0002（Cloudflare Workers / OpenNext の実際の罠）は D から撤退**: project_truth 候補 4（ADR0002+D-31、`wrangler deploy` が auto mode classifier に非決定的にブロックされる話）の方が「AI エージェント駆動開発ならではの技術的制約」という新規性で自分の元ネタ（OpenNext のプレビュー環境リダイレクト/パス解決トラブル）を上回る。project_truth の「D では割愛し E 側で軽く触れる」という提案を採用し、**この内容は (e) 技術スタックの 2 枚目（「実際に踏んだ罠」スライド）に格納する**。9〜11 番（開発プロセス）と隣接する内容なので、(e) の末尾に置けば (f) への橋渡しにもなる。

**最終 D 構成（3 枚固定）**: 12=ADR0009（Gem Index 撤去、後述で最厚遇）/ 13=ADR0003（GitHub App 認証の 6 軸フレームワーク）/ 14=ADR0007（DB レス設計）。

## 4. 候補 1（ADR0009 + D-33・実測で自作機能を撤去した話）を主役にする

**「宣伝にならないから薄める」ではなく「これこそ主役にする」と明確に言う。**

理由: 開発者聴衆が最も信頼するのは「うまくいった話」ではなく「作って、測って、自分の手で殺した話」。候補プール 227 件・`react`=8/100・`test`=7/100・`cli`=6/100・非 JS 系ほぼ 0 件という実測値は、この講演全体で最も具体的で反証可能な数字であり、project_truth が §5 で警告する「誇張・裏取り不能」の対極に位置する**最も誠実なコンテンツ**。ここを薄めると、講演全体の「誇張しない」という姿勢そのものの説得力が下がる。

**具体的な配分指示**: 12 番（0009）だけは自分が §「尺の定量検証」で置いた 60〜70 秒/枚の上限を **例外的に 90〜100 秒まで許容**する（実測値を bar chart 的に見せる必要があるため）。その埋め合わせは 15 番（まとめ）を簡素化して吸収する（まとめは「持ち帰れる考え方 2〜3 点」の箇条書きのみに削り、新規の主張を足さない）。可視化は visual_assets の new-02（採用 vs 却下の対比ボックス）をこの 1 枚に集中投入し、「候補プール 227 件」「一致率 8/7/6 件」「体感 3〜8 秒→0.5〜1 秒」の 3 つの数字だけをテキスト要素として焼き込む（要素数は 3〜4 個に絞り、自分の 150 字上限にも収まる）。

## 5. 枚数: 譲れない配分と削ってよい枠（16 枚で決着）

自分の 17 枚案を **16 枚に修正**し、narrative_design の 16 枚案と数を合わせるが、中身は以下のように組み替える。

**譲れない配分（死守）**:
- **(f) 開発プロセス 3 枚**（narrative_design の 9/10/11 とすでに一致。ここは争いなし）
- **(g) 技術的課題 3 枚**（§3 で確定した 0009/0003/0007。project_truth との合意により死守。0009 は時間配分で優遇）
- **(e) 技術スタック 2 枚**（narrative_design 案は 1 枚のみだったが、§3 で ADR0002/D-31 の「罠」コンテンツの置き場所として 2 枚目を新設する。これは project_truth の申し送り「E 側で軽く触れる」を実行に移すための必須枠であり、削れない）

**削ってよい枠（自分から譲る）**:
- **narrative_design の 4 番「被依存数を起点に…（ミッション全文+Hidden Gem 定義）」を削除し、8 番「Gem Score は…（算出ロジック深掘り）」に統合する。** 同じ「被依存数に対する star の残差」という定義を 2 枚に分けて 2 回説明するのは重複であり、自分が §1 で潰した「詰め込みすぎ」とは逆方向の「薄すぎる 2 枚への分割」も同様に無駄。ミッションステートメントは 3 番（課題フック巻き戻し）の見出し脇に 1 行だけ添えれば十分。
- **(d) アーキテクチャは narrative_design の 1 枚案を受け入れる**（自分の R1 案は 2 枚だったが撤回）。W-1〜W-3 は assertion 見出し 1 文＋図解だけで足りると判断し直す。(e) に 2 枚目を新設する分の帳尻をここで合わせる。
