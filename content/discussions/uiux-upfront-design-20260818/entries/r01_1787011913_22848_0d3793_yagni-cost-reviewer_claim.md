# YAGNI 判定: UI/UX 設計成果物の必要性判定

## 現状確認: 既に存在する成果物

1. **ユーザーストーリーマップ** (`user-story-map.md`)
   - バックボーン（A-1 ～ A-7）と流れ図が ASCII アート + 構造化表で明示
   - ユーザーストーリー 27 本（US-1 ～ US-27）に分解完了
   - 各 US に参照要件 ID・スライス割り当て済み

2. **UI/UX ガイドライン** (`ui-ux-guidelines.md`)
   - **技術スタック決定**: Tailwind v4 / shadcn/ui / next-themes
   - **デザイントークン基本構想**: 9 トークン × ライト/ダーク（実値は SP-2 で確定）
   - **タイポ・スペーシング原則**: 5 段階 / 4px グリッド
   - **各ページのレイアウト詳細設計**:
     - トップページ: コントロール配置・カード要素順序（ASCII 図で視覚化）・4 状態の出し分け方
     - 詳細ページ: 統計行配置・メタ情報表現方法
     - エラー表示: 種別別文言設計・a11y 要件
   - **a11y 実装指針**: route announcer・aria-live・focus 管理

3. **要件定義書** (`prd.md`)
   - 与件・上乗せ要件・非機能要件が ID で体系化

## 候補成果物の評価

### 1. 画面遷移図（Mermaid）

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 1-2（user-story-map.md §1 の A-1～A-7 を Mermaid にシリアライズ） |
| **維持コスト** | **高** — US 追加・削除・分割のたびに同期。実装フェーズで図と実装がドリフト常態化 |
| **効果** | **中** — ASCII ステップフロー図（user-story-map.md）が既に A-1→A-2→A-3... の時系列を示している。Mermaid は「ビジュアル」という +α だけ |
| **既存で足りるか** | **足りる** — user-story-map.md §1 の ASCII 図で流れは明確 |
| **推奨** | **❌ やらない** |

**理由（YAGNI）**: 既存のテキスト図で時系列フローは把握可能。図の本来の価値「デザイナ↔エンジニア間のコミュニケーション」が、個人開発 AI 実装では存在しない（通路が最初からない）。維持コストを負うだけ無駄。

### 2. サイトマップ / 画面一覧表

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 1（ルーティング設計表と統合すると効率的） |
| **維持コスト** | **低** — ルーティング確定後はほぼ不変 |
| **効果** | **中** — US と画面の対応（US-1=`/[locale]`・US-16=`/[locale]/repos/...`）をいま 1 表にまとめるだけで、実装時に参照性が上がる |
| **既存で足りるか** | **部分的に足りる** — user-story-map.md が US ごとに「どの機能か」を含むが、**URL 構造が専用表として見えない** |
| **推奨** | **🟢 やる**（ただし URL 設計表とセット化） |

**理由**: S-0 項目（US-9 で「URL に反映」と明記）だから。**URL パス・クエリパラメータ名・既定値を 1 表に集約する** と、実装前の仕様解釈ズレを減らせる。コストは軽い（SP 1）。

### 3. URL・ルーティング設計表（パス・クエリパラメータ名・既定値）

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 1 — Next.js app router 前提での パス / `searchParams` 仕様を表にまとめるだけ |
| **維持コスト** | **低** — ルーティング確定後は極めて安定 |
| **効果** | **大** — S-0 項目。実装時の「クエリパラメータ名の揺らぎ」「既定値の曖昧さ」を事前に潰す |
| **既存で足りるか** | **足りない** — US-9 は「キーワード・ページ・ロケール」だけを名指ししているが、パラメータ名（`q`? `query`?）や `page` の既定値（1 ベース? 0 ベース?）が決まっていない |
| **推奨** | **🟢 やる（必須）** |

**理由**: S-0 でリポジトリ公開・共有リンク長期保持が要件。パラメータ設計が後付けコストになると既存 URL 全破壊。実装前に確定必須。

### 4. ワイヤーフレーム（低忠実度）

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 3-5 — Figma で low-fi sketch、またはオンラインツール |
| **維持コスト** | **中** — 状態追加・コントロール位置変更のたびに更新 |
| **効果** | **小～中** — ui-ux-guidelines.md が以下を既に記載: |
| | - 要素の順序（§4.2 の `┌─────┐` 図） |
| | - 各要素のフォント・色・高さ規定（§4.2 の表） |
| | - スペーシング原則（§2.3） |
| | - 状態遷移（§4.4・§5） |
| **既存で足りるか** | **十分に足りる** — ガイドラインがテキスト + ASCII 図で相対位置・余白・色を詳述済み |
| **推奨** | **❌ やらない** |

**理由（YAGNI）**: ガイドラインの記述密度が既に「ワイヤーフレーム並み」。追加図は「きれい」という付加価値だけだが、実装フェーズで図が古くなり、無視される常態化リスク大。同期コスト >> 実装サポート効果。

### 5. 画面 × 状態マトリクス（初期 / 読み込み / 0 件 / エラー等）

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 2 — ページごとに状態一覧 × UI 表現を記入 |
| **維持コスト** | **中** — 新しい状態・エラー種別追加のたびに更新 |
| **効果** | **中** — トップページの 4 状態は ui-ux-guidelines.md §4.4 で既に表定義。**詳細ページ・エラー詳細ページは状態設計が未記載** |
| **既存で足りるか** | **部分的** — トップページは足りる。詳細ページ・404 の「戻る導線」「状態変化」は？ |
| **推奨** | **🟡 任意**（優先度は低い） |

**理由**: メインシナリオ（検索→一覧→詳細）の状態は既に §4.4・§5・§6 で埋まっている。全ページ統合表は「落とし穴防止」には有効だが、エネルギーをかけるなら **URL 設計表（S-0・先行確保）の方が先**。 実装開始後の「あ、この場面の状態表現どうする？」はゴリ押しで対応可能（UI ガイドラインが詳しいから）。

### 6. 高忠実度デザインカンプ / プロトタイプ（Figma）

| 項目 | 評価 |
|------|------|
| **作成コスト** | SP 8+ — ビジュアルデザイン + インタラクション検証 |
| **維持コスト** | **極度に高** — 実装で細部が変わるたびに同期。最終ピクセル合わせを強制するとコストが爆発 |
| **効果** | **中** — ビジュアル + インタラクション確認。ただし実装が進むと図は無視される傾向 |
| **既存で足りるか** | **十分に足りる** — デザイントークン（色・フォント・スペーシング）と ui-ux-guidelines.md の記述で、実装レベルでの統一性は確保可能 |

**理由（YAGNI）**: 個人開発 + AI 実装の文脈では、**Figma カンプ ↔ 実装の同期コストが成果物の再現価値を完全に上回る**。むしろ「実装を進めながら UI ガイドラインで例外対応・微調整」の方が現実的で軽い。

## 総括（推奨アクション）

### 🟢 **必ずやる**（S-0 先行確保）
- **URL・ルーティング設計表** (SP 1)
  - 記載内容: ページパス・クエリパラメータ名・既定値・制約
  - 例: `GET /[locale]/`、`GET /[locale]/repos/[owner]/[repo]`、`searchParams: { q, sort, limit, page }`
  - サイトマップとセット化（計 SP 1）

### 🟡 **やると便利だが省略可**
- **サイトマップ / 画面一覧表**（上記 URL 表とセット）
  - コスト軽い（SP 1）。実装時の参照性上昇。ただし必須ではない

### ❌ **やらない**（既存で十分・コスト > 価値）
- 画面遷移図（Mermaid）
- ワイヤーフレーム（低 / 高忠実度両方）
- 高忠実度デザインカンプ
- 統合 × 状態マトリクス（ui-ux-guidelines §4.4・§5 で既に定義）

## YAGNI の核となる原則（本プロジェクト）

1. **デザイナ ↔ エンジニアの通路が不在**
   - 個人開発で AI 実装。図の最大価値「職能間コミュニケーション」が消えている
   - 代わりに「実装が参照しやすい優先度順テキスト」の方が実用的

2. **後付けコスト > 事前図**（except S-0）
   - 実装フェーズで仕様微調整が必須（AI が仕様を照らし合わせて実装するため）
   - 古い図を同期するなら、その時間を「実装 → ガイドライン記述」に充てた方が効率的

3. **1 箇所しか使わない抽象化を先に作らない**（CLAUDE.md より）
   - トップページと詳細ページしかないのに「全ページ統合状態マトリクス」を先に作るのは YAGNI
   - 使い回す複数ページが出てから、共通パターンを抽象化

4. **S-0 は先行確保**（不可逆な破壊を避ける）
   - URL 設計だけは「後付けコスト = 既存リンク全破壊」だから先に決める
   - その他の図は「実装して確認」でも間に合う
