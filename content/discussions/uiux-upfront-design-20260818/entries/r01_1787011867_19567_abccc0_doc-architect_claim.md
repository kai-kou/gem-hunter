# doc-architect: 実証的判定（既存ドキュメントの現況調査）

## 1. サイトマップ（画面一覧）は導出できるか

**できる。画面は 2 つのみ**（`prd.md` §8.1 トップページ / §8.2 詳細ページ）。導出に必要なファイルは実質 1 つ（`prd.md` §8）で、`user-story-map.md` §1 のバックボーン図（A-1〜A-7）が行動レベルの補完情報を与える。画面数が 2 つしかないプロダクトでは「サイトマップ図」という成果物形式そのものが過剰投資になりやすい。

## 2. 画面遷移は既に書かれているか

**部分的に書かれているが、1 箇所に集約されていない。** 遷移の実体は `user-story-map.md` §5.3 の各 `SP-n` の「操作レビュー」手順に埋め込まれている（例: SP-3「カードを選ぶ→詳細ページへ遷移→戻る」、SP-2「`/`→`/ja` へリダイレクト」）。これは画面遷移図ではなく E2E テスト手順として書かれているが、**遷移そのものの情報量は網羅的**。

**抜けている遷移（実証済み）**:
- **ログイン/ログアウトの往復**: `prd.md` AR-5 詳細に「セッションは httpOnly Cookie」「ログアウト提供」と機能記述はあるが、GitHub OAuth への離脱→復帰という **画面をまたぐ遷移** を図示した箇所はゼロ。SP-8 の操作レビュー（`user-story-map.md` L373-377）も「ログインする→レート枠が切り替わる」の 1 行で、コールバック遷移の中間状態は書かれていない。
- **エラーからの復帰**: `prd.md` §7 とガイドライン §5.2 は「エラー種別 → 文言」の対応表であり、**画面から画面への遷移** ではなく **1 画面内の状態遷移** として書かれている（これは意図的でよい設計だが、「復帰」という語が示す "別の画面/状態へ移る" 経路までは図示されていない）。
- **404（詳細ページ）**: `prd.md` §7 に 1 行（Not Found 表示）はあるが、そこから一覧へ戻る導線が図示されているのは `ui-ux-guidelines.md` §6 の「一覧へ戻るを左上に固定」という **文章記述のみ**。
- **言語切替**: `US-2`（`user-story-map.md` L87）に 1 行あるのみで、切替前後の URL 形状（`/ja/...` ↔ `/en/...`）の遷移を図示した箇所はない。
- **ページ送り**: SP-7 操作レビュー（L362）にあるが単発で、他の状態（0 件・エラー）との組み合わせ遷移は書かれていない。

## 3. 🔴 URL 設計（パラメータ名・既定値・ロケールの置き場所）— 検証結果

**ロケールの置き場所は確定済み**: `prd.md` AR-4 詳細（L239）「`/ja/...` / `/en/...`」。これは実装者が迷わない粒度。

**しかしクエリパラメータの名前と既定値は、探した全ファイルのどこにも定義されていない。**

- `prd.md` §2.4（状態の置き場所表）は「検索キーワード・ページ・ソート・表示件数 → URL（`searchParams`）」としか書いておらず、キー名（`q`? `keyword`? `query`?）も既定値（`page=1`? `sort=best-match`?）も書いていない。
- `user-story-map.md` US-9（L99）は「S-0 の範囲はキーワード・ページ・ロケールの 3 つ」「ソート・件数は **パラメータ名と既定値だけを決めておく**」と明言しながら、**その決定を書く場所を一切指定していない**。「決めておく」という指示だけがあり、正本の置き場が存在しない。
- `ui-ux-guidelines.md` §4.1 も「すべての状態は URL の `searchParams` に反映する」という抽象論のみで、具体キー名には触れない。

→ **これは doc-architect の判定基準に照らして「本当に欠けている情報」である。** US-9 の指示を実行する場所が現状ゼロなので、このままでは SP-1/SP-2 の実装者が独自にキー名を決め、SP-7（ソート・件数追加）の実装者が別の命名慣習で追加する事故が起こり得る（`NFR-18`「キャッシュキー命名規約」と同種のリスクが URL パラメータ名にも存在するのに、こちらだけ正本がない）。

## 4. 状態（初期/読み込み中/0件/エラー種別）の網羅性

**トップページは十分**: `ui-ux-guidelines.md` §4.4 に 4 状態のマトリクスが明示され、`AC-8` / `prd.md` §7 と対応が取れている。

**詳細ページ側は抜けている**: `ui-ux-guidelines.md` §6（詳細ページ）は表示項目のみを規定し、**読み込み中・エラー（404 以外の 401/403/5xx 等）の状態表現に一切触れていない**。`prd.md` §7 のエラー種別表は画面を特定していないため、「404 は詳細ページに出る」ことは書いてあるが、「詳細ページでネットワーク到達不可が起きたらどう出すか」は不明。画面 × 状態のマトリクスとして見ると、**詳細ページ列がほぼ空欄**。

## 5. SSOT 分離とドリフト負債のリスク評価

本リポジトリは `user-story-map.md` §0.1 で「受け入れ条件を再掲しない」と明示するほど正本分離を厳格運用しており、新規ドキュメントの追加は次の 2 つのコストを常に伴う。

1. **保守コスト**: `prd.md` §2.5 未決事項・`open-questions.md` の決定ログ更新のたびに、新規ファイルとの整合を人力で取る必要が生まれる（現に `prd.md` と `user-story-map.md` の間だけでも 8 箇所以上の相互参照規律がある）。
2. **権威順の追加項目**: `intent-gate-rules.md` の権威順（ユーザー明示 > 仕様 > テスト > 現行コード）に「新規設計図」がどこに入るか不明確になり、矛盾時の解決コストが上がる。

**したがって「画面遷移図」を独立した正本ファイルとして新規作成することには反対する。** 情報のほとんどは既に存在し、欠けているのは「一覧性」であって「決定内容」ではない（例外は §3 の URL パラメータ名だけ）。

## 暫定結論（doc-architect）

**今作るべきもの**:
- ❶ `prd.md` §2.4 の拡充（新規ファイルではなく既存正本への追記）: クエリパラメータ名・既定値の表を 1 つ追加する。**正本は `prd.md`**（要件の正本であり、`NFR-18` のキャッシュキー命名規約と同じ性質の「後から変えると壊れる」情報のため）。US-9 が「決めておく」と要求している内容の置き場所を作るだけで、US-9 の指示自体は既に存在する。
- ❷ `ui-ux-guidelines.md` §6（詳細ページ）に状態表現の節を追記（§4.4 相当を詳細ページにも作る）。**正本は `ui-ux-guidelines.md`**（UI 実装判断基準の正本であるここに置くのが一貫する）。

**作らないもの**:
- 独立ファイルとしての画面遷移図・サイトマップ・ワイヤーフレーム。画面数が 2 つしかなく、遷移情報は `user-story-map.md` §5.3 の操作レビュー手順に実質的に存在する。新設すると「操作レビュー手順」と「遷移図」の 2 箇所が同じ事実を持つことになり、本リポジトリが最も警戒するドリフト（`D-8`）を自ら生む。
- ログイン/ログアウト・エラー復帰・404 の遷移は、**新しい図ではなく §5.3 の該当 SP（SP-8/SP-9）の操作レビュー手順自体に 1〜2 行足す形** で補う方が、正本を増やさずに済む。

**位置づけの一言**: 「欠けているのは絵ではなく、US-9 が要求した決定（URL パラメータ名表）そのもの」。絵を先に作ると本当の欠落（決定未了）を覆い隠すリスクがある。
