## 合意点（round 1〜2 を経て 5 名が到達した結論）

### 争点 A: 次に着手するもの — 🔴 「薄い垂直スライス」で合意（3 名が自説を撤回して収束）

- `product_vision` は R1 の「データ基盤 `sp:8` を UI 抜きで先行」を **撤回**、`constraints_guard` は R1 の「`SP-A`（データのみ）→ `SP-B`（UI）」の水平分割を **`C-2` 不成立につき撤回**、`ux_discovery` は「粗い基準」という表現を **撤回**して「最初から被依存数残差（＝ Gem Index の中核ロジック）を前提にしていた」と明確化した。
- 結論: **次スプリントは「npm 1 エコシステムの Gem Index パイプライン + それを描画する日次ダイジェスト画面」を 1 本にした垂直スライス**とする。データのみ／UI のみの水平分割は採らない。
  - 理由 1: 「静的 JSON を DevTools で目視確認」は `C-2`（デモ手順 5 行・アプリを操作して確認）を満たさない（`constraints_guard` の自己判定）。
  - 理由 2: 実データ（外れ値・欠損・名前解決漏れ）を見ずに UI の情報設計を決めると作り直しになる（`ux_discovery`）。
  - 理由 3: サンプリング軸の妥当性は画面に描画して初めて人間が気づける（`product_vision`）。

### 争点 B: 「リマインド」の実体 — 日次の有限ダイジェストを核に据える

| 案 | 判定 | 根拠 |
|---|---|---|
| 日次の有限ダイジェスト | 🔵 **採用（核）** | 無限フィードは NN/g 基準で比較・検分用途に非推奨、かつキーボード操作を複雑にする（`AC-9` / Lighthouse A11y 100 と衝突）。有限性側に倒す |
| 日次の決定論的シード（同じ日は全員同じ並び） | 🔵 **採用（内部実装）** | `data_pipeline` の「日付シード shuffle」と `ux_discovery` の日次ダイジェストは **同一メカニズム**だと確認された（用語の衝突だった） |
| 時間帯シャッフル（Product Hunt 30 分周期型） | ❌ **独立機能としては不採用** | 開いている間に内容が動く実装は WCAG 2.2.2（Pause, Stop, Hide）に抵触するリスク。日内バリエーションは再訪動機を生まない |
| 前回訪問からの差分 | 🔵 **上乗せに格下げ + フォールバック必須** | Safari ITP の 7 日キャップは「格下げ」で消えない。消えるのは**壊れる範囲**だけ。タイムスタンプ喪失時は全件表示へ自然劣化させる（エラー・空画面を出さない）ことが必須要件になる |
| RSS 配信 | 🔵 **採用可（後続）** | `prd.md` §11 `GR-7`（静的な「今週の Gem 一覧」）の延長線上。購読者リストを持たない Pull 型のため `D-5` 撤回は **不要** |
| メール / push 通知 | ❌ **不可** | 配信先リストの永続化が必要で `D-14`（サーバーに個人データを持たない）・`D-18`（永続ストア不採用）に正面抵触 |
| ログイン限定パーソナライズ | ❌ **不可（現行案では）** | `D-6`（ログインで機能差を作らない）に抵触。手入力による同等機能へ作り替えるなら救済可 |
| `package.json` 貼り付け | ⏸ **今回のスコープ外・別 Issue 化** | 🔴 「不採用」と記録しない。`R-2` を明確に満たす数少ない候補で、制約判定も「条件付き可」。スコープ問題であって却下ではない（`product_vision` の要求） |

### 争点 C: Gem Index — 算出方法は決定済み。未決はパラメータのみ

- 🔴 **[ADR 0009](../../docs/adr/0009-hidden-gem-score-definition.md)（状態: 承認）が既に算出方法を確定している**ことを 3 名が実ファイルで確認した。`Gem Index` = エコシステム内の「被依存数パーセンタイル順位」−「star パーセンタイル順位」。健全性（OpenSSF）は足切りに使い、**2 軸を合算しない**。
- したがって「単一スコアに潰さない」というリサーチ由来の指針は **既に実装済みの決定**であり、この場で再議論しない。
- ADR §2.3 が未確定として残すのは 5 点のみ: ① パーセンタイルの母集団定義 ② しきい値 ③ 配信件数 ④ 対象エコシステムの最終確定 ⑤ 名前解決。`Q-3` は「全部未決」ではなく「方法は決定済み・数値が未決」が正確。
- 🔴 **母集団の取り違えを防ぐ合意**（`product_vision` / `ux_discovery` が指摘 → `data_pipeline` が訂正）: 「薄いスライス」とは **エコシステムを npm 1 つに限る**という意味であり、**npm の中をさらにサンプリングすることではない**。パーセンタイルは npm 全量で計算し、絞ってよいのは「表示候補プールの件数」だけ。ここを取り違えると、母集団が「有名パッケージだけ」になって残差の分散が消え、`R-2` 違反（Trending の劣化コピー）が画面上で実証されてしまう。

### 争点 D: バッチの実行場所 — Cloudflare の外で回し、静的アセットとして配信

- `D-18`（永続ストアを採用しない）との境界を 1 行で確定: **「Worker がそのファイルへ実行時に書き込むか？」**。No なら対象外。バッチが外部で JSON を生成 → git commit → デプロイで丸ごと差し替え、は明確に No 側。
- ただし誤読リスクが実在する（この議論で 2 名が疑義を呈した）ため、**`D-18` に 1 行の注記を追加する**。
- SPOF（セッション / Routine が止まると更新が止まる）は認めた上で「無害化 + 検知して自己修復」で対処する。配信自体は止まらず、劣化するのは鮮度だけ。ダンプの更新周期が 2〜4 ヶ月であることを踏まえれば 1 サイクルの取りこぼしは許容範囲。鮮度チェックを既存の衛生スロットに載せる。

### 争点 E: CC BY-SA 4.0 の扱い — 保守的に運用し、判断のロックは公開判断時点に合わせる

- 配信 JSON のトップレベルに帰属メタデータ（`source` / `license` / `source_license_url` / 改変の明示）を持たせる。
- 🔴 **Ecosyste.ms の生テキスト（description 等）は再配信せず、数値・識別子・自作の派生値に限定する**。生テキストの転載は "substantial portion" の解釈を保守側へ押す。
- 実務コスト（競合による複製・将来の収益化時の足枷）は認識するが、現行 `D-3` は非商用前提のため実害は顕在化しない。**再確認のタイミングは `prd.md` §13 の「GitHub 利用規約の一次確認 = 第三者へ公開する時点」に合わせる**。

### 争点 F: 既存 `S-2` バックログの扱い

- `US-28`（お気に入り）・`US-29`（検索履歴）は localStorage ベースであり、**キーワード非依存の発見体験におけるパーソナライズの土台と同じ部品**である。別物として作らず、Gem ダイジェスト導入後に統合して設計する。
