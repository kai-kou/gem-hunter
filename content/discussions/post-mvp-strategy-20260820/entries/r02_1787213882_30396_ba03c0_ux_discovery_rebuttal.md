## 結論（更新）

ラウンド 1 の「日次ダイジェストを次スプリントに」は撤回しない。ただし **`product_vision` の R-2 批判は部分的に正しく、修正が必要**（前提の書き方が甘かった）。`data_pipeline` の「薄いスライス」案には母集団の選び方に懸念があり、名指しで指摘する。`constraints_guard` とは実質合意しているが「格下げ＝解決」ではない点を明確化する。`data_pipeline` の日付シード shuffle は自分が却下した案とは別物で、実は自分の案 1 の内部実装そのものであり対立していない。

---

## 1. `product_vision` / `data_pipeline` への回答: データなしでダイジェストの中身は何になるのか

`product_vision` の指摘（ラウンド1 §A・§B）: 「ランダム/日替わりで OSS を並べるだけ」なら Trending の劣化コピーで `R-2` 抵触。これは**私が実際に書いた提案には当たらないが、書き方が誤読を招く**ことは認める。

- **譲歩**: ラウンド1 で私が書いた「粗い基準」は言葉足らずだった。私が想定していたのは最初から「健全性フィルタ + 被依存数パーセンタイル逆順」であり、star だけの並べ替えは一度も提案していない。しかしこれは Gem Index の中核ロジック（残差計算）そのものであり、**「データが要らない」という意味では全くない**。誤解を招いた点は撤回し、明確化する。
- **反論**: とはいえ `product_vision` が主張する「`GR-1`/`GR-5`/`GR-6` のフルセットを `sp:8` で先に完成させ、UI はその後」という厳密な逐次順序にも同意しない。理由は UX 側の実務的な問題として、**実データ（外れ値・モノレポの名前解決漏れ・欠損）を見ずに UI の情報設計（多軸バッジのレイアウト・空値時の表示・カード内のどの指標を出すか）を決めると、後から作り直しになる**（`data_pipeline` がラウンド1 §A で書いた「モックだと後で手戻り」と同じ理由を UI 側からも言える）。
- **着地点**: `data_pipeline` の「薄いスライス」路線と `constraints_guard` の SP-A/SP-B 分割案に賛成する。ただし SP-A は「抽象的なデータ基盤」ではなく、**最初から SP-B（有限ダイジェスト UI）が要求する形（多軸バッジに載る指標・帰属メタデータ）に output スキーマを合わせて作る**べきで、この 2 スプリントは疎結合な「基盤→UI」ではなく **同じ縦切りの前後半**として設計する。これで `R-2` は満たしつつ（差別化ロジックを最初から実データで実装）、UI の手戻りリスクも避けられる。

## 2. `data_pipeline` への反論: 「npm 上位数百件」の母集団は私が設計した体験を壊す

`data_pipeline` の薄いスライス案（ラウンド1 §A）: 「1 エコシステム（npm）・上位数百件」に絞ったミニパイプラインを提案している。

🔴 **これは字義通りだと成立しない。** 「上位数百件」を「被依存数が多い順の上位」と読むなら、その母集団は定義上すでに **有名な巨大パッケージ**（lodash・react・express クラス）だけになる。ラウンド1 で私が C の項で書いた「novelty = その品質水準にしては知名度が低い」というバッジ文言は、**候補プール自体が「知名度が高いものだけ」で構成されていたら意味を成さない**。有名パッケージしか出ない画面に「隠れた名作です」という多軸バッジを貼ると、それこそ `product_vision` が警戒する「Trending の劣化コピー」に説明の面でも実体の面でも成り下がる。

**`data_pipeline` に名指しで確認したい**: 「上位数百件」は (a) 被依存数の絶対値上位 なのか、(b) 母集団全体でパーセンタイル残差を計算した上で、その残差が大きい（過小評価度が高い）順の上位数百件 なのか。UX 側が要求するのは後者 (b) であり、パーセンタイル計算そのものは母集団を薄く切ってはいけない（分布の裾が細るとパーセンタイルの意味が壊れる）。**薄くしてよいのは「表示候補プールの件数」であって、「パーセンタイル計算の元になる母集団」ではない。** 実装上は「ダウンロードする母集団は少数でも、その中で相対的に過小評価されているものを抽出するロジック」を先に固定してほしい。

## 3. `constraints_guard` への確認: 格下げは ITP 問題を消すのか、残すのか

**残る。消えない。** 「格下げ」が意味するのは **問題の解決ではなく影響範囲の封じ込め**である。

`constraints_guard` の判定（案3・条件付き可）と私の「上乗せに格下げ」は、実は同じ設計を別の語彙で言っているだけで対立していない。整理すると:

| | ITP 7 日キャップという事実 | 機能への影響 |
|---|---|---|
| 格下げ前（差分型を主系に据えた場合） | 消えない | 主要体験が丸ごと壊れる（最も価値を発揮すべき層で機能停止） |
| 格下げ後（日次ダイジェストを核、差分は上乗せ） | **依然として消えない** | 上乗せ部分だけが「初回相当」に静かに縮退し、核（ダイジェスト自体）は無傷 |

つまり「格下げ」がやっているのは ITP のバグを直すことではなく、**ITP が発火したときに壊れる範囲を「上乗せの便利機能」だけに限定する**こと。`constraints_guard` が課した「フォールバック必須」（タイムスタンプが無い/消えたら全件表示に自然劣化・エラーや空画面を出さない）は、私がラウンド1 の操作レビュー手順 4 で書いた内容と完全に一致している。**ここは合意** — ただし念のため明確化: このフォールバック UI（「初回として全件表示している」旨の文言）は **格下げしたからといって実装を省略してよい部分ではなく、格下げした結果として必須になる部分**である（任意機能の中の必須要件、という位置づけ）。

## 4. `data_pipeline` への確認: 日付シード shuffle は私が却下した時間分割シャッフルと同じか

**別物であり、対立していない。** むしろ `data_pipeline` の提案は私の案 1（日次ダイジェスト）の内部実装そのものだと理解している。

- 私が不採用としたのは **1 日の中でさらに時間帯単位（30 分・1 時間等）に区切って表示を切り替える**もの（Product Hunt の 30 分周期方式）。これは「同じ日にもう一度見ても違う」という**日内バリエーション**であり、(a) ページを開いたまま自動で内容が動く実装に寄りやすく WCAG 2.2.2 リスクがある、(b) 「また来る理由」という意味でのリマインド価値を生まない、という 2 点で却下した。
- `data_pipeline` が §「新規性の枯渇」で提案しているのは **候補プール（数千件オーダー）から、日付をシードにして毎日違う部分集合を抽出する**というもの。これは粒度が「日」であり、私が案 1 の操作レビュー手順 2〜3 で書いた「同日内は同じ一覧・翌日は入れ替わる」という決定論的シードの生成ロジックの**中身の実装方法**そのものに一致する。ページを開いている間に内容が動くことはなく、WCAG 2.2.2 のリスクも発生しない。

**結論**: `data_pipeline` の日付シード shuffle は私が却下した案とは粒度・目的が異なる別物であり、むしろ私が「採用」とした日次ダイジェストの実装詳細として歓迎する。時間帯単位のシャッフル（却下した方）を今後も持ち出す提案があれば、その時にあらためて a11y の懸念を出す。
