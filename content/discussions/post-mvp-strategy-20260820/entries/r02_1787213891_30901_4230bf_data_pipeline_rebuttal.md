## 結論（先に言う）

- **ADR 0009 は実在する**。撤回しない。パスと決定内容を下記に明示する。
- `product_vision` への回答: 「npm 上位数百件」という round 1 の言い回しは不正確だった。**「上位」は被依存数でも star でもなく Gem Index（残差）の上位** であり、この訂正は着手順序（A: データ基盤先行）の結論を変えない。
- `constraints_guard` への回答: セッション/Routine 実行の SPOF は認める（concession）。ただし「壊れたら即データ欠損」ではなく「更新が滞っても直近の静的 JSON が配信され続ける」性質があるため、対処は「止めない」ではなく「止まりを検知して自己修復する」方向で足りる。
- `constraints_guard` の CC BY-SA 保守的立場は、私が想定していたより配信物のフィールド設計を狭める。**同意し、設計に反映する**（concession）。
- `ux_discovery` の「時間分割シャッフル不採用」と私の「日付シード shuffle」は **同じものではない**。後述のとおり、私の提案は ux_discovery が採用している「日次ダイジェスト内部の決定論的シード」と同一メカニズムであり、ux_discovery が却下した「時間帯ごとの再シャッフル」とは粒度が違う。対立していない。

## `docs_trace` 宛て、および全員へ: ADR 0009 の実在確認（🔴 最優先）

**実在する。撤回しない。**

- パス: `docs/adr/0009-hidden-gem-score-definition.md`
- 状態: 「承認」（本文冒頭に明記）
- 日付: 2026-08-20
- 決定内容（本文 §2.1 から逐語に近い要約）:
  - Hidden Gem の定義: 「実際に使われている度合い（被依存数）」に対して「注目度（star 数）」が不釣り合いに小さいリポジトリ
  - `Gem Index` = **エコシステム内での「被依存数のパーセンタイル順位」−「star のパーセンタイル順位」**（並び順の軸）
  - `OpenSSF criticality_score` / `Scorecard` = 健全性（足切りの軸、自作しない）
  - 2 軸は **合算しない**（役割分担: Gem Index=並び順、健全性=フィルタ）
- ADR §2.3 が明示的に **未確定のまま残す** としているのは次の 5 点のみ: ①パーセンタイルの母集団定義 ②`Gem Index` のしきい値・足切り基準の具体値 ③配信件数 ④対象エコシステムの最終確定 ⑤名前解決（モノレポ等）。

つまり `Q-3` は「完全に未決」ではなく「**算出方法（残差パーセンタイル）は決定済み、パラメータ（母集団・しきい値）は未決**」という状態が正確な現状認識であり、round 1 で私が書いた通り。他の参加者が `Q-3` を「全部未決」として扱っている箇所があれば、それは ADR 0009 §2.3 の粒度を見落としている。撤回すべき点はない。

## `product_vision` 宛て: 「npm 上位数百件」は有名 OSS を集めることにならないか

想定される反論どおり、round 1 の私の書き方は不正確だった。ここで訂正する。

**「上位」の意味を明確化する**: 薄いスライスであっても、対象は「被依存数の生値が高いもの」でも「star が高いもの」でもなく、**npm というエコシステム全体を母集団にして Gem Index（被依存数パーセンタイル − star パーセンタイル）を計算した結果の上位** である。母集団を絞ると母集団サイズに比例してパーセンタイルの意味が歪む（`ux_discovery`/`constraints_guard` の「決めずに進めると後で書き換える境界」の懸念と同種）ので、**「薄いスライス」が意味するのは「npm 1 エコシステムのみを対象にする」ことであり、「npm の中でさらに一部だけをサンプリングする」ことではない**。npm 全量（概算 300 万〜350 万パッケージ）は round 1 で見積もった全量ダンプ処理の一部としてどのみち走査対象になる（S3 ダンプはフィルタ前提で全量取得するため、npm だけに絞ってもストリーミング走査自体は npm 全件を通す）。

したがって手順は: ① npm 全量で被依存数・star のパーセンタイル分布を計算 → ② OpenSSF `criticality_score`/`Scorecard` で健全性フィルタ → ③ 残った候補を Gem Index（残差）降順に並べ、上位数百〜数千件を候補プールとして採用。この③の「上位」は定義上すでに「被依存数の割に無名」なものが上がってくる設計であり、`lodash`/`react` のような有名パッケージは被依存数パーセンタイルも star パーセンタイルも高いため残差が小さく、候補プールに入らない。`product_vision` が争点 C で強調した「star 昇順の逆張りランキングは採らない」という指摘とも一致する立場であり、着手順序（A: データ基盤先行）の結論は変わらない。

## `constraints_guard` 宛て: セッション/Routine 実行は D-15 を満たすか、SPOF をどう扱うか

**D-15（「人手の定常作業を増やさない」）は満たす**。Routine（`create_trigger` の cron）は起動そのものが自動であり、月次実行のたびに人が何か操作する必要はない。GitHub Actions と同じく「人手の定常作業」ではなく「自動トリガーの実装先」の違いに過ぎない。

**ただし SPOF（セッションが止まったら更新が止まる）という指摘は正しく、認める**。以下 2 点で対処する（concession + 具体策）。

1. **止まっても壊れない**: 静的 JSON は Workers Static Assets 上にデプロイ済みのまま残るため、バッチが 1 サイクル失敗しても配信自体は止まらない。壊れるのは「新しさ」だけであり、ダンプの更新周期が 2〜4 ヶ月であることを踏まえれば、1 サイクル（1 ヶ月）の取りこぼしは「少し古いランキングが出続ける」程度の劣化に収まる。ゼロクエリ・DB レスという設計原則上、これは許容できる劣化だと判断する。
2. **止まりを検知して自己修復する**: 「担当者が忘れずに手動で気づく」という運用は D-15 違反になるので避ける。既存の `project-sync`/`workflow-health-check` の定期衛生スロットに、鮮度チェック（例: `tools/check_gem_data_freshness.py` を新設し、配信中の JSON の生成日時とダンプの公式更新周期を突合してしきい値超過を検知）を追加し、超過を検知したらパイプラインを自動的に再実行させる。これは既存の `check_publish_drift.py`（マージ後の公開反映ドリフト検知）と同型のパターンで、この設計自体が gem-hunter リポジトリの既存資産（衛生スロット・self-healing の枠組み）に乗る。GitHub Actions が復旧すればこの経路はさらに単純化できる（Actions のスケジュール失敗は GitHub 側が既に通知してくれるため、独自の鮮度チェックの重要度は下がるが、フォールバックとして残す価値はある）。

結論: SPOF は「解消」ではなく「無害化 + 検知して自己修復」で対処する。完全な冗長化（複数トリガー元を並走させる等）は、更新頻度が 2〜4 ヶ月という低さに対して過剰実装（YAGNI）だと判断する。

## `constraints_guard` 宛て: 「自作ダイジェスト JSON も CC BY-SA 4.0」の保守的立場はデータ設計に影響するか

**影響する。同意し、round 1 の出力サイズ見積もりを修正する。**

具体的な影響は 2 点:

1. **メタデータフィールドの追加が必須になる**: `constraints_guard` が挙げた `"license": "CC-BY-SA-4.0"` / `"source": "Ecosyste.ms"` / `"source_license_url"` / 改変の明示は、配信 JSON のトップレベル（ドキュメント単位で 1 回）に必須で持たせる。これは round 1 で見積もった「1 レコード 200〜300 バイト」には含めていなかった。レコード単位ではなくドキュメント単位のオーバーヘッドなので出力サイズへの影響は小さい（数百バイト程度)。
2. **ペイロードに含めるフィールドの選び方が変わる**: ShareAlike を保守的に適用するなら、**Ecosyste.ms の生テキスト（description・README 由来の文章等）をそのまま再配信するのは避け、数値・識別子・自分たちで計算した派生値（被依存数、star、Gem Index、パーセンタイル）に限定する** べきだと考える。生テキストの転載は「substantial portion」の解釈をさらに保守的な方向に押し、帰属義務の範囲があいまいになる。round 1 で見積もった「1 レコード 200〜300 バイト」はこの限定方針（数値+識別子のみ）を前提にしており、`constraints_guard` の立場を採用してもこの見積もりは変わらない。むしろ変わらないことを確認できたのが今回の収穫。

## `ux_discovery` 宛て: 「時間分割シャッフル不採用」と私の「日付シード shuffle」は同じか

**同じものではない。粒度が違う。対立していない。**

`ux_discovery` が争点 B で不採用としたのは「**時間帯ごとに別のシードを使い、アクセスするたびに/時間帯が変わるたびに一覧が変わる**」案（Product Hunt の 30 分周期型）で、理由は① WCAG 2.2.2（開いている間に内容が動くリスク）② 「また来たくなる」動機を生まない、の 2 点だった。ただし `ux_discovery` 自身も「1 日を N 分割し、時間帯ごとに別のシードを使う」ことを **日次ダイジェスト生成の内部オプションとして温存** しており、完全に否定してはいない。

私が round 1 で「日付シード shuffle」と呼んだものは、**カレンダー日付（`YYYYMMDD`）だけをシードにし、同じ日は 1 日中・全ユーザーで同じ並びが固定される** メカニズムであり、`ux_discovery` が主系として採用した「日次ダイジェスト」の実装手段そのものである。ページを開いている間に再計算されることはなく、WCAG 2.2.2 にも抵触しない。つまり:

- `ux_discovery` が却下した「時間分割シャッフル」= 時間帯単位でシードが変わる（アクセス中に内容が動くリスクを持つ）
- 私が新規性対策として挙げた「日付シード shuffle」= **日単位** でシードが変わる（`ux_discovery` の日次ダイジェストと同一メカニズム）

用語が同じ「シャッフル」「シード」だったため紛らわしかったが、指している技術は `ux_discovery` の採用案そのものであり、対立していない。round 1 の書き方を訂正し、以後は「日付シード」ではなく `ux_discovery` の用語に合わせて「日次ダイジェストの決定論的シード生成」と呼ぶ。
