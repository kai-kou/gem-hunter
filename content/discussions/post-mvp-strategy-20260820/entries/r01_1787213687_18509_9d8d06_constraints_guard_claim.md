## constraints_guard: 制約適合性の判定（round 1）

結論を先に: **7 案のうち不可は 1 件のみ（6: メール/push）。もう 1 件（7: ログイン限定パーソナライズ）は現行形では不可だが、ログイン非依存に作り替えれば救済可能。** 争点 E（ShareAlike）は「自作ダイジェスト JSON も CC BY-SA 4.0 として再配布可能にする」という保守的な立場を取るべき。争点 A は **フルセットだと `sp:8` を超える。データ基盤とダイジェスト UI の 2 スプリントに割るべき**。

### 争点 B: 7 案の抵触判定

### 争点 E: CC BY-SA 4.0 ShareAlike と帰属表示（🔴 最重要・断定する）

**立場**: 保守的側に倒し、**自作の合成ダイジェスト JSON・Gem Index も CC BY-SA 4.0 として扱う**（＝ 誰でも再利用可能にする）。

- 根拠: `supplement.md` §4.1 の公式文言は「all or a substantial portion のデータに sui generis database rights を伴うデータを組み合わせた場合」に継承義務が及ぶとしつつ、数値的な線引きを示していない。gem-hunter のダイジェストは Ecosyste.ms の **バルクダンプ（1,300 万件規模）から実質全件を走査して算出したランキングの一部** であり、「substantial portion に基づく派生物」と保守的に扱うのが安全（`D-3` の説明可能性とも整合: 白黒つかない領域はリスク回避側に倒す）。
- コストはほぼゼロ: gem-hunter は元々このデータを非独占的に公開する前提（商用ライセンスも検討していない）なので、CC BY-SA 4.0 を名乗ることに実害がない。ライセンス表明を **静的 JSON 自体のメタデータ**（`"license": "CC-BY-SA-4.0", "source": "Ecosyste.ms", "source_license_url": "..."）に埋め込む。
- **UI 帰属表示の最小要件**（`GR-6` の実体化）: ① ダイジェスト/ランキングを表示する画面には常に "Data via Ecosyste.ms (CC BY-SA 4.0)" とライセンスへのリンクをフッターではなく **当該コンポーネントの直近**（一覧の下 or ヘッダー内）に置く ② 改変の明示（"gem-hunter がパーセンタイル計算により再構成" 等の 1 行）③ RSS フィードの `<rights>` / `<generator>` にも同内容を入れる。
- コード側の AGPLv3 は **Ecosyste.ms のコードを流用しない限り波及しない**（gem-hunter は API/S3 経由でデータのみを消費するため無関係。念のため PR/ADR に「コードは参照していない」と一筆書く）。
- **NFR-33 相当の配慮も忘れない**: ダイジェストは `is:public` 相当のフィルタ済みデータのみを含めること（Ecosyste.ms 側は公開パッケージメタデータのみのはずだが、実装時に private/削除済みリポジトリの混入がないか検証する）。

### 争点 A: 次の一歩のスコープ（`sp:8` を超えないか）

**断定**: 7 案 + データ基盤 + ライセンス対応を **1 スプリントに詰め込むと `sp:8` を超える**。`session-sprint-rules.md` §3「`sp:8` 超なら分割」・`project-mission.md` の SP 表で「新規フェーズ着手（Phase 2 のデータパイプライン等）」は単体で `sp:8` 相当と定義されており、その上にダイジェスト UI・RSS・帰属表示・シャッフルロジックを重ねる余地はない。

**推奨分割**（2 スプリント構成）:
1. **SP-A（データ基盤・`sp:8`）**: Ecosyste.ms S3 バルクダンプの取得・パース → 集計フィールド（`dependent_packages_count` 等）の実在検証（`supplement.md` §4.2 の未検証事項を最初に潰す）→ パーセンタイル計算 → npm/PyPI 統合 → CC BY-SA メタデータ付き静的 JSON 出力。バッチのトリガー方式（後述 D）をここで確定させる。UI は最小限（既存一覧への統合のみ、または JSON の直接検証で可）。
2. **SP-B（ダイジェスト UI・`sp:5`）**: 案 1 + 2 + 5（有限ダイジェスト + 決定論的シャッフル + RSS）+ 帰属表示 UI。SP-A の JSON を消費するだけなので UI 中心で軽い。案 3・4・7（改良版）は **この場で決めなくてよい積み上げ候補** として `S-2` バックログに送る（後述）。

案 6 は不可なので着手対象から除外。案 7 はログイン非依存に作り替えた版のみ後続候補にする。

### 決めずに進めると後で全体を書き換える境界（3 点・断定）

1. **静的ダイジェスト JSON のスキーマとライセンスメタデータ**: 帰属表示・改変明示のフィールドを最初のスキーマ設計に含めないと、後から UI 全画面に手を入れる回収コストが発生する（`NFR-18` のキャッシュキー/スキーマバージョニングと同じ理由）。SP-A で確定させる。
2. **ダイジェストの母集団とパーソナライズ非依存性を先に固定する**: 「全員同じ N 件」を最初に決め切らないまま実装すると、後で誰か（案 7 のような)が個人化を混ぜたくなった時に `D-6` 違反のアーキテクチャ（ユーザー単位の計算・保存）へなし崩しで寄っていく危険がある。**SP-A/SP-B 双方で「入力はブラウザの手入力・URL・日付のみ」という不変条件を明記する**。
3. **バッチ実行方式（`D-15` 手離れ）**: GitHub Actions が制限中の現状で、S3 バルクダンプ更新（2〜4 ヶ月毎）の取り込みを **誰が / どう定期実行するか** を決めないまま静的 JSON 配信を始めると、更新が誰の責務でもない「手動デプロイ経路」が生まれ `D-15` を破る。Cloudflare Cron Triggers（Workers Free でも利用可）か、セッション起点の手動再生成 + 鮮度監視のどちらかを SP-A で確定させる。

### 争点 F（参考）: 既存 S-2 バックログとの関係

`US-28`（お気に入り）は案 7 改良版（手入力パーソナライズ）の代替導線になりうる（ログイン不要の「興味リスト」入力として再利用可）。`US-29`（検索履歴）は案 3（前回訪問差分）の実装基盤としてそのまま転用できる可能性が高い。両者を破棄せず、SP-B 以降で「新方針の部品」として再評価することを推奨（断定はしないが強い所感として残す）。
