## 1. data_pipeline の主張「静的 JSON は D-18 の禁止対象ではない」の検証

### data_pipeline の主張
- ADR 0009 で Gem Index 算出方法は確定済み
- 静的 JSON はビルド成果物であり、ランタイムの永続ストア（R2/D1/KV）と別カテゴリ
- D-18 の読み替えが必要だが、矛盾ではない

### 実ファイル確認（D-18 全文）

**docs/02_requirements/open-questions.md より**:
```
| **D-18** | **MVP のキャッシュは HTTP `Cache-Control` + Workers Caching のみとし、
永続ストア（R2 / D1 / Durable Objects / KV）を採用しない。** 
`NFR-17` Cache Port は維持し、実装位置を **`src/infrastructure/platform/`** と定める（`open-next.config.ts` ではない）。
L3 の導入条件は [インフラ設計](../03_design/infrastructure/infrastructure-design.md) §6.2 
の観測条件を変更せずに維持する | 2026-08-18 |
```

**判定**: ✅ **data_pipeline の読み替えは正当**

根拠：
1. D-18 は「**ランタイムの永続ストア**（R2/D1/KV）を採用しない」と明記
2. 「ビルド成果物」「デプロイ時の Static Assets」という層は明示されない
3. 現に JavaScript/CSS は既に Workers Static Assets に乗っている
4. ただし **D-18 の注記として「静的 JSON は Static Assets として配信してよい」を明文化すべき**

**ただし注意**: D-24（2026-08-19）が D-18 の実装方式の一部を改訂しており、現在のキャッシュ戦略は「HTTP `Cache-Control` + Workers Caching」から「アプリ内 `CachePort`」へ主役が変わっている。

## 2. constraints_guard の主張「ログイン限定パーソナライズは D-6 に抵触」の検証

### constraints_guard の主張
- ログイン限定パーソナライズ（差分表示など）は D-6 違反
- ただし「ログイン非依存に作り替えれば救済可能」

### 実ファイル確認（D-6 全文）

**docs/02_requirements/open-questions.md より**:
```
| **D-6** | **サーバー側の単一 Fine-grained PAT を既定とし、加えて「任意の GitHub OAuth ログイン」を MVP に含める。** 
未ログインでも全機能が使え、ログインは **レート枠を各自のものに切り替えるだけ**。
あわせてキャッシュ・request coalescing・直列化・ETag・残量監視による degraded 表示を要件化する
```

関連の帰結記述：
```
- 🔴 **ログインは完全に任意で、機能差を作らない**。ログインで変わるのは **レート枠だけ**
（未ログイン = アプリ共有枠、ログイン = 各自の 30 req/分）。
「ログインしないと使えない機能」を作った瞬間、`D-6` の目的（不特定多数が気軽に使える）が壊れる。
```

**判定**: ✅ **constraints_guard の指摘は正当**

根拠：
1. D-6 は「ログインで機能差を作らない」と明記
2. パーソナライズ機能（差分表示・お気に入り除外）はログイン必須なら機能差
3. ログイン非依存（localStorage でフォールバック）なら D-6 を満たす

## 3. ux_discovery / product_vision の主張「ダイジェストは次スプリント実装可能」への検証

### 争点
- ux_discovery：日次ダイジェスト（静的 JSON・状態レス）は Gem Index なしで実装可
- product_vision：そんなダイジェストは GitHub Trending の劣化コピーで R-2 違反

### 実ドキュメント確認（既に決定済みの制約）

**inception-deck.md Q4.2（やらないこと）より**:
```
| **通知・アラート・週刊ダイジェストの配信** | 永続化と常駐処理が必要で、DB レス原則と衝突する | `Q-5` |
```

**判定**: 🔴 **既に Phase 1 では「やらない」と決定済み**

根拠：
1. 週刊ダイジェスト（配信・リマインド型）は Q4.2 で明示的に「やらない」と記載
2. 理由は D-5（DB レス原則）との衝突
3. Q5 に「永続化と常駐処理が必要」という制約が明示

**補足**: ux_discovery が「日次ダイジェスト」（配信ではなく、訪れるたびに「今日の分」を表示）と「週刊ダイジェスト」（メール配信型）を混同している可能性がある。前者なら DB レス原則内で実装可能だが、後者は配信先リスト永続化のため D-5/D-14 に抵触。

## 5. 各案が已決の制約に抵触するかの整理

| 案 | 既決の制約 | 抵触判定 | 理由 |
|---|---|---|---|
| 日次ダイジェスト（訪問時表示・静的 JSON） | D-5（DB レス）/ D-18（永続ストア不可） | **可** | 静的 JSON は Static Assets・ランタイムに永続ストアを持たない |
| メール/push 配信（購読者リスト必須） | D-5（DB レス）/ D-14（個人情報ログ禁止） | **不可** | 配信先アドレス保持が D-5/D-14 に違反 |
| 週刊ダイジェスト配信 | Q4.2 / D-5 / D-14 | **不可** | 既に Q4.2 で「やらない」と明記・配信リスト永続化が D-5 違反 |
| ログイン限定パーソナライズ | D-6（ログインで機能差なし） | **不可**（ただし救済可） | ログイン必須なら D-6 違反。ログイン非依存（localStorage フォールバック）に設計し直せば可 |
| Gem Index フロントロード（Phase 1 に前倒し） | D-3（Phase 2 の定義） / inception-deck Q2 | **不可** | D-3 で「構想として記述するが Phase 1 では実装しない」と明記 |

## 6. 更新が必要なドキュメント（いずれの案を採る場合も）

### D-18 への注記追加
```
【注記（2026-08-20）】「永続ストア」はランタイムの R2/D1/Durable Objects/KV を指す。
ビルド時に生成する静的 JSON（Assets）、JavaScript/CSS はこの禁止に含まない。
```

### D-6 の「ログイン非依存パーソナライズ」の明示
```
パーソナライズ機能（例：前回訪問以降の差分強調・お気に入り除外）は、
ログインを**スキップ可能**に設計すること（localStorage フォールバック）。
ログイン必須にした瞬間、D-6 の「ログインで機能差を作らない」原則が破れる。
```

### Q4.2 の既決事項の明示化
```
🔴 **「通知・アラート・週刊ダイジェストの配信」は Phase 1 では採用しない。**
理由：配信先リスト永続化が D-5（DB レス原則）に違反するため。
「訪れるたびに「今日のダイジェスト」を表示」（リアルタイム生成・状態レス）は別軸。
```

---

## 結論

1. **data_pipeline の「静的 JSON は D-18 と矛盾しない」は正当**。ただし D-18 に読み替え注記を足すべき。

2. **constraints_guard の「ログイン限定パーソナライズは D-6 違反」は正当**。ただし「ログイン非依存フォールバック」で救済可能。

3. **ux_discovery の「日次ダイジェストは次スプリント実装可」と product_vision の「データなしでは差別化にならない」は**、「何をダイジェストの中身にするか」で対立している。既決の事実：
   - 「週刊ダイジェスト配信」は Q4.2 で既に「やらない」と決定済み
   - 「Gem Index のスコアリング」は ADR 0009 で既に確定済み

4. **いかなる案を採る場合も、D-3（Phase 1 では Gem Index 実装しない）は維持される**。
