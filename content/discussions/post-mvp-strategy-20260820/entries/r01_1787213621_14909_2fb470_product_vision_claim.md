## product_vision の立場（ラウンド1）

### 総論: A・B・C・F は 1 本の線でつながる

先に結論を書く。**「Gem Index のデータ基盤」と「ゼロクエリのリストアップ UI」を別プロジェクトとして並走させてはいけない。両者は同一機能の「データ層」と「提示層」であり、この順序（データ→提示）でしか差別化が成立しない。** `US-28`/`US-29` はその提示層に軽く再利用できる補助部品にすぎず、優先着手の理由にはならない。

---

### A: 次に着手するのは何か

**結論: Gem Index のデータ基盤（`GR-1`/`GR-5`/`GR-6` の最小構成）を先に着手し、ゼロクエリ UI はその上に「提示のバリエーション」として乗せる。`S-2` の積み上げ（`US-10`/`US-27`/`US-28`/`US-29`）を先に消化する理由はない。**

根拠は `R-2`（GitHub 純正検索で 1 行で書けるものは差別化にならない）そのものである。仮に Gem Index を持たずに「ランダム/日替わりで OSS を並べるだけ」のゼロクエリ UI を先に作ったら、それは GitHub Explore/Trending が既にやっていることの劣化コピーにしかならない（補完リサーチ §3.4: GitHub Trending は star 数だけで並べ「毎日 30 人がコミットする活発なプロジェクトが全く出てこない」と批判されている対象そのもの）。gem-hunter が主張できる差別化は唯一、**star に対して被依存数が不釣り合いに大きいものを提示できること**（`GR-1`）であり、これは Ecosyste.ms のデータなしには実現できない。

一方で `US-28`（お気に入り）`US-29`（検索履歴）は `S-2` に元々置かれている通り、既存の「検索して選ぶ」体験の周辺機能であり、ミッションの中核（star で埋もれた実利用 OSS を見つける）には貢献しない。`project-mission.md` の優先順位表「新機能を足すか、積み上げ基盤を整えるか → 基盤を優先する（`D-9`）」に照らせば、Gem Index データ基盤は「後から変えると全体を書き換える境界」（`S-0` の設計思想と同型）であり、ゼロクエリ UI・多軸バッジ・週刊ダイジェストのすべてがこのデータ基盤の上に乗る。基盤を後回しにして UI 側の枝葉（お気に入り・履歴）を先に積むのは `D-9` 違反の順序である。

**Dynamic 補正込みの見積もり感**: `GR-5`（静的データ配信）の最小構成 — Ecosyste.ms S3 バルクダンプ取得 → 被依存数抽出 → GitHub star とのパーセンタイル残差計算 → 日次バッチで静的 JSON 生成、は `project-mission.md` の SP 表で「新規フェーズ着手（アーキテクチャ変更）」`sp:8` 相当 + Dynamic 補正（一次確認未了の S3 ダンプの集計フィールド有無・補完リサーチ §5 の「❌ 未検証」項目）が乗る。**分割前提で `SP-13` と同様に先行スプリントとして切り出すべき規模**。

### B: 「リマインド的なリストアップ」の実体 — 代替解釈を先に立てる

🔴 飼い主の「リマインドされたい」を額面通り「通知が届く」と読むのは早計。少なくとも 3 通りの解釈がある。

1. **受動プッシュ型**: メール/通知のように向こうから届く（Hidden Gems 版メルマガ）
2. **受動プル型**: ログイン・履歴なしで、訪れるたびに「今日の分」が待っている（Wordle 型の日替わり有限リスト）
3. **差分型**: 「前回見てから増えた分」だけが強調される（既読管理を伴う）

このうち **1 は制約と正面から衝突する**（`D-14`: サーバーに個人データを持たない・ログ出力もしない。メール配信にはアドレス保持が要る。ディープリサーチ F-3 も Hugging Face Daily Papers のメール購読がログイン必須である点を明示し、gem-hunter では採用不可と結論づけている）。**3 は localStorage 依存で足元が崩れる**: 補完リサーチ §2.1 が明らかにした Safari ITP の 7 日キャップは「7 日間サイト訪問がないと `localStorage` ごと消える」という仕様であり、**「リマインドされたい＝久しぶりに思い出したい」というまさにその利用シーンで、思い出す頃には差分の基準点が消えている** という自己矛盾を抱える。

**結論: 実体は 2（受動プル型・有限日替わりダイジェスト）を主系とし、配信面として RSS を並走させる。** これはディープリサーチ F-12「方向性候補 A」を採用しつつ、リサーチが手薄だった「配信面」を独自に補う判断である。

- **なぜ 2 か**: NN/g の無限スクロール非推奨（F-2）は「探索・比較・上位数件の検分」には無限フィードが不適と明言しており、a11y ゲート（Lighthouse 100・キーボード完走）とも整合する。有限件数（例 5〜10 件）+ 明示的な区切りは制約充足性が最も高い（F-12 の④）。
- **なぜ RSS を足すか**: `D-14`（サーバーに個人データを持たない）と「リマインド」を両立させる最も素直な解は、**サーバーが状態を持つのではなく、ユーザー側のツール（RSS リーダー）に既読管理を委譲すること** である。日次バッチで生成する静的 JSON をそのまま Atom/RSS に変換するだけで実装コストはほぼゼロ（`GR-5` の副産物）。「メール購読」が制約違反なのに対し、RSS は購読者情報をサーバーが一切持たない。この論点は今回のディープリサーチ・補完リサーチのどちらも扱っておらず（未調査領域）、product_vision としての独自提案として明示しておく。他の参加者の反証を歓迎する。
- **時間分割シャッフル（候補 B・F-13）は MVP で採らない**: セレンディピティ研究（Kaminskas & Bridge 2 成分・UMAP'25 3 成分）はいずれも「意外性だけでは成立せず、relevance/enriching を伴わないと質が担保されない」と整理しており（F-13 根拠）、純粋な時間帯シャッフルは理論的裏付けを欠く。加えて URL 共有時に受け手が別の並びを見る（`SP-2` で確定した「URL の再現性」という `S-0` の不変境界と衝突しうる — シードを URL に埋め込む追加設計が要る）。**「新規性の枯渇」への対処法も先行研究に実例がない**（ディープリサーチ §5 の未解決の問い）ため、対処法が固まっていない技法を先に投入するのはリスクが高い。Phase 2.x の実験候補として保留するのが妥当。
- **差分型（3）は「壊れることを前提にした加点要素」にとどめる**: localStorage に前回訪問日時があれば「前回以降に増えた分」を強調表示してよいが、**それが無い（または消えた）場合は黙って「今日のダイジェスト」にフォールバックする** 設計にする。差分型を主要体験に据えると、Safari の長期未訪問ユーザー（＝最も「リマインド」を必要としている層）で機能が消える。
- **package.json 貼り付け型（npmgraph 前例・補完リサーチ §2.2）は別軸**: これは「能動的なコンテキスト入力」であり `キーワードを打たない` という点では zero-query だが、ユーザーがアクションを起こす必要がある点で「リマインド」の性質（向こうから来る/待っている）とは異なる。将来的に「あなたの `package.json` に近い Gem を教える」機能として面白いが、今回の争点 B の答えではない。混同しないこと。

### C: Gem Index をどう定義しどう見せるか

**結論: 並べ替えの軸は単一（星×被依存の残差パーセンタイル）のまま、UI 提示は多軸バッジで内訳を見せる「単一値 + 多軸内訳」の 2 層構成にする。単一スコアへの健全性の合算は既に `Q-1`/`Q-2` で却下済みであり、この結論を変える理由は今回の争点にはない。**

- 並べ替え軸を単一にする理由は目新しくない。`Q-3`（パーセンタイル順位の差）が既に決定済みであり、`Q-1`/`Q-2` の「健全性スコアを合算すると『健全だが有名』が上位に戻り、star 追随ランキングに退化する」という判断はそのまま Gem Index にも及ぶ。**この争点で唯一補強できるのは「なぜ多軸で見せるべきか」の根拠** であり、そこにディープリサーチ F-14 と UMAP'25 論文が使える。
- UMAP'25 論文（F-14 根拠）の逐語: "A formula that calculates experienced serendipity by summing the components fails to ensure this: one component can score exceptionally high, masking a low score in another"。これは「合算スコアは内訳を隠す」という一般命題であり、Gem Index を単一値で見せきる（内訳を出さない）実装は、たとえ並べ替え軸が単一であっても、**表示は分けるべき** という結論を支持する。
- 実例として Snyk / Socket.dev は「総合スコア + カテゴリ別内訳の併記」という 2 層構成を採っており（補完リサーチ §3.1）、これは自作せず既存プロダクトのパターンを踏襲すればよい。表示要素は最低限: 被依存数（`dependent_packages_count`/`dependent_repos_count`。Ecosyste.ms で個別フィールドとして取得可能・補完リサーチ §4.5）、star 数、最終更新。**健全性（OpenSSF）はバッジとして別掲するが Gem Index の計算には混ぜない**（`GR-2` は既存どおり独立した足切りフィルタに留める）。
- 説明可能性の効用は F-9（Explainable Recommendation が信頼・満足度を有意に高める、ただしトラストキャリブレーションの誤りにも注意）で裏付けられる。「なぜこれが Gem として出たか」を軸ごとに 1 行で言語化できる設計（例: 「被依存数は上位 5%、star は下位 40%」）にする。
- **偽 star 研究（補完リサーチ §1.1）をどう使うか**: 738 件の star 水増しパッケージの 70.46% が依存パッケージ数ゼロという事実は、「gem-hunter の指標（被依存数を分母/アンカーに据える設計）が、現実に確認されている操作手口に対して構造的に耐性を持つ」という **製品コピーとして使える一次証拠** である。これは README・ADR 0009（Hidden Gem スコア定義）に一次情報として引用すべきで、単なる背景説明に留めず「なぜ star 単独ランキングではなく被依存数残差を採ったか」の説明可能性（`project-mission.md` の判断基準「迷ったときは説明できる方を選ぶ」）を強化する具体的根拠になる。裏を返すと、**「star が低いだけ」の逆張りランキング（star 昇順）は絶対に採用してはならない**——それは偽 star とは逆方向だが同じ「単一シグナルへの過剰依存」の罠であり、被依存数という第二の軸があって初めて安全になる。

### F: 既存の `US-28` お気に入り・`US-29` 検索履歴は新方針の部品として再利用できるか

**結論: 部分的に再利用できるが、優先度を左右するほどの価値はない。着手順序（争点 A）を変える理由にはしない。**

- `US-28`（お気に入り・localStorage・端末間非同期が明示）は、ダイジェストの「これは自分がもう知っている」を除外するソフトなパーソナライズの元データとして転用できる。ただしこれは `D-6`（ログインで機能差を作らない）の範囲内で完結する localStorage 拡張であり、サーバー側の Gem Index データ基盤とは無関係な **クライアント層の話**。基盤着手の優先度には影響しない。
- `US-29`（検索履歴）も同様に、将来「過去に検索したトピックに近い Gem を優先表示する」というフィルタの種になりうるが、これは補完リサーチのどの検証済み事実にも支持されておらず、**投機的な提案** として扱うべき（Phase 2.x 以降・要検証）。今この争点に持ち込んで着手順序を動かす根拠にしない。
- 注意点: `US-28`/`US-29` はいずれも Safari ITP の 7 日キャップの影響を等しく受ける（補完リサーチ §2.1 の対象はストレージ全般）。zero-query ダイジェストの「差分型」を `US-28`/`US-29` の永続性に依存させる設計は、争点 B で述べた同じ弱点を継承するだけなので、**過度に依存する設計は避ける**。

### まとめ（争点をまたぐ一貫性チェック）

- A→B→C→F は「基盤（Gem Index データ）→ 提示（有限日替わり + RSS）→ 見せ方（単一軸並べ替え + 多軸内訳表示）→ 既存部品の軽い再利用」という一直線の依存関係にある。
- どの争点でも `R-2`（GitHub 純正検索で再現できるものは差別化にならない）を判定基準として一貫して適用した: ゼロクエリ UI 単体は再現可能（Trending の劣化コピー）、Gem Index を伴えば再現不可能（差別化として成立）。
- 偽 star 研究・Openbase/npms.io の教訓は、単に「参考になった」ではなく、それぞれ C（指標設計の耐性の説明可能性）と全体設計方針（静的バッチ・低運用コストへの支持）に直接効いている。
