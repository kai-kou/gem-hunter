## constraints_guard round 2: 4 点への回答（断定する）

### 1. `data_pipeline` への確認: `D-18` の読み替えは正しい

**同意する。趣旨は破っていない。** `D-18` が禁じているのは「Worker がリクエスト処理の実行時に読み書きする永続ストア」（R2/D1/DO/KV）であり、「ビルド時に生成されデプロイのたびに丸ごと置き換わる読み取り専用アセット」はそもそも別カテゴリ。`cloudflare-infrastructure.md` §5.1 が Static Assets を「無料・無制限」の別経路として明記している以上、JS/CSS と同じ扱いにする static JSON もこの境界の内側にある。

**境界のテストを 1 行で断定する**: 「Worker がそのファイルへ実行時に書き込むか？」。No なら `D-18` の対象外、Yes（部分更新・キャッシュ書き戻し等）なら対象内で禁止。data_pipeline 案（バッチが Cloudflare の外で JSON を生成 → git commit → デプロイで丸ごと差し替え）は明確に No 側。**`D-18` への 1 行注記は追加すべき**（誤読リスクは実在する。この議題自体で 2 名が「矛盾しないか」と聞いている時点で注記コストの正当性は証明済み）。

### 2. `data_pipeline` への事実確認: ADR 0009 は実在し、主張どおりの内容

`docs/adr/0009-hidden-gem-score-definition.md` を確認した。**主張は正確**:
- §2.1 で Gem Index = 「エコシステム内での被依存数パーセンタイル順位 − star のパーセンタイル順位」と算出方法を確定
- 役割分担も確定済み: Gem Index = 並び順（①過小評価度）/ `criticality_score` = 足切り（②健全性）、2 軸を合算しない（§3.2 で理由も明記）
- §2.3 で「意図的に未確定のまま残す」対象を明示（母集団定義・しきい値・配信件数・対象エコシステム最終確定・名前解決）— これは Q-3 の実データ待ち部分であり、算出**方法**とは別レイヤー

→ data_pipeline の「算出方法は ADR 0009 で決定済み・再論不要、しきい値だけ実データ待ち」は **正確**。この場で算出方法を再議論するのは無駄であり、争点 C はこの区分（方法=決定済み／数値=未決）を前提に進めてよい。

### 3. `product_vision` / `ux_discovery` / `data_pipeline` への譲歩: 自分の 2 スプリント分割は `C-2` で不成立、修正する

🔴 **自分の round 1 案（SP-A: データ基盤 `sp:8`、UI 最小限）を撤回し、`data_pipeline` の「薄いスライス」案・`ux_discovery` の 5 行デモ手順に合流する。**

`user-story-map.md` §5.2 `C-2`: 「デモ手順が 5 行以内で書ける（何を開き、何を入力し、何が見えれば成功か）」。同 §5.2 の規定はさらに強い: 「イネイブラーだけで構成されたスプリントを作ってよいのは `C-2` を満たせる場合に限る」。

自分が round 1 で書いた SP-A（「UI は最小限（既存一覧への統合のみ、または JSON の直接検証で可）」）を厳密に判定すると: 「静的 JSON の URL を直接開いてフィールドを目視確認する」は技術的には「開く／見る」を満たすが、**これは `C-2` の例が想定する『アプリを操作して確認する』デモではない**（`C-2` の悪い例「レート制限対策を実装する」と同型で、「バッチを実装する」も操作手順を書けと言われると app の中に確認できる場所がない）。つまり **自分の当初案は `C-2` の運用ゲートに抵触し、単独スプリントとして成立しない**。

**修正後の立場**: `data_pipeline` が既に提案していた「1 エコシステム（npm）・上位数百件のミニパイプライン」と、`ux_discovery` が既に書いた「日次ダイジェスト」の 5 行デモ（トップページを開く → 有限件数表示 → リロードで同一順序 → 日付モックで入れ替わり → キーボード完走）を **1 本のスプリント（SP-A′）に統合する**。これで `C-2` を満たしたまま `SD-1`（動作確認できる状態で終わる・開けるプレビュー URL）も満たす。見積もりは新規フェーズ着手 + Dynamic 補正（S3 ダンプの集計フィールド未検証・`supplement.md` §4.2）で `sp:8` を維持してよいが、**中身は「データ + 最小 UI」の垂直スライスに限定し、フルスケール化（PyPI 追加・RSS・帰属表示 UI の作り込み・ITP フォールバックの本実装）は SP-B（`sp:5`）に送る**。この修正は自分の争点 A の結論（2 スプリント分割）自体は変えないが、**分割の「切り方」を「データ→UI」の水平分割から「薄い垂直スライス→拡張」の垂直分割へ変える**。

### 4. `docs_trace` への反論: パターン B の一括りは誤り。RSS/静的ダイジェストは `D-5` 撤回を必要としない

`docs_trace` は round 1 §5「パターン B（別発見方式：週刊ダイジェスト / RSS 等）」を一括りにして「`D-5`（DB レス原則）と `Q-5`（やらないこと）を同時に撤回する必要あり」と結論しているが、**これは RSS と静的な日次/週刊ダイジェストには当てはまらない。過大な要求である。**

根拠: `prd.md` §11 の `GR-7` は「静的な『今週の Gem 一覧』ページ」を「週刊ダイジェストの配信版（永続化が必要）に対する DB レスの代替案（`Q-5`）」として **既に明記済み**。つまり「週刊ダイジェストを DB なしで代替する」という決定は `Q-5` の従属事項として **PRD にすでに存在する**。RSS も同型（購読者リストを持たない Pull 型・案 5、自分の round 1 判定「可」）。`D-5` を撤回する必要が生じるのは、`docs_trace` が同じ表の行に混ぜている **「通知（メール/push）」だけ**（自分の round 1 判定「不可」・`D-14`/`D-18` に正面抵触、これは `docs_trace` の指摘とも一致する）。

**訂正した表**:

| 案 | `docs_trace` の判定 | constraints_guard の訂正 |
|---|---|---|
| RSS 配信 | パターン B（`D-5` 撤回必須） | **`D-5` 撤回不要**。`GR-7` の代替案の延長線上にあり、静的バッチの副産物として作れる |
| 静的な日次/週刊ダイジェスト | パターン B（`D-5` 撤回必須） | **`D-5` 撤回不要**。まさに `GR-5`（静的データ配信）が想定していた実装そのもの |
| メール / push 通知 | パターン B（`D-5` 撤回必須） | **同意・`D-5` 撤回必須（または不可のまま却下）**。ここだけは `docs_trace` の判定が正しい |

`docs_trace` §2 のバックボーン整合性チェック（新 `A-n` が要る）自体は妥当な指摘であり、そこに異論はない。訂正するのは「B に分類した 3 案すべてが `D-5` 撤回コストを負う」という一般化のみ。**「今回追加する発見体験のうち `D-5` を揺るがすのは通知だけ」と切り分けることで、`docs_trace` が §4 で挙げた更新必須ファイル一覧（`prd.md`/`open-questions.md` への新規決定追加）も RSS・日次ダイジェストについては不要になり、ドキュメント整合性コストが `docs_trace` の見積もりより小さく済む**。
