## product_vision の譲歩（ラウンド2）

### 譲歩 1: 争点 A の順序対立 — 自分の R1 主張（「フルの `sp:8` データ基盤を UI 抜きで先に」）を撤回し、`data_pipeline` の「薄いスライス」案に同意する

R1 で自分は「Gem Index データ基盤（`GR-1`/`GR-5`/`GR-6` の最小構成、`sp:8` 相当）を UI より先に、`SP-13` と同型の先行スプリントとして切り出すべき」と主張した。`data_pipeline` は「データ基盤が先」という結論は同じだが、**「フルスケール（1,310 万件パイプライン）」ではなく「1 エコシステム・薄いスライスを先に通す」** べきだと具体化し、理由として `SD-1`（本物のプレビュー URL）と `SD-2`（TDD は本物の形をした JSON があれば書き始められる）の両方を満たせる最小単位だと述べている。

これは自分の R1 主張より正確なので撤回して同意する。理由: `sp:8` フルパイプラインを UI 抜きで走らせると、`session-sprint-rules.md` の「同一 `SP-n` が 3 回の firing を跨いでも `SD-1` に到達しない場合は分割」（`SP-1` の運用例）と同じリスクを最初から抱え込む。薄いスライスなら 1 スプリントで「データ→提示」の両方を通せる。

さらに `ux_discovery` の「日次ダイジェストを次の単独スプリントに」という主張も、よく読むと **矛盾しない**。`ux_discovery` は「Gem Index のスコアリング精緻化を待たずに、粗い基準（健全性フィルタ + 被依存数パーセンタイル逆順）でも `C-2` を満たせる」「UX 側は静的 JSON を受け取って有限リストとして描画するインターフェースだけ先に固定できれば着手できる」と述べており、この「粗い基準の静的 JSON」は `data_pipeline` が言う「薄いスライスの静的 JSON」と同一物である。つまり `ux_discovery`（UI 先行に見える）と `data_pipeline`（データ先行に見える）は、実は **同じ 1 スプリントを指している**——対立ではなく同義反復だった。

**決着案**: 次のスプリントは「（データ）薄いスライスのパイプライン + （UI）それを消費する日次ダイジェストの実描画」を **1 本のスプリント** として合体させる。データだけ・UI だけに分離しない。これにより `constraints_guard` の 2 スプリント分割案（`SP-A` データのみ `sp:8` → `SP-B` UI `sp:5`）よりも `SD-1`/`C-2` の要求を早く・確実に満たせる（詳細は別便のレビュートで `constraints_guard` に反論する）。

### 譲歩 2: 争点 B の時間分割シャッフルについて — `ux_discovery` の判定に同意し、自分の R1 の弱い立場を撤回する

R1 で自分は「セレンディピティ研究が意外性単独を支持しないから理論的裏付けを欠く」「Phase 2.x へ保留」とだけ述べ、扱いは「先送り」止まりだった。`ux_discovery` はこれをさらに具体化し、**Product Hunt 型の「開いている間に内容が動く」実装は WCAG 2.2.2（Pause, Stop, Hide）に抵触するリスクがある** という、自分の R1 になかった新しい強力な a11y 論拠を出した。gem-hunter の品質ゲートは Lighthouse Accessibility 100 が必達（`project-mission.md`）であり、この論拠は自分のセレンディピティ研究の論拠より直接的に効く。

`ux_discovery` の結論——「独立機能として不採用にし、日次ダイジェストの決定論的シード生成の内部技法（1 日を N 分割し時間帯ごとに別シードを使うオプション）として温存する」——の方が、自分の「Phase 2.x に先送り」より正確（「捨てる」のでも「先送り」のでもなく「ユーザー向けの独立した提示面にはしない」という区別）。これに同意し、自分の R1 の表現を訂正する。
