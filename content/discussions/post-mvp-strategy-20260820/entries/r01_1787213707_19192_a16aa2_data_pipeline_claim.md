## 結論（先に言う）

- **D**: バッチは Cloudflare 上では回さない。`D-18` は「ランタイムの永続ストア（R2/D1/DO/KV）」の禁止であって、**ビルド時にデプロイする静的アセットとは別カテゴリ**（現に JS/CSS は既に Workers Static Assets に乗っている）。矛盾はしない。ただし読み替えを明文化しないと事故るので、`D-18` に 1 行注記を足すべき。バッチの実行場所は **セッション実行 or Claude Code Remote の Routine（cron）** を暫定の一次経路にし、GitHub Actions 復旧後にそちらへ切り替える。Cloudflare Cron Triggers は不採用（後述）。
- **C**: Gem Index の**算出方法**（エコシステム内パーセンタイル順位の差）は ADR 0009 で確定済み・再論不要。**しきい値・配信件数の具体値**は今決めない（実データの分布を見てから）。ただし「母集団の切り方（npm と PyPI を混ぜない）」だけは今この場で決める。
- **A**: データ基盤を先に作る。UI 先行は「後で差し替える前提のモック」を書くだけの二度手間になり、`SD-1`（動作確認できる状態で終わる）の観点でも実データがないと操作レビューが成立しない。ただし「データ基盤 = フル 1,310 万件パイプライン」ではなく、**まず小さいスライスで通す**（後述）。
- **新規性の枯渇**: サーバー側で「既出」を追跡する仕組みは DB レスでは持てない。**候補プールを実際の配信件数より 1〜2 桁多く持ち、日付シードの決定論的シャッフルで見せる部分を毎日入れ替える**設計でごまかす。加えてダンプ更新（2〜4 ヶ月毎）のたびに候補プール自体が新陳代謝するので、枯渇は「完全には防げないが先延ばしにできる」。

## D: バッチをどこで回すか（最重要）

### D-18 との矛盾は見かけ上のもの

`open-questions.md` の `D-18` は「MVP のキャッシュは永続ストア（R2/D1/DO/KV）を採用しない」であり、`cloudflare-infrastructure.md` §2.1 の物理構成図でも「Worker はリクエストを処理して捨てるだけ」と明記されている。これは **「Worker が実行時に読み書きするランタイムストア」の禁止**であって、「デプロイ物に静的ファイルを含めること」の禁止ではない。実際 `cloudflare-infrastructure.md` §5.1 の条件 2 は「静的アセットは Workers Static Assets で配信する（**無料・無制限**）」と明記しており、JS/CSS/フォントは既にこの経路で配信している。

したがって設計としては:

```
バッチ（Cloudflare の外）
  → 静的 JSON を生成（例: public/data/gems-npm.json, gems-pypi.json）
  → git commit → PR → 自動マージ（main へは push/merge のみがトリガー・D-15）
  → wrangler deploy で Workers Static Assets として配信
```

これなら `D-18`（ランタイムストア不採用）にも `D-15`（デプロイトリガーは push/merge のみ）にも `NFR-21`（アプリランタイムに PaaS 固有 API を持ち込まない）にも抵触しない。**ただし `D-18` の文言だけを読むと「静的データも禁止」と誤読されるリスクが高い**（現に議題文でも「矛盾しないか」と聞かれている)。なので今回のスプリントの成果物として、`D-18` か `cloudflare-infrastructure.md` §4.2 に 1 行、「静的 JSON をビルド成果物として Static Assets に含めることは本項の対象外」と明記する注記コミットを提案する。地味だが将来の誤読・手戻りコストの方が高い。

### Cloudflare Cron Triggers を使わない理由

議題で選択肢として挙がっているので明示的に却下する。理由は 2 つ:

1. **書き込み先がない**。Cron Trigger で起動した Worker が計算結果をどこかに永続化しようとすると、選べるのは R2/KV/D1 しかなく `D-18` と正面衝突する。デプロイ済みの Static Assets へ実行時に書き戻すことはできない（Static Assets はビルド時に固定される読み取り専用アセットで、`cloudflare-infrastructure.md` の表にも「Workers Static Assets: 読み取り専用（revalidation 不可）」とある）。
2. **CPU 予算が壊滅的に足りない**。Free の 10ms/invocation は Cron Trigger にも適用される想定で、S3 ダンプ（1,310 万パッケージ）の解凍・走査・パーセンタイル計算は数十秒〜数分オーダーの CPU を要する処理であり、桁が 3〜4 桁違う。

### 実行場所の暫定案と概算

GitHub Actions は現在制限中（ジョブが数秒でログ 0 バイト失敗）なので、`D-23` の暫定運用（セッション実行）に倣い、まずは **Claude Code Remote の Routine（`create_trigger`、cron）** を使う。ダンプの更新頻度が 2〜4 ヶ月毎なので、月次でバッチセッションを起動し「更新があれば処理、なければ no-op」にする。GitHub Actions が復旧したら `wrangler-action` 相当のワークフローに移行し、この Routine は削除する（`D-15` の「運用の手離れ」原則どおり、最終的には人手ゼロの自動トリガーへ収束させる）。

概算（未検証の見積もりであることを明示する）:

- **S3 ダンプの取得**: 全量 1,310 万パッケージ分の tar.gz。1 パッケージのメタデータを 1〜3KB と仮定すると圧縮前で 15〜40GB、gzip 圧縮で 3〜8GB 程度と見積もる（実測していない。実装 1 歩目として `curl -sI` で `Content-Length` を確認するのが最初のタスクになる）。
- **対象を npm + PyPI（`GR-3`）に絞る**場合、npm は概算 300 万〜350 万パッケージ、PyPI は概算 60 万パッケージ規模と見て合計で全体の約 3 割程度。ダンプがエコシステム別に分割取得できない場合は全量ダウンロード後にフィルタする必要があり、上記の見積もりがそのまま処理時間に乗る。
- **処理時間**: セッション実行のダウンロード帯域を仮に 50〜100MB/s とすると 8GB のダウンロードは 1〜3 分。ストリーミング JSON（NDJSON 想定・全量を一度にメモリへ載せない）でのフィルタ・パーセンタイル計算は数分〜10 分オーダーと見積もる。1 ターン 8 ツール制限・タイムアウト対策（`session-safety-rules.md`）に触れるため、**バッチ本体は 1 本の長時間 Bash（`run_in_background: true`）に切り出し、パースはストリーミングで書く**必要がある。
- **出力サイズ**: 配信候補プールを仮に上位 2,000〜5,000 件（後述の新規性対策で必要な余剰込み）、1 レコード 200〜300 バイト程度とすると出力 JSON は 500KB〜1.5MB。Worker バンドル 3MB 制限とは別枠（Static Assets）なので気にする必要はないが、クライアント側でこの JSON をフェッチ・パースする前提なら初回転送コストとして許容範囲。
- **OpenSSF Scorecard**: 週次バッチ・100 万件規模で REST API 提供。フルダンプの全件を毎回 Scorecard に問い合わせるのは非現実的なので、**先に Gem Index（被依存数対 star の残差）で候補を絞ってから**、その候補（数千件オーダー）だけ Scorecard REST API で健全性を引く 2 段構成にする。月次のフル再計算とは別に、直近候補プールだけを週次で Scorecard 再チェックする軽量ジョブを足せる余地がある（Scorecard 側の更新頻度に合わせる）。

### アーキテクチャ上の置き場所

`application-architecture.md` にはまだバッチ・パイプラインの置き場所の規約が存在しない。**アプリの実行時レイヤー（`src/`）とは別**に、リポジトリ直下に `scripts/gem-pipeline/`（または `tools/` 配下）としてバッチ専用のスクリプト群を置くことを提案する。理由: `src/` はランタイム依存規則（`NFR-16`/`NFR-17`）の対象であり、バッチは Next.js のリクエストサイクルの外で動く別プロセスなので、同じ依存規則を適用する意味がない。出力（`public/data/*.json` 等)を `src/infrastructure/` のどのポートが読むかは UI 側の実装スプリントで決めればよく、今は「バッチはアプリの外」という境界線だけ決める。

## C: Gem Index の定義をこの場で決めるか

**決めない**。ADR 0009 で算出方法（エコシステム内パーセンタイル順位の差）と役割分担(並び順=Gem Index / 足切り=criticality_score)は既に確定しており、`prd.md` §13 もしきい値・配信件数・母集団の実データ依存部分を意図的に開けたままにしている。今この議論で数値を決め打つと「実データを見ずに前倒しで確定した」根拠のない決定になり、ADR 0009 §2.3 の設計判断と矛盾する。

ただし 1 点だけ今決めるべきものがある: **母集団はエコシステムごとに分離する**(npm の分布と PyPI の分布を混ぜてパーセンタイルを取らない)。理由は、被依存数のスケールがエコシステムごとに全く異なる(npm は 1 パッケージが数百〜数千の依存元を持つのが珍しくないが、PyPI は分布のレンジが違う)ため、混ぜたパーセンタイルは母集団の大きい方に支配されて意味を失う。これは「しきい値の具体値」ではなく「パーセンタイルの取り方(方法)」の話なので、`Q-3` の実データ待ちとは独立に決定できる。

## A: データ基盤が先か UI が先か

**データ基盤が先**。ただし「フルスケール」ではなく **薄いスライスを先に通す**べき。

理由:
1. `SD-1`(動作確認できる状態で終わる)は UI に本物のプレビュー URL を貼ることを要求する。Gem Index はモックデータで作ると、実データの分布(外れ値・欠損・モノレポの名前解決漏れ)で UI が壊れる箇所が後から出てきて手戻りになる。
2. 逆に「フルの 1,310 万件パイプラインを完成させてから UI に着手」も遅すぎる。`SD-2`(TDD 主体)の観点でも、UI 側のテストは「小さくても本物の形をした JSON」があれば書き始められる。

具体案: 最初のスプリントでは対象を **1 エコシステム(npm)・上位数百件**に絞ったミニパイプラインを通し(全量ダウンロードはするが処理対象を絞る、または将来的にダンプがエコシステム別に取得可能であればそちらを使う)、UI 側はこの小さい JSON を食わせて開発を進める。フルスケール化(PyPI 追加・候補プール拡大・週次 Scorecard 追従)は後続スプリントで積む。これは `D-10`(対象エコシステムは設定値として扱い追記で済む)の設計とも整合する。

## 新規性の枯渇にデータ側で何ができるか

DB レス(`D-5` 追補)である以上、「このユーザーに何を見せたか」をサーバー側で追跡する手段はない。取れる手は 3 つの組み合わせ:

1. **候補プールを配信件数より大きく持つ**: 例えば 1 回の表示件数が 20〜50 件なら、候補プールは 2,000〜5,000 件規模を確保する(バッチ側で OpenSSF フィルタ後に残る件数がこのオーダーに収まるよう、Scorecard 対象範囲を決める)。
2. **決定論的シード(日付ベース)でプールから毎日違う部分集合を提示**(`supplement.md` §2.3)。サーバー状態を持たずに「今日は違う」を実現できる、既存の弱点(未実証だが要素技術は確認済み)。
3. **ダンプ更新のたびに候補プールを入れ替える**(2〜4 ヶ月周期)。新しく閾値を超えたパッケージが入り、古いものが出る。これが唯一の「本当の新規性」の供給源で、①②はあくまで「同じプールの見せ方を変えているだけ」であることは正直に認識しておくべき。

`localStorage` で「既出」を除外する案(`supplement.md` §2.1 の Safari ITP 7 日キャップ)は**補助**に留める。ITP でリセットされても「ユーザーが同じものを再度見る」だけで実害は「軽い既視感」止まりであり、致命的な設計不備ではない(リマインド用途なので、多少の重複提示は許容範囲と割り切る)。無理に URL 共有やブックマーク導線で穴を塞ぎに行くのは、この Phase では過剰実装(YAGNI)だと考える。
