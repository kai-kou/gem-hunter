## product_vision の反論（ラウンド2）

> 争点 A の順序対立そのものについては別便の譲歩ポストで決着案（薄いスライス + UI を 1 スプリントに合体）を出した。ここでは、その決着案を前提に `data_pipeline` と `constraints_guard` の各主張の **具体的な瑕疵** に反論する。

### 反論 1: `data_pipeline` の「上位数百件」はミッションと両立しない——選別軸を明示しないと Gem Index が自己矛盾する

`data_pipeline` は争点 A で「最初のスプリントでは対象を **1 エコシステム(npm)・上位数百件** に絞ったミニパイプラインを通す」と提案したが、**「上位」の並べ替え軸が一度も明示されていない**。これは一般的な語感どおり「star 順」または「ダウンロード数順」と読まれる可能性が高く、もしそうなら致命的な自己矛盾を生む。

- gem-hunter が定義する Gem は「star に対して被依存数が不釣り合いに大きいもの」（`project-mission.md` ミッションステートメント）。star 順や DL 数順で上位数百件を切り出すと、その母集団は **既に有名で、かつ star と被依存数の両方が高い** パッケージだけで構成される（React・lodash 級）。この母集団の中で「星に対する被依存数の残差パーセンタイル」を計算しても、全員が「有名かつ健全」なので **残差の分散がほとんど出ない**。結果として「Gem として提示された」候補は、単に「有名パッケージの中でわずかに地味な有名パッケージ」でしかなく、真の Hidden Gem（無名だが多く使われている）は母集団に一件も含まれていないので **そもそも出現しようがない**。
- `data_pipeline` 自身が争点 C で「母集団が変わるとパーセンタイルの意味が変わる（エコシステムを混ぜてはいけない）」と正しく指摘している。**同じ論理が「上位数百件」というサンプリング自体にも及ぶ**——エコシステムを混ぜる以上に激しい偏り（「有名なものだけ」）を母集団に持ち込んでおきながら、その内部指摘を自分のサンプリング設計には適用していない。
- 実害は具体的: SD-1 の操作レビューでレビュアーが最初のプレビュー URL を開いたとき、そこに並ぶ「今日の Gem」が React や lodash だったら、それは即座に `R-2`（GitHub 純正検索で 1 行で書けるものは差別化にならない）違反の可視化そのものであり、GitHub Trending の劣化コピーだという自分（`product_vision`）の R1 の懸念がそのまま実証されてしまう。

**要求**: 「上位数百件」を **「被依存数パーセンタイルは中〜高だが star パーセンタイルは低い候補を意図的に含むように抽出したサンプル」**、あるいは最低でも **「star 順ではなくランダム/層化サンプリング」** に訂正すること。`data_pipeline` 自身の見積もりでは S3 ダンプは全量を一度ダウンロードする前提（`curl -sI` で `Content-Length` を確認する話をしている）なので、「取得は全量、フィルタで薄くする」という設計は変えずに済む——**フィルタの軸だけを「星の高さ」から「被依存パーセンタイルと star パーセンタイルの乖離」に変える** だけで解決する。これは最初のスキーマ設計に含めるべき不変条件の 1 つとして `constraints_guard` の「決めずに進めると後で全体を書き換える境界」リストに追加すべきだと考える。

### 反論 2: `constraints_guard` の `SP-A`（データのみ・`sp:8`）単独では `C-2`（5 行のデモ手順）を満たせない

`constraints_guard` の 2 スプリント分割案は `SP-A`（データ基盤・`sp:8`、UI は「既存一覧への統合のみ、または JSON の直接検証で可」）→ `SP-B`（ダイジェスト UI・`sp:5`）という順序である。**この `SP-A` の完了条件「JSON の直接検証で可」は `C-2`/`SD-1` を実質的に満たさない。**

- `SD-1` が要求するのは「ユーザーはリンクを開くだけで、`user-story-map.md` §5.3 の操作レビュー手順を完走できる」ことである。「JSON を DevTools で見る」はエンジニアの検証手段であって、**ユーザーが辿れる操作レビューの 5 行ではない**。`ux_discovery` が R1 で書いた日次ダイジェストの操作レビュー（トップページを開く→有限件数表示→リロードで再現→日付モックで入れ替え確認→詳細往復→キーボード完走）は、Gem Index を実際に画面に描画して初めて成立する手順であり、`SP-A` 単独ではこの 5 行のうち 1 行も満たせない。
- `SP-A` が「既存一覧への統合のみ」で済ませる場合も同様の弱さがある。既存の検索一覧に Gem Index を混ぜて出すのは、**キーワード検索を経由する時点で `A-2`（条件を組み立てる）に依存しており、「キーワードを入力せずとも」という飼い主の要望 (2) の核心を実演できていない**。`docs_trace` が R1 で指摘した通り、キーワード非依存の発見はバックボーンの新しい入口（新 A-n）を要する性質のものであり、既存一覧への統合という控えめな実装では「今回追加した振る舞い」をレビュアーが認識できない。
- **合わせて反論 1 の「上位数百件」問題がここでも効く**: 仮に `SP-A` を「JSON の直接検証」で完了させたとしても、その JSON の中身が「上位数百件＝有名パッケージ」のままなら、`SP-B` で UI を被せた瞬間に反論 1 の失敗が可視化されるだけで、`SP-A` を先に独立させたことで得られたはずの「早期検証」の利点が実現していない。**データとサンプリング軸の妥当性は、UI に描画して初めて人間が目視で気づける**（分布のグラフだけでは「これは差別化になっているか」を直感的に判断しにくい）。

**要求**: `SP-A` と `SP-B` を厳密に分離せず、**「薄いスライスのデータ + それを描画する最小限だが本物の日次ダイジェスト画面」を 1 スプリントの完了条件にする**（譲歩ポストで述べた決着案と同じ）。`data_pipeline` の薄いスライス提案（`sp` 見積もりは下がるはず）であれば、UI 分を足しても `sp:8` の枠に収まる可能性が高い。RSS・帰属表示 UI・時間分割シードのオプション化など `constraints_guard` の `SP-B` メニューはこの合体スプリントの **後続** として温存してよく、そこは反対しない。

### 反論 3（軽微・`ux_discovery` 宛）: package.json 貼り付けを「不採用」と書き残すと、二度と俎上に上がらないリスクがある

`ux_discovery` の争点 B 判定「package.json 貼り付けは別カテゴリとして切り離す（B の争点からは外す）」自体には同意する（自分も R1 で同じ結論だった）。ただし **「不採用」という言葉のまま議事録（ホワイトボード）に残すのは危険** だと指摘する。

- package.json 貼り付けは、`R-2`（GitHub 純正検索で 1 行で書けるものは差別化にならない）を明確に満たす数少ない候補であり（npmgraph 前例あり、補完リサーチ §2.2）、a11y・`D-14`・Safari ITP のいずれの制約にも `constraints_guard` の判定で「可（条件付き）」が出ている。つまり **プロダクト価値の観点では捨てるべき理由が 1 つも無い**——単に「今回のスプリントの争点 B（リマインド）には該当しない」というスコープ問題があるだけである。
- `user-instruction-issue-rules.md` 的な観点で言えば、「検討して却下した」という記録と「スコープ外なので別 Issue に切り出した」という記録は意味が全く違う。前者は再検討の障壁になり、後者は積み上げバックログとして生き残る。

**要求**: このラウンドの結論に「package.json 貼り付けは B の争点から **除外** し、`S-2` 積み上げ（またはそれ以降）の独立した検索入力手段として **Issue 化する**」という一文を明記し、「不採用」という語を使わないこと。
