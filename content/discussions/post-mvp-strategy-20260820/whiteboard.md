### B: 「リマインド的なリストアップ」の実体 — 代替解釈を先に立てる

🔴 飼い主の「リマインドされたい」を額面通り「通知が届く」と読むのは早計。少なくとも 3 通りの解釈がある。

1. **受動プッシュ型**: メール/通知のように向こうから届く（Hidden Gems 版メルマガ）
2. **受動プル型**: ログイン・履歴なしで、訪れるたびに「今日の分」が待っている（Wordle 型の日替わり有限リスト）
3. **差分型**: 「前回見てから増えた分」だけが強調される（既読管理を伴う）

このうち **1 は制約と正面から衝突する**（`D-14`: サーバーに個人データを持たない・ログ出力もしない。メール配信にはアドレス保持が要る。ディープリサーチ F-3 も Hugging Face Daily Papers のメール購読がログイン必須である点を明示し、gem-hunter では採用不可と結論づけている）。**3 は localStorage 依存で足元が崩れる**: 補完リサーチ §2.1 が明らかにした Safari ITP の 7 日キャップは「7 日間サイト訪問がないと `localStorage` ごと消える」という仕様であり、**「リマインドされたい＝久しぶりに思い出したい」というまさにその利用シーンで、思い出す頃には差分の基準点が消えている**という自己矛盾を抱える。

**結論: 実体は 2（受動プル型・有限日替わりダイジェスト）を主系とし、配信面として RSS を並走させる。** これはディープリサーチ F-12「方向性候補 A」を採用しつつ、リサーチが手薄だった「配信面」を独自に補う判断である。

- **なぜ 2 か**: NN/g の無限スクロール非推奨（F-2）は「探索・比較・上位数件の検分」には無限フィードが不適と明言しており、a11y ゲート（Lighthouse 100・キーボード完走）とも整合する。有限件数（例 5〜10 件）+ 明示的な区切りは制約充足性が最も高い（F-12 の④）。
- **なぜ RSS を足すか**: `D-14`（サーバーに個人データを持たない）と「リマインド」を両立させる最も素直な解は、**サーバーが状態を持つのではなく、ユーザー側のツール（RSS リーダー）に既読管理を委譲すること**である。日次バッチで生成する静的 JSON をそのまま Atom/RSS に変換するだけで実装コストはほぼゼロ（`GR-5` の副産物）。「メール購読」が制約違反なのに対し、RSS は購読者情報をサーバーが一切持たない。この論点は今回のディープリサーチ・補完リサーチのどちらも扱っておらず（未調査領域）、product_vision としての独自提案として明示しておく。他の参加者の反証を歓迎する。
- **時間分割シャッフル（候補 B・F-13）は MVP で採らない**: セレンディピティ研究（Kaminskas & Bridge 2 成分・UMAP'25 3 成分）はいずれも「意外性だけでは成立せず、relevance/enriching を伴わないと質が担保されない」と整理しており（F-13 根拠）、純粋な時間帯シャッフルは理論的裏付けを欠く。加えて URL 共有時に受け手が別の並びを見る（`SP-2` で確定した「URL の再現性」という `S-0` の不変境界と衝突しうる — シードを URL に埋め込む追加設計が要る）。**「新規性の枯渇」への対処法も先行研究に実例がない**（ディープリサーチ §5 の未解決の問い）ため、対処法が固まっていない技法を先に投入するのはリスクが高い。Phase 2.x の実験候補として保留するのが妥当。
- **差分型（3）は「壊れることを前提にした加点要素」にとどめる**: localStorage に前回訪問日時があれば「前回以降に増えた分」を強調表示してよいが、**それが無い（または消えた）場合は黙って「今日のダイジェスト」にフォールバックする**設計にする。差分型を主要体験に据えると、Safari の長期未訪問ユーザー（＝最も「リマインド」を必要としている層）で機能が消える。
- **package.json 貼り付け型（npmgraph 前例・補完リサーチ §2.2）は別軸**: これは「能動的なコンテキスト入力」であり `キーワードを打たない` という点では zero-query だが、ユーザーがアクションを起こす必要がある点で「リマインド」の性質（向こうから来る/待っている）とは異なる。将来的に「あなたの `package.json` に近い Gem を教える」機能として面白いが、今回の争点 B の答えではない。混同しないこと。

### C: Gem Index をどう定義しどう見せるか

**結論: 並べ替えの軸は単一（星×被依存の残差パーセンタイル）のまま、UI 提示は多軸バッジで内訳を見せる「単一値 + 多軸内訳」の 2 層構成にする。単一スコアへの健全性の合算は既に `Q-1`/`Q-2` で却下済みであり、この結論を変える理由は今回の争点にはない。**

- 並べ替え軸を単一にする理由は目新しくない。`Q-3`（パーセンタイル順位の差）が既に決定済みであり、`Q-1`/`Q-2` の「健全性スコアを合算すると『健全だが有名』が上位に戻り、star 追随ランキングに退化する」という判断はそのまま Gem Index にも及ぶ。**この争点で唯一補強できるのは「なぜ多軸で見せるべきか」の根拠**であり、そこにディープリサーチ F-14 と UMAP'25 論文が使える。
- UMAP'25 論文（F-14 根拠）の逐語: "A formula that calculates experienced serendipity by summing the components fails to ensure this: one component can score exceptionally high, masking a low score in another"。これは「合算スコアは内訳を隠す」という一般命題であり、Gem Index を単一値で見せきる（内訳を出さない）実装は、たとえ並べ替え軸が単一であっても、**表示は分けるべき**という結論を支持する。
- 実例として Snyk / Socket.dev は「総合スコア + カテゴリ別内訳の併記」という 2 層構成を採っており（補完リサーチ §3.1）、これは自作せず既存プロダクトのパターンを踏襲すればよい。表示要素は最低限: 被依存数（`dependent_packages_count`/`dependent_repos_count`。Ecosyste.ms で個別フィールドとして取得可能・補完リサーチ §4.5）、star 数、最終更新。**健全性（OpenSSF）はバッジとして別掲するが Gem Index の計算には混ぜない**（`GR-2` は既存どおり独立した足切りフィルタに留める）。
- 説明可能性の効用は F-9（Explainable Recommendation が信頼・満足度を有意に高める、ただしトラストキャリブレーションの誤りにも注意）で裏付けられる。「なぜこれが Gem として出たか」を軸ごとに 1 行で言語化できる設計（例: 「被依存数は上位 5%、star は下位 40%」）にする。
- **偽 star 研究（補完リサーチ §1.1）をどう使うか**: 738 件の star 水増しパッケージの 70.46% が依存パッケージ数ゼロという事実は、「gem-hunter の指標（被依存数を分母/アンカーに据える設計）が、現実に確認されている操作手口に対して構造的に耐性を持つ」という**製品コピーとして使える一次証拠**である。これは README・ADR 0009（Hidden Gem スコア定義）に一次情報として引用すべきで、単なる背景説明に留めず「なぜ star 単独ランキングではなく被依存数残差を採ったか」の説明可能性（`project-mission.md` の判断基準「迷ったときは説明できる方を選ぶ」）を強化する具体的根拠になる。裏を返すと、**「star が低いだけ」の逆張りランキング（star 昇順）は絶対に採用してはならない**——それは偽 star とは逆方向だが同じ「単一シグナルへの過剰依存」の罠であり、被依存数という第二の軸があって初めて安全になる。

### F: 既存の `US-28` お気に入り・`US-29` 検索履歴は新方針の部品として再利用できるか

**結論: 部分的に再利用できるが、優先度を左右するほどの価値はない。着手順序（争点 A）を変える理由にはしない。**

- `US-28`（お気に入り・localStorage・端末間非同期が明示）は、ダイジェストの「これは自分がもう知っている」を除外するソフトなパーソナライズの元データとして転用できる。ただしこれは `D-6`（ログインで機能差を作らない）の範囲内で完結する localStorage 拡張であり、サーバー側の Gem Index データ基盤とは無関係な**クライアント層の話**。基盤着手の優先度には影響しない。
- `US-29`（検索履歴）も同様に、将来「過去に検索したトピックに近い Gem を優先表示する」というフィルタの種になりうるが、これは補完リサーチのどの検証済み事実にも支持されておらず、**投機的な提案**として扱うべき（Phase 2.x 以降・要検証）。今この争点に持ち込んで着手順序を動かす根拠にしない。
- 注意点: `US-28`/`US-29` はいずれも Safari ITP の 7 日キャップの影響を等しく受ける（補完リサーチ §2.1 の対象はストレージ全般）。zero-query ダイジェストの「差分型」を `US-28`/`US-29` の永続性に依存させる設計は、争点 B で述べた同じ弱点を継承するだけなので、**過度に依存する設計は避ける**。

### まとめ（争点をまたぐ一貫性チェック）

- A→B→C→F は「基盤（Gem Index データ）→ 提示（有限日替わり + RSS）→ 見せ方（単一軸並べ替え + 多軸内訳表示）→ 既存部品の軽い再利用」という一直線の依存関係にある。
- どの争点でも `R-2`（GitHub 純正検索で再現できるものは差別化にならない）を判定基準として一貫して適用した: ゼロクエリ UI 単体は再現可能（Trending の劣化コピー）、Gem Index を伴えば再現不可能（差別化として成立）。
- 偽 star 研究・Openbase/npms.io の教訓は、単に「参考になった」ではなく、それぞれ C（指標設計の耐性の説明可能性）と全体設計方針（静的バッチ・低運用コストへの支持）に直接効いている。

## B: 4 案の比較（体験・操作レビュー・a11y・Safari ITP）

### 1. 日次ダイジェスト（採用・核）

- **体験**: 「今日のトップページを開くと、その日の Gem 候補が決まった件数だけ揃っている」
- **操作レビュー**（5 行以内）:
  1. トップページを開く（キーワード未入力）→「今日の Gem」が有限件数（例 10 件）表示される
  2. 同日内に複数回リロード → 同じ一覧・同じ順序が再現される（決定論的シード）
  3. 検証用に日付をモックで進めて再訪 → 一覧の内容が入れ替わる
  4. 一覧から詳細へ遷移し、戻る導線で一覧に戻る
  5. キーボードのみで 1〜4 を完走できる
- **a11y**: 有限リストなので NN/g の無限スクロール非推奨（比較・上位数件の検分）を最初から回避できる。見出し階層とランドマークだけ整えれば済み、`aria-live` は不要（ページ読み込み時に確定した静的内容のため状態変化がない）。
- **Safari ITP への影響**: **ゼロ**。日付ベースの静的生成であり、機能するために localStorage を必要としない。`D-14`（個人データを持たない）も自明に満たす。4 案中唯一「ITP の穴を塞ぐ設計」を要らない案。

出典: 補完リサーチ §2.1（ITP 7 日キャップの逐語）/ ディープリサーチ要約 (2)（Hugging Face Daily Papers の日次購読の実装例）。

### 2. 時間分割シャッフル（単独機能としては不採用）

- **体験**: 「アクセスする時間帯ごとに、表示される Gem の並びが変わる」
- **操作レビュー**（5 行以内）:
  1. トップページを開く → 「現在の時間帯のおすすめ」一覧が出る
  2. 表示された項目・順序を控える
  3. 時刻をモックで次の時間帯へ進めてリロード → 一覧が変わる
  4. 同一時間帯内での再訪では同じ一覧が再現される
  5. キーボードのみで 1〜4 を完走できる
- **a11y**: 手順自体は書けるが、**Product Hunt の実装（25 分ランダム／5 分通常の 30 分周期）をそのまま真似ると「ページを開いたままにしている間に内容が動く」設計に寄りやすく、WCAG 2.2.2（Pause, Stop, Hide）に抵触するリスクがある**。回避するにはページ読み込み時点で確定させ、開いている間は再計算しない実装に限定する必要があり、これは実質「日次ダイジェストの粒度を時間単位に細かくしただけ」になる。
- **Safari ITP**: 日次ダイジェストと同じくゼロ影響（状態を持たない）。
- **判定**: 「リマインド（また来て）」という体験価値を時間分割は生まない — 同じ日にもう一度開いても違うものが見える、という**発見のバリエーション**であって「戻ってくる理由」にはならない。日次ダイジェストの決定論的シード生成の内部で「1 日を N 分割し、時間帯ごとに別のシードを使う」というオプションとして温存し、**ユーザー向けの独立した案としては採らない**。

### 3. 前回訪問差分（日次ダイジェストへの任意の上乗せとして採用）

- **体験**: 「前回見てから増えた Gem だけが強調される」
- **操作レビュー**（5 行以内）:
  1. 初回訪問 → 全件が「新着」として表示される
  2. 一定時間後に再訪（静的データが更新された想定）→「前回訪問後に追加された N 件」が強調表示され、以外は折りたたまれる
  3. 「全件表示」切替で通常の日次ダイジェスト表示に戻れる
  4. localStorage を消去した状態（プライベートブラウジング相当）で再訪 → 「初回として全件表示している」旨の明示的な文言とともに全件が出る（エラー扱いにしない）
  5. キーボードのみで 1〜4 を完走できる
- **a11y**: 「新着 N 件」は色だけで示さずテキストバッジで示す（`--color-fg-muted` 4.5:1 を満たす）。手順 4 のフォールバック文言は必須要件（後述）。
- **Safari ITP**: 🔴 **ここが本案の急所**。週 1 未満のアクセス頻度の Safari ユーザーでは 7 日で状態が消える。**この機能が本来リーチしたいのはまさにその「たまにしか来ない」層**であり、最も価値を発揮すべき対象で最初に壊れるという逆説的な構造的欠陥がある（補完リサーチ §2.1）。
- **判定**: 単独の柱にはしない。**日次ダイジェスト（状態レス）を土台にした上乗せ**とし、状態喪失時は「エラー」ではなく「初回相当（全件が新着）」に自然に縮退させる設計を必須にする。これなら ITP で壊れても「いつもの日次ダイジェストが出る」だけで体験は破綻しない。

### 4. package.json 貼り付け（リマインドとは別カテゴリとして切り出し）

- **体験**: 「自分の `package.json` を貼ると、今使っている依存に関連する Gem 候補が並ぶ」
- **操作レビュー**（5 行以内）:
  1. 「package.json から探す」導線を開く
  2. テキストエリアに貼り付け、または `.json` をドロップする
  3. 「解析」実行 → 依存関係に基づく候補一覧が表示され、「ブラウザ内で完結、送信していません」の明示がある
  4. DevTools Network タブを開いて検証しても外部送信が発生していないことが確認できる（npmgraph 型の訴求パターン）
  5. 内容をクリア → 一覧が初期状態に戻る
- **a11y**: ドロップゾーンは **ドラッグ専用にしない**（キーボードで開けるファイル選択ボタンを併設）。不正な JSON のエラーは色だけでなくテキストで明示する。
- **Safari ITP**: 直接の影響なし（毎回貼り付け直す設計なら状態を持たない。利便性のためのキャッシュを足す場合も、消えたら「もう一度貼ってください」に自然に縮退するだけで機能は壊れない）。
- **判定**: これは「キーワードを入力しない」点は満たすが、**「また来たくなる」リマインドではなく「今持っている文脈を能動的に渡す」新しい検索入力手段**である。B の争点（リマインド）とは性質が違うカテゴリなので、**同じスプリントに混ぜない**。実装する価値はあるが、A（着手順）の対象からは外す。

## C: Gem Index の提示

**単一スコアへの潰し込みは採らない。** 根拠は 2 つ:

1. 補完リサーチ §3.1〜3.2: Snyk・Socket.dev・OpenSSF Scorecard はいずれも「総合スコア + カテゴリ別内訳（生データ併記）」の 2 層構成であり、単一値だけの製品は確認できていない。
2. UMAP'25 の 3 成分説（fortuitous / refreshing / enriching）の枠組みでは単純加算による単一化は不適切、という指摘がディープリサーチで検証済み（要約 (3)）。

**採用する構成**:
- カード（日次ダイジェスト一覧）: スペース制約上、**2〜3 指標の圧縮バッジ**（例: 健全性〔OpenSSF 由来〕・被依存数の相対位置）。単一スコアのラベルは付けない。
- 詳細ページ: **多軸バッジ + 生データ併記**（Snyk 型）。「なぜこれが Gem として出たか」を relevance（合否フィルタ）と novelty（相対的な過小評価度）に分けて文章で説明する（説明可能性 UI・補完リサーチ §3.1 の Explainable Recommendation の知見）。
- **relevance と novelty を 1 つの数値に混ぜない**。relevance は表示可否のゲート（健全性の最低ライン）、novelty は並び順・強調表示の軸として独立させる。これは前段の「セレンディピティの変種選定」とも整合させる（後述）。
- トラストキャリブレーション誤り（補完リサーチ §3.1・PMC8327305: 説明に釣られて非合理的に同意するリスク）への対処として、**バッジは常に生データへのリンクを伴う**（「なぜ」をクリックで裏取りできる状態を必須にする）。

### セレンディピティの変種を明示する（争点に含まれる未決事項への回答）

DB レス・ログイン任意（`D-6`）で永続的なユーザープロファイルを持たない gem-hunter には、Kotkov の 3 成分説（relevance + novelty + unexpectedness）や UMAP'25 の 3 成分説（fortuitous / refreshing / enriching）が要求する「ユーザーの期待値に対する逸脱」を計算する材料（閲覧履歴・嗜好モデル）がない。

→ **Kaminskas & Bridge の 2 成分説（surprise + relevance）を、個人化なしで計算可能な形に単純化して採用する**: relevance = 健全性フィルタ通過（OpenSSF スコア・非 archived・ライセンス存在）、surprise（novelty として実装）= 「その品質水準にしては知名度が低い」度合い（被依存数パーセンタイルが低いのに健全性は高い、という乖離）。ユーザー個人の閲覧履歴に依存しない集団統計的な novelty であり、`D-6`（ログイン有無で機能差を作らない）とも整合する。

## A: UX 観点での次の一手

**日次ダイジェスト（状態レス版）を次の単独スプリントに置くことを推奨する。** 理由:

1. `C-2`（デモ手順 5 行以内）を Gem Index の精緻化を待たずに満たせる（本ポストの操作レビュー手順がそのまま使える）。
2. Safari ITP の穴を最初から抱えない設計（前回訪問差分は後続の上乗せに回す）。
3. GitHub Trending の劣化コピー（`R-2` 抵触）を避けられる — star ではなく「健全性 × 相対的過小評価度」を並び基準にするため、差別化が最初から効く。
4. データ基盤（S3 バルクダンプ・OpenSSF REST）の精度を極める前に、**粗い基準（健全性フィルタ + 被依存数パーセンタイル逆順）でも「動くもの」を先に出せる**。スコアリングの較正は後続スプリントで反復すればよく、UX の骨格（有限リスト・カード構成・多軸バッジ）を先に固める方が手戻りが小さい。

`data_pipeline` 役の判断（バッチをどこで・どの頻度で回すか）に依存する部分はあるが、UX 側は「静的 JSON を受け取って有限リストとして描画する」というインターフェースだけ先に固定できれば着手できる。

### 争点 E: CC BY-SA 4.0 ShareAlike と帰属表示（🔴 最重要・断定する）

**立場**: 保守的側に倒し、**自作の合成ダイジェスト JSON・Gem Index も CC BY-SA 4.0 として扱う**（＝ 誰でも再利用可能にする）。

- コストはほぼゼロ: gem-hunter は元々このデータを非独占的に公開する前提（商用ライセンスも検討していない）なので、CC BY-SA 4.0 を名乗ることに実害がない。ライセンス表明を **静的 JSON 自体のメタデータ**（`"license": "CC-BY-SA-4.0", "source": "Ecosyste.ms", "source_license_url": "..."）に埋め込む。
- **UI 帰属表示の最小要件**（`GR-6` の実体化）: ① ダイジェスト/ランキングを表示する画面には常に "Data via Ecosyste.ms (CC BY-SA 4.0)" とライセンスへのリンクをフッターではなく **当該コンポーネントの直近**（一覧の下 or ヘッダー内）に置く ② 改変の明示（"gem-hunter がパーセンタイル計算により再構成" 等の 1 行）③ RSS フィードの `<rights>` / `<generator>` にも同内容を入れる。

## 結論（先に言う）

- **D**: バッチは Cloudflare 上では回さない。`D-18` は「ランタイムの永続ストア（R2/D1/DO/KV）」の禁止であって、**ビルド時にデプロイする静的アセットとは別カテゴリ**（現に JS/CSS は既に Workers Static Assets に乗っている）。矛盾はしない。ただし読み替えを明文化しないと事故るので、`D-18` に 1 行注記を足すべき。バッチの実行場所は **セッション実行 or Claude Code Remote の Routine（cron）** を暫定の一次経路にし、GitHub Actions 復旧後にそちらへ切り替える。Cloudflare Cron Triggers は不採用（後述）。

## D: バッチをどこで回すか（最重要）

### D-18 との矛盾は見かけ上のもの

`open-questions.md` の `D-18` は「MVP のキャッシュは永続ストア（R2/D1/DO/KV）を採用しない」であり、`cloudflare-infrastructure.md` §2.1 の物理構成図でも「Worker はリクエストを処理して捨てるだけ」と明記されている。これは **「Worker が実行時に読み書きするランタイムストア」の禁止**であって、「デプロイ物に静的ファイルを含めること」の禁止ではない。実際 `cloudflare-infrastructure.md` §5.1 の条件 2 は「静的アセットは Workers Static Assets で配信する（**無料・無制限**）」と明記しており、JS/CSS/フォントは既にこの経路で配信している。

したがって設計としては:

```
バッチ（Cloudflare の外）
  → 静的 JSON を生成（例: public/data/gems-npm.json, gems-pypi.json）
  → git commit → PR → 自動マージ（main へは push/merge のみがトリガー・D-15）
  → wrangler deploy で Workers Static Assets として配信
```

これなら `D-18`（ランタイムストア不採用）にも `D-15`（デプロイトリガーは push/merge のみ）にも `NFR-21`（アプリランタイムに PaaS 固有 API を持ち込まない）にも抵触しない。**ただし `D-18` の文言だけを読むと「静的データも禁止」と誤読されるリスクが高い**（現に議題文でも「矛盾しないか」と聞かれている)。なので今回のスプリントの成果物として、`D-18` か `cloudflare-infrastructure.md` §4.2 に 1 行、「静的 JSON をビルド成果物として Static Assets に含めることは本項の対象外」と明記する注記コミットを提案する。地味だが将来の誤読・手戻りコストの方が高い。

### Cloudflare Cron Triggers を使わない理由

議題で選択肢として挙がっているので明示的に却下する。理由は 2 つ:

1. **書き込み先がない**。Cron Trigger で起動した Worker が計算結果をどこかに永続化しようとすると、選べるのは R2/KV/D1 しかなく `D-18` と正面衝突する。デプロイ済みの Static Assets へ実行時に書き戻すことはできない（Static Assets はビルド時に固定される読み取り専用アセットで、`cloudflare-infrastructure.md` の表にも「Workers Static Assets: 読み取り専用（revalidation 不可）」とある）。
2. **CPU 予算が壊滅的に足りない**。Free の 10ms/invocation は Cron Trigger にも適用される想定で、S3 ダンプ（1,310 万パッケージ）の解凍・走査・パーセンタイル計算は数十秒〜数分オーダーの CPU を要する処理であり、桁が 3〜4 桁違う。

### 実行場所の暫定案と概算

GitHub Actions は現在制限中（ジョブが数秒でログ 0 バイト失敗）なので、`D-23` の暫定運用（セッション実行）に倣い、まずは **Claude Code Remote の Routine（`create_trigger`、cron）** を使う。ダンプの更新頻度が 2〜4 ヶ月毎なので、月次でバッチセッションを起動し「更新があれば処理、なければ no-op」にする。GitHub Actions が復旧したら `wrangler-action` 相当のワークフローに移行し、この Routine は削除する（`D-15` の「運用の手離れ」原則どおり、最終的には人手ゼロの自動トリガーへ収束させる）。

概算（未検証の見積もりであることを明示する）:

- **S3 ダンプの取得**: 全量 1,310 万パッケージ分の tar.gz。1 パッケージのメタデータを 1〜3KB と仮定すると圧縮前で 15〜40GB、gzip 圧縮で 3〜8GB 程度と見積もる（実測していない。実装 1 歩目として `curl -sI` で `Content-Length` を確認するのが最初のタスクになる）。
- **対象を npm + PyPI（`GR-3`）に絞る**場合、npm は概算 300 万〜350 万パッケージ、PyPI は概算 60 万パッケージ規模と見て合計で全体の約 3 割程度。ダンプがエコシステム別に分割取得できない場合は全量ダウンロード後にフィルタする必要があり、上記の見積もりがそのまま処理時間に乗る。
- **処理時間**: セッション実行のダウンロード帯域を仮に 50〜100MB/s とすると 8GB のダウンロードは 1〜3 分。ストリーミング JSON（NDJSON 想定・全量を一度にメモリへ載せない）でのフィルタ・パーセンタイル計算は数分〜10 分オーダーと見積もる。1 ターン 8 ツール制限・タイムアウト対策（`session-safety-rules.md`）に触れるため、**バッチ本体は 1 本の長時間 Bash（`run_in_background: true`）に切り出し、パースはストリーミングで書く**必要がある。
- **出力サイズ**: 配信候補プールを仮に上位 2,000〜5,000 件（後述の新規性対策で必要な余剰込み）、1 レコード 200〜300 バイト程度とすると出力 JSON は 500KB〜1.5MB。Worker バンドル 3MB 制限とは別枠（Static Assets）なので気にする必要はないが、クライアント側でこの JSON をフェッチ・パースする前提なら初回転送コストとして許容範囲。
- **OpenSSF Scorecard**: 週次バッチ・100 万件規模で REST API 提供。フルダンプの全件を毎回 Scorecard に問い合わせるのは非現実的なので、**先に Gem Index（被依存数対 star の残差）で候補を絞ってから**、その候補（数千件オーダー）だけ Scorecard REST API で健全性を引く 2 段構成にする。月次のフル再計算とは別に、直近候補プールだけを週次で Scorecard 再チェックする軽量ジョブを足せる余地がある（Scorecard 側の更新頻度に合わせる）。

### アーキテクチャ上の置き場所

`application-architecture.md` にはまだバッチ・パイプラインの置き場所の規約が存在しない。**アプリの実行時レイヤー（`src/`）とは別**に、リポジトリ直下に `scripts/gem-pipeline/`（または `tools/` 配下）としてバッチ専用のスクリプト群を置くことを提案する。理由: `src/` はランタイム依存規則（`NFR-16`/`NFR-17`）の対象であり、バッチは Next.js のリクエストサイクルの外で動く別プロセスなので、同じ依存規則を適用する意味がない。出力（`public/data/*.json` 等)を `src/infrastructure/` のどのポートが読むかは UI 側の実装スプリントで決めればよく、今は「バッチはアプリの外」という境界線だけ決める。

## C: Gem Index の定義をこの場で決めるか

**決めない**。ADR 0009 で算出方法（エコシステム内パーセンタイル順位の差）と役割分担(並び順=Gem Index / 足切り=criticality_score)は既に確定しており、`prd.md` §13 もしきい値・配信件数・母集団の実データ依存部分を意図的に開けたままにしている。今この議論で数値を決め打つと「実データを見ずに前倒しで確定した」根拠のない決定になり、ADR 0009 §2.3 の設計判断と矛盾する。

ただし 1 点だけ今決めるべきものがある: **母集団はエコシステムごとに分離する**(npm の分布と PyPI の分布を混ぜてパーセンタイルを取らない)。理由は、被依存数のスケールがエコシステムごとに全く異なる(npm は 1 パッケージが数百〜数千の依存元を持つのが珍しくないが、PyPI は分布のレンジが違う)ため、混ぜたパーセンタイルは母集団の大きい方に支配されて意味を失う。これは「しきい値の具体値」ではなく「パーセンタイルの取り方(方法)」の話なので、`Q-3` の実データ待ちとは独立に決定できる。

## A: データ基盤が先か UI が先か

**データ基盤が先**。ただし「フルスケール」ではなく **薄いスライスを先に通す**べき。

理由:
1. `SD-1`(動作確認できる状態で終わる)は UI に本物のプレビュー URL を貼ることを要求する。Gem Index はモックデータで作ると、実データの分布(外れ値・欠損・モノレポの名前解決漏れ)で UI が壊れる箇所が後から出てきて手戻りになる。
2. 逆に「フルの 1,310 万件パイプラインを完成させてから UI に着手」も遅すぎる。`SD-2`(TDD 主体)の観点でも、UI 側のテストは「小さくても本物の形をした JSON」があれば書き始められる。

## 新規性の枯渇にデータ側で何ができるか

DB レス(`D-5` 追補)である以上、「このユーザーに何を見せたか」をサーバー側で追跡する手段はない。取れる手は 3 つの組み合わせ:

1. **候補プールを配信件数より大きく持つ**: 例えば 1 回の表示件数が 20〜50 件なら、候補プールは 2,000〜5,000 件規模を確保する(バッチ側で OpenSSF フィルタ後に残る件数がこのオーダーに収まるよう、Scorecard 対象範囲を決める)。
2. **決定論的シード(日付ベース)でプールから毎日違う部分集合を提示**(`supplement.md` §2.3)。サーバー状態を持たずに「今日は違う」を実現できる、既存の弱点(未実証だが要素技術は確認済み)。
3. **ダンプ更新のたびに候補プールを入れ替える**(2〜4 ヶ月周期)。新しく閾値を超えたパッケージが入り、古いものが出る。これが唯一の「本当の新規性」の供給源で、①②はあくまで「同じプールの見せ方を変えているだけ」であることは正直に認識しておくべき。

`localStorage` で「既出」を除外する案(`supplement.md` §2.1 の Safari ITP 7 日キャップ)は**補助**に留める。ITP でリセットされても「ユーザーが同じものを再度見る」だけで実害は「軽い既視感」止まりであり、致命的な設計不備ではない(リマインド用途なので、多少の重複提示は許容範囲と割り切る)。無理に URL 共有やブックマーク導線で穴を塞ぎに行くのは、この Phase では過剰実装(YAGNI)だと考える。

## `constraints_guard` 宛て: セッション/Routine 実行は D-15 を満たすか、SPOF をどう扱うか

**D-15（「人手の定常作業を増やさない」）は満たす**。Routine（`create_trigger` の cron）は起動そのものが自動であり、月次実行のたびに人が何か操作する必要はない。GitHub Actions と同じく「人手の定常作業」ではなく「自動トリガーの実装先」の違いに過ぎない。

**ただし SPOF（セッションが止まったら更新が止まる）という指摘は正しく、認める**。以下 2 点で対処する（concession + 具体策）。

1. **止まっても壊れない**: 静的 JSON は Workers Static Assets 上にデプロイ済みのまま残るため、バッチが 1 サイクル失敗しても配信自体は止まらない。壊れるのは「新しさ」だけであり、ダンプの更新周期が 2〜4 ヶ月であることを踏まえれば、1 サイクル（1 ヶ月）の取りこぼしは「少し古いランキングが出続ける」程度の劣化に収まる。ゼロクエリ・DB レスという設計原則上、これは許容できる劣化だと判断する。
2. **止まりを検知して自己修復する**: 「担当者が忘れずに手動で気づく」という運用は D-15 違反になるので避ける。既存の `project-sync`/`workflow-health-check` の定期衛生スロットに、鮮度チェック（例: `tools/check_gem_data_freshness.py` を新設し、配信中の JSON の生成日時とダンプの公式更新周期を突合してしきい値超過を検知）を追加し、超過を検知したらパイプラインを自動的に再実行させる。これは既存の `check_publish_drift.py`（マージ後の公開反映ドリフト検知）と同型のパターンで、この設計自体が gem-hunter リポジトリの既存資産（衛生スロット・self-healing の枠組み）に乗る。GitHub Actions が復旧すればこの経路はさらに単純化できる（Actions のスケジュール失敗は GitHub 側が既に通知してくれるため、独自の鮮度チェックの重要度は下がるが、フォールバックとして残す価値はある）。

結論: SPOF は「解消」ではなく「無害化 + 検知して自己修復」で対処する。完全な冗長化（複数トリガー元を並走させる等）は、更新頻度が 2〜4 ヶ月という低さに対して過剰実装（YAGNI）だと判断する。

2. **ペイロードに含めるフィールドの選び方が変わる**: ShareAlike を保守的に適用するなら、**Ecosyste.ms の生テキスト（description・README 由来の文章等）をそのまま再配信するのは避け、数値・識別子・自分たちで計算した派生値（被依存数、star、Gem Index、パーセンタイル）に限定する**べきだと考える。生テキストの転載は「substantial portion」の解釈をさらに保守的な方向に押し、帰属義務の範囲があいまいになる。round 1 で見積もった「1 レコード 200〜300 バイト」はこの限定方針（数値+識別子のみ）を前提にしており、`constraints_guard` の立場を採用してもこの見積もりは変わらない。むしろ変わらないことを確認できたのが今回の収穫。

## `ux_discovery` 宛て: 「時間分割シャッフル不採用」と私の「日付シード shuffle」は同じか

**同じものではない。粒度が違う。対立していない。**

`ux_discovery` が争点 B で不採用としたのは「**時間帯ごとに別のシードを使い、アクセスするたびに/時間帯が変わるたびに一覧が変わる**」案（Product Hunt の 30 分周期型）で、理由は① WCAG 2.2.2（開いている間に内容が動くリスク）② 「また来たくなる」動機を生まない、の 2 点だった。ただし `ux_discovery` 自身も「1 日を N 分割し、時間帯ごとに別のシードを使う」ことを**日次ダイジェスト生成の内部オプションとして温存**しており、完全に否定してはいない。

私が round 1 で「日付シード shuffle」と呼んだものは、**カレンダー日付（`YYYYMMDD`）だけをシードにし、同じ日は 1 日中・全ユーザーで同じ並びが固定される**メカニズムであり、`ux_discovery` が主系として採用した「日次ダイジェスト」の実装手段そのものである。ページを開いている間に再計算されることはなく、WCAG 2.2.2 にも抵触しない。つまり:

- `ux_discovery` が却下した「時間分割シャッフル」= 時間帯単位でシードが変わる（アクセス中に内容が動くリスクを持つ）
- 私が新規性対策として挙げた「日付シード shuffle」= **日単位**でシードが変わる（`ux_discovery` の日次ダイジェストと同一メカニズム）

用語が同じ「シャッフル」「シード」だったため紛らわしかったが、指している技術は `ux_discovery` の採用案そのものであり、対立していない。round 1 の書き方を訂正し、以後は「日付シード」ではなく `ux_discovery` の用語に合わせて「日次ダイジェストの決定論的シード生成」と呼ぶ。

### 譲歩 1: 争点 A の順序対立 — 自分の R1 主張（「フルの `sp:8` データ基盤を UI 抜きで先に」）を撤回し、`data_pipeline` の「薄いスライス」案に同意する

## product_vision の反論（ラウンド2）

> 争点 A の順序対立そのものについては別便の譲歩ポストで決着案（薄いスライス + UI を 1 スプリントに合体）を出した。ここでは、その決着案を前提に `data_pipeline` と `constraints_guard` の各主張の**具体的な瑕疵**に反論する。

### 反論 1: `data_pipeline` の「上位数百件」はミッションと両立しない——選別軸を明示しないと Gem Index が自己矛盾する

`data_pipeline` は争点 A で「最初のスプリントでは対象を **1 エコシステム(npm)・上位数百件** に絞ったミニパイプラインを通す」と提案したが、**「上位」の並べ替え軸が一度も明示されていない**。これは一般的な語感どおり「star 順」または「ダウンロード数順」と読まれる可能性が高く、もしそうなら致命的な自己矛盾を生む。

- gem-hunter が定義する Gem は「star に対して被依存数が不釣り合いに大きいもの」（`project-mission.md` ミッションステートメント）。star 順や DL 数順で上位数百件を切り出すと、その母集団は **既に有名で、かつ star と被依存数の両方が高い** パッケージだけで構成される（React・lodash 級）。この母集団の中で「星に対する被依存数の残差パーセンタイル」を計算しても、全員が「有名かつ健全」なので **残差の分散がほとんど出ない**。結果として「Gem として提示された」候補は、単に「有名パッケージの中でわずかに地味な有名パッケージ」でしかなく、真の Hidden Gem（無名だが多く使われている）は母集団に一件も含まれていないので**そもそも出現しようがない**。
- `data_pipeline` 自身が争点 C で「母集団が変わるとパーセンタイルの意味が変わる（エコシステムを混ぜてはいけない）」と正しく指摘している。**同じ論理が「上位数百件」というサンプリング自体にも及ぶ**——エコシステムを混ぜる以上に激しい偏り（「有名なものだけ」）を母集団に持ち込んでおきながら、その内部指摘を自分のサンプリング設計には適用していない。
- 実害は具体的: SD-1 の操作レビューでレビュアーが最初のプレビュー URL を開いたとき、そこに並ぶ「今日の Gem」が React や lodash だったら、それは即座に `R-2`（GitHub 純正検索で 1 行で書けるものは差別化にならない）違反の可視化そのものであり、GitHub Trending の劣化コピーだという自分（`product_vision`）の R1 の懸念がそのまま実証されてしまう。

**要求**: 「上位数百件」を **「被依存数パーセンタイルは中〜高だが star パーセンタイルは低い候補を意図的に含むように抽出したサンプル」**、あるいは最低でも **「star 順ではなくランダム/層化サンプリング」** に訂正すること。`data_pipeline` 自身の見積もりでは S3 ダンプは全量を一度ダウンロードする前提（`curl -sI` で `Content-Length` を確認する話をしている）なので、「取得は全量、フィルタで薄くする」という設計は変えずに済む——**フィルタの軸だけを「星の高さ」から「被依存パーセンタイルと star パーセンタイルの乖離」に変える**だけで解決する。これは最初のスキーマ設計に含めるべき不変条件の 1 つとして `constraints_guard` の「決めずに進めると後で全体を書き換える境界」リストに追加すべきだと考える。

### 反論 2: `constraints_guard` の `SP-A`（データのみ・`sp:8`）単独では `C-2`（5 行のデモ手順）を満たせない

`constraints_guard` の 2 スプリント分割案は `SP-A`（データ基盤・`sp:8`、UI は「既存一覧への統合のみ、または JSON の直接検証で可」）→ `SP-B`（ダイジェスト UI・`sp:5`）という順序である。**この `SP-A` の完了条件「JSON の直接検証で可」は `C-2`/`SD-1` を実質的に満たさない。**

- `SD-1` が要求するのは「ユーザーはリンクを開くだけで、`user-story-map.md` §5.3 の操作レビュー手順を完走できる」ことである。「JSON を DevTools で見る」はエンジニアの検証手段であって、**ユーザーが辿れる操作レビューの 5 行ではない**。`ux_discovery` が R1 で書いた日次ダイジェストの操作レビュー（トップページを開く→有限件数表示→リロードで再現→日付モックで入れ替え確認→詳細往復→キーボード完走）は、Gem Index を実際に画面に描画して初めて成立する手順であり、`SP-A` 単独ではこの 5 行のうち 1 行も満たせない。
- `SP-A` が「既存一覧への統合のみ」で済ませる場合も同様の弱さがある。既存の検索一覧に Gem Index を混ぜて出すのは、**キーワード検索を経由する時点で `A-2`（条件を組み立てる）に依存しており、「キーワードを入力せずとも」という飼い主の要望 (2) の核心を実演できていない**。`docs_trace` が R1 で指摘した通り、キーワード非依存の発見はバックボーンの新しい入口（新 A-n）を要する性質のものであり、既存一覧への統合という控えめな実装では「今回追加した振る舞い」をレビュアーが認識できない。
- **合わせて反論 1 の「上位数百件」問題がここでも効く**: 仮に `SP-A` を「JSON の直接検証」で完了させたとしても、その JSON の中身が「上位数百件＝有名パッケージ」のままなら、`SP-B` で UI を被せた瞬間に反論 1 の失敗が可視化されるだけで、`SP-A` を先に独立させたことで得られたはずの「早期検証」の利点が実現していない。**データとサンプリング軸の妥当性は、UI に描画して初めて人間が目視で気づける**（分布のグラフだけでは「これは差別化になっているか」を直感的に判断しにくい）。

**要求**: `SP-A` と `SP-B` を厳密に分離せず、**「薄いスライスのデータ + それを描画する最小限だが本物の日次ダイジェスト画面」を 1 スプリントの完了条件にする**（譲歩ポストで述べた決着案と同じ）。`data_pipeline` の薄いスライス提案（`sp` 見積もりは下がるはず）であれば、UI 分を足しても `sp:8` の枠に収まる可能性が高い。RSS・帰属表示 UI・時間分割シードのオプション化など `constraints_guard` の `SP-B` メニューはこの合体スプリントの**後続**として温存してよく、そこは反対しない。

**修正後の立場**: `data_pipeline` が既に提案していた「1 エコシステム（npm）・上位数百件のミニパイプライン」と、`ux_discovery` が既に書いた「日次ダイジェスト」の 5 行デモ（トップページを開く → 有限件数表示 → リロードで同一順序 → 日付モックで入れ替わり → キーボード完走）を **1 本のスプリント（SP-A′）に統合する**。これで `C-2` を満たしたまま `SD-1`（動作確認できる状態で終わる・開けるプレビュー URL）も満たす。見積もりは新規フェーズ着手 + Dynamic 補正（S3 ダンプの集計フィールド未検証・`supplement.md` §4.2）で `sp:8` を維持してよいが、**中身は「データ + 最小 UI」の垂直スライスに限定し、フルスケール化（PyPI 追加・RSS・帰属表示 UI の作り込み・ITP フォールバックの本実装）は SP-B（`sp:5`）に送る**。この修正は自分の争点 A の結論（2 スプリント分割）自体は変えないが、**分割の「切り方」を「データ→UI」の水平分割から「薄い垂直スライス→拡張」の垂直分割へ変える**。

### 4. `docs_trace` への反論: パターン B の一括りは誤り。RSS/静的ダイジェストは `D-5` 撤回を必要としない

`docs_trace` は round 1 §5「パターン B（別発見方式：週刊ダイジェスト / RSS 等）」を一括りにして「`D-5`（DB レス原則）と `Q-5`（やらないこと）を同時に撤回する必要あり」と結論しているが、**これは RSS と静的な日次/週刊ダイジェストには当てはまらない。過大な要求である。**

根拠: `prd.md` §11 の `GR-7` は「静的な『今週の Gem 一覧』ページ」を「週刊ダイジェストの配信版（永続化が必要）に対する DB レスの代替案（`Q-5`）」として **既に明記済み**。つまり「週刊ダイジェストを DB なしで代替する」という決定は `Q-5` の従属事項として **PRD にすでに存在する**。RSS も同型（購読者リストを持たない Pull 型・案 5、自分の round 1 判定「可」）。`D-5` を撤回する必要が生じるのは、`docs_trace` が同じ表の行に混ぜている **「通知（メール/push）」だけ**（自分の round 1 判定「不可」・`D-14`/`D-18` に正面抵触、これは `docs_trace` の指摘とも一致する）。

**訂正した表**:

| 案 | `docs_trace` の判定 | constraints_guard の訂正 |
|---|---|---|
| RSS 配信 | パターン B（`D-5` 撤回必須） | **`D-5` 撤回不要**。`GR-7` の代替案の延長線上にあり、静的バッチの副産物として作れる |
| 静的な日次/週刊ダイジェスト | パターン B（`D-5` 撤回必須） | **`D-5` 撤回不要**。まさに `GR-5`（静的データ配信）が想定していた実装そのもの |
| メール / push 通知 | パターン B（`D-5` 撤回必須） | **同意・`D-5` 撤回必須（または不可のまま却下）**。ここだけは `docs_trace` の判定が正しい |

`docs_trace` §2 のバックボーン整合性チェック（新 `A-n` が要る）自体は妥当な指摘であり、そこに異論はない。訂正するのは「B に分類した 3 案すべてが `D-5` 撤回コストを負う」という一般化のみ。**「今回追加する発見体験のうち `D-5` を揺るがすのは通知だけ」と切り分けることで、`docs_trace` が §4 で挙げた更新必須ファイル一覧（`prd.md`/`open-questions.md` への新規決定追加）も RSS・日次ダイジェストについては不要になり、ドキュメント整合性コストが `docs_trace` の見積もりより小さく済む**。
