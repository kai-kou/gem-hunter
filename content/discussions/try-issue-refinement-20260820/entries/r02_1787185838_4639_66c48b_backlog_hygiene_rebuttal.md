## backlog_hygiene round2: 4 論点への応答

### 1) process_skeptic の「9本中5本が run_checks.sh 未接続」実測 → Epic の完了条件を修正する（concession寄りrebuttal）

この実測は machine-check を Epic 化する「べきか」自体は変えない（8件は依然閾値超）。変えるのは **Epic の完了条件**。`self-improvement-loop/SKILL.md` Step G-4 は Epic 本文に「子 Issue 一覧と統合の意図」を書けとしか言っておらず、「配線したか」を検証する項目が無い。これは前例（5本死蔵）を再生産する設計的欠陥だと process_skeptic の指摘を受けて認める。

提案: machine-check Epic の子 Issue 一覧に **「配線先」列を必須で追加** する（例: `run_checks.sh` 組み込み / pre-commit / スキル手動実行のいずれか）。「配線先」が空欄のまま子 Issue がクローズされることを Epic の完了条件から明示的に禁止する 1 行を Epic 本文に書く。これは G-4 の文言に手続きを足すだけで既存の権限（メインが Epic 本文を書く）の範囲に収まる。

### 2) app_quality の #130/#128 実バグ → カテゴリは変えないが Epic の外に緊急対応を切り出す

カテゴリ変更（machine-check→app）には反対する。#130 が担う「語彙表と実装の整合を継続検査する仕組み」自体は machine-check の性質のまま。一方で app_quality が見つけた **具体的な不一致**（`updatedAt` が `pushed_at` でなく `updated_at` 由来・`watchers`/`forks`/`openIssues` の命名 drift）は、検査ツールの完成を待たずに直せる **表示内容の実バグ** であり、Epic（消化順序が遅くなりうる追跡単位）に紐付けたまま眠らせるべきではない。

→ **#130 は machine-check Epic に残す**（#139 を吸収し「継続検査」の役割）が、**app_quality が特定した具体的な不一致の修正は別立ての緊急対応として切り出す** ことを提案する。新規 Issue 化してもよいし、#130 の本文に「Phase 0: 今すぐ直す（行番号付き不一致一覧）／ Phase 1: 継続検査スクリプト」と分割して Phase 0 だけ Epic 外で即着手してもよい（後者の方が Issue 増殖を避けられ好ましい）。これは 1) の「配線先」要求と同型で、**Epic は仕組み化のための追跡単位であり、個別の実害修正の受け皿にしない** という原則を一貫させる。

### 3) #137/#138/#131 の drop → hold へ差し戻す根拠は見つからなかった

Step G-3 の「切り口が少しでも違えば残す」は **重複統合（同一性の判定）の基準** であり、G-6 の「やめる/保留」判定は別の軸（CP-5 貢献度・着手コストの明瞭さ）を使う。したがって G-3 を根拠に drop への反対はできない、というのが構造面からの結論。#138・#131 は mission_po の言う通り KPI 接続ゼロ・可逆（not_planned で再オープン可）で drop に同意する。#137 のみ 1 点補足: 「検討する」で終わる Issue は削除してよいが、**検討そのものへの答えが今回の議論で出ている（process_skeptic「self-improvement-loop の議論の場で決めれば足りる」）ので、クローズコメントに結論を書き残す**（統合レビュー役は現時点で不要、というこの議論の暫定結論）。hold への差し戻しではなく drop の質を上げる提案。

### 4) #100+#110 を link_only に留めると「どちらも着手されない」か → 限定的な補強で対処

process_skeptic の失敗様式（統合すると両方薄まる）は merge のリスクだが、逆に link_only が「どちらも着手されない」リスクを生むのは、**組み合わせて初めて価値が出る場合** に限られる。#100（疎通検証）と #110（1コマンド束ね）は個別に単体で価値がある（検証だけでも、束ねるだけでも有用）ため、link_only のまま消化されても無駄にならない。よって merge へ転換する必要はないと判断するが、**放置リスクをゼロにするため**、@owner の priority/sp 再査定時に「同一消化サイクルでまとめて選ぶ」よう相互リンクコメントに 1 行添えることを提案する（トラッキング単位は分けたまま、選定順だけ揃える軽量な補強）。
