## 実測データ（発言前提）

- `tools/` 配下の Python スクリプトは **50 本**。うち `check_*.py` 命名の検査スクリプトは **9 本・合計 4246 行**、`self_review_check.py`（PR 前の総合機械チェック）が単体で **1032 行**。検査系だけで **合計 5278 行**、すでに小さくない資産。
- `run_checks.sh` が実際に呼ぶのは Lint / tsc / vitest / E2E（最大 600 秒タイムアウト）に加え、Python 検査 **5 本のみ**（`check_architecture_boundaries.py` `check_ui_dimensions.py` `check_contrast.py` `check_cjk_markdown.py` `self_review_check.py`）。
- 一方、`check_*.py` 9 本のうち **`check_agent_definitions.py` `check_claude_code_updates.py` `check_datetime_tz.py` `check_pending_pr_reviews.py` `check_skill_references.py` の 5 本は `run_checks.sh` から呼ばれていない**（フック・スキル・手動実行止まり）。つまり **既存の検査スクリプトの半数以上が PR ゲートの外** で運用されている。
- `run_checks.sh` は `run_check` を **逐次実行**（並列化なし）。チェックを 1 本足すたびに PR ゲートの壁時計時間が単純加算される構造。

この実態を踏まえ、争点ごとに見解を述べる。

## 争点 A（統合可否）— 主担当

5 候補は機械的な「同じファイルに触れている」類似性検知の産物であり、**中身の技術的性質が違うものを混ぜると両方薄まって実装されない** リスクが高い。個別判定する。

- **#100（プレビュー URL 疎通検証）+ #110（1 コマンド束ね）**: #110 の「束ねる」は CLI ラッパー、#100 の「疎通検証」は HTTP リトライ・タイムアウト設計を要する実装。統合自体は妥当（#110 を残し #100 を疎通検証ステップとして吸収）だが、**Done Criteria に「疎通検証（ステータスコード確認・リトライ）」を明記しないと、実装が易しい束ね機能だけ作られて検証部分が骨抜きになる典型パターン** になる。統合するなら吸収する観点を本文に明記することを条件にすべき。
- **#85（一括整形が並行編集ファイルを巻き込む）+ #93（並行実行中の破壊的 git 操作禁止）**: 原因が別（前者はファイルスコープ未確認、後者は git コマンド自体の禁止リスト）で対処法も別（スコープ検査 vs コマンド許可リスト）。Step G-3「切り口が少しでも違えば残す」に照らして **統合せずリンクのみ** が妥当。
- **#130（domain-model 語彙表と実装命名の整合）+ #139（ドキュメントのコード例示と実装の乖離）**: これは唯一、技術基盤（Markdown パース → 識別子抽出 → 実コード照合）を共有できる真の統合候補。ただし #130 は正規表現ベースの語彙表照合、#139 はコード例のパース＋実装照合で実装難度が段違い。**統合するなら「フェーズ 1: 語彙表照合（#130 相当）→ フェーズ 2: コード例照合（#139 相当）」と明記し、フェーズ 1 だけで放置されないようにする**。
- **#129（nullable フィールド一覧を doc へ）+ #136（依存計算値のハードコード禁止ルール化）**: 両方とも `domain-model.md` に触るという表面的一致だけで、片方は純ドキュメント追記、片方はコーディングルール策定。**論理的関連が薄く、これは類似検知の誤検知（false positive）と判断する**。統合対象から外し、リンクも不要。
- **#117（Cloudflare レート制限回避）+ #124（プレビュー動作実測の手順化）**: #117 が先に直らないと #124 の手順が rate limit で頻繁に失敗する、という **順序依存** はあるが統合はしない。リンクのみで十分。

## 争点 C（やめる Issue）— 主担当

`machine-check` 9 件は「新しい検査スクリプトを 1 本足す」提案の集積だが、**上述の通り既存 9 本中 5 本が run_checks.sh 未接続のまま放置されている実績がある**。この前例がある以上、新規提案は「どこに配線するか（run_checks.sh 組み込み / pre-commit フック / スキル手動実行）」を Done Criteria に明記しないものは、実装されても死蔵する確率が高い。個別に見る:

- **#138（fan-out 効果計測）**: 計測しても閾値判定・アクションが紐付いていない「とりあえず測る」Issue。テレメトリ追加は動機として弱く、CP-5 のどの KPI にも直結しない。**やめる（not_planned）を推奨**。必要になったら具体的な閾値判断（例:「fan-out のオーバーヘッドが N 秒を超えたら role 数を減らす」)とセットで再起票すべき。
- **#137（統合レビュー役の要否検討）**: 「検討する」だけの Issue で実装物がない。本来この種の判断は self-improvement-loop の議論型レビューその場で決めれば済み、専用 Issue として残す価値が薄い。**やめる** を推奨（必要なら決定をこの棚卸しの `open_questions` か Issue コメントに 1 行残すだけで足りる）。
- **#131（tsconfig.tsbuildinfo の扱いの明文化）**: 数行の運用メモで完結する内容。専用 Issue として sp 付与・優先度管理する費用対効果が低い。**やめる**、次にそのファイルを触る PR のついでに 1 行書けばよい。
- **#118（axe-core/playwright バージョン整合方針）**: 設定ドリフトの実害があり得るため #131・#137・#138 とは性質が違う。こちらは **やめない**（sp:1 で low〜medium 優先度のまま残す）。
- machine-check のうち **#116（ネットワークに出ていないことの再現可能な検証）** は理念は正しいが、実際にテスト環境でネットワーク呼び出しを再現可能に遮断・検証する仕組みは実装コストが高くフレーキーになりやすい（モック漏れの誤検知で `run_checks.sh` が頻繁に止まるリスク）。**やめるとまでは言わないが hold 推奨**（先に #104 や #134 のような軽量な静的検査で経験を積んでから着手すべき）。

## 争点 B（Epic 化）

`machine-check` を機械的に 1 Epic に束ねるのは反対。#130+#139 のように基盤を共有するもの以外は実装の独立性が高く、Epic 化しても「9 件を一括で終わらせなければ」という誤った圧力を生むだけ。Epic を作るなら **実装が実際に共有コードを持つクラスタ単位**（例: #130/#139 のドキュメント整合検査系だけ）に限定すべき。`parallel-safety` も同様で、#85/#93 のように原因が別なら Epic 化より個別追跡の方が消化スロット（priority 降順 → sp 昇順）が機能する。

## 争点 D（優先度）

「機械検査を足せば再発防止になる」という前提そのものを疑うべき。既に 5 本の検査が配線されず死蔵している実績がある以上、**machine-check 系を reflex的に priority:high にするのは危険**。#101 #109 #130 #134 が high になっている根拠が「実際に過去インシデントが発生したか」ではなく「あった方が良さそう」であれば medium 以下に下げることを推奨する。実インシデント起因（例: 過去に実際にドキュメント参照切れが本番に混入した等）が明示できるものだけ high 残置が妥当。

## 争点 E（取りこぼし点検）

自分のレンズから 1 点: 今回の統合候補リストは「同じファイルに触れる」という表層シグナルで機械生成されており（#129+#136 が好例）、**このリスト自体を鵜呑みにしないという spec の注意書き通り、少なくとも 1 件は誤検知だった**。他レーンの担当領域を奪っていないかについては、machine-check 系の一部（#104 の i18n 対称性、#109 の getByTestId）は ESLint カスタムルールで代替できる可能性があり、専用 Python スクリプトを増やす前に「lint 設定拡張で足りないか」を検討する余地がある（tools/ 肥大化の抑制になる）。
