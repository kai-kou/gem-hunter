## mission_po（ラウンド2: 反論・譲歩）

### 1. process_skeptic の「machine-check high 偏重への懐疑」と自分の「#92/#125/#116 昇格」提案は両立するか

**両立する。ただし #116 は撤回し process_skeptic 側に譲歩する。**

process_skeptic の懐疑対象は「検査を足せば再発防止になるという前提」で、名指しされたのは #101 #109 #130 #134（machine-check 系）。自分が high 昇格を提案した #92・#125 は machine-check ではなく `app` カテゴリで、しかも app_quality の実地確認により「暫定値の自己申告（#125）」「未検証の境界値（#92 関連の #135）」という**実装済みコードが露呈させている実欠陥**である。process_skeptic の基準「実インシデント起因のみ high 残置」に照らしても、#125 は `container.ts` の JSDoc 自身が「`R-5` 未確定の暫定値」と書いている時点で実インシデント予備軍そのものであり、この基準を満たす。つまり両者の基準は矛盾せず、**「検査追加系」と「実装欠陥系」を分けて扱うべき**という process_skeptic の論点を自分も採用する。

一方 **#116（ネットワーク非送出の検証）は撤回して hold に譲歩する。** 自分は round1 で「秘匿情報のクライアント露出防止ゲート」に接続すると書いたが、process_skeptic の記述（「テスト環境でネットワーク呼び出しを再現可能に遮断・検証」）とブリーフの分類（machine-check の静的検査ツール群）を読み直すと、#116 の実際の射程は**テストの hermeticity（実 API を叩かないテスト設計）**の話であり、秘匿情報露出防止ゲートへの接続は自分の深読みだった可能性が高い。もし本当に秘匿情報露出ゲート相当なら high 継続が妥当だが、Issue 本文の意図がどちらなのか現時点の要約からは確定できない。**この解釈の分岐は成果物（priority だけでなく実装スコープ）を変えるため、verdict の open_questions に「#116 の射程がテストの hermeticity 検証か、秘匿情報非露出の検証か」を明記すべきと提案する**（SD-3 第 2 系統相当ではなく Issue 本文の曖昧性だが、判断が割れているため記録は必要）。射程確定までは process_skeptic の hold 案を支持する。

### 2. app_quality の #130/#128 実バグ級不整合の発見 → priority 提案を撤回・引き上げる

**round1 の「#130 → medium 格下げ」を撤回する。** 自分は #130 を「ドキュメント-実装整合の検査」＝③説明可能性の薄い接続として medium に格下げ推奨したが、app_quality が実コード（`repository.ts:41` / `mapper.ts:59` / `ja.json:26`）を読んだ結果、**表示中の「最終更新」ラベルが `domain-model.md` が明示的に禁じている `updated_at`（`pushed_at` ではない）から作られている**という具体的な不整合を発見している。これは③説明可能性ではなく、**①与件充足**（`minimum-requirements.md` §7「詳細ページにリポジトリ名・オーナーアイコン・言語・Star数・Watcher数・Fork数・Issue数が表示される」＝表示データの正確性）に直結する実データ品質の問題であり、KPI 接続経路が自分の想定より強い。**#130 は high 継続を支持し直す**（#128 を吸収し、値の出どころ検証までスコープに含める app_quality 案に賛成）。

この事例は自分の判定軸（KPI 表への 1 ホップ接続）の弱点を露呈した: 検査カテゴリ名だけで③に分類し、実装を読まずに medium 判定した。以後、machine-check カテゴリの medium 格下げ提案（#101 #134）についても、app_quality の実地確認がまだない Issue は「暫定 medium、実装確認が出たら再査定」という留保を付ける。

### 3. backlog_hygiene の Epic ラベル `type:retro-try` 提案（`type:improvement` ではなく）

**賛成する。** 自分のレンズ（KPI 接続）からはラベル選択自体に優劣はないが、`type:improvement` を付けた場合に改善 Issue レーンの消化モードがこの Epic を実装対象として拾ってしまうという backlog_hygiene の指摘は、レーン規約（`improvement-lane-map.md` Rule 2・#160）と整合しており、これは③説明可能性（ルールの一貫性）にも寄与する。ただし念のため: Epic の priority/sp は @owner 権限（`session-sprint-rules.md` §4）であり、ラベル種別を変えても自分が D で提案した「KPI 1 ホップ接続を high の条件にする」という判定基準自体は変わらない——Epic 自体の priority は low〜medium に据え置く自分の round1 提案を維持する。
