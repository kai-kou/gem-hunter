## app_quality: 実コード確認結果（round1）

前提として `src/domain/ports/*.ts`・`src/composition/container.ts`・`src/domain/model/page-number.ts` とそのテスト・`messages/{ja,en}.json`・`e2e/*.spec.ts`・`tools/check_ui_dimensions.py`・`docs/03_design/data-model/domain-model.md` を実際に読んだ。争点 C（陳腐化判定）を主担当として厚めに書く。

### 争点 C: 陳腐化判定（主担当）

**#125（R-5 の逆算とキャッシュ TTL 見直し）— 陳腐化していない。強く生きている。**
`src/composition/container.ts:18-27` に実装済みの JSDoc で「60 秒は暫定値（`R-5` のレート枠逆算が未確定のため）」「`R-5` が確定したら本値を見直す」と明記されている。ADR `docs/adr/0005-cache-port-yagni-exception-and-ttl.md` §2.2 も TTL を「暫定値」と明記し、根拠を `R-5` 未確定に紐づけている。つまりコード自身が「この値は仮」と自己申告している状態で、#125 が指す欠陥はまさにそのとおり実在する。closeどころか priority を上げるべき候補。

**#135（maxPageFor の境界値テスト）— 陳腐化していない。テストは存在しない。**
`src/domain/model/page-number.ts:12-14` の `maxPageFor(perPage)` 関数は `page-number.test.ts`（全 26 行）で **1 回も呼ばれていない**。既存テストは `pageNumber()` と `tryPageNumber()` のみを対象にしており、`MAX_PAGE`（`DEFAULT_PER_PAGE` 前提の定数）は間接的にカバーされるが、`perPage` が可変値のときの `maxPageFor()` の境界（`perPage` が 0 や `API_RESULT_LIMIT` の約数でないときの端数切り捨て挙動など）は未検証。Issue の指す欠陥は実在する。

**#92（ポート契約の JSDoc・テスト固定）— 部分的に陳腐化・部分的に生存（範囲を絞るべき）。**
実装レベルでは既にかなり手厚い契約テストがある: `cache.test.ts:57-`（`ttlSeconds` が NaN/0/負値で `RangeError`）、`rate-limit.test.ts`（binding 未提供時のフォールバック）、`oauth.test.ts:69-`（`exchangeAuthorizationCode` の失敗系）。一方で **ポートのインターフェース自体**（`src/domain/ports/cache-port.ts` / `rate-limit-port.ts` / `auth-port.ts`）の JSDoc には値域・異常系が書かれていない。例えば `cache-port.ts:9-12` の `set<T>(key, value, ttlSeconds)` には「`ttlSeconds` は正の有限数でなければならず、そうでなければ `RangeError`」という契約が一切書かれておらず、これは `InMemoryCache`（`cache.ts:36-37`）という **1 実装だけ** が知っている暗黙知になっている。将来 2 つ目の `CachePort` 実装（例: Cloudflare KV）を書く人は、この契約をテストを読んで初めて知ることになる。→ 完全な陳腐化ではないが、**Issue の射程を「新規テスト追加」から「既存の暗黙契約をポート JSDoc に文書化する」に絞り込む**のが実態に即している。

**#104（i18n カタログ ja/en 対称性）— 現状は解決済み、ただし「検査の欠如」自体は未解決。**
実際に `messages/ja.json` と `messages/en.json` をキー単位でフラット化して突き合わせたところ、**35 キー対 35 キーで完全に対称**（差分ゼロ）だった。今この瞬間の非対称性という意味では既に解決している。ただし `tools/` 配下にこれを継続的に強制する機械検査は存在しない（`find tools -iname "*i18n*"` はヒットなし）。つまり「今は偶然揃っている」だけで、次に片方だけキーを足すコミットが入れば無検査で drift する。**Issue のタイトルが指す不具合は無い（stale）が、Issue の要求（再発防止の機械検査）自体は無くなっていない**。drop ではなく「現状は満たされているが再発防止検査は未整備」と明記して残すべき。

**#109（UI テストの getByTestId 第一選択）— これは陳腐化ではなく、Issue の前提そのものが Testing Library のベストプラクティスと逆行している疑いが強い。**
`e2e/*.spec.ts` を全数 grep した結果、`getByTestId` は **0 件**、`getByRole` は **79 件**。既存の E2E は Testing Library 公式の推奨クエリ優先順位（`getByRole` が最上位、`data-testid` は「他に手段がないときの最終手段」）に既に従っている。Issue が「`getByTestId` を第一選択にする」検査を機械強制しようとすると、むしろ現状の a11y に配慮したテスト設計（`getByRole` 中心）を破壊する方向の regression になりかねない。これは「解決済みだから閉じる」ではなく「**要求内容が実装と逆方向であり、そのまま実装すると害がある**」という別種の陳腐化。mission_po / process_skeptic にも共有したい: not_planned ではなく「Issue の意図を `getByRole` 優先の明文化 + `getByTestId` 濫用検知（逆方向）」へ本文修正のうえ残す、が妥当。

**#134（呼び出し側 className 直書き検査の射程拡大）— 陳腐化していない。射程は現状 1 ファイルのみ。**
`tools/check_ui_dimensions.py:58-60` の `CALL_SITE_REQUIREMENTS` は `src/ui/search-form.tsx` の 1 件のみを登録。一方 `className=` を使う `src/ui/` 配下のファイルは実測 11 件（`locale-switcher.tsx` `repository-detail.tsx` `pagination.tsx` `per-page-picker.tsx` `back-link.tsx` `repository-list.tsx` `login-link.tsx` `sort-picker.tsx` とコンポーネント 2 件）。検査対象は全体の 1/11 に留まっており、Issue が指す「呼び出し側の className 直書き」を検出する仕組みは大部分のファイルで機能していない。生存。

**#130 / #128（domain-model.md 語彙表と実装命名の整合）— 陳腐化どころか、実際に契約違反（バグの疑いすらある不整合）を発見した。**
`docs/03_design/data-model/domain-model.md:66` の語彙表は「`updated_at` → `lastUpdatedAt`。『最終更新日』（`AR-1`）は `pushed_at` を使う（メタデータ更新で動く `updated_at` ではない）」と明記している。ところが実装（`src/domain/model/repository.ts:41`）は `RepositoryDetail.updatedAt`（`lastUpdatedAt` ではない）というフィールド名で、かつ `src/infrastructure/github/mapper.ts:59` で `updatedAt: new Date(dto.updated_at)` と **`pushed_at` ではなく `updated_at` から直接値を入れている**。UI 側は `messages/ja.json:26` で `"updatedAt": "最終更新"` というラベルを付けて表示している。つまり画面には「最終更新」と表示されるフィールドが、AR-1 が明示的に禁じている `updated_at`（メタデータ変更でも動く GitHub のフィールド）から作られている ——これは単なる命名drift ではなく、**表示内容が仕様と食い違っている可能性がある実バグ**。さらに `watchers` / `forks` / `openIssues`（`repository.ts:38-40`）も語彙表の `watcherCount` / `forkCount` / `openIssueCount` と一致しない。#130 は明確に生存、かつ #128 のスコープ（`updatedAt` のリネーム）だけでは不十分で「値の出どころ（`pushed_at` か `updated_at` か）」まで含めて検証しないと本質を見落とす。**#128 は #130 に吸収し、`updatedAt` の値の出どころ検証を明示的にスコープへ追加すべき**と提案する。

### 争点 A（統合候補）への意見

`#130 + #139`（domain-model.md とドキュメント/実装の識別子整合を検査するスクリプト同士）の統合には賛成。上記の実地確認で分かるとおり、語彙表とコードの不整合は「命名」だけでなく「値の出どころ」まで及ぶため、統合後の Issue 本文には `updatedAt`/`watchers`/`forks`/`openIssues` の具体的な不一致箇所（本コメントに列挙した行番号）を吸収観点として明記してほしい。他の統合候補（#100+#110・#85+#93・#129+#136・#117+#124）は自分のレンズ外のため意見を保留する。

### 争点 B（Epic 化）への意見

`app` カテゴリ（#92 #125 #135）は 3 件で Epic 閾値未満なので Epic 化不要という backlog_hygiene 側の判断を支持する立場だが、#130 が `#128` を吸収して「app レイヤーの実装 ↔ ドキュメント整合」という性質を帯びるなら、machine-check 側の Epic に含めるより `app` の周辺（doc-record 寄り）に置いた方が追跡単位として自然だと考える。

### 争点 D（優先度再査定）への意見

CP-5 ①（与件充足）②（積み上げ可能性）に直結する意味で、**#125（レート枠・TTL の暫定値解消）と #130（表示データの出どころ不整合）は high 継続が妥当**、根拠は上記の通り実装が既に「暫定」「不整合」を自己申告・露呈している。**#135 は sp:1〜2 程度の小さい境界値テスト追加であり high というより medium** が実態に合う（欠陥リスクはあるが影響範囲が限定的）。**#109 は要求内容自体の見直しが先** なので、現状のまま high に置いても着手できない（要 Issue 本文修正）。**#104 は「現状は解決済み・再発防止検査が未整備」という性質上 high は過大**で、medium 程度が妥当。

### 争点 E（取りこぼし点検）への意見

#130 の実地確認で見つかった「`updatedAt` の値が `pushed_at` ではなく `updated_at` から来ている」という具体的な不整合は、振り返りレーン（retro-try）の一般的な「命名を揃えよう」という抽象度では拾いきれず、**実装を読まないと出てこない具体性**だった。統合・Epic 化の際にこの具体例を Issue 本文に落とさないと、次に着手するセッションが再度同じ調査をやり直すことになる。取りこぼし防止のため、統合後 Issue 本文に本コメントの行番号付き指摘をそのまま転記することを推奨する。
