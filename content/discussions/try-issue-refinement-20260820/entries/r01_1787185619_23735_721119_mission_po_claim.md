## mission_po（CP-5 ミッション貢献度レンズ）

### 前提整理
KPI は完成度指標のみ（与件 11/11・a11y 100・perf 90・CWV・主要フローテスト CI 成功・ADR 化）。優先順位は①与件充足 ②積み上げ可能性（テスト/CI/データアクセス層/キャッシュ境界）③説明可能性（ADR）④差別化 ⑤ドキュメント・運用改善。**この 5 段階のどこにも接続経路を説明できない Issue は、priority を上げる根拠がない**、というのが判定軸。

---

### 争点 C（やめる Issue の特定）— 主担当

指名された 4 件（#137 #138 #118 #131）を厳しく検討する。

- **#138（fan-out 効果の elapsed time / オーバーヘッド計測）→ drop 推奨。** KPI 表のどの項目（与件・a11y・perf・CWV・テスト CI・ADR）にも接続経路がない。エージェント運用の内部メトリクスであり、プロダクトの完成度に一切寄与しない。process_skeptic の懐疑（検査を増やすほど run_checks.sh が重くなる）とも整合する方向の drop。
- **#137（fan-out 後の統合レビュー役を pr-review-watcher に組み込むか「検討」）→ drop 推奨。** 「検討する」で終わる Issue は成果物を生まない。仮に統合レビュー役を作ったとしても、それが a11y/perf/CWV/テスト成功率のどれかを改善する経路を本文からは説明できない。せいぜい③説明可能性（レビュー記録の質）に薄く効く程度で、しかも「検討」段階のためコスト対効果が低い。
- **#131（tsconfig.tsbuildinfo の扱いの明文化）→ drop 推奨。** ビルド設定の内部挙動記録であり、⑤ドキュメント運用改善にすら弱い（読者はほぼ開発エージェント自身）。CP-5 のどの判断基準（`docs/project-mission.md` の判断基準表）にも該当しない。
- **#118（@axe-core/playwright と @playwright/test のバージョン整合「方針」検討）→ drop ではなく hold 推奨。** a11y=100 は品質ゲートの核（`minimum-requirements.md` には明記はないが `project-mission.md` の KPI 表・品質ゲートに直結）で、テスト基盤の整合が崩れると Lighthouse a11y 100 の CI ゲート自体が機能しなくなるリスクがある。ただし「方針を決める」だけでは実装に繋がらないため、app_quality が実コード（package.json のバージョン固定状況・CI の実行結果）を確認したうえで、既に問題が顕在化していなければ hold（次回レビュー: バージョン起因の CI 失敗が実際に起きたとき）に倒すのが妥当。drop 一歩手前。

**追加で厳しく見るべき候補**（争点 C の指示範囲を超えるが、KPI 接続の弱さで並ぶもの）: #84（ディープリサーチ synthesis 破損検知）は research-runner の運用信頼性の話で、プロダクト KPI とは無関係。drop とまでは言わないが、type:retro-try としては research レーンの内部改善に留まり、priority は low が上限。#94（Stop フック WIP 自動コミットが履歴を汚す）も同様に KPI 経路がなく、コミット履歴の可読性という運用上の好みの問題。backlog_hygiene の監査・衛生レーン境界の観点でも「衛生」寄りであり、改善 Issue レーンで high 化する理由がない。

### 争点 D（優先度の再査定方針）— 主担当

**現状の歪み（本文に明記されている事実）**: 現在の priority:high 13 件は #84 #91 #100 #101 #109 #115 #123 #124 #129 #130 #134 #135 #136。ここに **#92（ポート契約 JSDoc+テスト）・#125（レート枠逆算 + キャッシュ TTL 見直し）・#116（ネットワーク非送出の再現可能な検証）が入っていない**。これは重大な優先度の逆転である。

- #92 はポートの値域・異常時振る舞いをテストで固定する Issue で、②積み上げ可能性（テスト充実・回帰検知）に直結。`project-mission.md` の判断基準「新機能を足すか基盤を整えるか → 基盤を優先する（D-9）」にそのまま該当する。
- #125 はレート枠逆算とキャッシュ TTL 見直しで、①与件（API 呼び出しの安定運用）と②積み上げ可能性（キャッシュ境界）の両方に直結。
- #116 はネットワークに出ていないことの再現可能な検証で、`project-mission.md` の品質ゲート「GitHub API のトークンなど秘匿情報がクライアントへ露出していない」に直結する（これを下回ったらリリースしないと明記された項目）。

**再査定の提案基準**: 「KPI 表の項目（与件 / a11y / perf / CWV / テスト CI / ADR）のどれかに、1 ホップで接続経路を説明できるか」を high の条件にする。

- **high へ引き上げ推奨**: #92・#125・#116（上記の理由）。#135（maxPageFor 境界値テスト）は現状 high のままで妥当（①与件のページネーション要件 + ②テスト）。#109（getByTestId 優先の検査）も high 維持が妥当（②主要フローのテスト CI 成功に直結する安定性の話）。
- **medium へ格下げ推奨**: #101（ドキュメント参照切れ検査）・#130（domain-model 語彙整合検査）・#123（議論型レビュー結論の確定度分類）・#115（E2E 環境変数を env-vars.md へ）・#100 / #124（プレビュー運用系）・#91（既存ポート確認手順）。いずれも③説明可能性 or ⑤運用改善の薄い接続で、①②に直結する #92 #125 #116 #135 #109 より優先度が低くて当然。
- **low へ格下げ、または drop 検討**: #84（争点 C 参照）。#134（className 直書き検査）は UI 実装規律で⑤寄り、medium 止まりが妥当（high は過大）。
- #136（選択肢依存の計算値ハードコード禁止ルール化）は #135（maxPageFor 境界値）と実装対象が重なる可能性があり、②テスト設計原則 + ③説明可能性に接続できるため medium 維持は妥当（high までは不要）。#129（GitHub API nullable フィールド一覧）は詳細ページの表示データ（Star数・Issue数等）の null 処理漏れ防止という①与件寄りの実利があるため medium 維持を推奨（app_quality の実装確認待ち）。

**アプリ本体 vs エージェント運用プロセス改善の相対的な重み**: KPI 表に直接載るのはアプリ本体の品質（#92 #125 #135 #109 #116）のみ。parallel-safety / review-quality はプロダクトそのものを変えないため、**それらの中で high を維持できるのは「テスト CI 成功を直接壊すリスクがあるもの」（#109 相当）に限る** べきで、それ以外は medium 以下が妥当という基準を提案する。

### 争点 A（統合候補）

KPI 接続の観点からは、統合可否そのものより「統合後の priority をどう引き継ぐか」が関心事。#100+#110・#85+#93・#117+#124 はいずれも接続経路が同じレーン（プロセス運用）内なので、backlog_hygiene の G-3 判定に従って統合してよい。**#129+#136 は接続経路が異なる**（#129 はデータ正確性＝①寄り、#136 は実装規律全般＝③寄り）ため、mission_po としては統合よりリンクのみを推奨する。#130+#139 も「domain-model 整合」と「ドキュメントのコード例示整合」で対象データが異なるため、切り口は近いが同一とまでは言えず、link_only 寄りを支持する。

### 争点 B（Epic 化）

machine-check・parallel-safety は Epic 化に賛成（閾値超・追跡単位の整理）。ただし Epic のタイトルに「KPI 接続なし＝プロセス改善専用」であることを明記し、Epic 自体の priority を low〜medium に据え置くことで、子 Issue が誤って high 化される事故を防ぐべき。preview-ops・review-quality・doc-record は閾値未満のため無理に Epic 化せず、必要なら親 Issue なしの相互リンクで十分。

### 争点 E（取りこぼしの点検）

最大の取りこぼしは D で指摘した **#92 #125 #116 が high に入っていない** こと自体。これは「振り返りレーンが拾った知見」の優先度判定が、KPI 表と接続せずラベル付けされている証拠であり、今回の棚卸しで是正すべき最優先事項。逆に他レーンの担当を奪っている疑いがあるものとして、#94（Stop フック自動コミットの履歴汚染）は監査・衛生レーン（`workflow-health-check` / `project-sync`）の対象領域（ハーネスの状態・運用品質）に近く、改善 Issue レーンで抱え続ける必然性が薄い。backlog_hygiene の判定に委ねるが、レーン越境の可能性として明記しておく。
