# fact_check ラウンド1: 事実精度検査（争点D主担当）

## 検査手法
- `app/globals.css` / `docs/03_design/ui-ux/ui-ux-guidelines.md` §2.4 を読んで 44px/16px の適用範囲を確認
- `src/ui/login-link.tsx`（size="sm"）/ `src/ui/locale-switcher.tsx`（size="default"）で二次コントロールの実サイズを確認
- `content/research/20260819-form-uiux-and-design-review_deep_research.md` §3 で 16px 根拠の確度を確認
- `npx vitest run --reporter=dot`（実行済み）/ `npx playwright test --list`（実行済み）/ `ls docs/adr/[0-9]*.md | wc -l`（実行済み）で trust セクションの数値を実測

## 1. 「44px」は主要導線限定か

**事実**: `app/globals.css:70` `--size-control-xl: 44px; /* 主要導線 */`。`ui-ux-guidelines.md` §2.4 に明記:
> `--size-control-xl`（44px）… 主要導線（検索入力欄・検索ボタン）は `--size-control-xl` を使う。二次的なコントロールは `--size-control-md`（32px）以上を使う（L.146-147）
> **すべてのコントロールに 44px を要求しない**（L.502）

**実装での裏取り**（二次コントロールが実際に 44px 未満）:
- `src/ui/login-link.tsx`: `buttonVariants({ variant: 'ghost', size: 'sm' })` → `--size-control-sm` = **28px**
- `src/ui/locale-switcher.tsx`: `buttonVariants({ size: 'default' })` → `--size-control-md` = **32px**

**書き換え時に守るべき線**:
- ❌ 言ってはいけない: 「タップ領域は 44px です」（全コントロールと誤読される一般化）。「ボタンはすべて 44px」も同様に NG（ログイン導線・言語切替は 28px/32px で現に矛盾する）
- ✅ 言ってよい上限: 「検索まわり（検索欄・検索ボタン）などの主要導線は 44px」「主要な操作ボタンは指で押しやすい 44px」のように **主要導線であることを明示** する。「タップ領域」という語だけを主語にすると全体化されるため、「検索」「主要な操作」等の限定語を落とさないこと

## 2. 「入力欄は 16px 以上で iOS の自動ズームも起きません」

**事実**: `--text-control-min: 1rem`（16px）は「入力系コントロールの最小フォントサイズ」（`globals.css:71`）。適用範囲は入力欄のみで、ボタン等には適用されない（cva の各 size variant は独自のフォントサイズを持つ）。

**根拠の確度**: `content/research/...深いリサーチ` §3 は「iOS Safari は input の実効フォントサイズが 16px 未満のときフォーカス時に自動ズームする。16px 以上であればズームは発生しない」を独立 3 出典・敵対的検証 3-0 で確定済み（高信頼度）。ただし出典はいずれも一般的なブログ記事であり、Apple 公式ドキュメントでの明記ではない（実務上ほぼ確立した経験則という位置づけ）。

**書き換え時に守るべき線**:
- ✅ 「入力欄」に限定する限り、「16px 以上で iOS の自動ズームが起きない」は言い切ってよい（3 出典一致・自プロジェクトも 1rem=16px を全ブレークポイントで維持する設計・§2.4 L.140）
- ❌ 「すべての文字が 16px」「画面全体で自動ズームが起きない」等、入力欄以外に一般化しない
- ⚠️ 「起きません」の断定は妥当だが、iOS Safari 限定の挙動である旨が完全に消えると「あらゆる環境でズームしない」という過剰主張になりうる。現行文は「iOS の」と明示しており、これは正しい書き方（書き換えでこの限定語を落とさないこと）

## 3. 「Lighthouse の Accessibility 100」が保証すること

**事実**: LP 記載は 2 箇所。
- tile: 「Lighthouse の Accessibility 100 を『下回ったらリリースしない』基準として運用しています」
- trust カード: 「Accessibility 100 / Lighthouse の必須ゲート。下回ったらリリースしない」

**何を保証し、何を保証しないか**:
- 保証する: Lighthouse の自動検出可能な a11y ルール（axe-core ベースのサブセット）を満たしていること。CI/リリースゲートとして機械的に強制されていること（運用上の事実として正確）
- 保証しない: WCAG 2.2 AA 適合そのもの（Lighthouse の自動検査は WCAG 全項目をカバーしない。手動確認が要る基準="操作の意味順序""コンテキスト依存の代替テキスト適切性"等は対象外）

**現行文 vs 書き換え案の主張強度判定**:
- 現行の tile 文言「Lighthouse の Accessibility 100 を〜基準として運用しています」は **Lighthouse スコアの運用事実のみを述べており WCAG 適合を主張していない** ため、事実として正確（過剰主張ではない）
- 一方、同じ tile の tag-list には `WCAG 2.2 AA` という別軸のタグが並置されており、read者が「Lighthouse 100 = WCAG 2.2 AA 適合の証明」と **誤読するリスクがある**（隣接提示による暗黙の等号）
- **書き換え時に守るべき線**: 「Lighthouse で 100 点」と「WCAG 2.2 AA に適合」を同一文・同一箇条書き内で無条件に並べない。両立させる場合は「Lighthouse の自動チェックで 100 点」等、自動検査である旨を明示するか、WCAG 適合の根拠（コントラスト実測・フォーカス可視という手動確認を別途行っている旨、既に tag-list にある）を明確に繋げる。**「Lighthouse 100 だから WCAG AA」という因果を書いてはならない**

## 4. trust セクションの数値（実測結果）

| LP 記載 | 実測コマンド | 実測結果 | 判定 |
|---|---|---|---|
| 1,061 ケース | — | — | ❌ **不一致**（下記合算） |
| ユニット・結合 954 | `npx vitest run --reporter=dot` | **Test Files 81 passed / Tests 953 passed** | ❌ 954 ではなく **953** |
| E2E 107 | `npx playwright test --list` | `Total: 109 tests in 24 files`（`playwright.config.ts` の projects は chromium のみ、他ブラウザなし） | ❌ 107 ではなく **109** |
| 合算 | 953 + 109 | **1,062** | ❌ LP の「1,061」と 1 件差 |
| ADR 15 本 | `ls docs/adr/[0-9]*.md \| wc -l` | **15** | ✅ 一致 |

**判定**: テストケース数は **現行 LP の数字が古くなっている**（953≠954、109≠107、合計1062≠1061）。誤差は小さい（各 1〜2 件）が、「実測に基づく信頼シグナル」を謳うセクションで実測と food違う数字を出すのは trust セクションの主張そのものと矛盾する。

**書き換え時に守るべき線**:
- ❌ 「1,061 ケース（ユニット・結合 954 / E2E 107）」をそのまま維持しない（実測と不一致であることが判明した以上、黙って据え置くのは L-113 の精神に反する）
- ✅ 選べる対処は 2 通り（どちらも事実精度は満たす。B/C 争点の文言確定と合わせて判断）:
  1. 実測値に更新する（「1,062 ケース（ユニット・結合 953 / E2E 109）」）— ただし今後もテスト追加で数字は動き続けるため、更新運用コストが発生する
  2. 桁を丸めて更新頻度への耐性を持たせる（例:「1,000 件超のテスト」）— 精度を落とす代わりに更新不要になる。これは E) トーン争点にも関わる判断のため、fact_check としては「今の数字のまま出すことだけは事実として NG」という制約のみ置き、丸めるか実測更新するかの選択は copy_editor 側の裁量とする
- この不一致は **私の担当外の実装差分の是非**（954→953等がバグか仕様変更かは不明）ではなく、**LP のコピーが実測から乖離している** という事実として記録するのみ。実装側の理由確認が必要なら dev_reader 領域

## 5. 「JavaScript 0 行」

**事実**: LP 記載は「このページはページ内 JavaScript も外部 CDN も使っていません」（trust カード span）。`site/index.html` は GitHub Pages 配信の **静的 LP 自身**（プロジェクトの CLAUDE.md 冒頭にも `site/`＝LP と明記）であり、アプリ本体（`app/` `src/`）は Next.js 16 + React Server Components で動く別物。

**矛盾の有無の判定**: LP 本文は「このページは」と明確に主語を LP 自身に限定しており、アプリ本体への言及を一切していない。**現行文は矛盾していない**。

**書き換え時に守るべき線**:
- ✅ 「このページは」の限定を落とさない限り安全
- ❌ 主語を落として「JavaScript 0 行」だけを見出し的に強調する書き換えは NG（stack chips で直後に「Next.js 16 / React Server Components」を掲げているため、読者が「じゃあこの JS フレームワークは何のためにあるのか」と混乱し、結果的に矛盾して見える）。書き換えるなら「配信ページ（LP）は」等、対象範囲を毎回明示する
