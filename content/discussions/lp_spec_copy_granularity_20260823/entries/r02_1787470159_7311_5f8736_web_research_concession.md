## dev_reader への応答（論点1）: 比較対象は妥当か

**部分的に譲歩する。ただし結論は変わらない、むしろ強化される。**

ご指摘のとおり round 1 の 4 社（Vercel / Linear / PostHog / Plausible）は VC 資金の入った企業プロダクトで、「個人開発者が作った OSS ツール」である gem-hunter の比較対象として厳密ではなかった。そこで **本物の個人・小規模チーム運営の OSS ツール LP** を追加で 2 件、実際に WebFetch して観察し直した。

- **ntfy.sh**（個人開発の HTTP pub-sub 通知サービス・OSS）
  https://ntfy.sh/
  - 本文コピーに出てくる数値は GitHub star 数（"28,578+"）と料金プランの定量値（"2,500 daily messages" 等）のみ。**技術仕様（バージョン・サイズ・内部指標）は本文に一切出てこない**。
  - features の説明はベネフィット文が主体（例:「不正ログインや宅配到着をアラートできる」のようなユースケース記述）。
- **Miniflux**（個人開発の RSS リーダー・OSS・Apache 2.0）
  https://miniflux.app/
  - 出てくる数値は価格（$15/year）とトライアル日数（15-day）のみ。**技術仕様・パフォーマンス数値は皆無**。
  - features は「Optimized for readability」「Less is more!」のような価値観・ベネフィット文で書かれ、仕様の列挙は避けている。

**判定**: 「個人開発 OSS の LP なら仕様を出すはず」という dev_reader の仮説は、この 2 件では支持されなかった。むしろ **企業 LP（Vercel/Linear/PostHog）よりもさらに徹底して技術数値を排除している**（企業側は事業規模の数値だけは出すが、個人 OSS の 2 件はそれすら最小限）。Plausible だけが例外的に技術数値（54倍小型・稼働率）を trust/proof 文脈で出す構成だったが、これは「プライバシー訴求のための検証可能性」という Plausible 固有の戦略であり、「個人開発だから仕様を見せる」という一般則ではないと考えられる。

**結論への影響**: 比較対象を個人 OSS 寄りに補正しても、「features tile 本文に px 単位の内部実装値を裸で置く」慣行は依然として観測されない。round 1 の結論（数値の要否はセクションの主題＝信頼性の証跡か UX の状態説明かで決まる。trust セクションは残す・features tile の px は言い換える）は維持する。撤回するのは「比較対象の選定が企業寄りだった」という手続き上の弱さのみで、結論そのものではない。
