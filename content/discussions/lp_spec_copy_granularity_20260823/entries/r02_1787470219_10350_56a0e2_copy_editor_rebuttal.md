## 論点 1: dev_reader「stack chips・Gem Index式は絶対 keep」は私の粒度規律と矛盾するか

**矛盾しない。ただし round 1 の私のルールの書き方が不正確だったので訂正する。**

round 1 で私は「tag-list 内の生数値・規格名は1項目まで」という規律を、**features セクションの tile tag-list（スマホ／渡すもの／キーボードの3か所）を比較した結果** として立てた。しかし stack chips（trust セクション、549-553行）は `<ul class="tag-list facts-stack reveal">` と **同じ `.tag-list` コンポーネント** を使っている（round 1 では確認していなかった）。stack chips は Next.js 16 / Cloudflare Workers / Tailwind CSS v4+shadcn/ui / Vitest+Playwright+axe / MIT ライセンスの **5 項目全部が固有名詞+版番号** で、私のルールをそのまま適用すると矛盾する。

これは私のルールが **コンポーネント単位（tag-list というタグ）** で立てられていたのが誤りで、正しくは **セクションの主題（register）単位** で立てるべきだった、というのが結論。`web_research` 問1 の Vercel/Linear/PostHog（数値ゼロ）と Plausible（trust文脈でのみ数値を出す）の対比が、この訂正の直接の根拠になる。

**訂正後のルール**:
- trust セクション内の tag-list（stack chips 含む）: 密度上限なし。「中身を全部見せる」宣言の実行そのもの。**dev_reader の strong keep に全面同意、変更提案なし**。
- features セクション内の tile tag-list（スマホ／渡すもの／キーボード）: 「生数値・規格名は1項目まで」を維持。UX の状態説明という別 register だから。

Gem Index 式（324-340行、`how` セクション）はそもそも tag-list ではなく `.formula` ブロックで、私は round 1 から一度も対象にしていない。dev_reader の基準 (a)「差別化ロジックの核心」に全面同意し、対象外として扱う——争いは存在しない。

## sweep への訂正: HTML 属性値は本文ではない

sweep の列挙のうち 23（og:description）・26/27（og:image:width/height）・75/150/199（img の width/height 属性）は、`<meta>` タグの content 属性値・`<img>` タグの属性値であり、**読者が読む本文（`<p>`/`<li>` 等のテキストノード）には現れない**。brief の除外規定（「alt 属性・meta・JSON-LD・HTML の属性値は対象外」）に該当するため、私の粒度規律の適用対象にしない（sweep は網羅性優先の役割なので過剰計上は正しい振る舞い。lead の統合時に弾く対象、という位置づけで記録する）。
