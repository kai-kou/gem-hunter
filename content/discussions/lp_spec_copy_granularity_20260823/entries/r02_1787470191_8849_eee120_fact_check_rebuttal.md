# fact_check ラウンド2: 4 論点への判定

## 1. copy_editor 確定案の判定（tag-list / 本文1文目）

**判定: 3 項目・本文とも「言ってよい上限」の範囲内。越えているものはない。**

| 対象 | 文言 | 判定 | 理由 |
|---|---|---|---|
| tag-list ① | 主要ボタン 44px | ✅ 合格 | 「主要」という限定語が残っており、round1 の要求（「主要導線」「主な操作ボタン」等の限定語を落とさない）を満たす。round1 で確認済みの実装（`--size-control-xl` は検索入力欄・検索ボタンにのみ適用、login-link/locale-switcherは28px/32px）と矛盾しない |
| tag-list ② | 入力ズームなし | ✅ 合格 | 「入力」に限定されており、round1 の要求（16px は入力欄限定）を満たす。数値を削って outcome 化しているが、事実精度は数値の有無ではなく射程の正確さで判定するため問題なし |
| tag-list ③ | レイアウトはそのまま | ✅ 合格（対象外） | 数値・技術主張を含まない構造説明。事実精度の検査対象外 |
| 本文1文目 | 主な操作ボタンは指で押しやすい大きさにしてあり、入力欄をタップしても画面が勝手に拡大されません。 | ✅ 合格・ただし 1 点だけ確認事項あり | 「主な操作ボタン」で44px側の限定はクリア。ズーム文には round1 で必須とした「iOS の」という限定語が消えている |

### ズーム文の「iOS」省略について（concession寄りの判定）

round1 で私は「iOS Safari 限定の挙動である旨が消えると『あらゆる環境でズームしない』という過剰主張になりうる」と書いたが、round2 で再検討した結論は **これは過剰主張ではなく true な一般化** である、に訂正する（**concession**）。理由: 自動ズームは iOS Safari 固有のバグであり、他ブラウザ・他 OS はそもそも入力フォーカスでズームしない。したがって「画面が勝手に拡大されません」は環境を限定せずとも普遍的に真。iOS 限定語を落としても虚偽にはならない。
とはいえ **将来への耐性は iOS 明記のほうが高い**（万一将来他ブラウザに同種挙動が生まれても、この文は「なぜズームしないか」の因果を語っていないぶん影響を受けない、という意味では copy_editor 案の方がむしろ安全側）。→ **この 1 点は事実精度としての NG ではなく任意の文体判断** であり、copy_editor 案を止める理由にはならない。B/C の確定文言をこのまま通してよい。

## 2. dev_reader「stack chips（Next.js 16 等）は絶対 keep」への危険判定

**危険はある。ただし「今 Next.js 16 が誤りだ」という主張はできない（round1 で package.json 未確認・round2 も対象ファイル再読制約のため未確認 = 断定しない）。**

危険の構造は、trust セクションのテストケース数（954/107）と **全く同型**: LP 内にハードコードされた具体数値・バージョン番号は、実装が変わっても自動追随しない。今回の議論で trust の数値がすでに 1 件ズレていた（953/109 が実測）ことが、この構造的リスクが **空想ではなく実際に発現した前例** であることを示している。stack chips のバージョン番号（Next.js 16 / Tailwind CSS v4 / Playwright 等）も同じ「手打ちの静的な値」であり、次回のメジャーアップデート時に LP だけ古いままになる構造的な陳腐化リスクを持つ。

**keep 自体への反対ではない**（dev_reader の基準(c)＝固有名詞・規格名として残す判断は事実精度と衝突しない）。ただし round1〜2 の実測知見として次を synthesizer に申し送る:
- stack chips のバージョン番号は「一度書いたら更新されない」前提を LP 運用側が意識しておくべき（trust の数値と同じカテゴリの負債）
- 現時点で `Next.js 16` が `package.json` の実バージョンと一致しているかは **今回未確認**（対象ファイル再読の制約により round2 では検証していない。断定しない）。keep を決定する前に、dev_reader かレビュー担当が 1 回だけ `package.json` と突合することを推奨する（事実精度としての最終ゲート）

## 3. web_research「44px は規格原文でも数値で書かれているので正当」と私の「主要導線限定」の両立性

**両立する。反論ではなく補強。両者は別の問いに答えている。**

- web_research の主張が答えている問い: 「44px という **数値そのもの** は LP が勝手に作った数字か、それとも実在の規格に基づく数字か」→ 実在（WCAG 2.5.5・Apple HIG）に基づく、これは正しい
- 私が round1 で立てた制約が答えている問い: 「gem-hunter という **この実装** において、44px は何に適用されているか」→ 主要導線（検索欄・検索ボタン）のみ。二次コントロールは 28px/32px

**原文の射程を確認した結果（round1 で web_research が引用した原文を再利用）**: WCAG 2.5.5 原文は "The size of the target for pointer inputs is at least 44 by 44 CSS pixels **except when**: …"（4 例外）— つまり **規格自体は「原則すべてのポインタ入力ターゲット」に適用範囲を置いており、「主要導線のみ」という限定は規格側にはない**。Apple HIG の "a button needs a hit region of at least 44x44 pt" も同様に対象を限定していない。

→ したがって「主要導線限定」は **WCAG/HIG が定めた射程ではなく、gem-hunter が AA 準拠を維持しつつ AAA 相当を上乗せする範囲を自主的に絞った、プロジェクト固有の設計判断**（`ui-ux-guidelines.md` L.502「すべてのコントロールに 44px を要求しない」）。LP がこれを書く際に必要な限定句は、**規格の限定ではなく「gem-hunter がどこに適用したか」の限定** として書かねばならない。copy_editor 案「主要ボタン 44px」はこの区別を正しく踏まえている（規格名を出さずに、適用範囲だけを言っている）ので問題ない。

**web_research が挙げた 44px(WCAG/HIG) vs 48px(web.dev) の揺れについて**: LP 本文・tag-list のいずれも「WCAG」「Apple」等の規格名を 44px の隣に明記していない（`WCAG 2.2 AA` タグは別の tile＝キーボード操作性の文脈に付いており、44px の tile には規格名の言及がない）。規格名を名指ししない限り 44 と 48 の業界内の揺れは LP の事実精度に影響しない。**規格名を新たに追記する書き換え案が出た場合のみ、この揺れへの対応が必要になる**（現状の copy_editor 案は規格名を追加していないので対応不要）。

## 4. trust 数値の不一致: 「LP が古い」か「計測方法の違い」か（round2 追加検証・ファイル読み込み許可あり）

**切り分けた結論: 計測方法の差ではなく、LP が古い（手打ちの数字が実装の変化に追随していない）。**

追加確認（package.json）:
```
"test": "vitest run"        ← 私が実行したコマンドと同一。差分なし
"test:e2e": "playwright test"  ← playwright.config.ts の testDir/testMatch と `--list` は同一設定を参照。フィルタ差分なし
```
`playwright.config.ts`: `testDir: 'e2e'` / `testMatch: '**/*.spec.ts'`。projects は chromium 1 つのみで重複計上の余地はない。round1 で確認済みの skip/todo 検索も 0 件。→ **計測方法の差は無い**（`--list` は実行対象と同一集合を列挙している）。

さらに `content/discussions/lp_github_pages_review/` という **本 LP に対する過去の別ラウンドの議論記録** を確認したところ、当時は trust カードの数値が `約 560 + 88` という異なる値だった形跡があり（`sec-trust.png` 講評・fact_check エントリに `ADR 15 本 = 15 ファイル` の実測記録あり）、その後 `954 / 107` に手動更新され、今回さらに実装が進んで `953 / 109` になっている。つまり **この数値は過去に少なくとも 1 回、人力で更新された前例があり、今回また 1〜2 件分ズレた** ——「一度直しても実装が進めばまたズレる」という構造的な陳腐化パターンが実測で再現されたことになる。

**LP に書くべき正しい数値（確定）**:
> **ユニット・結合 953 / E2E 109（合計 1,062）**（2026-08-23 時点の実測値）

ただし、この数字も次のコミットで再びズレる。round1 で示した 2 択（実測値に更新 / 桁を丸めて更新頻度耐性を持たせる）のうち、今回 stack chips でも同型の陳腐化リスクが見つかったことを踏まえると、**「LP 内の実装依存の生数値（テスト件数・バージョン番号）は今後も同じ理由で継続的にズレる」という一般化した申し送りを synthesizer に上げるべき** と判断する。個別修正だけでなく、E（トーン・構造）側でこのカテゴリの数値の扱い方針（丸める/更新運用を決める）を一度確定させることを推奨する。
