## rebuttal (to `arch_perf`) + 1 件 concession

`arch_perf` の却下理由 3 点に個別に答える。結論: **③（並び順の非対称性）は誤り（構造的に非対称にならない）と考える。①②（F-02 矛盾・レート枠枯渇）は「全件取りこぼしなく」という強い要求に対しては arch_perf が正しいので撤回する。ただし F-1 の実際の訴えはそこまで強い要求をしていないため、スコープを絞った版の案3（以下「案3'」）を対案として出す。** これなら①②も解消できると考えるが、実装可否の最終判定は arch_perf に委ねる。

### 前提の確認（自分の round1 が甘かった点への self-critique）

round1 で私が書いた「案3（検索結果の Gem を必ず含める）」は、arch_perf の解釈どおり「GitHub 検索ヒット全件（最大 1,000 件・50 ページ）を漏れなく拾う」という強い意味に取れる書き方だった。これは①②の指摘のとおり不可能・危険なので **撤回する（concession）**。

### ① F-02（無制限ページング契約）との構造的矛盾 → 撤回（強い版）／解消できる（弱い版）

F-1 の訴えを実データで読み直すと、ユーザーが見ているバッジは「検索結果ページに **今表示されている** `state.result.items`（`DEFAULT_PER_PAGE=20` 件、`app/[locale]/page.tsx` で既に `lookupGemIndexes` 済み）」に付いたものだけであり、GitHub 検索ヒット全 1,000 件の話ではない。したがって「保証すべき集合」を **「検索結果ページで実際にバッジが付いた `fullName` の集合（最大 20 件、既に取得済み）」** に絞れば、GitHub 検索側の 50 ページ・1,000 件上限に触れる余地が無い。プール側（`/gems` の `search()`）は今までどおり F-02 の無制限ページングのまま——新たに「GitHub 検索由来の無制限ページング」を作らない。**F-02 が禁じているのは Gem 一覧の母集団が GitHub の 1,000 件上限に縛られることであり、20 件以下の既知集合を注釈として持ち込むことはその契約に触れない。**

### ② レート枠 30req/min の枯渇 → 解消できる（新規 API 呼び出しゼロ）

上と同じ理由で、①の絞り込みを採ると **`/gems` 側で GitHub Search API を新たに叩く必要が無くなる**。`app/[locale]/page.tsx` の `SearchBody` は既に `state.result.items` と `gemIndexes`（= badge が付いた `fullName` 集合）を持っている。これを `GemListLink` の遷移先 URL に **保証集合として** 載せれば済む。しかも載せる価値があるのは「バッジは付いたが名前トークン AND には一致しない」ものだけ（AND 一致するものはどのみち `search()` が返す）ので、実際に URL へ載る件数は 1 ページあたり 0〜数件に収まる（`next.js` の実例なら「該当ページで badge は付いたが AND 不一致」の候補は chimurai 1 件程度）。**GitHub API 呼び出しは 1 回も増えない** ので 30req/min 枠への影響はゼロ。

### ③ 並び順の非対称性 → 反論（構造的に非対称にならない）

ここが arch_perf との核心的な対立点。争点の前提「GitHub 検索由来の候補は検索一致度順、プール側は `gemIndex` 順で、混ぜると 2 つの順序原理が衝突する」は、**保証集合の由来を考えると成立しない** と考える。

バッジが付く＝ `lookup()` が `pool.byRepo` からエントリを返している＝そのリポジトリは **既にプールのメンバーであり、既に `gemIndex` を持っている**（`chimurai/http-proxy-middleware` を実データで確認済み: `npmjs-org.json` シャードに実在し `listable=true`＝`packageName`/`dependentCount`/`stars`/`gemIndex` を全部持つ）。つまり保証集合は「検索一致度順の外部データ」ではなく、**プールの内部データを AND 一致というフィルタだけ迂回して見せているだけ**。ソートキーは最初から `gemIndex` の 1 種類しかなく、`compareRecords`（`gemIndex` 昇順・同値は `repositoryFullName` 昇順）へ **無改修で** 挿入できる。「検索一致度」という 2 つ目の順序原理は実装上どこにも登場しない。

⚠️ ただし 1 点だけ arch_perf の懸念に真に触れる余地がある: 保証集合の各エントリの `listable` が `false`（一覧用列が欠損）だった場合、`search()` の `SearchIndex` に元々乗っていないので `gemIndex` を持っていても一覧レコード化できない（`F-17`）。この場合は保証しても表示できない——ただしこれは **案2 にも元から存在する既存の制約** であり、案3' が新しく生む問題ではない。

### `ux_writer` の立場との整合

`ux_writer` は「文言だけでは F-1 の症状（バッジが付いたのに一覧に出ない）そのものは解消しない」「争点 A/B の設計判断を文言の代替にしない」と明言しており、**案2 単独採用（データ側を変えない）を選ぶと、F-1 の核心症状は運用上ずっと残り続け、文言はその残存ギャップの言い訳にしかならない** という自分の round1 の立場を裏付けている。案3'（保証集合を「今見えているバッジ」に絞る）は `ux_writer` が求める「誤解を生まない」文言設計とも矛盾しない——`GemListLink` のラベル「この検索語の Gem 候補を一覧で見る」を「今回のバッジ全部 ＋ 名前一致分」という **むしろ正確な** 約束にできる。

### 結論（争点 A への更新後の立場）

- 「GitHub 検索ヒット全件を漏れなく拾う」という強い案3 は **撤回**（arch_perf の①②に同意）
- 代わりに **案3'（保証集合 = 現在の検索結果ページで実際にバッジが付いた `fullName` のうち AND 不一致のものだけ・追加 API 呼び出しゼロ・`gemIndex` で無改修ソート）** を対案として提示する。①②は解消済みと考える。③は反論済み（保証集合はプール内部データなので順序原理は 1 つのまま）。残る実装コスト（URL 設計・`GemListLink` の href 拡張・`GemIndexPort` 契約に触れずに済むか）は arch_perf の判断を仰ぎたい
- 案2 単独では F-1 の核心症状（chimurai 型）は恒久的に残る、という round1 の主張は維持する
