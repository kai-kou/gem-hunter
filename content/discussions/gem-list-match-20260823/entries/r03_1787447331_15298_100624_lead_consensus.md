## 合意点（lead 整理）

### 全員が同意した事実
1. **バッジと一覧は判定基準が別物**。バッジ＝プール所属照会（検索語と無関係）、一覧＝repo 名・パッケージ名の全語 AND 単語境界一致（`D-37`）。`q=next.js` は `['next','js']` の AND で 1 件に落ちる。
2. **`chimurai/http-proxy-middleware` 型（GitHub が description でヒットさせた候補）は、名前照合を何度緩めても一覧に出ない**。緩和は「クエリのトークンのうちどれを残すか」の操作でしかなく、クエリに無い語（`http`/`proxy`/`middleware`）へは広がらない（`arch_perf` が明示的に concede）。
3. **閾値緩和（AND ヒット数が N 件未満なら 1 語緩和）は不採用**。`next` 単独緩和は 38 件中 37 件（97.4%）がノイズ（`search_semantics` 実測）。`arch_perf`・`ux_writer` とも撤回・同意した。`.js` 接尾辞の特別扱いも `D-37` の「形態素解析はしない」に抵触し不採用。
4. **全件保証ハイブリッド（GitHub 検索 1,000 件を総なめして `lookup`）は不採用**。1 表示で最大 50 回の API 呼び出しになり、installation token の 30 req/min を 1 操作で溶かす（`arch_perf`）。`search_semantics` が撤回した。
5. **`D-36`/`D-37`/`D-38` は `open-questions.md` の決定表に実在する**（`docs_trace` の round 1 の「見当たらない」は誤りで、本人が round 2 で訂正済み）。
6. **今回の症状は `D-37` の既知フォローアップ「薄いヒット（1〜2 件しか出ない検索語が 42 語中 4 語・9.5%）」と同系だが、緩和が発火しない（AND=1 ≠ 0）ため現設計では解消されない**（`docs_trace`）。

### 収束した対案: 案3'（scoped hybrid・追加 API 呼び出しゼロ）
`arch_perf` と `search_semantics` が独立に同じ形へ収束した。

- `/gems` への導線は必ず検索結果ページ経由。そこには **既に取得済みの** `state.result.items` と `gemIndexes`（バッジが付いた `fullName` 集合・最大 20 件）がある
- そのうち **AND 不一致のものだけ** を `GemListLink` の href に載せ、`/gems` 側でプール名照合の結果へマージする
- **GitHub API 呼び出しは 1 回も増えない**。マージ対象はプール内部データなので `gemIndex` を既に持ち、`compareRecords`（`gemIndex` 昇順・同値は `repositoryFullName` 昇順）へ無改修で挿入できる（順序原理は 1 つのまま＝`arch_perf` の「並び順の非対称性」懸念は成立しない）
- URL 改変で任意のリポジトリを注入することはできない（プールに載っていない `fullName` は無視される）

### 残る対立（lead が裁定せずユーザーへ上げる）
`ux_writer` は **案2（データ側は変えず文言を是正）** を支持し、案3 系を「1 ページ目だけ完全・2 ページ目から性質が変わる部分完全性は、今より悪い期待破壊を生む」と反論した。

🔴 **lead の見立て**: この反論は `arch_perf` の round 1 版（全件保証ハイブリッド）に対しては正しいが、**収束後の案3' には当たらない**。案3' の同伴集合は URL に固定された ≤20 件で、マージ後の集合はその URL に対して決定論的、並びも `gemIndex` 単一原理なので「2 ページ目から構成が変わる」ことはない。ただし **同じ `/gems?q=...` でも検索結果から来たか直接開いたかで結果が変わる**（同伴分の有無）という非対称は案3' にも実在し、`ux_writer` の警戒はその形で残る。

これは **仕様解釈の分岐**（どちらでも筋が通り、選択で成果物が変わる）なので `SD-3` 第 2 系統としてユーザー確認へ回す。
