# ux_writer round2 rebuttal

## 争点 A: UX 観点の判定 — 案2（arch_perf）を支持する。案3（search_semantics）は「ラベルの約束」を結局果たせない

### 判定基準の確認

「この検索語の Gem 候補を一覧で見る」というラベルが利用者に暗黙で約束しているのは、字面上は 2 通り読める:
(i) 「この検索でバッジが付いた候補と同一集合が出る」（F-1 で利用者が実際に持った期待）
(ii) 「この検索語に関連する Gem 候補が見られる」（ラベルの文字どおりの主張）

search_semantics の主張は (i) を基準に案3 を推している。だが arch_perf の round1 実測（争点 A・案3 節）を読むと、**案3 も (i) を厳密には満たせない**: 「取りこぼしなく全部」は GitHub 検索の 1,000 件上限内でしかフェッチできず、F-02（Gem 一覧に 50 ページ上限を適用しない）と両立させるには 2 ページ目以降でプール側だけの非対称構成になる、と arch_perf は具体的に示している（`totalCount` 不整合・並び順の破綻・レート枠消費まで含めて)。つまり**案3 が実際にユーザーへ出せるのは「1 ページ目だけ完全、2 ページ目から突然性質が変わる一覧」**であり、これは (i) の期待を部分的にしか満たさない。

そして UX 的にはこの部分完全性のほうが今の状態より**悪化しうる**: 「クリックしたら 1 件しか出ない」は 1 回の失望で完結するが、「1 ページ目は期待どおりなのに 2 ページ目から急に減る／構成が変わる」は**同じセッション内で挙動が裏切られる**体験で、原因の説明も一段難しい（「なぜ 2 ページ目からルールが変わるのか」を文言でどう伝えるかという新しい難題が生まれる）。round1 で自分が示した立場「文言は驚きを減らせるが、構造的なズレそのものは埋められない」がそのまま案3 にも当てはまる ── むしろ案3 は「ほぼ埋まっているように見えて実は埋まっていない」分、round1 で警戒した**誤った完全性の期待を助長するリスクが案2 より高い**。

したがって UX 観点の結論: **(i) を基準にしても案3 は勝てない（部分完全性はむしろ新しい混乱を生む）。(ii) を基準にするなら案2 で十分満たせる（「関連する」であって「同一」とは書いていない前提に立てば）。** よって**案2 を支持**する。ただし (ii) で押し通すには、今のラベル文言が (i) 寄りに読める（「この検索語の」＝同一視を誘発する）ことの是正が必須。round1 で「据え置き」とした判断はここで撤回する。

## 争点 B への concession（search_semantics 支持）

search_semantics のチェック3・4（閾値緩和や `.js` 接尾辞分割は `next` 単独 38 件中 37 件がノイズ、`io` 等の頻出語では破滅的）には UX 観点からも同意する。Gem 印は「star 数のわりに過小評価」という**精度が命の弱いシグナル**であり、母数を広げてノイズ比率が上がると、利用者が「Gem の印は当てにならない」と学習してしまうコストの方が「1 件しか出ない」より高くつく。**閾値緩和・接尾辞分割どちらも不採用に賛成**（争点B は search_semantics の結論を支持する concession）。

## 案2 採用を前提にした文言の逐語書き換え（据え置きの撤回・具体案）

「この検索語の」＝badge との同一視を誘発する言い回しを、「名前が一致する」＝ D-37 の照合規則を正直に反映する言い回しへ揃える。3 箇所をセットで直す（1 箇所だけ直すと表現がバラつき、争点 C の一貫性要件に反する）。

### 1. `home.gemListLink.label`

```
ja現: この検索語の Gem 候補を一覧で見る
ja新: 名前が一致する Gem 候補を一覧で見る

en現: See Gem candidates for this keyword
en新: See Gem candidates matching this name
```

### 2. `gems.heading`

```
ja現: 「{query}」の Gem
ja新: 「{query}」に名前が一致する Gem

en現: Gems for "{query}"
en新: Gems matching "{query}"
```

### 3. `gems.description`

```
ja現: 検索語に関連する Gem 候補を、過小評価度（Gem Index）が高い順に一覧します。
ja新: 検索語とリポジトリ名・パッケージ名が一致する Gem 候補を、過小評価度（Gem Index）が高い順に一覧します。

en現: Browse the Gem candidates related to your keyword, the most underrated ones first.
en新: Browse Gem candidates whose repository or package name matches your keyword, the most underrated ones first.
```

### round1 の `home.gemBadge.intro`（検索結果見出し直下の説明文）との整合

round1 で提案した案 A（「Gem」マークは、star 数のわりに多くのパッケージから使われているリポジトリに付きます）は**そのまま維持**でよい。ここは「バッジとは何か」の定義であり、上記 3 箇所の書き換えが「一覧側の絞り込み方法」を担当するので役割は競合しない。むしろ両方を組み合わせることで、利用者は「バッジ＝候補プールにいる印」「一覧＝名前が一致するものだけの絞り込み」という**2 つの別概念**として自然に読める導線になる（round1 で立てた「文言は誤解を生まない書き方に倒す」という方針の実装がこれで完成する）。

`gems.unmatchableQuery` / `gems.empty` / `gems.relaxedNotice` は既に「単語境界一致」「限定的な候補プール」を明示しており、上記書き換え後も語彙は衝突しない（そのまま維持）。
