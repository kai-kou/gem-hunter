## 争点 A への rebuttal + 部分 concession（宛先: search_semantics）

### concede する点（明確に）

`chimurai/http-proxy-middleware` のような **description ヒット由来のバッジ** を案2（閾値緩和）が拾う経路は存在しない、という指摘は **認める**。理由も同意する: `GemIndexPort#search` の母集団はプールの `repositoryFullName` + `packageName` のトークンのみ（`static-gem-index.ts` の `mergeTokens`）で、GitHub の description 文字列そのものは静的シャード（`D-38`）に含まれていない。緩和（`selectMostSelectiveToken`）は「クエリのトークンのうちどれかを残す」操作でしかなく、クエリに存在しない語（`http`/`proxy`/`middleware`）へ広げる経路をロジック的に持ちようがない。**これは自分が round1 で書いた「残る限界」の内容と完全に一致する**ので、ここは新しい譲歩というより round1 時点で既に織り込み済みの限界として再確認する。

さらに **チェック3 の実測（`next` 単独緩和 = 38 件中 37 件ノイズ）は、案2 の「AND ヒット数が閾値未満なら 1 語緩和」という具体形を perf 観点からも支持できない材料になる**、とここで追加で認める。理由: 緩和後の結果セットが実質的にノイズ支配（97.4%）になるなら、緩和判定の「計算コストは増えない」という round1 の自分の主張（争点 A の防御ライン）は無意味になる——コストは同じでも UX 上のリターンがマイナスなら採用する理由がない。**閾値を下げる方向の案2 拡張は撤回する。**

### 数値で示す: 案2（現行ロジックのまま・閾値変更なし）は F-1 の主訴をどこまで解消するか

**答え: 0 件。** 現行ロジック（AND=0 のときだけ緩和）は `q=next.js` で AND=1（`vercel/next.js`）のため、そもそも緩和条件に触れない。つまり「案2 = 緩和条件の見直し」を選んだとしても、見直し方向が「閾値を上げて発火させる」なら 37/38 ノイズを持ち込むだけで正味の改善はマイナス、見直し方向が「発火条件を厳密化・現状維持」なら F-1 の主訴（chimurai 分の取りこぼし）に対しては **文字どおり無風**。search_semantics の結論（「案2 は F-1 の核心症状を原理的に解決できない」）に **同意する**。

### rebuttal: だが「だから案3（無制限ハイブリッド）」には perf 観点で乗れない

案3 が「badge が付いた対象を一覧が必ず含む」を **無条件に** 満たそうとすると、GitHub 検索の全ヒット（最大 1,000 件・50 ページ）を総なめして `lookup()` にかける必要がある。これを 1 回の `/gems` 表示で行うと:

- 1 回のページ表示で最大 **50 回の GitHub Search API 呼び出し**（`DEFAULT_PER_PAGE=20` × 50 ページ = 1,000 件）が要る
- installation token（共有枠・SP-8 未ログイン時の既定経路）は **30 req/min**。1 ユーザーの 1 操作で枠の大半〜全部を溶かし、同時間帯の他ユーザーの検索が枯渇する
- `TTL_SEARCH_SECONDS=60` のキャッシュ（`container.ts`）はキーワード単位なので、この全ページ走査自体はキャッシュで一度は緩和できるが、**初回ヒット時のレイテンシ**（50 回の直列/並列 API 呼び出し）は Workers の実行時間制約とユーザー体感の両方を悪化させる

つまり search_semantics の結論を採用するなら、「badge を必ず含める」という要求水準そのものを緩めない限り、perf 的に実装不可能な設計を選ぶことになる。ここは argue し続ける。

### 対案（scoped hybrid）: 全件保証は諦め、"いま見えているページ" だけを保証する

`/gems` への導線（`GemListLink`）は必ず検索結果ページ（`app/[locale]/page.tsx` の `SearchBody`）経由で踏まれる。その時点で `state.result.items`（**既に取得済み・追加 API 呼び出しゼロ**、`DEFAULT_PER_PAGE=20` 件以内）と、その `fullName` に対する `lookupGemIndexes` の結果（**既に呼んでいる**、`gemIndexes` 変数）が手元にある。

- `GemListLink` の `href` に、いま見えている検索結果のうち **badge が付いた `fullName` の一覧**（最大 20 件・`buildSearchUrl` のクエリ拡張、または短い ID 化）を積む
- `/gems` 側は、プール名照合の結果（案2 現状維持）に、この "同伴リスト" のうち **未ヒット分だけ** を追加でマージする（追加の GitHub API 呼び出し **ゼロ**・追加の `lookup()` 呼び出しも不要、渡された `fullName` はそのまま prepend/inject すればよい）
- コストは実質ゼロ（既存レスポンスの中身を URL 経由で運ぶだけ）。レート枠・cold start・CPU のいずれにも新規負荷が乗らない

**これは F-1 の実例（chimurai が検索結果 1 ページ目に見えている状態から『一覧で見る』を押すケース）を正確に解決する**——search_semantics が実測で示した「バッジが見えているのに一覧に出ない」というまさにそのユーザー体験を、見えている範囲については構造的に一致させられる。

**ただし正直に開示する限界**: これは「いま見ているページ（最大 20 件）の badge だけ」を保証するのであって、search_semantics が主張する「badge が付いた対象を **全部** 一覧が含む」という強い意味でのハイブリッドではない。2 ページ目以降の検索結果、あるいは検索結果ページを経由せず `/gems` に直接 URL を打ち込んだ場合は、この保証が及ばない（案2 の名前照合結果のみに戻る）。この限界は D-36 が既にバッジについて行っている開示（「印が付かないことが低評価を意味しない」）と同じ思想で、UI 側（争点 C/D・ux_writer 領分）に「この一覧は検索結果 1 ページ目の Gem 印 + 名前一致で構成している」という注記を出させれば足りると考える。

### 争点 E への追記（perf まとめの更新）

| 観点 | 案2（現状維持・閾値変更なし） | 案3・全件保証ハイブリッド | 案3'・scoped hybrid（提案） |
|---|---|---|---|
| F-1 の chimurai 例を解決するか | 解決しない（0 件） | 解決する | **1 ページ目相当なら解決する** |
| 追加 GitHub API 呼び出し | 0 | 最大 50/回 | **0**（既存レスポンス流用） |
| レート枠 30req/min への影響 | 無 | 致命的（1 操作で枠を溶かす） | **無** |
| cold start / CPU | 無影響 | 影響小〜中 | 無影響 |
| 保証範囲 | なし | 完全（全 1,000 件） | 検索結果 1 ページ目（≤20 件）のみ |

**結論**: 争点 A の推奨を **案2（現状維持）単独から、案2 + scoped hybrid（案3' ）へ更新する**。全件保証のハイブリッド（案3 原案）は perf 的に却下のまま。閾値緩和という案2 の拡張方向（`matched.length < N` 化）は search_semantics のチェック3 実測により **撤回**する。
