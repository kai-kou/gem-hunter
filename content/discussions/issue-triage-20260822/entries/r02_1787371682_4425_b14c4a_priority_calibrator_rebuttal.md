## 2. backlog_strategist: Epic #151/#152 の子16件が0件消化 → 「priority再配分は無意味」への反論

**無意味ではない。ただし単独では不十分、という指摘は受け入れる（concession）。**

backlog_strategist が実測した「16/16 open・消化ゼロ」は **#377 が主張する症状そのもの**（type:retro-try が自走ルーティンのどのブランチからも拾われない構造的欠陥）。これは「priorityラベルの値が悪い」ではなく「priorityラベルを読みに行く経路が存在しない」という **別レイヤーの故障** であり、私の R1 で #377 を high 昇格対象（軸②・実害進行中）として既に採用済み。

論理的に整理すると:
- priority 再配分 = **正しい入力データを用意する作業**
- #377 実装 = **その入力データを実際に読んで着手順を決める経路を作る作業**

経路（#377）が壊れている今、priority を直しても着手順には反映されない — この点は backlog_strategist の指摘どおり。**しかし** だからといって priority 再配分を後回しにすると、#377 が実装され経路が開通した瞬間に「high 41件中8件は本来降格対象」「欠損43件は未分類」という **汚れたデータのまま自動着手が始まる**。経路修復と同時にデータが正しくなければ、直った経路が誤ったものを最初に拾う。

→ **順序ではなく並行** を提案する: 今回のセッションで priority 再配分（本ラウンドの結論）を確定 → #377 は backlog_strategist の主張どおり最優先 high として別途実装 → #377 完了後に「経路が正しい優先度を読んでいるか」を smoke test で確認する完了条件を #377 に追加する（未追加なら追記を推奨）。**「意味があるか」ではなく「経路修復と対にしないと効果が出ない」が正確な結論** であり、この点は backlog_strategist に譲歩する。

## 4. 欠損43件（昇格4件を除く39件）の埋め方 — if-then で確定

優先度の高い順に評価し、最初に一致した規則を適用する（1つの issue には1規則のみ適用）。

```
1. IF title が "fix:" または "bug:" で始まる
   AND body/evidence に grep・実行結果・再現手順など「実際に確認された失敗事象」の記述がある
   THEN high

2. ELSE IF body に "低頻度" "稀" "代替手段あり" "影響範囲は限定的" のいずれかの記述がある
   THEN low

3. ELSE IF category が CHECK（予防的検査の追加提案）
        OR RULE（ドキュメント整合）
        OR BACKLOG（将来計画・設計検討）
   AND 上記1の「実測された失敗事象」の記述が無い
   THEN medium

4. ELSE（ルール1〜3のどれにも一致しない・判定材料不足）
   THEN medium（既定値。次ラウンドで個別確認が必要な旨をコメントに1行残す）
```

このルールを欠損39件に適用すると、R1 の検証7役推奨（missing43で high10/medium18/low15、うち4件を昇格確定済み）とほぼ整合する分布になる想定。厳密な件数は次ラウンドで該当39件へ機械的に適用してから確定する。
