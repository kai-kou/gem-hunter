## backlog_strategist R2: rebuttal + concession

### 1. 「#377 実装はスコープ外」への応答 — 今回できることを Epic 抜きで列挙する

指摘は妥当。R1 の「唯一有効な打ち手は #377 実装」は言い過ぎで、**このセッションの手札（ラベル追加・本文追記・優先度・クローズ）だけで今すぐ retro-try 母数を減らせる分** を過小評価していた。実測（`target_issues.json` に対する再突合）:

| 提案書の操作 | retro-try ラベル付き件数 |
|---|---|
| 提案 A（completed クローズ・8 件） | **1 件**（#85） |
| 提案 B（not_planned クローズ・6 件） | **2 件**（#282, #283） |
| 提案 C（duplicate クローズ・dup 側 10 件） | **7 件**（#94, #341, #104, #344, #201, #100, #258） |
| **合計** | **10 件を今日クローズできる** |

→ **Epic を作らずとも、A/B/C をそのまま実行するだけで retro-try 109 件 → 99 件（-9%）に減らせる**。これは #377 の解消を待たない、今回のセッションで完結する具体的な打ち手。ここは自分の R1 の主張を修正する（`concession`）: 「#377 実装が唯一有効」ではなく「A/B/C 実行が即効・#377 実装が根治」の 2 段構え。

### 2. dedupe_skeptic「4 組で固有要求が失われる」への応答 — 保全先は Epic ではなく keep 側の本文追記

同意する（`concession`）。Epic は保全先として不適切（#151/#152 の運用ルール自体が「子はクローズしない＝Epic 本文を編集する運用ではない」）。コーディネータが列挙した 4 手札のうち **「本文追記」がそのまま答え**:

- #321 keep 側に「未使用キー検出」「コード参照存在チェック」を追記 → #104 close
- #221 keep 側に `lineno_at()` 共通化を追記 → #81 close
- #319 keep 側に「自動1回再指示」「プロンプト文言見直し」を追記 → #344 close
- #159 keep 側に `session-concurrency-rules.md` と grep 完了条件を追記 → #258 close

**Epic 抜きでも固有要求は消えない**。むしろ Epic に逃がすと「Epic 本文を編集 → 子は close しない」運用のせいで要求が Epic 側に散り、keep 側 Issue 単体を見た人が要求全体を把握できなくなる（今回実測した #151/#152 の消化ゼロと同じ「見えるが拾われない」構造を dedupe 要求にまで広げるだけ）。本文追記のほうが optionally 安全。

### 3. priority_calibrator「high 42 件（23%）」への応答 — 比率だけでは機能しない。到達可能性という直交軸が要る

反論（`rebuttal`）。42/182 という比率は「high の中でどれから着手するか」の情報量としては機能するが、**182 件のうち 109 件（60%）が type:retro-try＝現状どの priority を付けても構造的に到達不能** という事実の前では、比率設計だけでは着手順を決められない。

具体例: priority_calibrator の昇格候補 4 件（#365 #338 #341 #354）のうち **#341 は type:retro-try**（R1 で確認済み・#94/#322 と三重統合対象でもある）。high に昇格しても sprint-cycle-router の決定木には乗らない（#377 実証済み）。一方 #227（同じく賛成の昇格候補）は type:retro-try ではなく `type:bug` のみなので、priority:high 昇格が実際に着手順へ反映される。

→ **priority 軸だけでは「high の中に到達可能なものと不可能なものが混在する」状態を解消できない**。到達可能性（reachable via 現行ルーティン / #377 待ち）を priority とは別の判定軸として持たないと、high 42 件の中身が「上げても動かない」ものだらけになりかねない。今回の手札の範囲で言えば、**retro-try ラベルが付いている Issue には priority を上げる前に「#377 解消待ち」である旨を本文へ 1 行追記する** 運用が現実的な代替（新規ラベル追加は今回のスコープ判断に委ねる）。

### 4. docs_trace への確認 + 恒久策の提案

docs_trace の「棚卸しは改善 Issue レーン・整理モードの担当」の確認に同意する（`concession`）。その上で、**次回以降この棚卸しセッション自体を繰り返さないための恒久策を 1 つに絞る**:

> **#377 の完了条件 4 番目（「同種の経路断絶を再発検知する機械検査」）を、`workflow-health-check`（監査・衛生レーン）の定期監査項目として実装する。** 具体的には `improvement-lane-map.md` の各レーンの「主な起動」欄に書かれたスキル名が、実際に `sprint-cycle-router` の決定木 Step 1〜9 のいずれかから呼ばれているかを機械照合するスクリプト（`tools/check_lane_reachability.py` 相当）。

理由: 今回発見できた「Epic #151/#152 が 2 日間 16/16 件消化ゼロ」は、**人間（セッション）が手動で番号突合しないと見つからない** 状態だった。この検知を自動化すれば、次に同種の「ドキュメント上はレーンがあるが実装が呼ばない」欠陥が発生しても、次回の棚卸しセッションを待たずに検出できる。これは retro-try に限定されない汎用チェックなので、workflow-health-check の週次ゲートに載せるのが lane-map 上も筋が通る（監査・衛生レーンの担当範囲＝「Issue/PR の状態」の一種として「到達可能性」も含められる）。
