# 棚卸し提案の整合性検査（docs_trace・R1）

## 検査対象・ルール照合結果

### 1. 棚卸しの担当レーン（improvement-lane-map.md から）

**規定**: improvement-lane-map.md §2「ルール 4」
```
対象が「溜まった改善 Issue の山そのもの」（分類・重複統合・Epic 境界の判断）
→ 改善 Issue レーンの **整理モード**
```

**判定**: 提案書の A〜E 全体は「溜まった open 182 件の整理」に該当。
整理モード（self-improvement-loop）が担当。**ルール合致**。

---

### 2. クローズしてよい主体

#### 提案 A / B（state_reason=completed / not_planned でのクローズ）

**規定**: improvement-lane-map.md §3
```
`status:` の操作はメインアシスタントが行う
```

**規定**: user-instruction-issue-rules.md §1「Issue 化の判断フロー」
```
Issue クローズ（PR 本文に `Closes #N`）は自動マージ後の自動処理
→ ユーザー確認不要
```

**判定**: **メインセッションが自律的にクローズしてよい**（A-1〜A-6 該当なし）。
ただし A §144 の争点「クローズすると意図が消えるのではないか」について：

- Issue のコメント履歴は state=closed 後も永続。
- ただし issue-triage 議論で「後継 Issue 起票が必要なケース」は明示される必要あり（例: #144 は「専用 CSRF トークン導入は本 Issue へ先送り」とコメント明記なら、後発 Issue を起票してから close すべき）。

→ **ルール合致だが、提案 A 各件について後継 Issue 起票の有無確認が必要**。

---

### 3. #380 への priority 付与可否

**提案書行 162**: 
```
#380: priority (なし) → **high** … status:in-progress済みで着手中と思われるが、
成果物（議論記録・D-33更新）は本チェックアウト時点では未反映
```

#### 複数セッション共存時の操作ルール

**規定**: session-concurrency-rules.md
```
レイヤー 2: Issue ラベルによる論理ロック
`status:waiting-claude` → `status:in-progress` を処理の「最初のアクション」
として即座に変更
```

**規定**: owner.md §2「権限の境界」
```
許可されるラベル操作は `sp:*` と `priority:*` のみ
禁止: `status:*` ラベルの操作
```

**判定**: 
- #380 が `status:in-progress` 済みの場合、他セッションが着手中。
- owner による `priority:*` ラベル操作は **許可範囲** ← `status:` 操作ではない。
- ただし **レイヤー 1「discover スクリプトの排他チェック」でオープン PR・`status:in-progress` の検出時に確認** が先行すべき。

→ **提案自体は OK だが、実行前に #380 の現在状態（他セッション着手中か、完了済み待ちか）を CP-4 多層防御で確認**。

---

### 4. owner エージェント権限の境界（owner.md から）

**規定**: owner.md §2「権限の境界」
| 許可 | 禁止 |
|------|------|
| `sp:*` / `priority:*` の付与・変更 | `status:*` ラベルの操作 |
| バックログ順序・受け入れ基準の決定（コメント追記） | Issue のクローズ・本文の書き換え |
| sp 較正の提案・実行 | A-1〜A-6 の自動承認 |

**検査対象**: 提案 E での priority / sp 改訂

- #310 / #317「priority P2 → medium」：非標準ラベル修正 → 許可範囲 ✓
- #380「priority (なし) → high」：新規 priority 付与 → 許可範囲 ✓
- sp 改訂全般（#27 etc.）→ 許可範囲 ✓

→ **owner 権限の逸脱なし**。

### 5. ルール矛盾の洗い出し

#### 5.1 「Issue クローズ権限」の委任先が二重に記載されていないか

- improvement-lane-map.md §3：メインアシスタント（`status:` 操作）
- owner.md §2：「Issue のクローズ・本文の書き換え」は禁止
- 提案 A/B：メイン側でクローズ実行

**判定**: **矛盾なし**。owner は `status:` 操作を禁止されているが、メイン側は許可。
Issue のクローズは state_reason を指定する GitHub API（`issue_write` / `mcp__github__issue_write`）で、owner ではなくメインが実行。

#### 5.2 #380 の「status:in-progress 中の同時 priority 変更」が CP-4 に反するか

- CP-4：「常に複数セッションが並行稼働している前提」
- session-concurrency-rules.md レイヤー 2：`status:in-progress` は「パイプライン開始時の最初のアクション」
- レイヤー 5：「直近 10 分以内に人間側活動がある PR を `active_session: true` として除外」

**判定**: **反しない**。ラベル操作（priority 変更）は Issue の内容・状態に影響を与えない。
ただし「他セッション着手中なら、完了を待つ vs 今すぐ priority 上げるか」の判断は別途要。
→ 運用判断であり、ルール逸脱ではない。

#### 5.3 「積極的なクローズが記録の喪失につながるか」（user-instruction-issue-rules.md から）

**規定**: 
```
Issue は「なぜ変更したか」を記録する唯一の場所
```

**該当ケース**: 提案 A §144「CSRF トークン導入は本 Issue へ先送り」と明記されているのに closed にする

**判定**: **記録は消えない**（state=closed でもコメント・関連 PR は参照可）。
ただし、**後発の対応 Issue を明示的に起票してから close すべき**
（現在 #144 のコメントに「先送り」と書かれているだけなら、別途 Issue を起票して先送り内容を移す）。

→ **提案実行前に、提案 A 各件について「後継 Issue 起票要否」の確認が必須**。

## 議論型レビューとしての留保

### A に対して
- §144「クローズすると意図が消える」は正当な指摘。後継 Issue を起票するか、Issue を open のままにするかの判断基準が必要。

### C に対して
- 提案書自身が疑問を提示（「重複判定が過剰か」「古い履歴を捨てる判断が正しいか」）。
- ※ 実装判断は重複統合とクローズが別操作なため、「重複として mark」と「close」を分離するルール確認が要。

### D に対して
- 新規 Epic 5 本は **改善 Issue レーン・整理モードの責務** で、ルール上は OK。
- ただし「#153 / #377 の先行解消論」は運用判断（優先順位）であり、ルール逸脱ではない。

### E に対して
- priority 分布の上限（high 件数キャップ）は **本ルールに記載がない**。
- 提案値「high 追加 7 件で総数 48 件」が「機能する分布」かは、owner の判断軸次第。
- **ルール矛盾ではなく、見積もり・優先度システム設計の問題**。

1. **棚卸し自体は改善 Issue レーン・整理モードの担当** ✓

3. **#380 への priority 付与は owner 許可範囲** ✓（CP-4 多層防御の確認後）
4. **owner ラベル権限の逸脱なし** ✓
5. **ルール矛盾（コンフリクト）なし** ✓

クローズ前に後継 Issue 起票の有無を確認すべし（user-instruction-issue-rules.md の「Why」の永続化）。
