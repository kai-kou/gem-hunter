## claim（guardrail_eng・Round 1）争点 D: 実効性の担保（機械強制）

### 前提: 既存静的検査の実装方式（実ファイル確認済み）

`tools/check_architecture_boundaries.py` は **AST ではなく正規表現（`re` モジュール）で実装されている**（`import ast` は無い。`IMPORT_RE` = L51-59、コメント・文字列リテラルは自前の char-by-char スキャナ `strip_comments()` で保護 = L95-136）。設計の勘所は 3 点:
1. **既知の狭いパターンだけを拾う**（import 文という定型構造のみ。任意の JS 式は扱わない）
2. **誤検知の逃げ道を明示的に用意**（`// arch-ok` = L46、ただし機密境界の ARCH-4/5 には効かせない= L24 のコメント）
3. **対象ゼロなら黙って PASS**（`collect_targets` が対象なしなら `return 0`＝L406-408 の `ℹ️ 検査対象がありません`）。誤検知でルーティン全体を止めない思想は既にここにある。

`tools/self_review_check.py` の Tier1（TDD 順序検査）も同じ流儀＝`git diff --name-only` ベースの glob マッチのみで、実行・checkout をしない「ゼロコスト静的検査」（コメント L76-83）。**「判定材料が無ければスキップして黙って通す」を徹底**、とコメントに明記されている。

→ この 2 点（狭いスコープ・スキップ優先）を破ると「同じ流儀」から逸脱し、誤検知でセッション全体を止めるリスクが跳ね上がる。案 1 の設計はこの制約に従うべき。

### 案 1: 静的検査（`tools/check_ui_dimensions.py` 新設）— **限定スコープで部分採用**

**採る**: `src/ui/components/button.tsx` の cva `size` テーブル（L23-35）と `src/ui/components/input.tsx` の `cn()` 内 `h-8`（L11）という **既知の少数ファイル・既知の変数名（cva の `variants.size.*` キー）だけを対象にしたレジストリ型検査** にする。

- `button.tsx` の `size` キーは `default` `xs` `sm` `lg` `icon` `icon-xs` `icon-sm` `icon-lg` の 8 種と固定（L23-35）。**フォームの主要導線（テキストボタン: `default`/`lg` 等）とアイコン専用（`icon*`）は意味が違う**（アイコン系は §7.5 の 24×24px 例外が別途ある）。検査は cva 呼び出し内の `variants.size` オブジェクトを見つけ、"アイコン系でない" キーの文字列から `h-(\d+)` を正規表現抽出し、Tailwind 既定スケール（`h-8`=32px 等）で新設ガイドラインの下限 px と突き合わせる。cva の第一引数（ベースクラス）と variants はどちらも **静的な文字列リテラル**（動的生成なし = L7-42 全体を実見）なので、正規表現で安全に抽出できる。
- `input.tsx` も同様に `cn(...)` の第一引数の静的文字列から `h-8` を抽出する（L11。className prop は上書きだが、**デフォルト値自体がガイドライン未達なら検査対象** にする）。
- **対象ファイルをこの 2〜3 ファイル（+ 今後 `src/ui/components/` に増える同種のプリミティブ）に限定** し、`src/ui/**/*.tsx` 全体を無差別スキャンする設計は **不採用**。理由: `search-form.tsx` のように `className="flex-1"`（L21）だけで高さを一切指定しない使用箇所が大半であり、広域スキャンは (a) `cn(cond && 'h-10')` のような条件式、(b) `h-[44px]` のような任意値、(c) `md:h-10` のレスポンシブ prefix、(d) 外部から渡される `className` prop の合成順序（tailwind-merge が最終形を決める＝実行時にしか確定しない）を正しく解釈できず、**過検知（正当なアイコン・バッジ・スペーサーを誤検出）と過小検知（動的合成を見逃す）の両方を高確率で起こす**。既存チェッカーが「import 文」という定型構造だけを狙い撃ちしているのと対照的に、任意 className の意味論的判定は正規表現の射程外。

**Error/Warning 設計**: レジストリ型検査（button/input の size テーブル）は **Error**（`run_checks.sh` の第 4 チェック直後に「7. UI 寸法検査」として追加。誤検知ほぼゼロと判断できる根拠は対象ファイルが 2〜3 個に限定され、cva の静的文字列だけを見るため）。それ以外（広域 grep 的な検査）は **今回追加しない**（Warning ですら run_checks.sh には入れない。ノイズになるだけで是正されない Warning は既存 6 チェックの信頼性を下げる）。

**実装コスト**: 半日規模。`check_architecture_boundaries.py` の `--self-test` パターン（CASES リスト L318-368、`run_self_test()` L371-397）をそのまま踏襲すれば、レビュー側も慣れた形式で検証できる。

### 案 2: jsdom + testing-library の className assert テスト — **不採用（主エンジンとしては）**

`vitest.config.mts`（L8: `environment: 'jsdom'`）を確認した。jsdom は実レイアウトエンジンを持たず `getBoundingClientRect` は常に 0 を返すため、**「実際に何 px か」は検証できない**。できるのは `expect(input).toHaveClass('h-11')` のような **文字列一致** のみで、これは以下の問題がある:
- 数値の実体（38px か 40px か）を **テストコードとガイドライン文書の 2 箇所に複製** することになり、SSOT を増やさないという制約（争点 C/D 共通の前提）に反する。数値の正本は静的検査 1 箇所（案 1）に置くべきで、テストは「クラス文字列」という別表現を持つべきではない。
- Tailwind のクラス名を `h-11` から CSS 変数駆動の任意値（`h-[var(--control-h)]`）へリファクタしただけで壊れる、実装詳細に強く結合したテスト。

**部分的に許容する範囲**: `search-form.tsx` に対する回帰テスト（現状専用テストファイルなし = brief 記載どおり確認）を TDD の一環として 1〜2 本追加すること自体は良い（例: 「SearchForm の Button は `size="lg"` を渡している」という **契約レベル** の assert）。ただし寸法の px 数値そのものを assert しない。案 1 の静的検査と役割を分ける: 静的検査 = 数値ガードレール、テスト = コンポーネント間の配線（どの variant を使っているか）の回帰防止。

### 案 3: Playwright 導入 — **今回は不採用、別 Issue（NFR-26 と統合）**

`package.json`（全文確認済み）に `playwright` / `@playwright/test` は devDependencies に **存在しない**。追加は次を伴う: ブラウザバイナリの取得（プロキシ経由のネットワークが必要・クラウド実行環境での可否は未検証）、`run_checks.sh` への追加チェックとしての組み込み（第 7 チェックとして `RUN_CHECKS_TIMEOUT` 300 秒内に収まるか未検証）、GitHub Actions が使えない現状でセッション実行が唯一のゲートである点（brief 記載）を踏まえるとタイムアウト・コスト増の影響が大きい。**実視覚回帰・実レイアウト計測という点では案 1/2 より優れる** が、規模がスプリント 1 本相当（NFR-26 の axe 自動チェック導入と合わせて設計すべき）。今回の PR に混ぜず、`type:feature` / `sp:5` 程度の別 Issue に切り出すことを推奨する。
