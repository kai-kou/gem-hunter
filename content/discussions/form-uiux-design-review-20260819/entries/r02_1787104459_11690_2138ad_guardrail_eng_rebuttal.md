## rebuttal（guardrail_eng・Round 2）

### 0. ux_standards の §2.4 案への回答: CSS 変数トークン化は round1 案より優れている（譲歩）

ux_standards が提案する `--size-control-sm/md/lg` トークン化（`app/globals.css` の `@theme` ブロックに追加。既存パターンは `app/globals.css:7-29` で確認済み＝ `--color-*` を `@theme inline` に集約する SSOT 設計）に **同意し、round1 の検査設計を修正する**。

round1 では「Tailwind 既定スケールの `h-8`=32px のような **生の数値** を Python 側にハードコードして下限と突き合わせる」という設計だった。これだと WCAG フロア値そのものは `ui-ux-guidelines.md` と検査スクリプトの **2 箇所** に実質重複する（ドキュメントの数値を変えてもスクリプトが追従しない = SSOT を増やさないという制約に抵触しかける）。

**修正案**: 検査対象を「生の `h-\d+` / `text-\w+` リテラルの禁止」に変える。
- `button.tsx` / `input.tsx` の cva `size` テーブルが `h-(--size-control-sm)` のような **CSS 変数参照**（Tailwind v4 の任意値記法）を使っているかを検査し、**生のユーティリティ値（`h-8` 等）が直書きされていたら Error**（トークン経由を強制）。これは `check_architecture_boundaries.py:62-64` の `VENDOR_BINDING_RE`（「事業者固有バインディングへの直アクセスを禁止し、必ず `src/infrastructure/platform/` の抽象を経由させる」= L205-209）と **全く同型の設計パターン**。「素の実装詳細に触るな、抽象（トークン）を経由しろ」という既存の流儀をそのまま転用できる。
- フロア値（24px・16px）自体は `app/globals.css` の `--size-control-sm` 等の **実際の宣言値を正規表現で読み取って** 動的に取得する（`--size-control-(sm|md|lg):\s*([\d.]+)px` 相当）。**Python にハードコードするのは「どの tier が WCAG 必須か」という tier ↔ ポリシーの対応表だけ**（= `check_architecture_boundaries.py:166-173` の `FORBIDDEN_TARGETS` dict と同じ「層 → ルール」のマッピング方式）。数値そのものの正本は `globals.css` 1 箇所に一本化される。

→ **round1 の「実装コスト半日」は撤回し、「1 日程度」に修正する**（2 ファイル間のクロス参照ロジックが増えるため）。ただし複雑さの質は既存チェッカーの流儀の範囲内に収まる。

### 1. §2.4 の各規定は機械検査で守れるか（名指しで回答）

| §2.4 の規定 | 機械検査で判定可能か |
|---|---|
| `--size-control-sm` 24px フロア（必須） | **できる**（上記トークン強制 + globals.css の値チェック） |
| `--size-control-lg` 主要導線のフォントサイズ 16px 未満禁止（必須・iOS ズーム回避） | **できる**。`text-base`/`text-sm` 等は Tailwind 固定スケール（12/14/16/18/20px）なので、cva 文字列中の **無プレフィックス（＝モバイル既定）** の `text-*` トークンを抽出し 16px 未満なら Error にできる |
| `--size-control-md` / `lg` の高さそのもの（推奨値） | **できない（明記する）**。ux_standards 自身が「推奨」と位置づけており（表の🔵注記）、根拠のない変更を許容する余地がある値は機械的な合否基準にできない。**レビュー観点に回す**（§4 で回答） |
| モバイル/デスクトップの出し分け設計の妥当性（「なぜこの層は出し分け、この層は固定か」という設計判断） | **できない**。「主要導線は出し分けない」「中間層は出し分ける」は意味的な設計判断であり、静的検査はパターン一致しかできない。**Error にはしない**（下記2で「構造だけ検出できる」と回答） |

### 2. レスポンシブな出し分け（`h-11 md:h-9` 相当）への具体的な振る舞い

トークン化後は `h-(--size-control-lg) md:h-(--size-control-md)` のような形になる想定。検査の具体案:

1. cva の各 variant 文字列から `(?:^|\s)(?:([a-z0-9]+):)?h-\(--([\w-]+)\)` でプレフィックス（無ければ base=モバイル）とトークン名のペアを **全て** 抽出する
2. `globals.css` から各トークンの px 値を解決する
3. Tailwind のモバイルファースト・カスケード規則（無プレフィックス値が既定、`md:` 以上は該当ブレークポイント以上でのみ上書き）に従い、**{ブレークポイント: 実効トークン}** の表を組み立てる（sm/md/lg/xl の並び順に「その prefix 以下で最後に登場した値」を採用する単純な畳み込みで実装できる。既存チェッカーの正規表現ベースの流儀を破らない）
4. その実効値が、**§2.4 の config テーブル（`{variant key: {breakpoint: 許容 tier}}`）に照らして下回っていないか**を判定する。この config は Python 側に明示的に持つ（`FORBIDDEN_TARGETS` 方式）。例: `default`（検索ボタン相当）は「全ブレークポイントで `--size-control-lg` 以上」と固定し、`md:` で `--size-control-sm` に落ちていたら Error
5. **「出し分けの設計判断が正しいか」（ux_standards の言う『主要導線は出し分けない』という方針自体の妥当性）は検査しない** — config テーブルへの登録はレビュー時に人（または Layer 1 の UI 観点ファインダー）が承認して初めて検査対象になる、という運用にする。**新規コントロール追加時は config テーブルへの追記が要る**という制約は、`check_architecture_boundaries.py` が新しい層を `LAYER_PREFIXES` に追記しないと検査対象にならないのと同じ既存の限界であり、目新しい弱点ではない。

**結論**: プレフィックス付きクラスがトークン参照の形で書かれている限り、ブレークポイントごとの下限判定は **できる**。ただし「その config テーブルの中身（どの variant がどの tier に属すべきか）」自体は人間が決めて登録するものであり、検査は「登録された規約からの逸脱」だけを機械的に守る、という役割分担になる。

### 3. `className` 経由の上書き（例: `SearchForm` が `<Input className="h-8" />` のように直接渡す）は防げるか

**部分的にしか防げない。穴を名指しし、埋め方を 2 段で示す。**

- **防げる範囲**: `search-form.tsx` のような **既知の呼び出しサイトに限定して登録**し、そこに渡される **リテラル文字列の** `className` prop（`cn()` や三項演算子を挟まない、JSX 属性値がそのまま文字列リテラルであるケース）から `h-*`/`text-*`/トークン以外の生値を抽出して同じ Error 判定にかける。実際 `search-form.tsx:21`（`className="flex-1"`）はまさにこの形で、`flex-1` には高さ指定が無いことも正規表現で確認できる（＝現状は違反なしと判定できる）。今回のスプリントでは `search-form.tsx` を検査対象ファイルとして明示登録することを推奨する。
- **防げない範囲（明言する）**: `cn(condition && 'h-6', className)` のような **動的合成**、変数展開、`className={smallVariant ? 'h-6' : 'h-9'}` のような条件式は、静的にどの文字列が最終的に採用されるか確定できないため **検出できない**。これは round1 で不採用と判断した「広域無差別スキャン」が抱えていたのと同じ限界で、対象ファイルを絞っても消えない。
- **埋め方**:
  1. （機械側で軽減）**未登録の呼び出しサイト**で `<Input>`/`<Button>` に literal な `h-*`/`text-*` を含む `className` が渡されているのを見つけたら **Warning**（Error にはしない＝未登録であること自体は設計判断の余地があるため）で「サイズ影響 className が検出されました。意図的なら config に登録してください」と促す。これは低コストで実装できる「気づきの網」であり、run_checks.sh を止めない。
  2. （残りはレビュー観点に回す）動的合成によるサイズ上書きは機械検査の対象外と **明言し**、review_process の「受け入れ判定役」4 点目（UI/デザイン判定）に **1 行だけ**追加してもらうことを提案する: 「className の動的合成でコントロールサイズが縮んでいないか（機械検査の対象外）」。基準の実体（tier・px）はここに書かず、「機械検査の対象外である」という **境界の事実だけ**を書く形なので SSOT 増殖にはならない。

### 4. review_process への回答: 検査が保証する範囲（具体項目リスト）

「機械が見る部分をレビュー観点に重複して書かない」という境界要求に対し、**私の静的検査が保証する範囲**を確定させる。これ以外はレビュー観点（`code-review` の UI ファインダー / `pr-review-watcher` Step 7 の受け入れ判定役）に委ねてよい。

**機械検査が保証する（Error・run_checks.sh に統合）**:
1. `button.tsx` / `input.tsx` の cva size テーブルに、CSS 変数トークン（`h-(--size-control-*)` 相当）ではない生の `h-*`/`size-*` リテラルが直書きされていないこと
2. 上記ファイルの無プレフィックス（モバイル既定）`text-*` が 16px 未満でないこと
3. `app/globals.css` の `--size-control-sm` 宣言値が 24px 未満でないこと（WCAG 2.5.8 フロアの実体保証）
4. レスポンシブ prefix 付きトークン参照について、config テーブルに登録された tier の実効値がブレークポイントごとに下回っていないこと（登録済み variant のみ）
5. 登録済み呼び出しサイト（`search-form.tsx` 等）でリテラル className により上記フロアを下回っていないこと

**機械検査が保証しない（Warning に留めるか、レビュー観点に明示的に委ねる）**:
a. `--size-control-md`/`lg` の推奨高さ値そのものの妥当性（根拠のない変更か否かの判断）
b. 動的・条件付き className によるサイズ上書き（Warning で気づきのみ、確定判定はレビュー）
c. 未登録の新規コントロール（SP-2 以降）が config テーブルに追記されているか（Warning で促すのみ）
d. 実際のブラウザでの体感操作性（今回の発端そのもの）— Playwright 不採用（round1 結論を維持）に伴い、Step 7 のプレビュー URL 目視が引き続き唯一の担保

review_process の「①code-review Step 1 に条件付き追加」「③ pr-review-watcher Step 7 の受け入れ判定役に4点目追加」という結論に **異議はない**。ただし4点目の文言には上記 a/b/c/d の **「機械検査の対象外である」という境界の事実**を含めることを提案する（基準の実体は書かない・SSOT は増やさない）。

### 5. 結論のアップデート（争点 D）

round1 の「レジストリ型静的検査を Error として採用」という結論は維持しつつ、実装設計を **トークン強制方式**（VENDOR_BINDING_RE と同型）に修正する。これにより ux_standards のトークン化案（争点 A/B）と技術的に完全に整合し、数値の正本を `globals.css` に一本化できる（Python 側は「tier ↔ ポリシー」の対応表と「トークン経由を強制する」ロジックだけを持つ）。
