### ux_standards / Round 1 claim

## 1. なぜ §7.5 は今回の欠陥を防げなかったか（構造的理由）

`docs/03_design/ui-ux/ui-ux-guidelines.md:220-224`（§7.5 ターゲットサイズ）を実際に読むと、規定は次の 1 文に限定されている。

> 「ページネーションのページ番号、アイコンのみのコントロールは 24×24 CSS px 以上」

これが今回の欠陥（検索入力欄・検索ボタンの縦幅が小さい）を防げなかった理由は 3 つある。**単一原因ではなく 3 つの欠落が重なっている**。

1. **対象範囲の欠落**: §7.5 の対象は「ページネーションのページ番号」「アイコンのみのコントロール」に明示的に限定されており、**検索入力欄・テキスト付きボタン（＝主要導線のフォームコントロール）は文面上そもそも対象外**。`src/ui/components/input.tsx:11` の `h-8`（32px）、`src/ui/components/button.tsx:25`（default size, `h-8`＝32px）は数値上は 24px を満たしているため、§7.5 だけを機械的に当てても「違反」を検出できない。つまりこれは規定違反ではなく **規定の穴**。
2. **粒度の欠落（フロア値のみで推奨値がない）**: §7.5 は WCAG 2.2 の 2.5.8（AA・24×24px は下限）をそのまま採用しているだけで、**「主要導線のコントロールはフロアより大きくすべき」という視覚的卓越性・操作性の推奨値を持たない**。24×24px は「これ未満は不可」という下限であり、「これで快適」という目標値ではない。今回の飼い主フィードバック「縦幅が小さく操作性が良くない」はまさにフロアと快適値の違いを指摘している。
3. **出し分けの欠落**: §7.5 にはモバイル/デスクトップの区別がない。タッチ操作が主のモバイルでは指のサイズに対して 24px は窮屈（Apple HIG 44pt・Material Design 48dp が長年の実務推奨）だが、マウス操作のデスクトップでは 24px でも問題になりにくい。この非対称性を規定していないため、レスポンシブな出し分けの発想自体が UI 実装側に存在しなかった（`input.tsx:11` の唯一のブレークポイント分岐は `md:text-sm` というフォントサイズだけで、高さは全ブレークポイント共通の `h-8` 固定）。

**根拠ファイル**: `docs/03_design/ui-ux/ui-ux-guidelines.md:220-224`（§7.5 原文）/ `src/ui/components/input.tsx:11` / `src/ui/components/button.tsx:23-41`（cva size variants）/ `src/ui/search-form.tsx:11-24`（SearchForm は size 未指定＝default を継承）。

## 2. WCAG 2.5.8 と 2.5.5 の関係（論点として明記）

- **2.5.8 Target Size (Minimum)**（レベル **AA**）: 24×24 CSS px 以上、または隣接ターゲットとの間隔確保、または複数の例外（インラインテキストリンク・ユーザーエージェント制御・必須の代替表現がある場合等）。本プロジェクトの目標適合レベルは `NFR-10`（`docs/02_requirements/prd.md:294`）で **AA** と明記されているため、**2.5.8 が法的・要件上の必須ライン**。
- **2.5.5 Target Size (Enhanced)**（レベル **AAA**）: 44×44 CSS px 以上。AAA は本プロジェクトの目標適合レベル外（`NFR-10` は AA まで）。**したがって 2.5.5 を「必須」として書くのは NFR-10 の適合レベルと矛盾する。**
- 結論: ガイドラインに書くのは **「2.5.8＝必須の下限（全コントロール共通）」+「主要導線コントロールは 2.5.5 相当（44px 目安）を推奨値として上乗せする（AAA ではなく社内ベストプラクティスとして採用）」** という **二層構造** にする。二層であることを§0 の「判定できる指示」の粒度で書く（「推奨」と「必須」を表の列で明確に分離し、レビューでどちらの逸脱かを機械的に区別できるようにする）。

## 3. モバイル/デスクトップの出し分けの要否

**要る。** 理由は上記 §1-3 の通り、タッチ操作とポインタ操作でターゲットサイズの快適域が異なるため。ただし「出し分け」を Tailwind の `md:` prefix で高さそのものに適用するのは実装コストが低い一方、**主要導線（検索入力欄・検索ボタン）は「常に主役として大きく見せたい」という視覚的卓越性の要求もある**（§4.1 に「検索欄の直下に横並びのコントロール行」とあり、検索欄自体がページの主役）。したがって:

- **主要導線（検索入力欄・検索ボタン）**: モバイル/デスクトップ問わず、フロア（24px）より明確に大きい高さを既定にする（視覚的卓越性 + タッチ域の両方を満たす）。数値は要出典確認（並行リサーチの Material Design 3 / GOV.UK / Primer の入力欄高さの実測値で確定）。
- **二次的な小型コントロール**（アイコンのみのボタン、ページ番号）: 現行 §7.5 のまま 24px フロアを維持。ここは変更不要。
- **出し分けが必要になるのはこの中間層**（例: 将来 SP-2 以降で追加されるソート切替・件数切替のドロップダウントリガー）。これらはモバイルでは 44px 相当、デスクトップでは 32-36px 相当、という `md:` 出し分けを新設ルールに含めるべき。

## 4. 入力欄のフォントサイズと iOS ズームの関係

`src/ui/components/input.tsx:11` を実測すると、`text-base`（16px、既定 = モバイル含む全ブレークポイント）を **`md:text-sm`（14px）が `md`（768px）以上でのみ上書き** する構造になっている。iOS Safari は **フォーカス時の input 実効フォントサイズが 16px 未満だとページを自動ズームする** 既知挙動があり、768px 未満のモバイル実機では現状 `text-base`＝16px が効いているため、**現状は偶然ズームを回避できている**。

ただしこれは **ガイドラインに明文化されていない偶然の安全** であり、次のような変更で容易に壊れる:
- 誰かが「モバイルとデスクトップで文字サイズを統一しよう」と `text-base md:text-sm` を `text-sm` 単独に書き換える
- 新規コンポーネント（検索欄以外の入力欄）を追加する際に `text-sm` を安易にコピーする

→ **新設する節に「入力系コントロールのモバイル時フォントサイズは 16px 未満にしない（iOS 自動ズーム回避）」を明示ルールとして書く**。これは §7.5 のターゲットサイズとは別の軸（フォントサイズ）だが、フォームコントロールの寸法基準と同じ節にまとめるのが自然（同じ「入力欄が快適に使えるか」という関心事のため）。

## 5. 新設する節の設計（§0 の「判定できる指示」を満たす形）

### 見出し・位置

`docs/03_design/ui-ux/ui-ux-guidelines.md` の **§2（デザイントークン）に新設**: **`§2.4 コントロールサイズトークン`**（§2.3 タイポグラフィとスペーシングの直後、§3 レイアウトの前）。

理由: §2 は既に「色トークンは `--color-*` で `@theme` に定義し、生の値を直書きしない」という **SSOT パターン（トークン化）** を確立している（§2.1）。フォームコントロールの高さも同じ設計思想（`app/globals.css` の `@theme` にセマンティックな `--size-control-*` トークンを追加し、`input.tsx` / `button.tsx` の cva はそのトークン経由で値を引く）で統一するのが一貫性がある。§7.5（アクセシビリティ章）は「なぜこの値か（WCAG 適合根拠）」を書く場所として残し、**実装で使う数値そのものの正本は §2.4 に一本化** する（§7.5 からは §2.4 へのリンクのみにする＝ SSOT を増やさない）。

### 表の列構成

```markdown
### 2.4 コントロールサイズトークン

| トークン名 | 用途 | 高さ（モバイル / デスクトップ）| フォントサイズ下限 | 根拠 |
|---|---|---|---|---|
| `--size-control-sm` | 二次的アイコンボタン・ページ番号 | 24px / 24px（§7.5 のフロア。変更なし）| — | WCAG 2.2 2.5.8（AA・必須） |
| `--size-control-md` | 標準ボタン・標準入力欄（一覧の補助操作等）| {要出典確認} / {要出典確認} | 16px | {リサーチで確定: 例 M3 / GOV.UK 実測値} |
| `--size-control-lg` | **主要導線**（検索入力欄・検索ボタン等、ページの主役コントロール）| {要出典確認・目安 44px 相当} / {要出典確認} | 16px（iOS ズーム回避・必須） | WCAG 2.2 2.5.5 相当を推奨値として採用（AAA 準拠を謳うものではない）|

**必須 / 推奨の区別**（§0 準拠）:
- 🔴 **必須**: `--size-control-sm` の 24px フロアと、`--size-control-lg` のフォントサイズ 16px 下限は **レビューで機械的に違反判定する**（下回ったら NG）。
- 🔵 **推奨**: `--size-control-md` / `--size-control-lg` の高さそのものは目安値（下回っても即 NG にはしないが、根拠なく変更する場合はレビューで確認する）。
```

**列に「モバイル / デスクトップ」を分けた理由**: §1-3 で述べた出し分けの必要性を表の構造そのもので強制する（文章で「出し分けてください」と書くより、表の列があること自体が実装者に出し分けを思い出させる）。

**記述の粒度**: 個別 px 値は本ラウンドでは断定しない（`{要出典確認}` プレースホルダのまま提出。リサーチ結果が届き次第、この表のプレースホルダだけを埋めて確定する。表の構造・列・必須/推奨の区分・iOS ズーム回避の 16px は WCAG 仕様と実機挙動から確定できるためプレースホルダにしない）。

### §7.5 の改修

§7.5 冒頭に 1 行追加: 「主要導線コントロールの高さの正本は §2.4。本節は WCAG 2.2 の適合根拠のみを扱う」。表の内容そのものは重複させない。

## 6. 争点 B（実装の修正範囲）への言及

- **input.tsx / button.tsx の cva 内で `h-8` 等の生値を `h-(--size-control-md)` のような CSS 変数参照に置き換える**（Tailwind v4 の任意値記法。`app/globals.css` の `@theme` で定義した値を単一の場所から引く）。これにより「値を変えたいときは globals.css の 1 箇所を直せば全体に波及する」という §2.1 と同じトークン設計を維持できる。
- **SearchForm は `size="lg"` 相当（新設する `--size-control-lg` に対応する cva variant）を明示指定する**。default variant 自体は変更しない（他画面の補助的なボタン・入力欄まで巻き込んで一律に大きくしない。SP-2 以降のページネーション等は §7.5 のフロアのまま据え置くのが適切なため、default の意味を変えるのは影響範囲が読めない）。
- shadcn 再生成リスクについては `docs/03_design/ui-ux/ui-ux-guidelines.md:37`（既存ルール「`shadcn add` した生成物を読まずにマージしない」）が既に手当て済みなので、cva 変更自体を理由に別の仕組みを追加する必要はない。**新規追加事項ではなく既存ルールの適用範囲内**。

## 結論（ファイル単位）

- **改修**: `docs/03_design/ui-ux/ui-ux-guidelines.md`（新設 §2.4 + §7.5 に参照 1 行追加）/ `app/globals.css`（`--size-control-sm/md/lg` トークン追加）/ `src/ui/components/input.tsx` / `src/ui/components/button.tsx`（cva を新トークン参照に変更 + `lg` 相当 variant の高さ調整）/ `src/ui/search-form.tsx`（`size="lg"` 明示指定）。
- **この PR でやること**: 上記の構造変更 + プレースホルダ値の暫定採用（リサーチ結果到着後に数値だけ差し替える追いコミット、または本 PR 内で確定させる。並行リサーチのタイミング次第）。
- **やらないこと**: `--size-control-sm`（24px フロア）自体は変更しない。SP-2 以降の他コントロールへの一括適用はこの PR のスコープ外（トークンの器だけ用意し、適用は各コントロール実装時に §2.4 を読んで行う＝ `sprint-development-rules.md` `SD-4` の自律参照に委ねる）。
