### ux_standards / Round 2 rebuttal

## 1. guardrail_eng への応答（レジストリ型静的検査の対象範囲）

**同意する部分**: `src/ui/**/*.tsx` の広域スキャンを不採用にした判断（round1 の guardrail_eng claim・案1' 不採用）は正しい。`cn(cond && 'h-10')` や `className` の合成順序は静的に解けないという指摘はその通りで、私の §2.4 案もそこまでの機械保証を前提にしていない。

**しかし、guardrail_eng の指摘（「SearchForm 側でサイズ指定するケースをどう扱うか」）は自分の Round1 案の穴を正確に突いている。これは concede する。**

Round1 で私は「SearchForm は `size="lg"` 相当を明示指定する」と書いたが、`src/ui/components/input.tsx:5-17` を実測すると **Input には `size` variant が存在しない**（`button.tsx` の cva `variants.size` のような選択式テーブルではなく、`cn()` 内に `h-8` が単一の生値として直書きされているだけ）。つまり Round1 の私の提案は「選べる仕組みが無いものを選ぶ」という前提の欠落があった。このままだと SearchForm 側が寸法を変えたくなったとき、開発者が取りうる手段は **`className="h-11"` のような呼び出し側での生の上書き**しかなく、これはまさに guardrail_eng がレジストリ型検査の射程外（=検出不能）と明言した経路そのものに落ちる。

**修正案**: 争点 B のファイル変更に以下を追加する。

- `src/ui/components/input.tsx` を `button.tsx` と同じ **cva パターンに変更し、`size` variant テーブルを新設**する（`default` / `lg` の最低 2 段階。`lg` が §2.4 の `--size-control-lg` に対応）。
- **SearchForm は `className` で高さ・フォントサイズを一切指定せず、`size="lg"` という named prop でのみ選ぶ**（呼び出し側での生の `h-*`/`text-*` 上書きを禁止する、という一文を §2.4 に明記する）。
- これにより guardrail_eng の案1（レジストリ型検査）の対象ファイルが「`button.tsx` の `variants.size` + `input.tsx` の新設 `variants.size`」の**2ファイル・2テーブルに揃う**（guardrail_eng が Round1 で書いた「今後 `src/ui/components/` に増える同種のプリミティブ」に含まれる範囲内であり、案1の設計方針を破らない）。

**「cva の外で className に直接 h-* を書かれたケース」への残余リスクへの回答**: これは guardrail_eng 自身が「広域スキャンは不採用」と判定した以上、**静的検査では原理的に閉じられない**。ここは役割分担で埋める。§2.4 に「フォームコントロールの高さ・フォントサイズは必ず `size` variant 経由で指定し、呼び出し側で `h-*`/`text-*` を直接書かない」という**判定可能な禁止規定**を明文化した上で、review_process が提案する code-review Step1 の UI/a11y ファインダー（フレッシュ文脈の意味論的レビュー）にこの規定を判定させる。数値の正本は増やさず（§2.4 のまま）、「呼び出し側で生クラスを書いていないか」という**パターンの逸脱判定**だけをファインダーに委ねる、という二層構成にする。

## 2. review_process への応答（新設エージェントなし・観点表拡張で足りるか）

**①（code-review Step1 拡張）には同意する。** 私が §1 で修正した「`size` variant 経由を強制する」規定は、まさに review_process の言う「基準の実体は書かず参照させるだけ」の型に合う。フレッシュ文脈のファインダーは実画面を見られなくても、**ソースコードから「default のまま検索欄に使っていないか」「呼び出し側で生の `h-*` を書いていないか」を判定できる** ——これは視覚判断ではなくパターン判断であり、§2.4 を named-token 化したことで初めて機械可読になる（§2.4 案がなければ①は「なんとなく小さい」を判定できず機能しない。逆に言えば①の実効性は §2.4 の設計に依存している）。

**③（Step7 受け入れ判定役 3点→4点）は必要条件だが、粒度に懸念が残る。ここは一部反論する。**

Step7 の受け入れ判定役はサブエージェントであり、**実際のプレビュー URL を視覚的に開いて「縦幅が小さい」と判断する能力を持たない**（今回の欠陥はまさに人間がスクリーンショットを見て気づいたもので、コードの数値だけでは「WCAG 2.2 の 24px は満たしている」ため検出できなかった＝Round1 §1 で述べた通り）。4点目の文言が「`ui-ux-guidelines.md` の該当節を参照し寸法・タイポ・ターゲットサイズ規定を満たすか判定する」というコード上の数値照合だけだと、**①の code-review ファインダーと同じ判定を Step7 でもう一度やるだけ**になり、視覚的な「操作性」という飼い主の本来の指摘軸をどちらのレイヤーも拾えない。

**追加提案**: 4点目の文言に「`sprint-development-rules.md` `SD-1` のプレビュー URL を実際に開き（人間側の開封を前提とする、または開けるサブエージェントがいればそれを使う）、§2.4 の主要導線コントロールが視覚的に主役として十分な大きさに見えるかを目視確認した旨を PR コメントに記録する」を加える。これは新しい判定基準の実体を増やすのではなく（§2.4 の「主要導線は推奨値を満たす」という既存規定の**目視確認手段**を明記するだけ）、SSOT は増えない。

**④（self-reviewer 不採用）に同意**。理由も round1 の指摘（自己修正盲点）で足りている。

## 3. docs_trace への応答（§2.4 案が生む新たな矛盾・§4.5 / §7.5 との整理）

**docs_trace の証拠（行147・行222・行242）を受けて、Round1 の自分の提案に不足があったことを認める。**

Round1 で私は「§7.5 冒頭に §2.4 への参照 1 行を追加する」とだけ書き、**`docs/03_design/ui-ux/ui-ux-guidelines.md:147`（§4.5 ページネーション「ページ番号ボタンは 24×24 CSS px 以上」）と `:242`（§7.7 手動チェックリスト「アイコンボタンの実測サイズが 24×24px 以上」）を見落としていた**。§2.4 を新設して「コントロールサイズの数値の正本は §2.4」と宣言した以上、この2箇所も同じ数値（24px）を独自に保持したままにすると、**§2.4 を作ったこと自体が新しい重複源になる**（docs_trace が Round1 の「結論4」で指摘した「SSOT が複数に分散」を、直そうとして別の形で再生産することになる）。

**修正案（整理表）**:

| 箇所 | 現状 | 修正後 |
|---|---|---|
| `:147`（§4.5） | 「ページ番号ボタンは 24×24 CSS px 以上（WCAG 2.2 の 2.5.8）」 | 「ページ番号ボタンは `--size-control-sm`（§2.4）以上（WCAG 2.2 の 2.5.8）」に置換。数値は書かない |
| `:220-224`（§7.5） | 24×24px の値を直接規定 | Round1提案通り、値は §2.4 参照に一本化。本節は WCAG 適合根拠（2.5.8 と 2.5.5 の関係・§0 で論じた必須/推奨の二層構造）の解説に専念 |
| `:242`（§7.7 チェックリスト） | 「アイコンボタンの実測サイズが 24×24px 以上」 | 「アイコンボタンの実測サイズが `--size-control-sm`（§2.4）以上」に置換。**チェックリストは手動確認の実行手順であり、確認对象の名称を持つのは正しいが、数値そのものを持つ必要はない** |

これで §2.4 が **唯一の数値の正本**になり、§4.5・§7.5・§7.7 はいずれも「参照 + その文脈での使い方の説明」だけを持つ（§2.1 のカラートークンが「用途」列を持ちながら値そのものは `@theme` にしか書かないのと同じ構造に揃う）。

**§4.5 との論理的な矛盾の有無**: 数値自体（24px フロア = `--size-control-sm`）は変更しないため、§4.5 の実体規定と §2.4 は矛盾しない。矛盾していたのは「同じ規範を2箇所に別々の文で書いていた」という**表現の重複**であり、docs_trace の指摘どおり Round1 の自分の提案はこの重複を §7.5 でしか解消していなかった。

**docs_trace の SP 波及指摘（結論1「寸法基準が未決定 → ページネーション・ソート・件数切替の設計が曖昧」）への回答**: §2.4 を §2（デザイントークン、文書全体に適用される章）に置いた設計判断は、まさにこの波及範囲（SP-2 以降の新規コントロール）を見越したものである。`--size-control-sm`（二次的コントロール）と将来追加されるソート・件数切替は §2.4 の中間層（Round1 §3 で述べた「二次的な小型コントロール」の枠）に自然に収まり、新設コントロールごとにガイドラインへ新しい数値規定を追記する必要がない。この点は docs_trace の懸念への直接の回答になっている。

**docs_trace の結論2（SD-1/SD-2 と Playwright 未導入の乖離）については**、§2.4 は E2E・Playwright の有無に依存しない設計（静的トークン + cva variant + code-review の意味論的判定）なので、この乖離を悪化させることも解消することもない。争点 E（今回のスコープ線引き）の中で「Playwright 導入は別 Issue」という guardrail_eng の結論と矛盾しない。

## 結論（Round2 での修正点まとめ）

1. `input.tsx` に `size` variant（cva）を新設し、SearchForm は `size="lg"` のみで指定・生の `h-*`/`text-*` 上書きを禁止する規定を §2.4 に追加（guardrail_eng の検査対象と整合させる）。
2. Step7 受け入れ判定役の4点目に「プレビュー URL を実際に開いて主要導線の視覚的卓越性を目視確認した旨を記録する」を追加（review_process 案への補強）。
3. `:147`（§4.5）と `:242`（§7.7）の 24px 直書きを `--size-control-sm`（§2.4）参照に置換し、数値の正本を §2.4 に完全一本化する（docs_trace の指摘を受けた Round1 案の修正）。
