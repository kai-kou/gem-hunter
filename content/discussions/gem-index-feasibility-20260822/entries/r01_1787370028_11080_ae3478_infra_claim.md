# infra: 争点C（配信方式）結論 + A/B/E への含意（round1）

## 結論（推奨）: ④ isolate内メモリキャッシュ（module-scope singleton Map）を主方式に

`env.ASSETS.fetch()` で単一の圧縮済み JSON（1 ファイル）を **isolate が生成された最初のリクエストでのみ** 取得・parse し、`sharedGemDigestPort`（`container.ts`）と同じ **モジュールスコープ singleton** に `Map<repoFullName, gemIndex>` として保持する。2 回目以降のリクエストは subrequest 0・CPU は `Map.get()` × 100 件（マイクロ秒オーダー）で完結する。

**却下案とその理由**
- **① シャード化 JSON + `ASSETS.fetch`**: 実測ベースでシミュレートした結果、shard 数 N を増減しても「検索結果 100 件がヒットする distinct shard 数」は N=32 で ~31（ほぼ全シャード＝データの 96%）、N=256 で ~83（データの 32%）、N=1024 で ~95（データの 9%）と、**N を増やすほど転送量は減るが subrequest 数は増える** というトレードオフになり、Free の subrequest 上限 50/invocation を N≥64 付近で超える（下表参照）。GitHub 検索 API 呼び出し 1 本と合算するとさらに margin が減る。「シャード分割で J oin コストを下げる」という発想自体が、**検索結果がランダムに散る 100 件である限り機能しない**（birthday paradox でほぼ全シャードに当たる）。シャーディングは④の補助（cold start 分散・部分更新）としてのみ検討価値あり、主方式には不採用。
- **② ソート済みバイナリ + Range 二分探索**: ブリーフィング記載どおり Static Assets の Range 未対応報告があり未検証。今回のリサーチ（`cloudflare-infrastructure.md` / リサーチ一次情報）にも Range 対応の明記なし。**検証コストに見合わないため不採用**（要検証扱いのまま採用しない）。
- **③ D1 `IN (...)` クエリ**: `open-questions.md` `D-18`（R2/D1/DO/KV を**明示列挙**して不採用と確定・`D-24` でも「この部分は変更しない」と明記）に抵触。**`D-27` の境界注記（"Worker が実行時にそのファイルへ書き込むか"）は静的アセット *ファイル* の判定基準であり、D1 はファイルではなく永続クエリエンジンなので D-27 の救済対象にならない**（書き込みの有無に関わらず D-18 が D1 の採用自体を禁止）。よって **D1 は infra 制約として却下**（`NFR-21`/`INF-5` 云々以前に `D-18` で確定済み）。
- **⑤ バンドル焼き込み継続**: `D-33` が既に「10 万件規模は Workers Free のバンドル 3MB 上限を圧迫する」として却下済み。加えて `import` 方式は**データ更新のたびに JS バンドルの再ビルド・再デプロイが要る**（Static Assets の「デプロイで丸ごと差し替え」という `D-28` の設計意図と逆行）。不採用を維持。

## 数値根拠（シミュレーション・実測ベース）
- 母集団 109,469 件・raw 3.3MB / gzip 1.34MB（ブリーフィング実測値）。
- shard 数 N と検索 100 件がヒットする distinct shard 数の期待値（一様分布仮定・birthday paradox 近似 `N・(1-e^(-100/N))`）:

| N | 期待ヒットshard数 | 転送量(概算, 全体比) | Free subrequest 50 に収まるか |
|---|---|---|---|
| 32 | ~31 | ~96%（≈1.28MB gzip） | ぎりぎり(31+GitHub分1=32) |
| 64 | ~51 | ~79%（≈1.06MB gzip） | 超過(51+1=52) |
| 256 | ~83 | ~32%（≈0.43MB gzip） | 大幅超過 |
| 1024 | ~95 | ~9%（≈0.12MB gzip） | 大幅超過 |

→ **シャーディングは「転送量を減らすほど subrequest 数が増える」二律背反**で、Free の 50/invocation 制約下では実用的な N が存在しない（N=32 でも余裕がほぼゼロ）。④（1 ファイル・1 subrequest・isolateキャッシュ）はこの二律背反自体を回避する。

- ④ の cold start コスト（isolate 生成直後の 1 リクエストのみ）: JSON.parse(3.3MB) は V8 実測目安 200〜400MB/s 相当で **概算 8〜16ms**。Free の CPU 10ms/invocation の**すれすれ〜超過**になり得る（cold start 時に限り 1027 リスクあり）。**現状アカウントは実は Workers Paid（`cloudflare-infrastructure.md` §5 2026-08-20 実機確認・$5/月+従量）** であり、Paid では `limits.cpu_ms` を明示設定して従量課金に倒せるため cold start 超過は「停止」ではなく「課金」で吸収できる。Free 想定のままなら **JSON をやめて typed array ベースの軽量バイナリ形式**（ソート済み文字列配列 + `Float32Array`/量子化 `Int16Array`）に変えて parse コストを 3〜5 倍程度削る対策が必要（未検証・推奨改善案）。
- warm isolate 中の 2 回目以降: `Map.get()` × 100 は無視できるコスト。isolate の生存期間中は事実上 0 コストで join できる。

## A（再導入可否）への含意
配信方式は④で Free/Paid いずれでも技術的に成立する（Paid なら余裕、Free なら軽量バイナリ化が前提）。ただし **`D-33` の再導入条件（非 npm を含み一般語 100 件中 30%+ ヒット）を満たすのはデータ側（12 レジストリ×15,000件計画）の仕事**であり、配信方式の実現可能性だけでは再導入を正当化しない。infra 目線では「④ + cold start 対策が実装・実測（`wrangler tail` で p95 CPU 確認・§5.3 と同じ手法）できてから再導入」を推奨。

## B（母集団規模の上限）への含意
Static Assets のファイル上限（25MiB/ファイル・20,000ファイル）は 109K 件どころか 100 万件規模（raw ~30MB）でも単体では問題にならない。**実際のボトルネックはファイルサイズではなく cold start の JSON parse コスト**。目安として raw JSON を ~10MB 以内（現状の 3 倍程度、CPU 換算で 25〜50ms 相当）に収めるなら Paid で許容範囲、Free ならこの規模で軽量バイナリ形式が必須になる。母集団を無制限に拡大する設計は避け、「配信用の最小 shape（repoFullName + gemIndex の 2 値）を保った上で件数上限を決め打ちする」方針を推奨。

## E（運用）への含意
④・①いずれも「Worker が実行時に書き込まない読み取り専用ファイルの差し替え」なので `D-27` の境界注記どおり `D-18` 抵触なし。バッチ生成場所（Cloudflare 外・セッション/Routine cron）・更新頻度（日次）・デプロイ差し替えという運用設計は変更不要。ただし④は isolate 生存期間に依存するため、**デプロイ直後は必ず 1 回 cold start が発生し全リクエストが同じ CPU コストを払う**（①のシャーディングと違い、devopsとして「デプロイ直後の p95 CPU」を計測対象に含めるべき）。
