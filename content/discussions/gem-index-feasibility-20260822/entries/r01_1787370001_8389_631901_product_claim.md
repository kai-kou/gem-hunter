## product: 結論（推奨とセットで）

### A. 検索への Gem Index 再導入 — 「検索結果の主ソート軸」としての全面再導入は却下

**推奨（★）**: ソート軸復活ではなく、**②Gem 専用の発見面（エコシステム別・topics 絞り込みの Gem 一覧ページ）+ ①検索結果への軽量バッジ表示（付くものにだけ、ソートはしない）** の組み合わせに倒す。
**却下**: 「sort=gem-index をそのまま検索へ戻す」案。理由は 3 点。

1. 実測 19〜36%（react 32 / test 36 / image 19）は D-33 の閾値「30%」ぎりぎり未達〜僅かに上回る水準で、カテゴリ差が大きい（image processing は 8 割強が空欄）。「機能として成立している」と言い切るには弱い。
2. **ソート軸は「並べ替えた結果、上から意味のある順に並ぶ」という期待値そのものが壊れる。** Gem Index の付かない 64〜81% をどう扱うか（末尾固定？ NULL 混在？）に関わらず、「一部だけ並べ替わって残りは無意味順」という体験になる。これは D-33 の rejected 理由①（体感速度）とは別物の不満で、**静的化で速度を解決しても消えない**。争点 E の feedback item 10「数値が出ない不安」は形を変えて再燃するリスクが高い。
3. D-33 rejected②（10 万件プール拡大は Worker バンドル圧迫）は Static Assets 配信の実測（3MB gzip 枠に非計上・無料無制限配信）で **前提が崩れている**。ここは進展として評価できる。

### 「30% で成立か」の再定義（憶測明記）

30% という数字自体が粗い。**発見面に主軸を移せば、この基準論争自体が不要になる** — Gem 一覧ページは定義上 100% Gem Index 付きのアイテムしか載らないため。バッジ表示も「あれば出す・なければ何も出さない」設計にすれば空状態が発生しない。**検索の主ソートとしての再導入条件を上げ直すなら**（憶測）「トップ 20 件中 40% 以上、かつ主要 7 エコシステム全てで 0 件になるクエリがない」を提案するが、これは未検証で追加計測が要る。現時点では **主ソート化は保留**、発見面+ バッジで先に価値を出す方が説明可能性が高い。

### 代案比較（B の判定）

| 代案 | 判定 | 理由 |
|---|---|---|
| ①バッジのみ | **採用（バッジ部分として）** | 空状態が構造的に起きない。検索の主体験を壊さない |
| ②Gem 専用発見面 | **採用（主軸として推奨）** | 母集団=Gem データそのものなので被覆率問題が原理的に発生しない。R-2（GitHub 純正 1 クエリで再現不可）の点で①より強い差別化 — 「被依存数順に topics 絞り込み」は GitHub 検索にはない |
| ③検索対象を Gem コーパスにする | **却下** | Q2 エレベーターピッチ / `FR-1`「GitHub 公開リポジトリ検索」と矛盾。検索対象を 12 レジストリ×15,000 のプールに絞ると「GitHub 全体を検索できる」という中核提供価値が壊れる |
| ④現状維持（今日の Gem のみ） | **却下** | 母集団拡大の実測（非 npm 約 3 割達成・120,187 リポジトリ）を活かさない機会損失。ミッション（実利用に対する star 不足の発見）が「今日の Gem」1 枠だけに閉じ込められたまま |

### D. UX 判定

- ソートとして出す: **却下**（上記 A-2）。
- バッジとして出す: **採用**。ただし「バッジが付かない = 何かが劣る」という誤読を避ける説明文が要る（Gem Index は npm 以外を含む限定母集団のカバレッジ指標であり、付かないことは低評価を意味しない、という注記）。
- 別の発見面（Gem 一覧・エコシステム別）: **採用・主軸に推奨**。

### E との整合（初見ユーザーの不安再燃を防げるか）

防げる、というのが product の判断。争点 E の不安の本体は「待たされた末に大半が情報なしに落ちる失望」であり、これは **検索結果の主体験に Gem Index を持ち込む限り、母集団をどれだけ拡大しても構造的に再発する**（キーワードの多様性 = ロングテールに対し、母集団は有限である以上、必ずどこかで空になる）。発見面に主軸を移せば「検索は検索、Gem 発見は別の入口」と役割分離でき、検索結果に対する期待値を汚さない。

### D-3（説明可能性）への寄与

「なぜ検索の主ソートに使わなかったか」を実測データ（19〜36%・カテゴリ差）で説明できる設計変更は、選考課題としての説明力が高い。「機能を作り込みすぎず、実測に基づいて適切にスコープを絞った」という判断こそが `D-3` の主目的（与件充足 + 設計判断の説明可能性）に資する。

### B/C（データ設計・配信）への product 要求（infra/data 向け）

- **全体パーセンタイル再計算は必須（品質ゲート級）**: レジストリ内順位のまま混在表示すると、実測で「上位 5 件が Elixir の極小パッケージ」という結果になっており、ミッションの主張（実利用に対する star 不足）と矛盾する表示になる。これを直さないままの再導入は却下する。
- モノレポ集約ルールは（憶測）保守的な指標の方が説明しやすいため、合算より代表値（最大値）寄りを推奨するが、data レーンの判断を優先する。
- 発見面（Gem 一覧ページ）は表示件数を絞れる（上位 N 件でよい）ため、検索結果全件へのバッジ付与よりインフラ負荷・実装難度が低く、C の配信方式論争を回避しやすい第一歩になる。
