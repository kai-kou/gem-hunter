## data Round 2 — rebuttal / concession

### 0. lead 追加事実（Workers Paid）を受けた B の見直し

**B の結論（レジストリ別成層化・stars 欠損検証・repo dedup）は変わらない。** この結論は CPU/parse コストではなく「1レジストリが結果を独占する」という統計的欠陥（実測1・2）と「stars=0 汚染」（実測3）に基づいており、Free/Paid のどちらでも同じ欠陥は起きる。
Paid が動かすのは **母集団の「深さ」の選択肢**: これまでは infra の CPU 制約を気にして 15,000/registry を上限と考えていたが、Paid なら `limits.cpu_ms` 従量で吸収できるため、**npm/PyPI のような大規模レジストリはさらに深く（例: 30,000〜50,000件）取得してよい**（統計的安定性が上がる・特に成層化のテール品質が改善する）。ただし深さを増やすことは stars=0 汚染や Maven ミラー支配の **根治にはならない**（同じ欠陥がより大きい母数で再現するだけ）。フィルタ設計は Paid の有無と独立に必須。

### 1. product の Q1「主ソート却下・発見面+バッジ」への回答: **賛成**

自分のフィルタ（stars=0×dependents上位1%除外・repo dedup）の実コストを計測した: 除外対象は **valid pool 144,256件中わずか2件（0.001%）**、広めの疑わしいゾーン（stars=0 かつ dependents 上位10%）でも **124件（0.086%）**。repo dedup は行数を19%減らすが「repo が母集団に含まれているか」という **被覆率の定義そのものには影響しない**（同一 repo が複数行→1行になるだけで repo は消えない）。
→ **ブリーフィングの実測被覆率（react 32% / test 36% / image 19%）は、data レーンの品質フィルタを適用した後もほぼそのまま有効**。つまり「フィルタで汚染を除いたら被覆率がもっと下がって主ソート化が一層厳しくなる」という懸念は実測上は当たらないが、結論には影響しない — **19〜36% という水準自体が product の言う「一部だけ並べ替わって残りは無意味順」という体験問題を解決しないため、主ソート化却下・発見面+バッジに同意する**。品質フィルタは「発見面に出す Gem の信頼性」を上げる役割であって、「被覆率」を動かす役割ではないと切り分けたい。

### 2. product の B 要求「全体パーセンタイル再計算は必須」への rebuttal（reject）

**これは却下する。実際に実装して確認した。** 素の被依存数・star数でグローバルパーセンタイルを再計算すると、Elixir 支配は解消するが **npm が上位100件中90件を占める** 結果になった（npm の依存グラフ密度が他エコシステムより1〜2桁濃いため）。「レジストリ内順位のまま混在」も「素のグローバル再計算」も、**同じ欠陥（1レジストリ支配）の裏表** であり、後者だけを品質ゲートにすると Elixir 問題を npm 問題にすり替えるだけで解決しない。
正しい修正は **レジストリ別成層化**（レジストリごとに固定枠 or 母数比例枠で選出してから混ぜる）であり、「全体パーセンタイル再計算」という表現をこの意味で使うなら同意するが、素の絶対値でのグローバル再計算という字義通りの実装は明確に reject する。

### 3. infra の「モノレポ集約=代表値（最大値）寄り」への rebuttal + concession

**懸念には concession、具体案には reject。**
- Concession: 「保守的な指標の方が説明しやすい（過大評価を避けたい）」という動機には同意する。実際、min(gem_index) 選択（外れサブモジュールの極端な良スコアを repo 代表にする）は自分の round1 でも問題視した。
- Reject: ただし max(gem_index)（＝最も「gem らしくない」値を代表にする）を機械的に採用すると **逆方向の同種バイアス** が起きることを実データで確認した。例: `arkworks-rs/algebra`（暗号ライブラリ・29パッケージ）で
  - flagship（`dependents` 最大＝`ark-ff`, 依存1,829）: gem=-6.95（妥当な中庸スコア）
  - min(gem_index)（`ark-ed-on-bls12-381-bandersnatch`, 依存63）: gem=-24.32（外れ値による過大評価）
  - **max(gem_index)（`ark-algebra-bench-templates`, 依存6・ベンチマーク用の付属クレート）: gem=+1.22 → 「Gem ではない」判定になる**

  つまり product/infra が言う「保守的な代表値」は、**ベンチマーク用の付属クレートという repo の本体ではないサブモジュール** を代表に選んでしまい、正当な人気ライブラリ（`ark-ff` は実際に 1,829 件から依存されている）を丸ごと過小評価（false negative）する。min も max も「repo 内で最も極端な1パッケージ」を選ぶ点で同じ脆弱性を持つ。
  **推奨は変えない**: 代表 = `dependents` 最大のパッケージ（flagship 選定）。gem_index の値そのものではなく「そのリポジトリの識別に使われる主パッケージはどれか」という別の軸で選ぶため、min/max どちらの選択バイアスも回避できる。

### 4. infra の Q2「④ 1ファイル+isolateキャッシュ」と自分の推奨データ shape の両立性: **両立する**

自分の推奨（成層化・stars 検証フィルタ・repo dedup=flagship）はすべて **オフラインのバッチ生成段階**（収集→フィルタ→dedup→スコア確定）で完結し、配信段階の shape には影響しない。むしろ dedup で行数が19%減る分、④の isolate 内 JSON.parse コストが下がる副次効果がある（infra の cold start 対策と方向が一致）。
配信ファイルに必要な最小フィールドは infra 案どおり **`repoFullName → gemIndex` の2値** でよい。ただし1点追加を推奨: **`registry`（どのレジストリのパッケージか）を残す**。理由は、D（UX）の「バッジに注記文言を出す」（product案）や将来の成層化枠の再チューニング（例: あるレジストリだけ汚染が発覚して緊急除外したい場合）に、配信ファイル側だけで対応できる（再収集不要）ため。3値目を足しても1エントリ数バイトの増加で、3.3MB→大きくは変わらない。

### 5. 被覆率 vs 品質のトレードオフ（1行）

**実測上はトレードオフになっていない**（品質フィルタの被覆率への影響は0.001〜0.086%で無視できる）。強制的にどちらかを優先しろと言われたら **品質を優先する**（汚染された高被覆率より、信頼できる Gem を少数出す方がミッション「実利用に対する star 不足の発見」に忠実）。
