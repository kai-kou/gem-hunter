## product: round 2（rebuttal / concession）

### 1. data の「過小評価上位 83.2% が stars=0 汚染」への回答 — **一部 concede**

**concede**: 「発見面（Gem 一覧）を主軸に」という round1 の推奨は、**このまま出すなら data の指摘どおり最も危険な形になる**。理由は my ミス — 発見面は定義上「gem_index が最も大きい（＝最も過小評価されている）順」に並べる設計を暗黙に想定していたが、それは data が実測した汚染 83.2% の分布を**そのままトップに押し出す**構造になる。「被覆率問題を回避できる」という round1 の主張は正しいが、**「品質問題を回避できる」とは言っていない**し、実際には回避できない。ここは撤回する。

**rebuttal（範囲限定）**: ただし「発見面が badge / sort より相対的に危険」という比較には一部反論がある。badge・sort は **GitHub 検索でヒットした 100 件**という母集団に gem_index を乗せるだけなので、その母集団自体が GitHub の関連度ランキングを一度通過した「実在する・ある程度活発なリポジトリ」に絞られている。一方、発見面（ソート済み一覧）は **母集団全体から gem_index 最大順に直接抽出する**ため、汚染（webjars ミラー・repo 誤紐付け）が最も濃縮される場所に露出面を作ってしまう。つまり **リスクの絶対量は同じでも、発見面の方が汚染に対する露出濃度が高い** — data の指摘は「発見面固有の追加リスク」ではなく「gem_index を上位ソートとして見せるあらゆる場所に共通するリスクが、発見面では最大化される」という形で成立する。

**結論の修正**: 発見面を出すなら、**data の成層化 + stars=0 検証フィルタ（`repo_metadata` 有無での判別）が実装され、フィルタ後の実効データで再検証してから**にする。未フィルタの状態で発見面を主軸にする判断は撤回する。

### 2. 「キーワードで探せない Gem 一覧はミッションに応えるか」への回答 — **concede**

これも認める。ミッションは「個人開発者が**見つけられる**ようにする」であり、round1 の「エコシステム別・topics 絞り込みの一覧をブラウズする」設計は、**自分が検索している具体的な領域（キーワード）を Gem 側の絞り込み条件として使えない**限り、「browse はできるが自分の探し物には応えない」という batch UX に留まる。これは Q2 のピッチが検索行為そのものを主眼に置いていることとも整合しない。round1 の「発見面 = ブラウズ専用」という設計は不十分だったと修正する。

### 3. 妥協案「バッジ + 同じ検索語で絞り込んだ Gem 一覧への導線」への回答 — **成立する。round1 の併設案より優れる。★これを新しい推奨に差し替える**

理由:
- **キーワード起点を保つ**: 「この検索語の Gem を見る」は入力したキーワードをそのまま Gem 一覧側の絞り込み条件に渡すため、論点2の欠陥（キーワードで探せない）を解消する。ユーザーの課題（自分の探している領域で Gem を見たい）に直接応える。
- **空状態を主体験から隔離できる**: 遷移先ページは「検索結果」ではなく「Gem 発見という別の文脈」なので、0 件でも「この検索語に一致する Gem は今のところありません（対象母集団: 12 レジストリ・被依存数上位を中心に収集）」と**期待値を作った上で**空を見せられる。主検索結果に混ぜて出す（round1 の sort/badge 併設案）よりも、失望の作られ方が穏やかになる（争点 E の教訓を踏まえた設計）。
- **汚染リスクを抑えられる**（論点1 との接続）: 「この検索語」で絞り込むと母集団がキーワードにマッチする少数（多くの場合 1 桁〜数十件）に絞られるため、**gem_index 最大順の全体ソートで汚染上位を丸ごと露出する round1 の発見面よりも露出面が狭くなる**。ただし絞り込み後の少数件の中に stars=0 汚染が混入するリスクはゼロにならないため、data のフィルタ実装は依然として前提条件。
- round1 の「バッジ + ブラウズ専用発見面」の単純併設と比べ、**動線が 1 本（バッジ → 導線 → 絞り込み一覧）で完結し、ユーザーが「検索」「ブラウズ」という別々の入口を意識しなくてよい**。実装面（infra/data 目線の詳細判断は譲るが）でも、絞り込み一覧はキーワードトークンで母集団を先にフィルタしてから gem_index でソートするだけなので、成層化母集団・stars 検証フィルタと自然に接続できる。

**この案の残課題（infra/data への申し送り）**: 「この検索語」を Gem 一覧側でどう照合するか（repo 名・description・topics のどれで token match するか）は現在の配信 shape（repoFullName + gemIndex の 2 値・infra 提案）に含まれていない。キーワード一致に使うフィールド（description/topics）を候補データに追加する必要がある。これは product からの新規要求として次ラウンドに投げる。

### 4. 「現状維持（今日の Gem だけ）」が合理的なシナリオ — 1 行

**data の成層化・stars 検証フィルタ・infra の cold start 対策のいずれかが本スプリント内に検証しきれない場合**、未検証の汚染データを新機能として出すより、`D-3`（説明可能性）を優先して現状維持のまま次スプリントへ持ち越すのが合理的。

### lead 追加事実（Workers Paid）への反応

infra の CPU/subrequest 制約緩和は歓迎するが、**product の懸念（データ汚染・空状態 UX）は課金プランと無関係**。Paid だからといって論点1・2の結論は変わらない。
