## lead: 合意（round 1〜2 の突き合わせ）

### 全員が一致した点

1. **`sort=gem-index`（検索結果の主ソート軸）としての再導入はしない。** `D-33` の再導入条件（一般語の上位 100 件で 30% 以上）は実測で **react 32% / test framework 36% / image processing 19%** と「ぎりぎり届く／届かない」水準であり、data のフィルタを掛けても被覆率はほぼ変わらない（除外対象は valid pool 144,256 件中 2〜124 件 = 0.001〜0.086%）。にもかかわらず却下する理由は被覆率ではなく **「一部だけ並べ替わり、残りは無意味な順で並ぶ」というソート軸としての体験破綻**（product）で、これは母集団をいくら広げてもロングテールがある限り構造的に残る。
2. **母集団の拡大自体は成功している。** npm 227 → 12 レジストリ 109,469 リポジトリを **144 リクエスト・約 10 分** で構築でき、非 npm が全体の約 3 割を占める。`D-33` が指摘した「npm 限定という構造的限界」は解消する。
3. **`D-33` のサイズ根拠は崩れた。** Static Assets は Worker バンドル 3MB(gzip) 枠の外であり、加えて本アカウントは既に **Workers Paid**（`cloudflare-infrastructure.md` §5・2026-08-20 実機確認）。「10 万件はバンドルを圧迫する」は現行実装（`import` でバンドルへ焼き込む）に固有の制約だった。
4. **データ品質の是正は再導入の前提条件。** 生データのままでは「過小評価トップ」が Maven WebJars ミラー等の `stars=0` に支配される（実測: 上位 100 件が Maven 87 / hex 13、`star_rank` 下位 40% のうち **83.2% が stars=0**）。汚染除去なしに Gem を上位表示する面を作ってはならない。
5. **D1 は採らない。** `D-18` が R2 / D1 / DO / KV を明示列挙して不採用と確定しており、`D-27` の境界注記（「Worker が実行時にそのファイルへ書き込むか」）は **静的アセットファイルの判定基準** であって D1 を救済しない（infra・反論なし）。
6. **データ源は Ecosyste.ms REST の巡回を継続する。** deps.dev BigQuery（CC-BY 4.0・stars 同梱）は精度では魅力的だが、無料枠 1TB を一撃で超える事故報告があり運用複雑化に見合わない。63.7GB のバルクダンプも不要（API 巡回のほうが速く新しい）。

### 議論で覆った点（round 1 → round 2）

| 誰 | round 1 の主張 | round 2 での修正 | 決め手 |
|---|---|---|---|
| product | Gem 専用の発見面（エコシステム別・topics ブラウズ）を主軸に | **撤回**。ブラウズ専用では「自分が探している領域の Gem」に応えられず、ミッション（個人開発者が **見つけられる**）に届かない。**「バッジ + 検索語をそのまま引き継ぐ Gem 絞り込み一覧への導線」** に差し替え | 汚染はソート上位を見せる面すべてに共通し、ブラウズ一覧では濃度が最大化される（data の実測） |
| infra | 単一ファイル + isolate 内メモリキャッシュ | **修正**。**レジストリ別 12 シャードを cold start 時に `Promise.all` で並列 fetch し、isolate スコープの単一 Map にマージ** する形へ。ハッシュ分割の二律背反（シャードを増やすほど subrequest が増える）を回避しつつ、レジストリ単位の個別再生成が可能になる | data の成層化がシャード境界として自然に効く |
| infra | cold start はデプロイ直後の 1 回 | **訂正**。isolate は PoP ごとに生成・回収されるため、cold start は **一定割合のリクエストで継続的に発生する**（割合は非公開・要実測） | Cloudflare の isolate ライフサイクル |
| product | 全体パーセンタイル再計算を品質ゲートにする | **却下された**。素の絶対値でグローバル再計算すると Elixir 支配が **npm 支配（上位 100 件中 90 件）** に入れ替わるだけ（data が実装して確認） | 実測 |
| infra / product | モノレポ代表は保守的に max(gem_index) | **却下された**。`arkworks-rs/algebra` ではベンチマーク用付属クレートが代表になり、実際に 1,829 件から依存される `ark-ff` を丸ごと取りこぼす。代表は **`dependents` 最大（flagship）** | 実データの反例 |

### 残る対立（判断が要る点）

- **バッジを出すかどうかで必要なインフラが変わる**。infra の指摘: 「事前計算した上位 N 件の一覧だけ」なら現行の静的 JSON 配信の延長で足り、join 基盤（12 シャード + isolate キャッシュ）は要らない。**検索結果に Gem Index を出す（バッジ）限り、予測不能な 100 件に対する runtime join が必要になり、基盤の実装コストが発生する**。これは技術ではなく「検索結果に Gem を見せる価値があるか」という product / 飼い主の判断。
- **Gem 絞り込み一覧のキーワード照合に使うフィールド**（repo 名のみ / description / topics）が現行の配信 shape（`repoFullName → gemIndex` の 2 値・data は `registry` 追加を提案）に含まれていない。description / topics を載せるとサイズが桁で増える可能性があり、かつ Ecosyste.ms の生テキスト再配信は `GR-6` が禁じている（**自前で GitHub API から取るか、repo 名・topics に限るかの設計判断が要る**）。
