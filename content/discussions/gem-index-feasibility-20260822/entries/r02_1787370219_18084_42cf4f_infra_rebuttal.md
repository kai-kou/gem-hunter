# infra: round2 rebuttal（Paid前提の再検証 + product/data への応答）

## 1. Paid前提でも④（isolate内メモリキャッシュ）は変わらない。`limits.cpu_ms` は暫定 **50ms**

結論は不変。理由: ④の優位性は「subrequest 1 本・warm時0コスト」という**Free/Paid どちらでも効く**性質で、Paid化で緩和されるのは①（シャード分割）側の subrequest 制約だけであり、①と④の優劣関係（④が二律背反を回避する）は変わらない。

`limits.cpu_ms` は **50ms** を提案する。根拠: round1 の cold start 見積り 8〜16ms（JSON.parse 3.3MB・V8 目安 200〜400MB/s）に対し ~3〜5x のマージンを取り、SSR 本体の未計測 CPU（今回のブリーフィングに実測値なし）を吸収する余地を残す。Paid のデフォルト（30,000ms=30秒）は denial-of-wallet 対策として機能しないため、明示設定は必須（`cloudflare-infrastructure.md` §5.3 手順3が既に「Claude が `limits.cpu_ms` の設定を確認なしで済ませる」を許可している）。**この 50ms は未検証の初期値**であり、`wrangler tail --format json`（§5.3 と同じ手法）で p95 CPU を実測してから 20〜30ms 程度まで締める、という 2 段階運用を推奨する。

## 2. product の「発見面主軸＋バッジ」案への回答: **発見面だけなら現行バンドル継続で足りる。バッジがある限り④は必要**

- **発見面（上位 N 件の静的ページ）単独なら同意・配信方式の刷新は不要**。表示対象が「事前計算した固定の上位 N 件」に閉じるなら、母集団 109K 全体を runtime に持つ必要がなく、現行 `daily-digest.json`（57KB）と同じ **バンドル焼き込み or 単純 Static Assets 配信をそのまま N 件分に拡張**すれば済む（N=500 でも数百KB級、3MB bundle 枠にもまったく抵触しない）。今回のシミュレーション・cold start 議論・shard 二律背反はすべて「**検索結果という予測不能な集合に対して join する**」ケース専用の問題であり、固定リストには最初から発生しない。
- **ただし product 自身の B 判定表は①バッジ（検索結果への軽量バッジ）も「採用」としている**。バッジ表示は GitHub 検索 API が返す任意の 100 件（母集団のどれが来るか予測不可能）に対して「付くか付かないか」を判定する必要があり、これは実質的に本論点 C の join 問題そのもの（値を返すか flag だけ返すかの違いに過ぎない）。**バッジを残す限り④（またはそれに準じる runtime join 手段）は引き続き必要**。「発見面だけで足りるのでは」という問いへの答えは **条件付き Yes**: バッジを落として発見面のみにするなら配信刷新は不要、バッジを残すなら不要にならない。判断は product/lead 側の UX トレードオフに委ねるが、infra としては「バッジ 1 機能のためだけに④の実装コスト（isolate cache 設計・cold start 対策・`limits.cpu_ms` 運用）を払う価値があるか」を再検討材料として提示する。

## 3. data の成層化・dedupe・star フィルタが配信ファイルに与える効果: **サイズは10〜15%減、形は「レジストリ別12shard」との相性が良い**

- **サイズ**: stars=0 汚染候補（母数の9.4%）を Gem 対象から除外し、モノレポを repo 単位で flagship 1 件へ dedupe（現状すでに repo 単位 109,469 件なので追加の削減は主に stars フィルタ分）しても、全体サイズは**桁は変わらず 10〜15% 減 程度**（raw 3.3MB→ 概算 2.8〜3.0MB）。round1 の cold start 見積り（8〜16ms）や `limits.cpu_ms` の数値を大きく変えるほどではない。
- **形**: data の「レジストリ別成層化」は**①の N=固定・ハッシュ分割よりも自然で優れたシャード境界**になる。round1 で①を却下したのは「検索結果100件がハッシュ分割shardへランダムに散り、birthday paradoxでほぼ全shardに当たる」ためだが、**レジストリ別12shard（1レジストリ1ファイル、各数百KB）を④の cold start 時に `Promise.all` で12本まとめて並列fetchし、isolateスコープの単一 Map にマージする**という設計なら、①の欠陥（shard数を増やすほどsubrequestが増える二律背反）を回避しつつ、data 側の運用上の利点（**レジストリ単位で個別に再生成・差し替えできる**＝1レジストリの更新失敗が他レジストリの鮮度を道連れにしない、`D-28` の SPOF 無害化方針とも整合）を取り込める。**round1の「単一ファイル」は撤回し、「12shard・cold start一括fetch・isolateキャッシュ」に修正する**（④の骨格は維持、data の入力を受けた具体化）。

## 4. cold start の実害規模（Paid前提）: **「1回だけ」ではなく isolate ごと・かつ isolate は複数同時稼働する**

「デプロイ直後の全リクエストが同じコストを払う」は不正確な単純化だった、訂正する。Cloudflare の Workers は世界中の PoP に**多数の isolate が並行して立ち上がる**ため、cold start は「デプロイ直後の1回」ではなく、**トラフィックのある PoP それぞれで、isolate が新規生成される・アイドルタイムアウトで回収される・メモリ圧迫で退避される、といった契機のたびに繰り返し発生する**（正確な evict 間隔は Cloudflare 非公開・未確定 = 憶測含む）。したがって実害は「デプロイ直後の一過性」ではなく「**一定割合のリクエストが継続的に cold start コストを払い続ける**」性質のもの。Paid ではこれは「停止」ではなく「その割合のリクエストだけ CPU 課金が高くなる」実害に留まるが、**割合が未知数である以上、`wrangler tail` の p95/p99 CPU 実測（§5.3 と同じ手法）を実装後に必ず行い、`limits.cpu_ms=50` が実際の分布に対して妥当か検証すべき**という結論は変えない。日次デプロイのタイミングでは新バージョンの isolate が新規生成されるため、その直後は cold start 率が一時的に上振れする点は round1 の指摘どおり残る。
