## data（データ源・母集団・指標設計）Round 1

自分で `/tmp/pool_big.json`（18万件・12レジストリ・rankings込み）を python3 で集計し直した実測を根拠にする。憶測は明記する。

### 追加実測（このラウンドで新たに取得）

1. **レジストリ内 rank をそのまま混在ソートすると Maven/hex が支配する**（ブリーフィングの「hex/CRAN/pub」説を補強・訂正）。`dep_rank - star_rank`（API 提供値）が最小の上位100件の内訳: `repo1.maven.org 87 / hex.pm 13`。上位はいずれも `stars=0` の Maven Webjars ミラー（`org.webjars:sockjs-client` 等・依存4,021件で star=0）— **実利用ではなく自動生成の再配布パッケージ**。
2. **逆に、母集団全体で生の被依存数・star数を使ってグローバルパーセンタイルを再計算すると npm が支配する**（自分で実装して確認）。上位100件の内訳: `npmjs.org 90 / rubygems.org 4 / proxy.golang.org 4 / pypi.org 2`。理由は npm の依存グラフ密度が他エコシステムより桁違いに濃い（1エントリの絶対被依存数が他レジストリの同順位より1〜2桁大きい）ため、**素の絶対値パーセンタイルはエコシステム間の「依存グラフの濃さ」の違いをそのまま順位に持ち込む**。
   → **A(レジストリ内 rank 単純結合) と B(素のグローバル再計算) はどちらも却下**。片方は Maven/hex 支配、もう片方は npm 支配で、対称的に同じ欠陥（1レジストリ支配）を反対方向に起こしている。
3. **`stars=0` は「真の0」と「repo 紐付け不良」が混在する疑い（実例で確認）**: `is-color-stop`（npm・被依存 1,899,064・repo=`pigcan/is-color-stop`・stars=0）。1.9M件から依存される超基盤パッケージが実 star 0 は typosquat/フォーク乗っ取りによる repo 誤紐付けの可能性が高い（ADR 0009 §2.3 が指摘する「未検証データ」リスクの具体例）。`stars=0` の母数は 137,688 件中 12,956 件（9.4%）だが、star_rank>60（下位40%）の中では 83.2%（1,980/2,381）が stars=0 — **「過小評価上位」は「stars=0 の塊」にほぼ支配される構造**。stars=0 を無検証で採用すると、真のギャップではなく repo 紐付け不良・自動生成ミラーが上位を埋める。
4. **モノレポ集約**: 複数パッケージが同一 repo を指すのは 120,187 repo 中 6,900（5.7%）。うち **95.5%（6,591件）が同一レジストリ内**（Maven multi-module・crates workspace・NuGet 分割等のビルド分割であり、複数エコシステム展開ではない）。cross-registry の「本当の多言語バインディング」はわずか 309 件（4.5%）。
   - 集約ルールの実害: 同一 repo 内の gem_index の spread（max−min）は中央値 0.7pt だが p90 で 6.0pt・最大 60pt。**tail で無視できない差**。
   - 直感に反する発見: パッケージ数が多い repo（Quarkus 等の大規模フレームワーク）ほど「最良サブモジュールの gem_index」の中央値は **-6.37→-2.01 と浅くなる**（単純パッケージ数1の repo の方が深い）。つまり sum/min で「モジュール数が多いほど有利」というバイアスは実データ上は逆方向（大規模組織化プロジェクトは元々知名度があるため）。ただし tail 6pt/60pt の spread は残るため、**sum は明確に却下**（同一レジストリ内の workspace 分割が95%を占める以上、sum は同じ repo の被依存数を人為的に水増しする）。

### 論点への回答

**B（母集団設計・自分の主レンズ）**
- **推す**: レジストリ別成層化（stratified quota）。Ecosyste.ms が既に提供する「レジストリ内 percentile」をそのまま使い、**レジストリごとに固定 or 母数比例の枠** で候補を選出してから混ぜる（例: 12レジストリ×上位N件、または母数対数比例）。実測 3 の npm 過多・実測 1 の Maven/hex 過多は「1レジストリが結果を独占する」という同一欠陥の両極であり、成層化はその欠陥を構造的に潰す。
- **却下**: 生のレジストリ内 rank 単純結合（現状 ADR 実装が示唆する自然な延長）／素のグローバル再計算（B の代替案として一見公平に見えるが実測で npm 支配と判明）。
- **推す**: `stars=0` を無条件に信頼しない。最低限、`stars` が **明示的に取得できた値か API 欠損時のデフォルトか** を区別するフィールドを持たせる（Ecosyste.ms のレスポンスで `repo_metadata` オブジェクト自体の有無を見る。今回のフラット化データでは判別不能だったが元 API では可能）。加えて `dependents` が極端に大きく `stars` が 0 の組は経験則フィルタ（例: dependents 上位1% かつ stars=0 は要目視/除外）にかける。
- **却下**: `stars=0` をそのまま「過小評価の証拠」として採用する現状ロジック延長。1.9M依存の実例が示す通り、上位を汚染するリスクが高い。
- **推す**: モノレポは repo 単位で dedupe。代表パッケージは「`dependents` 最大のパッケージ」を採用（flagship 選定・sum ではないので水増しなし、min ではないので外れサブモジュールによる過大評価もない）。cross-registry（4.5%）のみ、レジストリごとに別エントリとして残してよい（別コミュニティへの露出は実体が異なるため）。
- **却下**: sum 集約（同一レジストリ内 workspace 分割が 95% を占め、被依存数の水増しになる）／無条件 min 集約（tail で 60pt スプレッドがあり、外れサブモジュール1つが repo 全体の評価を決めてしまう）。

**A（検索への再導入）**: 自分のレンズでは反対材料を追加する。今回の実測でも「Gem Index が付く」候補の質そのものに repo 紐付け不良のリスクが混ざっており、**被覆率30%達成が即再導入の十分条件にはならない**（分子の質が実測で疑わしい）。成層化＋stars 検証フィルタを実装し、汚染候補を除いた後の実効被覆率で再評価すべき。現状の 32%（12レジストリ×15,000, react）はフィルタ前の生数値であることに注意。

**C（配信）へのデータ側制約**: 成層化母集団はレジストリ単位で自然に分割できるため、レジストリ別シャード JSON（① 案）と相性がよい。1 レジストリ 15,000 件・rankings + repo + dependents + stars のみなら 1 シャード数百KB級（既存57KB×12倍程度と概算）で、CPU 10ms 制約内で個別 parse できる粒度になる（グローバル1本の3.3MB/1.34MB gzip を毎回 parse する設計より安全）。

**D（UX）へのデータ側制約**: フィルタ後の実効被覆率はブリーフィングの生数値（19〜36%）より下がる可能性が高い（stars=0 汚染除去・成層化で「見た目だけ過小評価」の候補を落とすため）。**Gem Index を検索の既定ソートにするのは時期尚早**。バッジ／専用フィード案を推す。

**E（運用）**: `dependents` 最大による monorepo 代表選定は Ecosyste.ms の既存フィールドのみで機械的に決まるため追加 API 呼び出し不要（収集コストは変わらない）。deps.dev BigQuery への乗り換えは却下（1TB無料枠事故リスク・CC-BY自体は問題ないが運用複雑化に見合わない）。Ecosyste.ms REST 継続を推す。
