### A. 検索への Gem Index 再導入 — 「検索結果の主ソート軸」としての全面再導入は却下

**推奨（★）**: ソート軸復活ではなく、**②Gem 専用の発見面（エコシステム別・topics 絞り込みの Gem 一覧ページ）+ ①検索結果への軽量バッジ表示（付くものにだけ、ソートはしない）** の組み合わせに倒す。
**却下**: 「sort=gem-index をそのまま検索へ戻す」案。理由は 3 点。

1. 実測 19〜36%（react 32 / test 36 / image 19）は D-33 の閾値「30%」ぎりぎり未達〜僅かに上回る水準で、カテゴリ差が大きい（image processing は 8 割強が空欄）。「機能として成立している」と言い切るには弱い。
2. **ソート軸は「並べ替えた結果、上から意味のある順に並ぶ」という期待値そのものが壊れる。** Gem Index の付かない 64〜81% をどう扱うか（末尾固定？ NULL 混在？）に関わらず、「一部だけ並べ替わって残りは無意味順」という体験になる。これは D-33 の rejected 理由①（体感速度）とは別物の不満で、**静的化で速度を解決しても消えない**。争点 E の feedback item 10「数値が出ない不安」は形を変えて再燃するリスクが高い。
3. D-33 rejected②（10 万件プール拡大は Worker バンドル圧迫）は Static Assets 配信の実測（3MB gzip 枠に非計上・無料無制限配信）で **前提が崩れている**。ここは進展として評価できる。

### 「30% で成立か」の再定義（憶測明記）

30% という数字自体が粗い。**発見面に主軸を移せば、この基準論争自体が不要になる** — Gem 一覧ページは定義上 100% Gem Index 付きのアイテムしか載らないため。バッジ表示も「あれば出す・なければ何も出さない」設計にすれば空状態が発生しない。**検索の主ソートとしての再導入条件を上げ直すなら**（憶測）「トップ 20 件中 40% 以上、かつ主要 7 エコシステム全てで 0 件になるクエリがない」を提案するが、これは未検証で追加計測が要る。現時点では **主ソート化は保留**、発見面+ バッジで先に価値を出す方が説明可能性が高い。

# infra: 争点C（配信方式）結論 + A/B/E への含意（round1）

## 結論（推奨）: ④ isolate内メモリキャッシュ（module-scope singleton Map）を主方式に

`env.ASSETS.fetch()` で単一の圧縮済み JSON（1 ファイル）を **isolate が生成された最初のリクエストでのみ** 取得・parse し、`sharedGemDigestPort`（`container.ts`）と同じ **モジュールスコープ singleton** に `Map<repoFullName, gemIndex>` として保持する。2 回目以降のリクエストは subrequest 0・CPU は `Map.get()` × 100 件（マイクロ秒オーダー）で完結する。

**却下案とその理由**
- **① シャード化 JSON + `ASSETS.fetch`**: 実測ベースでシミュレートした結果、shard 数 N を増減しても「検索結果 100 件がヒットする distinct shard 数」は N=32 で ~31（ほぼ全シャード＝データの 96%）、N=256 で ~83（データの 32%）、N=1024 で ~95（データの 9%）と、**N を増やすほど転送量は減るが subrequest 数は増える** というトレードオフになり、Free の subrequest 上限 50/invocation を N≥64 付近で超える（下表参照）。GitHub 検索 API 呼び出し 1 本と合算するとさらに margin が減る。「シャード分割で J oin コストを下げる」という発想自体が、**検索結果がランダムに散る 100 件である限り機能しない**（birthday paradox でほぼ全シャードに当たる）。シャーディングは④の補助（cold start 分散・部分更新）としてのみ検討価値あり、主方式には不採用。
- **② ソート済みバイナリ + Range 二分探索**: ブリーフィング記載どおり Static Assets の Range 未対応報告があり未検証。今回のリサーチ（`cloudflare-infrastructure.md` / リサーチ一次情報）にも Range 対応の明記なし。**検証コストに見合わないため不採用**（要検証扱いのまま採用しない）。
- **③ D1 `IN (...)` クエリ**: `open-questions.md` `D-18`（R2/D1/DO/KV を **明示列挙** して不採用と確定・`D-24` でも「この部分は変更しない」と明記）に抵触。**`D-27` の境界注記（"Worker が実行時にそのファイルへ書き込むか"）は静的アセット *ファイル* の判定基準であり、D1 はファイルではなく永続クエリエンジンなので D-27 の救済対象にならない**（書き込みの有無に関わらず D-18 が D1 の採用自体を禁止）。よって **D1 は infra 制約として却下**（`NFR-21`/`INF-5` 云々以前に `D-18` で確定済み）。
- **⑤ バンドル焼き込み継続**: `D-33` が既に「10 万件規模は Workers Free のバンドル 3MB 上限を圧迫する」として却下済み。加えて `import` 方式は **データ更新のたびに JS バンドルの再ビルド・再デプロイが要る**（Static Assets の「デプロイで丸ごと差し替え」という `D-28` の設計意図と逆行）。不採用を維持。

## 数値根拠（シミュレーション・実測ベース）
- 母集団 109,469 件・raw 3.3MB / gzip 1.34MB（ブリーフィング実測値）。
- shard 数 N と検索 100 件がヒットする distinct shard 数の期待値（一様分布仮定・birthday paradox 近似 `N・(1-e^(-100/N))`）:

| N | 期待ヒットshard数 | 転送量(概算, 全体比) | Free subrequest 50 に収まるか |
|---|---|---|---|
| 32 | ~31 | ~96%（≈1.28MB gzip） | ぎりぎり(31+GitHub分1=32) |
| 64 | ~51 | ~79%（≈1.06MB gzip） | 超過(51+1=52) |
| 256 | ~83 | ~32%（≈0.43MB gzip） | 大幅超過 |
| 1024 | ~95 | ~9%（≈0.12MB gzip） | 大幅超過 |

→ **シャーディングは「転送量を減らすほど subrequest 数が増える」二律背反** で、Free の 50/invocation 制約下では実用的な N が存在しない（N=32 でも余裕がほぼゼロ）。④（1 ファイル・1 subrequest・isolateキャッシュ）はこの二律背反自体を回避する。

- ④ の cold start コスト（isolate 生成直後の 1 リクエストのみ）: JSON.parse(3.3MB) は V8 実測目安 200〜400MB/s 相当で **概算 8〜16ms**。Free の CPU 10ms/invocation の **すれすれ〜超過** になり得る（cold start 時に限り 1027 リスクあり）。**現状アカウントは実は Workers Paid（`cloudflare-infrastructure.md` §5 2026-08-20 実機確認・$5/月+従量）** であり、Paid では `limits.cpu_ms` を明示設定して従量課金に倒せるため cold start 超過は「停止」ではなく「課金」で吸収できる。Free 想定のままなら **JSON をやめて typed array ベースの軽量バイナリ形式**（ソート済み文字列配列 + `Float32Array`/量子化 `Int16Array`）に変えて parse コストを 3〜5 倍程度削る対策が必要（未検証・推奨改善案）。
- warm isolate 中の 2 回目以降: `Map.get()` × 100 は無視できるコスト。isolate の生存期間中は事実上 0 コストで join できる。

## A（再導入可否）への含意
配信方式は④で Free/Paid いずれでも技術的に成立する（Paid なら余裕、Free なら軽量バイナリ化が前提）。ただし **`D-33` の再導入条件（非 npm を含み一般語 100 件中 30%+ ヒット）を満たすのはデータ側（12 レジストリ×15,000件計画）の仕事** であり、配信方式の実現可能性だけでは再導入を正当化しない。infra 目線では「④ + cold start 対策が実装・実測（`wrangler tail` で p95 CPU 確認・§5.3 と同じ手法）できてから再導入」を推奨。

## B（母集団規模の上限）への含意
Static Assets のファイル上限（25MiB/ファイル・20,000ファイル）は 109K 件どころか 100 万件規模（raw ~30MB）でも単体では問題にならない。**実際のボトルネックはファイルサイズではなく cold start の JSON parse コスト**。目安として raw JSON を ~10MB 以内（現状の 3 倍程度、CPU 換算で 25〜50ms 相当）に収めるなら Paid で許容範囲、Free ならこの規模で軽量バイナリ形式が必須になる。母集団を無制限に拡大する設計は避け、「配信用の最小 shape（repoFullName + gemIndex の 2 値）を保った上で件数上限を決め打ちする」方針を推奨。

## E（運用）への含意
④・①いずれも「Worker が実行時に書き込まない読み取り専用ファイルの差し替え」なので `D-27` の境界注記どおり `D-18` 抵触なし。バッチ生成場所（Cloudflare 外・セッション/Routine cron）・更新頻度（日次）・デプロイ差し替えという運用設計は変更不要。ただし④は isolate 生存期間に依存するため、**デプロイ直後は必ず 1 回 cold start が発生し全リクエストが同じ CPU コストを払う**（①のシャーディングと違い、devopsとして「デプロイ直後の p95 CPU」を計測対象に含めるべき）。

### 追加実測（このラウンドで新たに取得）

1. **レジストリ内 rank をそのまま混在ソートすると Maven/hex が支配する**（ブリーフィングの「hex/CRAN/pub」説を補強・訂正）。`dep_rank - star_rank`（API 提供値）が最小の上位100件の内訳: `repo1.maven.org 87 / hex.pm 13`。上位はいずれも `stars=0` の Maven Webjars ミラー（`org.webjars:sockjs-client` 等・依存4,021件で star=0）— **実利用ではなく自動生成の再配布パッケージ**。
2. **逆に、母集団全体で生の被依存数・star数を使ってグローバルパーセンタイルを再計算すると npm が支配する**（自分で実装して確認）。上位100件の内訳: `npmjs.org 90 / rubygems.org 4 / proxy.golang.org 4 / pypi.org 2`。理由は npm の依存グラフ密度が他エコシステムより桁違いに濃い（1エントリの絶対被依存数が他レジストリの同順位より1〜2桁大きい）ため、**素の絶対値パーセンタイルはエコシステム間の「依存グラフの濃さ」の違いをそのまま順位に持ち込む**。
   → **A(レジストリ内 rank 単純結合) と B(素のグローバル再計算) はどちらも却下**。片方は Maven/hex 支配、もう片方は npm 支配で、対称的に同じ欠陥（1レジストリ支配）を反対方向に起こしている。
3. **`stars=0` は「真の0」と「repo 紐付け不良」が混在する疑い（実例で確認）**: `is-color-stop`（npm・被依存 1,899,064・repo=`pigcan/is-color-stop`・stars=0）。1.9M件から依存される超基盤パッケージが実 star 0 は typosquat/フォーク乗っ取りによる repo 誤紐付けの可能性が高い（ADR 0009 §2.3 が指摘する「未検証データ」リスクの具体例）。`stars=0` の母数は 137,688 件中 12,956 件（9.4%）だが、star_rank>60（下位40%）の中では 83.2%（1,980/2,381）が stars=0 — **「過小評価上位」は「stars=0 の塊」にほぼ支配される構造**。stars=0 を無検証で採用すると、真のギャップではなく repo 紐付け不良・自動生成ミラーが上位を埋める。
4. **モノレポ集約**: 複数パッケージが同一 repo を指すのは 120,187 repo 中 6,900（5.7%）。うち **95.5%（6,591件）が同一レジストリ内**（Maven multi-module・crates workspace・NuGet 分割等のビルド分割であり、複数エコシステム展開ではない）。cross-registry の「本当の多言語バインディング」はわずか 309 件（4.5%）。
   - 集約ルールの実害: 同一 repo 内の gem_index の spread（max−min）は中央値 0.7pt だが p90 で 6.0pt・最大 60pt。**tail で無視できない差**。
   - 直感に反する発見: パッケージ数が多い repo（Quarkus 等の大規模フレームワーク）ほど「最良サブモジュールの gem_index」の中央値は **-6.37→-2.01 と浅くなる**（単純パッケージ数1の repo の方が深い）。つまり sum/min で「モジュール数が多いほど有利」というバイアスは実データ上は逆方向（大規模組織化プロジェクトは元々知名度があるため）。ただし tail 6pt/60pt の spread は残るため、**sum は明確に却下**（同一レジストリ内の workspace 分割が95%を占める以上、sum は同じ repo の被依存数を人為的に水増しする）。

### 論点への回答

**B（母集団設計・自分の主レンズ）**
- **推す**: レジストリ別成層化（stratified quota）。Ecosyste.ms が既に提供する「レジストリ内 percentile」をそのまま使い、**レジストリごとに固定 or 母数比例の枠** で候補を選出してから混ぜる（例: 12レジストリ×上位N件、または母数対数比例）。実測 3 の npm 過多・実測 1 の Maven/hex 過多は「1レジストリが結果を独占する」という同一欠陥の両極であり、成層化はその欠陥を構造的に潰す。
- **却下**: 生のレジストリ内 rank 単純結合（現状 ADR 実装が示唆する自然な延長）／素のグローバル再計算（B の代替案として一見公平に見えるが実測で npm 支配と判明）。
- **推す**: `stars=0` を無条件に信頼しない。最低限、`stars` が **明示的に取得できた値か API 欠損時のデフォルトか** を区別するフィールドを持たせる（Ecosyste.ms のレスポンスで `repo_metadata` オブジェクト自体の有無を見る。今回のフラット化データでは判別不能だったが元 API では可能）。加えて `dependents` が極端に大きく `stars` が 0 の組は経験則フィルタ（例: dependents 上位1% かつ stars=0 は要目視/除外）にかける。
- **却下**: `stars=0` をそのまま「過小評価の証拠」として採用する現状ロジック延長。1.9M依存の実例が示す通り、上位を汚染するリスクが高い。
- **推す**: モノレポは repo 単位で dedupe。代表パッケージは「`dependents` 最大のパッケージ」を採用（flagship 選定・sum ではないので水増しなし、min ではないので外れサブモジュールによる過大評価もない）。cross-registry（4.5%）のみ、レジストリごとに別エントリとして残してよい（別コミュニティへの露出は実体が異なるため）。
- **却下**: sum 集約（同一レジストリ内 workspace 分割が 95% を占め、被依存数の水増しになる）／無条件 min 集約（tail で 60pt スプレッドがあり、外れサブモジュール1つが repo 全体の評価を決めてしまう）。

自分の推奨（成層化・stars 検証フィルタ・repo dedup=flagship）はすべて **オフラインのバッチ生成段階**（収集→フィルタ→dedup→スコア確定）で完結し、配信段階の shape には影響しない。むしろ dedup で行数が19%減る分、④の isolate 内 JSON.parse コストが下がる副次効果がある（infra の cold start 対策と方向が一致）。
配信ファイルに必要な最小フィールドは infra 案どおり **`repoFullName → gemIndex` の2値** でよい。ただし1点追加を推奨: **`registry`（どのレジストリのパッケージか）を残す**。理由は、D（UX）の「バッジに注記文言を出す」（product案）や将来の成層化枠の再チューニング（例: あるレジストリだけ汚染が発覚して緊急除外したい場合）に、配信ファイル側だけで対応できる（再収集不要）ため。3値目を足しても1エントリ数バイトの増加で、3.3MB→大きくは変わらない。

### 5. 被覆率 vs 品質のトレードオフ（1行）

**実測上はトレードオフになっていない**（品質フィルタの被覆率への影響は0.001〜0.086%で無視できる）。強制的にどちらかを優先しろと言われたら **品質を優先する**（汚染された高被覆率より、信頼できる Gem を少数出す方がミッション「実利用に対する star 不足の発見」に忠実）。
