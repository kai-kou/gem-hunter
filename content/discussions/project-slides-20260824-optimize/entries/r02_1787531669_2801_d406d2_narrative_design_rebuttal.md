# narrative_design: round 2 rebuttal（4 論点への回答）

## 1. 🔴 スライド 13: 削除案には反対。ただし「41 項目への修正 + 再生成」という round1 の自分の提案は撤回する（一部譲歩）

**結論**: 13 は残す。12 への 1 行圧縮では Layer 0 の役割を代替できない。一方で、数値修正のために `new-05` を再生成する必要は無い（date-stamp で解決できる）。

### なぜ「12 へ 1 行」では代替できないか（検証結果）

dev_audience の削除案は「13 の情報＝41 項目・self-test あり」という **数値** だけを見て「12 に 1 行足せば十分」と判断しているが、13 の本文には TDD（12 の主題）に属さない情報が最低 3 点ある。

- 「アーキテクチャの依存規則もここで落ちる」— テストの話ではなく **依存規則の機械検査**（`check_architecture_boundaries.py`）の話
- 「結果の Markdown 表を PR 本文に貼るのが必須…フックが PR 作成をブロックする」— **hook によるワークフロー強制** の話。TDD とは無関係
- 「品質ゲートと本番デプロイに GitHub Actions は使わず…Actions の唯一の用途は Gem 候補プールの日次生成」— **CI インフラの使用範囲** の話

これらを 12 の「テストを先に書き、緑でなければ進めない」という見出しの下に押し込めると、「開発者が書くテスト（TDD）」と「PR をブロックする機械的な門（Layer 0）」という **別の主体・別の強制力を持つ 2 つの仕組み** が 1 枚に混ざる。これは 1 スライド 1 メッセージの原則そのものに反する統合であり、圧縮ではなく損失になる。

さらに構造上の実害がある。**スライド 15 の本文が既に「機械ゲート」という語を名指しで使っている**（「PR 作成 → 機械ゲート + セルフレビュー → 指摘対応 → squash マージ」）。13 を削除すると、この語を定義するスライドが無いまま 15 で唐突に登場することになり、11→12→13→14→15 という一本の筋の中で 15 が参照する概念が宙に浮く。これは pacing の問題ではなく **参照整合性の破損** なので、パイプラインが切れるという反論は成立すると判断する。

### ただし project_truth の A 判定への対応は、regenerate ではなく date-stamp で解決できる（round1 の自分の提案を撤回）

project_truth が 13 を「A（直さないと嘘になる）」と判定した根拠は、数値そのものの誤りではなく「**日付スタンプが無いので現在形の主張に読める**」ことだった（12・15 は `（2026-08-23 時点）` を明記しているので B 扱い）。lead の調査によれば、41 項目への増加は 2026-08-23 改訂"後"に入った #546・#556 由来であり、**2026-08-23 時点では 38 項目という記載は正しかった**。

したがって、12・15 と同じ書式に揃えて「検査は 38 項目（2026-08-23 時点）。…」と日付を付けるだけで、project_truth 自身の A/B 判定基準に照らして B（古いが嘘ではない）に落ちる。これは text-only 修正で、`new-05` の再生成は不要になる。41 へ書き換えても発表当日にはまた古くなっている可能性があり（visual_assets 指摘の通りこの手の数値は動く）、日付スタンプの方が息の長い解決策でもある。

**再生成コストの帰結**: 13 は残す・削除しない・regenerate しない。dev_audience が懸念していた「古い数字を保守し続けるコスト」も、日付スタンプ化で以後発生しなくなる（12・15 と同じ運用に揃うだけ）。

## 2. スライド 1（表紙）: 判断を更新する（concession）

round1 では「本文 1 点目『gem-hunter』が見出しと重複しているが、直すためだけに `new-01` を再生成するのは費用対効果に見合わない」と判断した。

visual_assets の目視報告（「見っける」の文字化け）が事実であれば、**再生成はこの誤字修正のためだけで既に不可避** になる。つまり私が「見合わない」と判断していたコストは、この論点とは独立に別の理由でどのみち発生する。この新事実の下では、コストを理由にした反対は前提が崩れており、**判断を更新する**。

**更新後の提案**: `new-01` を再生成するタイミングで、本文 1 点目「gem-hunter」（見出しと重複・実質的な情報価値ゼロ）を削除し、2 点構成（「star では埋もれる『実際に使われている OSS』を見つける」／「開発者向け解説 / {日付}」）に整理する。表紙は layout が `title`（`bullets` ではない）なので text_budget の 5〜7 点ルールの対象外と読むのが自然であり、点数を減らすこと自体に基準違反は無い。誤字修正のついでに直す限りコストは増分ゼロ。

## 3. スライド 6: `replace`（差し替え）に同意する（round1 の「$0 で直せる」前提を撤回）

round1 の自分の提案（見出し変更 + 与件 11/11 の 1 行差し込み・画像は `08-doc-relations.webp` を流用継続）は、**画像自体には手を入れない** ことを前提にしていた。visual_assets が指摘した「帯タグ ADR14 件 vs 実測 15 件」の不一致は、私の提案とは無関係にこの画像に既に存在する欠陥であり、これを知った上で欠陥入りの画像を流用し続けるのは、このデッキの一貫した誠実さの約束と整合しない。

判断材料は decision I の前例（slide 16・`10-gem-score.webp` の `criticality_score` 矛盾）と全く同型: **画像内の断定的な数字が実装事実と食い違っている** ケースであり、あのときは「本文から事実を後退させて図に合わせる案」を明確に却下し、画像側を差し替えている。同じ基準を今回だけ緩める理由がない。

**結論**: `replace` に同意する（$0.037 のコストを支払う）。ただし提案を 1 つ添える — 新しい `08-doc-relations` 相当の画像には、本文が触れていない数字（ADR 件数のような）を単独で焼き込まない設計にしてほしい（visual_assets への申し送り）。今回の欠陥は「本文にない数字が画像だけに残っていた」ことが根本原因であり、次に ADR が増えたときに同じ陳腐化を繰り返さないための予防線になる。

**私の見出し・本文提案そのものは変えない**: 「要件は 1 本の PRD に集約し、11 項目を満たした」という見出しと、与件 11/11 の 1 行差し込みは、`replace` 後の新しい画像のモチーフ・焼き込みテキストとしてそのまま使ってよい（画像がドキュメント関係図であることに変わりはないので、私の提案とモチーフの整合性は保たれる）。

## 4. スライド 3 の見出し: 両立する（衝突しない）

私の見出し案「検索の並び順は変えない。絞り込むのは Gem 一覧だけ」は **`Gem Index` という語を一切使っていない**。dev_audience の提案は本文（elements）側の「過小評価が強い順（**Gem Index** が小さい順）」という 1 点から `Gem Index` という未定義語を外し、点数を 7 点から 4〜5 点に減らす、という **本文側の編集**。見出し（title）と本文（elements）は別のフィールドで、双方とも変更対象が重ならないため衝突しない。

**統合案**: 見出しは私の案を採用、本文は dev_audience の案（「過小評価スコア順に 20 件ずつ並ぶ」のように命名を避けて 16 で回収する）を採用。両方とも実 UI スクリーンショット（`shot-03`）で焼き込みテキストではないため、組み合わせても再生成コストはゼロのまま。
