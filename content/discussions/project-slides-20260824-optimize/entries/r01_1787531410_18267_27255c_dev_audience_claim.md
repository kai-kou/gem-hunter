# dev_audience R1: 21枚を聴き切れるか（枚数配分の観点）

前回議論（0822）で自分（前任）が推した「アウトカム先出し」「開発プロセスは動作フローに凝縮」という方針が、21枚化でどう実装されたかを検証する。同じ論点は蒸し返さず、実装結果に対する評価に絞る。

## 1. 離脱ポイント 3 か所（具体スライド番号）

### (A) スライド 3 — 「Gem Index」を未定義のまま名乗ってしまう
スライド3は本文7点（438字級の密度ではないが7点は多い）。3点目「過小評価が強い順（Gem Index が小さい順）」が、**その用語の定義（スライド16）より13枚も先に登場する**。前回自分が推した「アウトカム先出し」は"動くものを見せて安心させる"ためのフックだったはずが、実装では専門用語の先出しになっている。開発者は「Gem Index って何？」と引っかかった状態のまま先送りされ、離脱ではなく **未解決の疑問を抱えたまま次に進まされる** ことがストレスになる。ここは退屈による離脱ではなく、定義不在による混乱由来の離脱。

### (B) スライド 11〜15（開発プロセス 5 枚連続）
表紙〜スライド10まででプロダクトと技術スタックを見せ終えた直後、5枚連続で「AIエージェントの運用ルール」に入る。text_budget超過が12(327)/13(336)/14(304)/15(350)と4/5枚で発生しており、しかも13は「機械検証の自己テストが18項目」というメタ・オン・メタな内容。プロダクトの話から離れて「開発体制の話」に5枚（60〜70秒×5=約5〜6分）を使うのは、17〜20（技術的課題）という本題への到達を遅らせる。前回ラウンドで project_truth 自身が「実績値（遵守率等）は確認できていない」「規範として存在する事実」と留保をつけた領域でもあり、証拠密度が本題（17〜18）より薄い。ここが中弛みの中心。

### (C) スライド 19〜20（ADR 型トレードオフの反復疲れ）
17→18で「作って測って殺した」→「前提が変わって測り直して復活させた」という起伏のある物語を90〜100秒かけて聴かせたあと、19（認証6軸）・20（DBレス）が同じ「却下/採用」の定型フォーマットで連続する。19・20単体は悪くないが、**17-18の情動的ピークの直後に同型スライドが2枚続く** ことで「またこのパターンか」という反復疲れが起きやすい。とくに19は前回議論で project_truth が「持ち帰れる判断軸」として高評価した内容だが、17-18ほどのドラマがなく、直後に置くと見劣りする配置になっている。

## 2. 開発プロセス部（11〜15・24%）は厚すぎるか

**厚すぎる。5枚→4枚への削減を推奨する。**

根拠:
- text_budget超過が5枚中4枚で発生（12/13/14/15）。内容が薄いのではなく、**詰め込みすぎて薄く感じにくくなっている** 逆説的な状態。
- スライド13の「41項目」という数字自体、lead の実測で **現行スライドの記載(38)が既に古い** ことが判明している（#546/#556で41に増加済み）。プロセス部を厚く保つコストの中に「数字が古くなりやすい部分をメンテし続けるコスト」が含まれる。開発者聴衆は数字を検算する層なので、古い数字が1つでも見つかると「他の数字も怪しい」という不信に波及するリスクがある（このデッキの強みである"誠実さ"を自ら毀損する）。**枚数の議論とは独立に、13は数字修正が必須**（生成画像のため焼き込み修正＝再生成が要る）。
- 削るなら **スライド13を削除し、「41項目・self-testあり」を1行に圧縮してスライド12（既存流用・07-design.webp"ではなくtesting-strategy.webp）の末尾に追記する** 案を推す。12は既存流用画像なので elements 変更は画像再生成を伴わない（lead調査）。13を丸ごと削除すれば新規生成コストはゼロ。中身を活かしたいなら「41項目」を12に1行足すだけで、テキスト版PPTX・構成mdは更新されるが画像は変わらないので追加コストなし。
- 増やすなら足す先ではなく削る側だと考える。今の5枚は「AIエージェント運用が丁寧に設計されている」ことを示すには十分すぎ、開発者が最も知りたい「動くコードの技術判断」（17〜20）へ尺を回すほうが費用対効果が高い。

**再生成コストとのトレードオフ判断**: 13を削除するだけなら $0 ・リスクゼロ（最も安全な選択）。12へ1行追記するのも $0（既存流用画像のため）。14・15を結合するような大掛かりな再編は new-12/new-13 の再生成（各$0.037）と絵柄統一リスクを伴うため、**やるなら「削除+既存流用スライドへの追記」に留め、生成画像同士の統合はコストに見合わない**、というのが自分の結論。

## 3. 前半（1〜5）のアウトカム先出しは機能しているか

**機能はしているが、スライド3が過積載でその効果を薄めている。**

- 実UIスクリーンショット3連続（2・3・4）という構成自体は前回議論の結論（アウトカム先出し採用）を素直に実装しており、"何ができるか"を言葉でなく画面で見せる狙いは正しい。3枚とも別画面・別機能なので絵として単調ではない。
- ただしスライド4は本文222字（下限割れ）で軽いのに対し、スライド3は7点で最も重い。**3画面の情報量にばらつきがありすぎる**（3が突出して重い）。「動くものを見せて安心させる」フックとしては、3を4〜5点に削って身軽にし、Gem Index という語の先出しをやめる（「過小評価スコア順」で留め、命名は16で回収する）だけで解決する。この修正はスクリーンショット流用のため **画像再生成コストゼロ**（lead確認済みの依存グラフどおり）。
- 4枚目で"飽きる"というより、3枚目の情報過多と用語の先出しで **3枚目の時点で軽い消化不良を起こす**、というのがより正確な診断。4枚目自体は軽いので単独では問題ない。

## 4. 与件11項目充足は有益かノイズか（断定する）

**有益。ノイズではない。ただし今の粒度（21枚のどこにも出てこない）は機会損失であり、フルチェックリスト化もやりすぎ。1行だけスライド6に足すのが正解。**

理由を明示する:
- 開発者聴衆がこのデッキを聴きながら無意識に検算しているのは「与件（選考課題・外部要件）をちゃんと片付けた上で、17〜20のような踏み込んだ判断をしているのか、それとも与件を疎かにして面白い部分だけ作ったのか」という点。後者だと「趣味の実装に逃げた」という評価になりかねない。**「全11項目充足（❌0件）」という1事実は、17〜20の"上乗せ"パートの正当性を裏で支える保証書として機能する**。これがないと、聴衆は17〜20を「本題を疎かにした寄り道」と誤読するリスクがゼロではない。
- ただしフルチェックリストをスライド化するのは逆効果（前回議論で自分自身が「詰め込みすぎ」として名指しした失敗パターンの再演になる）。**1行で足りる**: 例「外部与件（受け入れ基準11項目）は全て充足。ここから先はその上に積んだ話」。
- 置き場所はスライド6が最適。理由: (1) 既に「外部から与えられた要件でスコープを絞り直した」という文脈がある、(2) 06fbdcf 既存流用画像（08-doc-relations.webp）なので elements 追記が **画像再生成ゼロ**、(3) 17〜20直前ではなく序盤（技術説明に入る前）に置くことで、後半の"上乗せ"パートを聴く前に前提として刷り込める。

**再生成コストとのトレードオフ**: このスライド6への1行追記は $0 ・リスクゼロ。やらない理由がない、と断定する。

## 5. 一番刺さる 3 枚 / 一番刺さらない 3 枚

**刺さる**:
1. **スライド17**（作って測って自分で殺した） — 実測データが最も厚く、"宣伝スライドでは出しにくい失敗"を見せる誠実さが開発者に効く。既に90〜100秒枠が付いており妥当。
2. **スライド18**（前提が変わって測り直し、殺した判断を覆した） — 17の続編として"自分の実測を自分の実測で覆す"という二重の誠実さ。ADR15本中でここだけ「決定→撤回→再検討」の全サイクルが見える。
3. **スライド10**（プレビューでだけ壊れる罠の実測表） — 「path-to-regexp が validate:true で呼ばれる」「wrangler deploy が非決定的にブロックされる」という、Cloudflare/Edge ランタイムで消耗したことのある開発者なら即座に共感する"あるある"。一般論の技術スタック紹介（9）より遥かに具体的。

**刺さらない**:
1. **スライド9**（技術スタック一覧） — Next.js/Tailwind/Cloudflare/Vitest/Playwright の名前列挙で、経験豊富な開発者ほど"知っている情報"の比率が高い。text_budget も358字と超過しており、密度の割に新規性が低い最たる例。10（実際に踏んだ罠）と隣接しているため、9の凡庸さが余計に際立つ。
2. **スライド8**（層を足す条件 W-1〜W-3） — 中身自体は具体的だが、「レイヤーは安易に増やさない」という主張自体はエンジニアリング一般論として手垢がついており、7（アーキテクチャ本体）と9（技術スタック）に挟まれて独立枠を割く必然性が薄い。
3. **スライド19**（認証6軸） — 判断軸としての一般化度は高く内容自体は悪くないが、17-18の情動的ピーク直後に「却下/採用」定型フォーマットの3巡目・4巡目として置かれることで相対的に見劣りする（§1(C)参照）。単独で見れば刺さる部類だが、**配置が刺さり方を殺している**。

## 6. 時間配分（60〜70秒基準で増減すべきスライド）

**増やすべき**:
- **スライド7**（アーキテクチャ・7層） — text_budget実測438字は全21枚中最大。60〜70秒では読み上げと理解が両立しない。既存流用画像（07-design.webp）なので **コンテンツ変更なしでも時間配分の変更だけなら再生成コスト完全ゼロ**。90秒程度に伸ばすのが最も安全な改善。
- **スライド18**（覆した判断） — 348字で、しかも"どんでん返し"の説明的難度が高い（前提がどう変わったかを丁寧に話さないと"ご都合主義"に見えるリスクがある）。80秒程度への微増を推奨。

**減らすべき**（上記の増加分の原資として）:
- **スライド1**（表紙） — 名前とキャッチコピーのみ。20〜30秒で十分。
- **スライド4**（今日のGemダイジェスト） — 222字で下限割れ、内容も軽い。45〜50秒で足りる。
- **スライド21**（まとめ） — 204字で下限割れ。クロージングは巻きで良く、40〜50秒で足りる。
- **スライド9**（技術スタック） — §5で「刺さらない」と評価した通り、読み上げを絞って50秒程度に圧縮し、浮いた時間を7・18へ回す。

差し引きすると 1(-10s) + 4(-15s) + 21(-15s) + 9(-15s) ≒ 55秒の原資に対し、7(+20s) + 18(+10s) ≒ 30秒の追加で収まる計算になり、11〜15を1枚削減した分（§2）と合わせれば22〜25分の総尺は崩れない。

## まとめ（再生成コストの総括）
