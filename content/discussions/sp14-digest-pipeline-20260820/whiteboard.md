# round 1: 母集団整合性とスコア算出の正しさ（data_integrity）

## 主張の要旨

Ecosyste.ms の `rankings` フィールドは **母集団の範囲（scope）だけでなく極性（polarity）も未検証** であり、いずれも OpenAPI にドキュメント文字列が存在しない（補完リサーチ §4.5 で確認済み）。この二重の未検証性がある限り、`rankings` フィールドを Gem Index の入力として直接使うのは危険であり、**ADR 0009 の定義に忠実な自前パーセンタイル計算を最初から前提にすべき**と考える。以下、根拠と具体案を述べる。

## 1. `rankings` の母集団は npm 単独か混合かの検証手段

書面上の実測事実（システム提供）: chalk の `rankings.stargazers_count=0.6435`, `rankings.dependent_packages_count=0.0005476`。chalk は npm で最も広く依存されるパッケージの一つ（直接依存者だけで数万件規模）であるにもかかわらず `dependent_packages_count` の rankings 値が 0.0005476 と極端に小さい。これは「1.0 に近いほど上位」という通常のパーセンタイル慣習では説明がつかない（chalk が下位 0.05% になるのは実態と矛盾する）。→ **極性が「値が小さいほど上位（rank/total 型）」である可能性が高く、これ自体が要検証**（§3 で扱う）。

母集団スコープの検証手段として、以下 3 経路を提案する（優先順位順）。

### 手段 A（最優先・決定的）: Ecosyste.ms のソースコードで算出ロジックを直接確認する
Ecosyste.ms（`ecosyste-ms/packages`、OSS）の GitHub リポジトリで `rankings` を計算しているモデルコード（Rails想定・`app/models/package.rb` 等）を検索し、パーセンタイル計算のスコープ（`registry_id` でグルーピングしているか、全レジストリ横断か）を直接確認する。ドキュメント不在の空白を埋める一次情報として最も信頼できる。`mcp__github__search_code` または WebFetch で `github.com/ecosyste-ms/packages` を調査する。

### 手段 B（実測・間接証拠）: 同一絶対値ペアのクロスエコシステム比較
`dependent_packages_count` の絶対値がほぼ等しい npm パッケージと他エコシステム（PyPI・crates.io）パッケージのペアを 3〜5 組選び、`rankings.dependent_packages_count` を比較する。
- 母集団が **エコシステムごとに閉じている** なら、npm（母数が非常に大きい・推定 200 万件超）と crates.io（母数が小さい）とでは同じ絶対値でもパーセンタイル値が異なるはず（同じ絶対値でも「その中での相対位置」が母数の大小で変わる）。
- 母集団が **全エコシステム混合** なら、同じ絶対値のペアはほぼ同じパーセンタイル値になるはず（同一の分布に対して順位付けされているため）。
- 実装コスト: 各レジストリのパッケージ総数は `GET /api/v1/registries` で取得できる（レジストリごとの `packages_count` が返る）。総数の桁が異なるレジストリ同士（npm vs crates.io 等）を選べば検出力が高い。

### 手段 C（補強）: レジストリスコープ済みエンドポイントの有無を確認
`GET /api/v1/registries/{registry}/packages?sort=rankings` のようにレジストリを固定した一覧エンドポイントが存在するかを確認する。存在し、かつ `sort=rankings` した際の並びがレジストリ内で完結しているなら、少なくとも「クエリ時点でのスコープ制御」は可能なことがわかる（ただし rankings 値自体が事前計算済みの固定値であれば、クエリのスコープ指定とは無関係にグローバル計算されている可能性が残るため、決定力は A・B に劣る）。

**推奨する実行順序**: A（ソース確認）を先に行い、それで確証が得られない場合のみ B（実測）で裏付ける。C は補助的位置づけ。

## 2. 自前パーセンタイル計算のアルゴリズム設計（ADR 0009 に忠実な形）

上記 1 の検証結果によらず、**§2.6 の不変条件（母集団は npm 全量）を満たすことを自分たちで証明可能にするためにも、rankings フィールドに依存せず自前計算する方針を基本線として推奨する**（vendor のブラックボックス値を信頼する形だと、後から母集団や極性の定義が変わっても検知できない）。

```
入力: npm 全量ダンプ（S3 バルクダンプ or レジストリ全件。D-28 のバッチ工程内）
  各パッケージについて:
    - dependent_packages_count（Ecosyste.ms が提供する生カウント。npm 全パッケージが対象）
    - stargazers_count（GitHub 解決できたパッケージのみ取得可能。§4 で述べる非対称性に注意）

Stage 1（母集団パーセンタイル計算・全量に対して1回だけ実施）:
  A_dep = npm 全パッケージの dependent_packages_count を昇順ソートした配列（長さ N_dep = npm 全パッケージ数）
  A_star = GitHub 解決済み npm パッケージの stargazers_count を昇順ソートした配列（長さ N_star ≤ N_dep）

  各パッケージ x について:
    percentile_dep(x)  = rank_asc(A_dep,  x.dependent_packages_count) / N_dep
    percentile_star(x) = rank_asc(A_star, x.stargazers_count)         / N_star
    # rank_asc: 配列中で x 以下の値を持つ要素数（二分探索 O(log N)）
    # 値が大きいほど percentile → 1.0 に近づく（「上位」＝1.0 側と自分たちで定義し固定する）

    Gem Index(x) = percentile_dep(x) − percentile_star(x)
    # ADR 0009 §2.1 のとおり: 被依存数パーセンタイル − star パーセンタイル。1つのスコアに他の軸（健全性）を合算しない。

Stage 2（健全性フィルタ・Gem Index とは独立に適用）:
  candidate_pool = { x ∈ 全量 | Scorecard(x) が定めた閾値を満たす AND GitHub 解決済み }
  # Gem Index の計算（Stage 1）より後に、かつ Stage 1 の計算対象母集団には影響を与えない形で適用する

Stage 3（表示候補プールの絞り込み・§2.6 が明示的に許可する箇所）:
  日次ダイジェスト = candidate_pool から日付シードで決定論的に選出した既定 5 件
```

**実装上のポイント**:
- `rank_asc` は O(N log N) のソート 1 回 + パッケージ数 M 件分の二分探索 O(M log N) で計算でき、npm 全量（推定 200 万パッケージ）規模でもバッチ実行（Cloudflare 外・D-28）なら現実的な計算量である。
- Stage 1 の母集団（`A_dep` / `A_star` の元データ）と Stage 2/3 のフィルタ処理を **コード上も別関数・別ステージに分離** し、Stage 2 のフィルタ結果を Stage 1 の入力に混入させない（後述 §3）。

## 3. ADR 0014 §2.6 不変条件を満たすデータパイプラインの形

§2.6 の不変条件（「母集団は npm 全量、絞ってよいのは表示候補プールの件数だけ」）を実装で守らせるには、**パーセンタイル計算ステージと候補プール絞り込みステージを物理的に別処理として分離し、後者の出力が前者の入力に絶対に流れ込まない構造**にする必要がある。上記 §2 の Stage 1 → Stage 2 → Stage 3 の一方向パイプラインはこれを満たす設計である。

具体化すべき点:
1. **バッチジョブのディレクトリ / スクリプト単位を分ける**（例: `scripts/batch/01-compute-population-percentiles.*` は npm 全量ダンプだけを入力に取り、フィルタ条件を一切受け取らない。`scripts/batch/02-build-candidate-pool.*` は Stage 1 の出力（全パッケージ分の Gem Index 付きレコード）を入力に取り、Scorecard 閾値・GitHub 解決可否でフィルタする）。
2. **Stage 1 の出力は「npm 全パッケージ分」の中間データセットとして必ず全件保持する**（フィルタ後の件数と混同しないよう、中間データセットのレコード数を検証項目にする。例: `assert 中間データセット件数 == npm 全量ダンプの件数`）。
3. **回帰防止の機械チェック**: Stage 1 のコードが Scorecard・health・GitHub 解決可否などのフィルタ条件を一切参照していないことを、依存関係の静的検査（import/呼び出しグラフ）または単体テストで担保する。「母集団を絞ってしまう」バグは実行結果を見ても気づきにくい（分布が滑らかに縮むだけで一見動いているように見える）ため、コードレベルで混入を機械的に防ぐ必要がある。
4. Stage 3（日次選出）の絞り込みは Gem Index の計算後に行われるため、§2.6 が禁じる「母集団を絞る」には該当しない（「表示候補プールの件数を絞る」に該当し許可される）。この区別を実装コメント・テスト名に明示し、将来の変更でこの境界が曖昧化しないようにする。

## 4. 健全性フィルタ（Scorecard）と Gem Index の独立性の確認

ADR 0009 §2.1/§3.2 は「過小評価度（Gem Index・並び順）」と「健全性（criticality_score→Scorecard・足切り）」を役割分担させ、1 つのスコアに合算しないと定めている。ADR 0014 はこの方針を再定義せず踏襲する（§2.6）。上記 §2 の Stage 1/Stage 2 分離はこの不変条件をそのまま実装に落とし込んだものであり、以下を確認事項として明示する。

- Scorecard スコアは Gem Index の算出式（percentile_dep − percentile_star）のどの項にも入力として現れない。Stage 2 の **フィルタ条件としてのみ** 使う（真偽値の足切り、または閾値以上のみ通過）。
- フィルタの適用順序が重要: Scorecard フィルタを **Stage 1（母集団パーセンタイル計算）より先に適用しない**。先に適用すると、パーセンタイル計算の母集団が「健全性フィルタを通過したパッケージだけ」に縮小し、§2.6 の不変条件（母集団は npm 全量）に違反する。この順序制約は §3 のパイプライン分離設計で自動的に守られるが、実装時にステージ順序を入れ替えないことを明示的なチェック項目として残すべきである。
- 一点、`rankings.dependent_packages_count`（未検証時点で実測されている値）自体が Scorecard 等のフィルタ後の母集団で事前計算されている可能性も否定できない（ベンダー側の実装詳細が不明なため）。これも §1 の手段 A（ソースコード確認）で解消すべき論点であり、rankings フィールドを直接使わず自前計算する方針（§2）を採ればこの懸念自体が構造的に無効化される。

## 未解決として残す論点（次ラウンドで扱いたい）

- stargazers_count の母集団（`A_star`）は GitHub 解決できたパッケージのみで構成されるため、`A_dep`（npm 全量）より母数が小さい非対称な状態になる。この非対称性が Gem Index の解釈（「npm 全量に対する順位」と言い切れるか）にどう影響するかは、ADR 0014 の文言だけでは明確に判定できない。GitHub 未解決パッケージをどう扱うか（候補から除外／percentile_star を欠損として扱う等）は data_pipeline 側の名前解決設計と合わせて詰める必要がある。

### (4) SPOF（バッチ停止・API 障害）の無害化・自己修復の実装方針

D-28: 「SPOF は無害化 + 検知して自己修復で対処し、配信自体は止めず鮮度のみ劣化させる」。

**具体方針**:
1. **無害化（フェイルクローズド生成）**: バッチは「新しい JSON を生成 → スキーマ・件数のバリデーション通過 → 成功時のみ commit」の順で行う。生成失敗・API 障害・バリデーション不合格時は **既存の commit 済み JSON を一切変更しない**。これにより Worker は常に「最後に成功した生成物」を配信し続け、エラー画面・空配列を絶対に出さない（`D-14` 同様、失敗を配信面に露出させない）。
2. **検知**: Routine 実行の最後に成否を記録する。既存の `[publish-sync]` Issue パターン（`pr-review-flow-summary.md` に実例あり: 反映できないセッションは `[publish-sync]` Issue に記録して沈黙しない）を踏襲し、失敗時は `[batch-generation]` 等のラベル付き Issue を自動起票/更新する。新しい抽象化レイヤーを増やさず既存パターンを再利用する。
3. **自己修復**: 次回 Routine 実行が自動的にリトライ役を兼ねる（cron の周期そのものがリトライ機構）。追加で「連続 N 回失敗 or 最終成功から生成周期の 3 倍以上経過」を Routine 起動時にチェックし、閾値超過時のみ Issue の優先度を上げる（緊急の追加実行はしない — YAGNI。過剰な自己修復ロジックを先回りで作らない）。
4. **鮮度メタデータ**: JSON に `generated_at`（UTC）を必ず含める（`SP-15` 操作レビュー手順 1 の「データ生成日」表示の元データとしても使う）。**SP-14 時点では UI 表示までは不要**（それは SP-15 のスコープ）だが、フィールド自体は SP-14 のバッチ設計に含めておくことで SP-15 での手戻りを避ける。
5. **API 障害時のフォールバック範囲**: Ecosyste.ms API が完全に落ちている場合、その回の Routine は「今回はスキップ」を選び、既存データの配信続行に徹する。部分成功（一部パッケージだけ取得失敗）の場合は、その回の生成自体を丸ごと不採用にする（部分的に古いデータと新しいデータが混在した JSON をコミットしない — 母集団パーセンタイル計算の整合性が壊れるため）。

### 1. S3 バルクダンプ全量処理 vs REST API 個別呼び出し のコスト・実現可能性比較

3 方式で比較する（②は当初想定していなかったが実測 b で判明した第 3 の道）。

| 方式 | リクエスト数 | 転送量 | レート制限適合 | 判定 |
|---|---|---|---|---|
| ① S3 バルクダンプ全量処理 | 1 ファイル | 未計測（全 registry 込みで過去実績 13.1M パッケージ分、npm 単体は不明） | 無関係（S3 は Ecosyste.ms のレート制限外） | **f/g により匿名アクセス自体が拒否**され現状不成立 |
| ② REST 個別呼び出し（1 パッケージ = 1 リクエスト） | npm 5,760,152 件 | 小（1 件 ≈ 数 KB〜数十 KB） | 5,760,152 / 5,000 req/h ≈ **1,152 時間 ≈ 48 日** | **完全に非現実的**（バッチの実行時間として成立しない） |
| ③ REST **一覧エンドポイント**をページネーション（`per_page=1000`） | 5,760,152 / 1,000 ≈ **5,761 リクエスト** | **≈135MB × 5,761 ページ ≈ 778GB** | リクエスト数はほぼ 1 時間分の枠に収まる（わずかに超過するため 2 時間で分割） | **リクエスト数は現実的だが、転送量（≈778GB）が新たなボトルネック** |

**結論**: ②（個別呼び出しで全量走査）は数値上ありえない。①（S3）は現状アクセス不能（§3 参照）。③（一覧 API のページネーション）は **レート制限の観点では現実的**（リクエスト数は 5,761 で 1〜2 時間枠に収まる）が、**転送量 778GB がそのままでは重すぎる**。この転送量は `repo_metadata` / `keywords_array` / `funding_links` / `issue_metadata` 等、Gem Index の計算に不要な大きいフィールドが 1 件 ≈135KB のほとんどを占めていることが原因（実測 c の `rankings` 自体は数百バイト）。**フィールド絞り込み（`fields=` 相当のクエリパラメータの有無）を round2 で確認できれば、③の転送量は 1〜2 桁圧縮できる見込み**（未確認・要検証事項として提起する）。

### 2. 母集団パーセンタイル計算に必要な件数 ×レート制限 5000req/hour の整合性（数値検証）

- npm 全体の母集団件数: **Ecosyste.ms 視点で 5,760,152 件**（実測 a）。ADR 0014 §2.6 は「母集団を npm 全量で閉じて計算し、サンプリングしない」ことを不変条件としているため、この件数を割り引くことはできない。
- **自前でパーセンタイルを計算する場合**（＝母集団全件のスコアを収集してソートし直す場合）: 上記③の 5,761 リクエスト・778GB が必要件数。
- **一方、`rankings` フィールド（実測 c・d で npm 内で閉じて事前計算済みと確認）をそのまま使う場合**、自前でのパーセンタイル再計算は不要になる。この場合に必要なのは「候補として提示しうるパッケージの `rankings` を読む」ことだけであり、件数は候補プールの規模（ADR 0014 §5.3.2 の「上位数百〜数千件」）に縮小する。
  - 例: 候補プール 5,000 件を `per_page=1000` の一覧 API で取得 → **5 リクエスト**（体感ゼロコスト。5,000 req/h の 0.1%）。
  - ただし「候補プールをどう選ぶか」自体が母集団全体を見ないと決められない（後述 §3 の circularity）。

**数値としての結論**: 個別 REST 呼び出しでの母集団全量走査（48 日）は 5000req/h と整合しない。一覧 API のページネーションなら**リクエスト数としては整合する**（5,761 req ≈ 1〜2 時間）が、**転送量 778GB という別の制約が新たに発生**するため、「整合する／しない」は一次元のレート制限だけでは判定できない、という点を報告する。

### 3. S3 バルクダンプの bot 保護回避策、および API 経由での母集団パーセンタイル構成の具体案

**回避策の探索結果（本ラウンドで実施・すべて不成立）**:
- open-data ページは Anubis（JS 実行必須の proof-of-work 型）で保護されており、単純 HTTP GET では突破不可（実測 e）
- S3 バケットへの直接アクセス（ルート一覧・推測ファイル名への GetObject）はいずれも `AccessDenied`（実測 f/g）。これは Anubis 由来のブロックではなく **S3 バケットポリシー自体が匿名アクセスを拒否している**ため、Anubis を回避しても解決しない可能性が高い
- 本セッションには `aws` CLI が未導入で、AWS SigV4 署名済みリクエスト（`--no-sign-request` 含む）での再検証は未実施。生 curl の匿名 GET と署名済みリクエストで挙動が変わる可能性はゼロではないため、**「S3 は完全に不可能」と断定はしない**（round2 で `boto3`/`aws-cli` 導入後の再検証を推奨）

**「無ければ API 経由でどう構成するか」の具体案（本命として提案）**:

1. **`GET /registries/npmjs.org/packages?sort=dependent_packages_count&order=desc&per_page=1000&page=N` を全ページ走査**し、各レコードの `rankings.dependent_packages_count` と `rankings.stargazers_count`（npm 内で閉じて Ecosyste.ms が事前計算済み・実測 d で裏付け済み）をそのまま Gem Index の入力にする。**自前でパーセンタイルを再計算しない**（ADR 0009 §2.2「既存スコアを再実装しない」の精神とも整合）。
2. **転送量対策**: レスポンスをストリーミングパース（`ijson` 等）し、`name` / `dependent_packages_count` / `rankings` / `repository_url` 等 Gem Index に必要な数十バイト〜数百バイトだけを抽出してから残りを即破棄する。これにより **メモリ・ディスク使用量は転送バイト数（778GB）ではなく抽出後のデータ量**（5.76M 件 × 数百バイト ≈ 1〜2GB 相当）に抑えられる（転送そのものは発生するため帯域コストは残るが、ストレージ・後続処理コストは実用範囲に収まる）。
3. `rankings` に **star 側のパーセンタイルも含まれる**ため（実測 c）、「dependents 降順」以外の追加ソートは不要 — 1 回のフルスキャンで Gem Index = f(rankings.dependent_packages_count, rankings.stargazers_count) を全件計算できる。
4. **健全性フィルタ（`criticality_score`）** はこの一覧エンドポイントには含まれていない（未確認）ため、別経路（OpenSSF の公開データセット等）との突合が別途必要 — ADR 0014 §5 未確定事項 4 と同一の宿題として残る。

### 4. D-28「Cloudflare 外のセッション / Routine の cron で回す」の実装形（具体案）

**現状で GitHub Actions が使えない**（`CLAUDE.md` / `D-23`）ため、D-28 の「セッション / Routine の cron」は文字どおり **Claude Code Scheduled Tasks（本リポジトリの `docs/routines/` 配下のルーティン定義）** を指すと解釈するのが唯一整合する読み方。

- **ルーティン定義**: `docs/routines/gem-index-batch-routine.md` を新設し、`sprint-cycle-routine.md` と同じ形式（発火間隔・担当スキルの記述）で登録する。実行頻度は §2 の実測（フルスキャンに 1〜2 時間・レート制限枠を跨ぐ）を踏まえ **週次**を提案（S3 の 2〜4 ヶ月更新サイクルよりむしろ高頻度に鮮度を保てる副次効果がある）。
- **実行スクリプト**: `tools/generate_gem_index.py`（新規）。処理は 4 フェーズに分割し、`checkpoint` スキルのパターン（Phase 境界で git commit）で長時間処理のタイムアウト耐性を持たせる。
  1. **fetch**: 一覧 API を `per_page=1000` でページネーションしながらストリーミングパースし、必要フィールドのみを中間ファイル（例 `content/data/_intermediate/npm-rankings-{date}.jsonl`）に追記
  2. **compute**: 中間ファイルから Gem Index（= `rankings.stargazers_count − rankings.dependent_packages_count`。実測 h の向き（0=最上位）に基づく符号は round2 で最終確定）を計算し、上位候補を抽出
  3. **filter**: 健全性シグナル（`criticality_score` 等・別途取得）で足切り
  4. **publish**: 出典メタデータ（`D-29`: `source`/`license`/`source_license_url`/`generated_at`）を含む最終 JSON を `public/data/gems/npm/latest.json`（想定パス）へ書き出し
- **長時間実行対策**: `session-safety-rules.md` の「1 ターン最大 8 ツール呼び出し」制約に対し、fetch フェーズは `Bash(run_in_background: true)` で実行し、`Monitor` で完了を待つ（ポーリング sleep 禁止）。5,761 リクエスト・778GB という規模を踏まえ、**1 回のルーティン発火で完走しない場合は ADR 0014 §5.3.2 の「3 回の firing を跨ぐ分割」と同じ規律**（中間ファイルを commit して次回発火で再開）を適用する。
- **反映**: 生成した静的 JSON は通常の作業ブランチ → PR（`pr-review-flow-summary.md` のフロー）→ マージ → 既存の wrangler デプロイパイプラインで Static Assets として配信（D-28 の「git commit → デプロイで丸ごと差し替え」をそのまま踏襲、Worker 実行時書き込みなしなので `D-18` 抵触なし）。
- **SPOF 無害化**: バッチ失敗時は既存 JSON がそのまま配信され続ける（鮮度劣化のみ・配信停止しない）。`generated_at` を見て閾値（例: 10 日超）を超えたら次回ルーティン発火時に自己修復（再実行 + 失敗時は Issue 自動起票）。

---

### この分析が他の論点に与える影響（要 round2 検討）

- ADR 0014 は D-28 で「S3 バルクダンプを用いる」と明記しているが、本ラウンドの実測では **S3 は匿名アクセスが拒否され、REST 一覧 API + 事前計算済み `rankings` の方が現時点でアクセス可能**という逆転した根拠が得られた。データソースをどちらにするかは ADR の記述を上書きしうる論点のため、他レンズの検証（特にライセンス・帰属表示レンズ）と突き合わせて判断してほしい。
- 転送量 778GB という数字は「フィールド絞り込みができるか」が未確認のままの上限値であり、round2 で `fields=` 系パラメータの有無を確認できれば大きく圧縮できる可能性が高い。

## 1. データソース変更が既存ドキュメントに与える影響

## 2. 「rankings フィールドは npm 内で閉じて計算済み」という data_pipeline の立証と、data_integrity の警告の並立

### 相互矛盾のように見える記述

**data_integrity の主張（§1）**:
- 「`rankings` フィールドの母集団スコープ・極性が未検証であり危険」
- 「自前パーセンタイル計算を基本線とすべき」

**data_pipeline の実測（実測 d）**:
- `ecosyste-ms/packages` の GitHub ソースコードを確認し、`rankings` が `registry` 経由で npm 単独スコープで計算されていることを立証（コード引用: `rankings[:stargazers_count] = registry.top_percentage_for(...)`）

### 実は矛盾していない理由

**data_integrity は「立証できるまでは信用するな」という stance** → 正当性あり（vendor blackbox への依存排除）。
**data_pipeline は「立証した」という fact** → 同じく正当性あり。

**この並立がもたらす判断点**:
- `rankings` を直接使う → リクエスト数 5,761・転送量 778GB（フィールド絞り込み未確認）
- 自前計算に切り替える → リクエスト数は同じだが、メモリ・後続処理は npm 全量走査に必要（data_integrity §2 参照）

**constraints_guard の指摘が的確**: 「論点 B（rankings の母集団スコープ確認）が sp:8 見積もりを左右する」。data_integrity の方法論（手段 A: ソースコード確認）は既に data_pipeline が実施済みで結果（GitHub ソース確認で npm 内スコープ立証）が出ている。

### 推奨アクション

1. **data_integrity の手段 A（ソース確認）は既に data_pipeline が実施済み** → round 2 では「GitHub ソースの当該部分を引き継ぎ、極性（0=最上位 vs 1=最上位）の最終確認」に焦点を絞るべき（実測 h で「0=最上位推定」との note 有り）。
2. **「rankings を信用する」の最終判断は data_integrity の手段 B（クロスエコシステム比較）で補強** → npm と PyPI のペアで相互検証するのは data_pipeline が Phase 2 に進む際の自信につながる。

## 2. concession: 極性（0=最上位）の矛盾指摘も、data_pipeline の実測 h で説明可能と判明

round1 で私は「chalk の `rankings.dependent_packages_count=0.0005476` が chalk の実際の人気度と矛盾する」と指摘したが、これは data_pipeline の実測 h（typescript: `dependent_packages_count=488,056`（実利用トップクラス）に対し `rankings.dependent_packages_count=0.0` → 0.0 が最上位という向き）によって **矛盾ではなく、単に「0 に近いほど上位」という向きの convention だった**ことが判明した。chalk の 0.0005476 はむしろ「被依存数で上位 0.05%」という筋の通った値であり、round1 の指摘（矛盾の指摘）はここで撤回する。

## 3. rebuttal（軽微・予防的）: 向きの反転は式の符号設計に事故のリスクを残す

ただし、この「0=最上位」convention と、ADR 0009 の文言「被依存数のパーセンタイル順位 − star のパーセンタイル順位」が素直に想定する **「高い値=多い方」という自然な convention** は逆向きである。この点を数式で確認する。

- ADR 0009 が意図する式（自然な convention。percentile が高い = その指標が多い）:
  `Gem Index = percentile_dep(自然) − percentile_star(自然)`
- Ecosyste.ms の `rankings`（0=最上位 convention）から自然な convention へ変換すると:
  `percentile_dep(自然) = 1 − rankings.dependent_packages_count`
  `percentile_star(自然) = 1 − rankings.stargazers_count`
- 代入すると:
  `Gem Index = (1 − rankings.dependent_packages_count) − (1 − rankings.stargazers_count) = rankings.stargazers_count − rankings.dependent_packages_count`

→ data_pipeline が §4 で提案した式（`rankings.stargazers_count − rankings.dependent_packages_count`）は、**両軸が同じ極性で反転しているために減算で自動的にキャンセルされ、ADR 0009 が意図する式と数学的に一致する**。式そのものは正しいと確認できた。

**しかしこれは「たまたま両辺が同じ向きに反転しているために結果的に正しい」だけであり、直感的には正しく見えない（`rankings.stargazers_count` を単独で「star が多いほど大きい値」と誤読するとバグを埋め込む）。** 実装時に以下 2 点を必須にすることを提案する（これは対立ではなく、data_pipeline の設計への追加要求）。

1. 実装コード（`tools/generate_gem_index.py` の compute フェーズ）に、上記の変換式（`1 − rankings.*` → キャンセル）をコメントとして明記する。「なぜ `star − dep` の順で引き算するのか」を将来の実装者が rankings の生値だけを見て誤読しないようにする。
2. **golden test を必須にする**: typescript（`rankings.dependent_packages_count=0.0`, `rankings.stargazers_count=0.0505` → Gem Index ≈ +0.05・被依存/star とも上位のため中立に近い正の値）と chalk（`rankings.dependent_packages_count=0.0005476`, `rankings.stargazers_count=0.6435` → Gem Index ≈ +0.64・被依存は上位だが star は相対的に低い＝典型的な「隠れた名品」寄りの高い正の値）の実測ペアを単体テストの固定値として組み込み、符号を取り違えるリグレッションを機械的に検出できるようにする。

## 4. 新たな未解決論点（data_pipeline の実測ではまだ解消されていない・round1「残す論点」の延長）

### 反論 1（rebuttal）: 「Routine cron 一択・週次〜月次」は転送量 778GB / 5,761 req という新事実の下でも両立するか

**結論: 両立するが、両立の仕方は「どちらのデータ取得方式を採るか」で全く別物になる。頻度の議論を単一の数字で語るのは不正確だった。**

### 反論 2（rebuttal）: 778GB / 1〜2h の自前計算案が Routine cron・D-15 と両立するための追加要件

data_pipeline §4 の実装案（fetch → compute → filter → publish の 4 フェーズ、`checkpoint` スキルで中間ファイルを commit）は方向性として妥当だが、**D-15「運用の手離れ」を満たすには以下 2 点が未確認のまま残っている**。これを満たさない限り自前計算案は「Routine cron 一択」の前提を崩す。

1. **レート制限のペーシングが完全自動でなければならない**: 「2 時間で分割」が人間の再開操作を要する設計だと、D-15 が禁じる「人手が残る定常作業」が発生する。バッチスクリプト自身が時間帯をまたいで sleep/backoff し、無人で完走する実装であることを明記してほしい（`Bash(run_in_background: true)` + `Monitor` は起動側の話であり、レート制限待機そのものの自動化とは別問題）。
2. **中間ファイルの commit 先はマージ前の作業ブランチ/PR に限定する**: fetch フェーズが複数 firing にまたがって中間ファイル（`content/data/_intermediate/npm-rankings-{date}.jsonl`）を commit する場合、**そのブランチが `main` にマージされるのは publish フェーズ完了・バリデーション通過後のみ**であることを設計上保証する必要がある。そうでないと、fetch/compute 途中の firing でクラッシュした際に不完全な中間データが `main` 経由でデプロイされるリスクが生まれ、round1 で私が要求した「部分成功時は丸ごと不採用にする」というフェイルクローズド原則が崩れる。data_pipeline 案の 4 フェーズ構成自体はこの原則と両立可能だが、**「commit のタイミングと対象ブランチ」を明示的に設計に書き加えることを依頼する**。

この 2 点が満たされるなら自前計算案も Routine cron・D-15 と両立する。満たされない/確認できない場合は、頻度をさらに下げる（月次）か、下記の rankings 信頼案へ倒すことを推奨する。

### 反論 3（rebuttal・本題）: data_integrity の「rankings 危険」と data_pipeline の「rankings そのまま使える」— 制約レンズからの判定

data_integrity が round1 で最優先に提案した検証手段は「**手段 A: Ecosyste.ms のソースコードで算出ロジックを直接確認する**」だった。data_pipeline は本ラウンドでまさにこれを実行し、`ecosyste-ms/packages` の `package.rb` `load_rankings` で `registry.top_percentage_for(self, :stargazers_count)` という **registry（= npm）単位で閉じた計算**であることをソースから確認した（実測 d）。

**この判定が D-15 / Workers Free CPU 予算に与える影響を評価する:**

- **D-15 への影響は極めて大きい**: rankings 信頼案が採用できれば、バッチは「サーバー側ソート済み上位ページを数リクエスト取得するだけ」に縮小し、data_integrity が提案した Stage1/Stage2/Stage3 の自前パイプライン（母集団全件保持・混入防止の単体テスト・依存関係の静的検査まで要求する重い設計）は**まるごと不要になる**。sp:8 の「薄いスライス」方針（round1 で私が指摘した論点）にとって、これは実装コストを 1〜2 桁圧縮する差であり、D-15 の「定常作業の一覧化・自動化」の対象そのものが小さくなる（自動化すべき作業が少なければ手離れの実現も容易になる）。反論2で挙げた「2 時間に及ぶレート制限ペーシングの完全自動化」「中間ファイルのブランチ隔離」という追加要件も、rankings 信頼案なら実質的に消える(5 リクエストなら 1 レート制限枠内に確実に収まり、複数 firing にまたがる中間状態も発生しない)。
- **Workers Free CPU 予算への影響は「ない」**: これは論点を混同しないよう明示しておきたい。ADR 0014 §2.2 により並べ替え計算はどちらの方式でもクライアント側で行われる設計であり、rankings をそのまま使うか自前計算するかは **バッチ側（Cloudflare 外）の内部実装の違いに過ぎず、Worker の CPU 消費には一切影響しない**。round1 で私が出した CPU 予算の判定（✅ 適合・SSR で並べ替えない限り問題なし）は、この論点の決着とは独立に成立し続ける。

**私の推奨（sp:8 スコープの観点から）**: rankings 信頼案を主設計として採用し、data_integrity の Stage1/2/3 自前計算パイプラインは「極性検証が失敗した場合のフォールバック」として**設計ドキュメントに残すだけに留め、今回は実装しない**（YAGNI・CLAUDE.md「1 箇所しか使わない抽象化レイヤーを先回りで追加しない」）。極性の検証自体は data_pipeline が示した通り数サンプルの追加確認で足り、778GB の全件走査は不要である。

**data_integrity への確認依頼**: 「vendor のブラックボックス値は後から定義が変わっても検知できない」という残存懸念（round1 §4 末尾）はスコープ論点とは別の運用リスクとして理解した。これは自前計算パイプラインを常設する理由にはならず、**軽量なサニティチェック**（例: 既知の主要パッケージ数件の rankings 順位が想定範囲内か・レスポンスの `rankings` キー構成が変化していないかを Routine 実行時にアサートする）で足りると考えるが、この代替で懸念が解消するか意見を聞きたい。

## data_pipeline round2: rebuttal / concession

### data_integrity への rebuttal（論点B: rankings の母集団スコープ・極性）— `top_percentage_for` の実装を特定し決着させた

`data_integrity` が「最優先・決定的」と位置づけた**手段A（ソースコード確認）を round1〜round2 で完遂**し、呼び出し元（`package.rb`）だけでなく **`top_percentage_for` 自体の実装本体**（`registry.rb`）まで特定できた。

```ruby
# registry.rb
def top_percentage_for(package, field)
  return nil if package.send(field).nil?
  Rails.cache.fetch("top_percentage_for/#{id}/#{field}/#{package.send(field)}", expires_in: 1.day) do
    packages.active.where("#{field} > ?", package.send(field)).count.to_f / packages_count * 100
  end
end
```

これで **2 つの論点が同時に、統計的推論ではなく実装の引用として確定する**。

1. **母集団スコープ**: `packages`（＝ `registry has_many :packages`）と `packages_count` はいずれも `registry`（= npm）に属するパッケージ集合に限定される。全レジストリ横断ではありえない。**論点B は npm 単独スコープで決着**。
2. **極性と値域**: `count(該当フィールドが自分より厳密に大きいパッケージ数) / 全体件数 × 100`。**値域は 0〜100（0〜1 ではなく百分率）、0 に近いほど「自分より上位が存在しない＝最上位」、100 に近いほど「ほぼ全員が自分より上位＝最下位」**という向き。

**round2 中盤の自己訂正の経緯（透明性のため記録する）**: 私は round2 序盤で `is-thirteen`（`rankings.dependent_packages_count=1.6345`）や `before-after-hook`（`rankings.stargazers_count=5.366`）が **1.0 を超えている**ことを見て「`[0,1]` の percentile という仮説は誤りだった」と一度 **撤回**しかけた。しかし `top_percentage_for` の実装本体を特定した結果、これは仮説の誤りではなく **単に値域が `[0,1]` ではなく `[0,100]`（百分率）だった**ことが原因だと判明した。`5.366` は「5.366%（上位 5.4 パーセンタイル相当）」として何ら矛盾しない正常値である。**この撤回は撤回する**（元の「値が小さいほど上位」という極性の理解は正しかった。誤っていたのは私の値域の解釈だけ）。

**ADR 0009 §2.1 の「パーセンタイル順位の差」への写像も確定できる**: `top_percentage_for` は「上位からの順位割合（0=最上位）」なので、通常の意味でのパーセンタイル（大きいほど上位）に変換すると `percentile(x) = 100 − rankings[field]`。ADR 0009 の Gem Index = `percentile(依存数) − percentile(star)` に代入すると

```
Gem Index = (100 − rankings.dependent_packages_count) − (100 − rankings.stargazers_count)
          = rankings.stargazers_count − rankings.dependent_packages_count
```

となり、**round1 で私が提案した式（符号反転前後の定数項は打ち消し合う）がそのまま ADR 0009 の定義と数式的に等価であることが証明できた**。よって round1 の「rankings をそのまま Gem Index の入力に使ってよい」という結論を、実装コードの裏付け付きで維持する。

### data_integrity への rebuttal（自前パーセンタイル計算パイプラインの必要性）

`top_percentage_for` の実装が Ecosyste.ms 内部で **キャッシュ付きの単純な `COUNT(*) WHERE field > x`** であること自体もわかった。これは自前実装（data_integrity §2 の `rank_asc` 二分探索方式）と **アルゴリズム的に同値**（順序統計量の相対位置を数える点で同一）であり、Ecosyste.ms が「別の定義」を使っているわけではない。したがって data_integrity が懸念していた「ベンダーのブラックボックスが ADR 0009 の定義とズレている可能性」は、**実装レベルで整合していると確認できた**。

一方で、data_integrity の Stage1〜3 分離という「母集団を絞らせないためのコード構造」提案には引き続き同意する（concession）。ただし入力を **S3 バルクダンプ（round1 実測: `AccessDenied` で不成立）や REST 一覧 API の全量ページネーション（round1 実測: 5,761 リクエスト・約 778GB）に置く必要はない** — `rankings` は Ecosyste.ms 側で **日次キャッシュ済みの事前計算値**（`expires_in: 1.day`）として個々のパッケージレコードに同梱されているため、我々のバッチが母集団全体をスキャンし直す必要がない。Stage1（母集団パーセンタイル計算）に相当する処理は **Ecosyste.ms 側で完了済み**であり、我々のバッチは Stage2（健全性フィルタ）・Stage3（候補プール抽出）だけを実装すればよい。これにより 778GB の転送量問題も同時に解消される（候補プール数百〜数千件分の `rankings` を読むだけで済む）。

**唯一残る留意点**: `Rails.cache.fetch(..., expires_in: 1.day)` なので `rankings` の鮮度は最大 1 日ずれる可能性がある。ADR 0014 §2.2 が要求する「日付が変わると顔ぶれが入れ替わる」のはクライアント側の日付シード選出であり、`rankings` 自体の 1 日ラグは実害にならないと判断するが、念のため次ラウンドで docs_trace / constraints_guard の見解も聞きたい。

### constraints_guard への回答（論点Bの優先解決依頼・778GBの現実性）

- **論点B**: 上記のとおり `top_percentage_for` の実装引用により **スコープ・極性・ADR 0009 定義との数式的等価性の 3 点を同時に決着**させた。constraints_guard が「sp:8 の実現可能性を左右する」と位置づけた最優先事項は解消できたと考える。
- **778GB の現実性**: ご指摘の懸念は正しかったが、原因の理解を修正したい。「REST 全量ページネーションで自前計算する」場合にのみ発生するコストであり、`rankings` を信頼して直接使う設計（今回決着した内容）ではそもそも発生しない。S3（`AccessDenied`）・REST 全量自前計算（778GB）の両方を避け、**候補プール規模（数百〜数千件）の個別 `GET .../packages/{name}` または `per_page` 一覧 API 呼び出しだけで完結する**ため、constraints_guard 317行目の想定（「rankings が npm 単独スコープと確認できれば S3 ETL 不要」）がそのまま成立する。
- **バッチ頻度**: `rankings` が Ecosyste.ms 側で 1 日キャッシュである実測を踏まえ、**週次〜月次の再取得で十分**という constraints_guard の提案に同意する（concession）。むしろ頻度を上げても `rankings` 自体は 1 日単位でしか更新されないため、必要以上に高頻度化する理由はない。
