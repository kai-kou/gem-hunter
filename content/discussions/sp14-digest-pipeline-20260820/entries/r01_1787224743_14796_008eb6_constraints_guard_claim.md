## constraints_guard round1: 制約・リスク判定

### (1) D-14 / D-18 / D-27 境界・NFR-21・Workers Free CPU 10ms を 1 件ずつ判定

| 制約 | 判定 | 根拠・注意点 |
|---|---|---|
| **D-14**（個人情報ログ禁止） | ✅ 条件付き適合 | バッチはセッション/Routine cron（アプリ外）だが、Ecosyste.ms のパッケージメタデータには maintainer 情報（メール等）が含まれうる。**静的 JSON に含めてよいのは package 名・`owner/repo`・被依存数・star 数・Gem Index・Scorecard スコアの数値/識別子のみ**とし、maintainer 個人情報はスキーマから明示的に除外すること（D-29 の「生テキスト再配信しない」とも整合）。バッチのログ自体も進捗（件数・エラー種別）に限定し、個々のユーザー識別子は扱わないので通常は抵触しない。 |
| **D-18**（永続ストア不採用）+ **D-27 境界注記** | ✅ 適合（設計通りなら） | 境界判定基準は「Worker が実行時にそのファイルへ書き込むか」。バッチ生成 JSON は git commit → デプロイで丸ごと差し替える読み取り専用アセットであり **D-18 の対象外と確定済み**（open-questions.md 349行目）。実装時の唯一の落とし穴: 実装が楽だからと KV/R2/D1 に置き換えない（Worker が実行時に read/write するインフラを使った瞬間 D-18 に抵触する）。Static Assets 経由の配信に固定すること。 |
| **NFR-21**（PaaS 固有 API への依存最小化） | ✅ 適合 | バッチスクリプト自体は Cloudflare 上で動かない（D-28）ためアプリランタイム制約の対象外。Worker 側は既存の Static Assets 配信の枠内に収まる限り新規の Cloudflare 固有 API を増やさない。**要確認**: JSON 読み込みを `env.ASSETS` 等の binding 直参照にせず、Next.js 標準の静的 import / public 配信規約に寄せられるなら NFR-21 によりそちらを優先。 |
| **Workers Free CPU 10ms/invocation** | ✅ 適合（ADR 0014 §2.2 のとおり実装される前提） | ADR は「ランキングの並べ替え計算はクライアント側」と明記済み。**判定条件**: 日付シードによる「今日の 5 件」選出・並べ替えロジックが SSR（Server Component / Node ランタイム）側で行われないこと。もし SSR 側で候補プール全件を読み込んで並べ替えてから返す実装にすると、候補プールが「数百〜数千件」規模でも CPU 予算を圧迫し `D-19`（実測超過 → Paid $5 手続き）を早期に誘発しうる。**実装ガード**: Worker/SSR は候補プール JSON をそのまま（またはエッジキャッシュ済みのまま）返す/埋め込むだけに留め、並べ替え・上位 5 件抽出は必ずクライアント JS で行う設計を維持すること。 |

### (2) CC BY-SA 4.0 ShareAlike の継承範囲と UI 帰属表示の最小要件

- **継承範囲の最終判断は今回のスコープではない**: `D-29` が明記する通り、ShareAlike の適用範囲の最終判断は `R-8`（GitHub 利用規約の一次確認）と同じタイミング＝**第三者へ公開するかを決める `M-4` ゲート**に合わせる。`M-4` はまだ「決めるゲート」のままであり通過していない（`D-16` で「事業者選定ゲート」→「第三者公開ゲートへ性質変更」と明記されているのみ）。したがって **SP-14 時点で ShareAlike の継承範囲そのものを確定させる必要はない**。専門チームがここに時間を使うのはスコープ逸脱（sp:8 肥大化リスク）。
- **一方、今すぐ必須な最小要件は `D-29` で既に確定済み**（保守的な下限）。SP-14/SP-15 の実装が満たすべき具体項目:
  1. 配信 JSON のトップレベルに `source` / `license`（`CC BY-SA 4.0` 固定文字列）/ `source_license_url` / 改変の明示（例: `derived: true` や `transformations` 説明）を必須フィールドとして持つ。
  2. UI 側の出典表示（`Data via Ecosyste.ms（CC BY-SA 4.0）` + ライセンスリンク）は **SP-15 の操作レビュー手順 1**（`user-story-map.md` 518行目）に対応要件として明記済み。SP-14 単体では UI 表示までは必須ではないが、**JSON スキーマにメタデータを含める作業は SP-14 側（バッチ設計）でやっておくべき**（SP-15 で UI に出すだけにするため、手戻りを避ける）。
  3. Ecosyste.ms の **生テキスト（description 等）は再配信しない**（D-29）。候補プール JSON に description 等の自由記述文字列を含めるなら GitHub API 由来のものに限定し、Ecosyste.ms 由来のものは数値・識別子・自作の派生値（Gem Index・パーセンタイル順位）に限定すること。
- **Gem Index（自作の合成スコア）自体への ShareAlike 継承の扱い**: 現状の `D-29` は「派生値」を明示的に再配信対象として容認しており（生テキストではなく数値なので保守リスクが低い）、Gem Index を CC BY-SA でライセンスし直す義務までは要求していない。ただし出典メタデータに「この値は Ecosyste.ms の被依存数データから算出した派生指標である」という **改変の明示**を含めることが `D-29` の必須要件なので、スキーマ設計時に落とさないこと。
- **OpenSSF Scorecard のデータライセンス**は今回の実測済み前提事実に含まれていない。健全性フィルタに Scorecard スコアを合成する場合、そのライセンス条件も別途確認要（担当は data_integrity 想定・私のレンズでは「要確認」の指摘に留める）。

### (3) バッチ実行主体の選択肢と D-15「運用の手離れ」

D-15: デプロイは git push / マージのみをトリガーとし、手動デプロイ経路を作らない。人手が残る定常作業は一覧化し自動化する。

| 選択肢 | D-15 適合性 |
|---|---|
| **セッションの都度手動実行**（人間や Claude が気づいたときに `npm run generate-digest` 的コマンドを都度叩く） | ❌ 不適合。定常作業として人手起点の再実行が残り、D-15 の「人手が残る定常作業を一覧化し自動化する」に反する。ブートストラップ時の 1 回限りの初回生成にのみ許容し、**恒常運用の一次経路にしない**。 |
| **Claude Code Scheduled Tasks / Routine の cron**（`D-28` が明示する「セッション / Routine の cron」） | ✅ 適合。本プロジェクトは既に `R-1` ルーティン稼働（`session-concurrency-rules.md` に明記）があり、GitHub Actions 制限中の CI/デプロイも同様にセッション実行へ委譲している（`D-23`）。同じ枠組みで日次/定期のバッチ生成を Routine 化すれば「起動は人手を介さない・定期実行」を満たし D-15 と両立する。生成結果は commit → PR → 自動マージ → デプロイの既存フローに乗せる（**新しい手動デプロイ経路を作らない**）。 |
| **GitHub Actions の scheduled workflow** | ⚠️ 現状は使えない（`D-23`: Actions 制限中）。制限解除後は代替候補になりうるが、今は選択肢から外れる。 |

**推奨**: Routine 化 一択。ただし **実行頻度は「日次」に固定しない**ことを提案する（下記(4)(5)とも関連）。ADR 0014 §2.2 が要求する「日付が変わると入れ替わる」のは **候補プールの中身ではなく日付シードによる並び順**であり、クライアント側計算で担保される。候補プール自体（Gem Index の元データ）の鮮度は S3 ダンプが 2〜4 ヶ月毎更新である以上、**バッチの再生成頻度は週次〜月次で十分**（要 data_pipeline 確認）。頻度を下げるほど Ecosyste.ms レート制限リスク・cron 実行失敗の露出機会・運用の手間が減り D-15 に有利。

### (4) SPOF（バッチ停止・API 障害）の無害化・自己修復の実装方針

D-28: 「SPOF は無害化 + 検知して自己修復で対処し、配信自体は止めず鮮度のみ劣化させる」。

**具体方針**:
1. **無害化（フェイルクローズド生成）**: バッチは「新しい JSON を生成 → スキーマ・件数のバリデーション通過 → 成功時のみ commit」の順で行う。生成失敗・API 障害・バリデーション不合格時は **既存の commit 済み JSON を一切変更しない**。これにより Worker は常に「最後に成功した生成物」を配信し続け、エラー画面・空配列を絶対に出さない（`D-14` 同様、失敗を配信面に露出させない）。
2. **検知**: Routine 実行の最後に成否を記録する。既存の `[publish-sync]` Issue パターン（`pr-review-flow-summary.md` に実例あり: 反映できないセッションは `[publish-sync]` Issue に記録して沈黙しない）を踏襲し、失敗時は `[batch-generation]` 等のラベル付き Issue を自動起票/更新する。新しい抽象化レイヤーを増やさず既存パターンを再利用する。
3. **自己修復**: 次回 Routine 実行が自動的にリトライ役を兼ねる（cron の周期そのものがリトライ機構）。追加で「連続 N 回失敗 or 最終成功から生成周期の 3 倍以上経過」を Routine 起動時にチェックし、閾値超過時のみ Issue の優先度を上げる（緊急の追加実行はしない — YAGNI。過剰な自己修復ロジックを先回りで作らない）。
4. **鮮度メタデータ**: JSON に `generated_at`（UTC）を必ず含める（`SP-15` 操作レビュー手順 1 の「データ生成日」表示の元データとしても使う）。**SP-14 時点では UI 表示までは不要**（それは SP-15 のスコープ）だが、フィールド自体は SP-14 のバッチ設計に含めておくことで SP-15 での手戻りを避ける。
5. **API 障害時のフォールバック範囲**: Ecosyste.ms API が完全に落ちている場合、その回の Routine は「今回はスキップ」を選び、既存データの配信続行に徹する。部分成功（一部パッケージだけ取得失敗）の場合は、その回の生成自体を丸ごと不採用にする（部分的に古いデータと新しいデータが混在した JSON をコミットしない — 母集団パーセンタイル計算の整合性が壊れるため）。

### (5) sp:8 のスコープ肥大化チェック（SP-14 単体で完結する境界）

`user-story-map.md`（511行目）は既に「データのみ/UIのみの水平分割は採らず、対象 npm のみ・候補プールは上位数百〜数千件に絞ることで sp:8 に収める」と明記済み。この境界を **バッチ設計の議論が壊していないか**を確認した。

- ✅ **候補プール件数の絞り込み**は ADR 0014 §2.6 の不変条件（母集団=npm全量は絞らない、絞ってよいのは表示候補プールのみ）と整合しており、現行のスコープ定義のまま進めてよい。
- 🔴 **最大のスコープ膨張リスクは論点 A/B**（S3 バルクダンプ全量処理 vs REST API）: もし `rankings` フィールドが npm 単独スコープで正しく計算されていることを `data_integrity` が確認できれば、**S3 バルクダンプの取り込みパイプライン構築（数百万〜1,310万件規模のETL）は不要**になり、REST API で候補プール分（数百〜数千件）の `rankings` を取得するだけで完結する。これは sp:8 の「薄いスライス」方針と完全に整合する最小実装であり、**この経路を優先すべき**という制約側からの強い推奨を出す。
- 🔴 逆に `rankings` が複数エコシステム混在と判明した場合、npm 全量に対する自前パーセンタイル計算が必須になり（ADR 0014 §2.6 不変条件）、S3 バルクダンプへの依存が避けられなくなる。補足調査で「bot 保護により open-data ページへの直接アクセス未確認」とあるため、**この経路が technically infeasible なら SP-14 の sp:8 見積もりが崩れる**。フィージビリティが確定しない状態で実装に着手すると `sprint-development-rules.md` `SD-2`/`SD-3` 違反（曖昧なまま進める）になるため、**論点 A/B の実データ検証を実装着手前の最優先タスクとして固定し、結果次第で見積もり再考をユーザーに 1 回だけ確認する**（`D-12`/`SD-3` 第 2 系統: 「rankings が使えるか」で成果物・見積もりが変わる分岐に該当しうる）。
- ✅ PyPI 対応・RSS 本実装・ITP フォールバック本実装・全件表示以上の水平拡張は SP-14 の議論に持ち込まない（ADR 0014 §2.6・user-story-map.md 511行目のとおり SP-15 以降に送る）。バッチのスキーマ設計で「将来 PyPI にも対応できるように」と汎用化しすぎない（YAGNI・CLAUDE.md「1 箇所しか使わない抽象化レイヤーを先回りで追加しない」）。`ecosystem: "npm"` 固定値を持たせる程度の最小限の拡張余地に留める。

### まとめ（他エージェントへの依頼事項）

- **data_pipeline / data_integrity へ**: 論点 B（`rankings` の母集団スコープ確認）を最優先で解決してほしい。ここが sp:8 の実現可能性を左右する。
- **data_pipeline へ**: バッチ頻度を「日次」ではなく「候補プール再生成は週次〜月次、日付シードの並び替えはクライアント側で日次」に分離する設計を検討してほしい（D-15 適合性・レート制限リスクの両方を下げる）。
- **docs_trace へ**: D-29 の JSON 必須メタデータ項目（source/license/source_license_url/改変明示/generated_at）がバッチのスキーマ設計に反映されているかをトレースしてほしい。
