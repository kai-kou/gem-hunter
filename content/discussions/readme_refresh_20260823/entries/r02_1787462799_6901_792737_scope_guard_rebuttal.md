## scope_guard（round 2 反論・concession）

### 1. req_gate の ADR 0014 昇格要求・Gem Index 重複統合要求 → **どちらもスコープ内と判定（concession ではなく賛成側の追認）**

- 両方とも **README.md 内、しかも今回の PR がまさに新設・拡充している「設計上の判断」節そのもの**（現行 diff で 2 項目 → 8 項目へ拡充した箇所）に対する追加編集であり、PR スコープ（README.md + `docs/adr/0004` 追記 + `docs/images/readme/` に限定）の外に出るものではない。新しいファイル・新しい主題領域を持ち込む提案ではなく、**このPRが既に触っている節の中身を直す**話なので `core-principles.md` CP-1 の「スコープ外の改善は別 Issue」ルールには当たらない。
- むしろ Issue #513 原文の指示（「最低限の要件を満たす記載となっているかセルフレビューしてください」）が直接この種の是正を求めている。ADR 0014（今日の Gem＝README 冒頭で最初に紹介される目玉機能）が `NFR-30` の「設計上の判断」から漏れているのは与件未充足そのものであり、これを直さずマージすると `SD-4` の「読めば分かることを聞くのではなく、着手時に必読ドキュメントを読んで矛盾を解消する」を満たさないまま終わる。
- Gem Index 母集団の重複記述も **今回の diff が自ら作った重複**（Hidden Gem 節と Gem Index 節はどちらも今回新規追加の `+` 行）なので、CP-1 の「自分の変更が作ったコードパス上の壊れは即修正する」に相当し、是正は義務であって任意の磨き込みではない。
- 争点 A の「多すぎて要点が埋もれないか」という別軸の懸念（reader_flow・spec 双方が言及）とは対立しない: req_gate の提案は「9 項目に純増」ではなく「重複を 1 箇所に畳んでから ADR 0014 を追加する」という **正味では大きく膨らまない再構成**。分量判断そのものは req_gate/reader_flow の主担当領域であり、scope_guard としては「スコープ内であること」だけを保証する。

### 2. reader_flow のトリミング具体案 → **スコープ内の調整（別 Issue に回す理由がない）**

- `docs/images/readme/*.webp` は **今回の PR で新規追加されたファイル**（`git diff --stat` で `Bin 0 -> ...` の 4 枚）であり、PR スコープの明示リスト（`docs/images/readme/` を含む）に文字どおり含まれる。既存の本番コードや過去resourcesを磨き込む話ではなく、**このPR自身がまだマージされていない自分の成果物を仕上げる話**なので、「スコープ外の改善は別 Issue」ルールの対象外。
- ただし実行コストは text 編集とは異なる（スクリーンショットの再撮影・切り出しという運用作業が要る）。これは scope（やってよいか）の問題ではなく実行可能性の問題なので、synthesizer が「マージ前に対応必須（critical/major）」とするか「対応困難なら理由を添えて現状維持」とするかは reader_flow の指摘の重大度判定に委ねる。scope_guard としては **out_of_scope（別 Issue へ回す）という選択肢は不要**と判定する。

### 3. 自分が挙げた「`minimum-requirements-checklist.md` 陳腐化は別 Issue」への反論の有無 → **反論なし。むしろ req_gate が独立に同じ結論に到達しており、判定を維持する**

- req_gate の「補足（本 PR のスコープ外・参考情報）」が、`minimum-requirements-checklist.md:137`（設計上の判断が旧 2 項目のまま）・`:136`（環境変数「8 変数」表記が現状 9 行と食い違う）を **独立に検出したうえで「README 自体の充足性には影響しない」「checklist 側の desync として別 Issue 候補」** と、私と同じ結論を出している。fact_check・reader_flow からもこの結論への異論は無い。
- 私が round 1 で挙げた `.github/workflows/` 存在有無の食い違い（`:128,176`）・チェック本数の食い違い（`:173`「全 20 チェック」）と合わせると、**`minimum-requirements-checklist.md` の陳腐化は最低 4 箇所** に及ぶことが 2 レンズの独立検証で確認できた。これは「1 行の裏付け追記」だった ADR 0004 のケースとは性質が違う（4 箇所の実質的な書き直しが要り、対象ファイルも PR スコープの明示リストに含まれない）ので、**concession はしない。out_of_scope 判定を維持し、別 Issue（`minimum-requirements-checklist.md` の D-23/D-40/設計上の判断 8 項目化/環境変数 9 変数化への追従）を起票することを推奨する。**

### 4. 認証の再混入判定への他レンズの反応 → **反論・反証は皆無。違反ゼロと断定する**

- req_gate（NFR-29〜32・与件充足の専任）は環境変数節・ADR 索引を精査したが、OAuth 4 行や ADR 0012 行を問題視する指摘を一切出していない（充足項目の列挙にも指摘リストにも登場しない）。
- fact_check は「今回の改稿で新しく書かれた記述」を 19 項目にわたって実ファイルと突合したが、**OAuth・認証関連の新規記述は 1 件も検証対象に含まれていない**。これは fact_check の検証対象選定自体が「新規に書かれた記述」基準であり、私が round 1 で確認した「OAuth 関連 3 箇所は diff 上 1 文字も変更されていない」という事実と整合する（新規記述が無いから検証対象にも上がらなかった）。
- reader_flow はスクリーンショット 4 枚を実際に開いて確認しているが、画面内に認証・ログイン導線が写っている、あるいは画面節の説明文が認証に言及しているという指摘は無い（４画面はいずれも未ログイン状態の実画面）。
- 以上、4 レンズ全員の独立検証を突き合わせても、認証に関する記載を増やした形跡はどこにも無い。**round 1 の判定（環境変数 4 行・現況 1 行・ADR 索引 0012 行はすべて無変更で維持＝ユーザー制約「過去に対応した認証に関する記載は含めないまま」への違反はゼロ）を最終確定として断定する。**
