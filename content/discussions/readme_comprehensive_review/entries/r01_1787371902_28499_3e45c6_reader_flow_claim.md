## 読者導線レンズ: README.md 検証結果

### 前提として実測した事実
- `DEFAULT_LOCALE = 'ja'`（`src/domain/model/locale.ts`）。ルート `/` は `next.config.ts` の `redirects()`（`src/ui/url/locale-redirect.ts`）で `/ja/...` へリダイレクトされる実装。`LOCALES = ['ja', 'en']` で `/en` も正規にサポート。
- LP（`site/index.html`）footer は本番ツールへ **`/ja`（日本語）と `/en`（English）の 2 本を明示リンク**している（`https://gem-hunter.kinamocchi-tech.workers.dev/ja` / `/en`）。README の「使ってみる」は `/ja` の 1 本のみ ＝ **LP と README で言語導線が非対称**。
- LP footer は GitHub リポジトリ根 / `docs/` / `docs/adr/` / `LICENSE` へリンクしており、**README（≒リポジトリ根）への逆導線は成立している**。ただし LP 本文には「スクリーンショット・できること一覧がある」ことを README 側からは示していない（README 5 行目は「紹介ページ」とだけ）。
- `site/assets/img/shot-{mobile,search,digest}.webp` の3枚が LP に既にあり、LP は「PC でも使えます」「いま動いている機能」等の節で画面を見せている。README 本体に画面は一切ない。
- CI は D-23 により存在しない（GitHub Actions 制限中）。README にバッジは無い。

### 1. 冒頭10行の評価（3読者共通）
現行は「1行説明 → 使ってみる(/ja) → 紹介ページ → 旧称注記」の4要素で10行未満。

- **レビュアー**（与件充足・設計判断を確かめたい）: 冒頭から知りたいのは「どこに設計判断とADRがあるか」だが、その導線が無いまま L10 でいきなり `npm ci` 等のローカル開発手順に入る。設計判断節（L64〜）・ADR表（L99〜）まで **54行以上スクロールしないと辿り着けない**。
- **OSS 第三者**: 「検索プラットフォーム」とは分かるが、**何が検索できるのか・Hidden Gem や日次ダイジェストのような差別化機能**が一切書かれていない。LP にはあるが README 単体（GitHub 検索経由・npm 経由等で直接 README に来た場合）ではゼロ情報。
- **コントリビュータ**: 直後が「開発（ローカル）」節なのでここは良好。
- **旧称注記**（L8）は 3 読者いずれにとっても初見で優先度が低い情報（プロダクト来歴のメタ情報）で、10 行という狭い枠を消費している。

### 2. README → LP → 本番の導線順路
- README→LP は成立するが、リンクテキスト「紹介ページ」だけでは **LP に何があるか（スクショ・機能・FAQ・作り）が伝わらず、クリック動機が弱い**。
- LP→README（GitHub リポジトリ根）の逆導線は footer で成立済み。役割分担そのもの（LP=製品ピッチ、README=技術ドキュメント入口）は妥当で、**README にスクリーンショットを重複して埋め込む必要はない**（LP に一任してよい）。ただし README 側がその役割分担を読者に説明していないため、「READMEにスクショが無い」ことが欠落に見えてしまっている。

### 3. スクリーンショット/機能概要の要否
- **埋め込み不要**（LP が専任・重複回避・README 132行がさらに肥大化する）。
- ただし **「LPで何が見られるか」を一言添えるリンク文言の改善は必要**（分量増はほぼゼロ、1行の書き換えのみ）。

### 4. `/ja` 固定の妥当性
- 実装上 `/` は `/ja` にリダイレクトされるため `/ja` を直接指すこと自体は誤りではない。
- しかし **LP は `/ja` と `/en` を両方明示している**のに README は `/ja` のみ ＝ 英語話者の第三者読者に対して非対称。README 側にも英語版へのリンクを 1 行足すべき（与件充足を見るレビュアーには影響しないが、OSS 第三者導線としては欠落）。

### 5. バッジの要否
- **CI バッジは追加すべきでない**（D-23: GitHub Actions が制限中で実 CI が存在しない。バッジを付けると実態と矛盾する虚偽表示になる）。
- ライセンス表記は末尾 L121-132 に文章で明記済みで十分（MIT + NOTICE 対象外の明記があり、バッジ化の実利は薄い）。
- Node バージョンバッジも「Node.js 22 以上が必要」の1文（L12）で足りており、バッジ化は優先度低。
- **結論: バッジは追加しない（現状維持）**。

### 6. 目次・節並び順・132行という分量、docs/README.md との重複
- 目次は無い。GitHub の自動アウトライン機能はあるが、**レビュアーが最優先で見たい「設計上の判断」「ADR」節が中盤以降（L64・L99）に埋もれている**のは目次の欠如というより「開発（ローカル）」「環境変数」という開発者向け詳細（L10-52、43行）が先に来る構成の問題。
- README「## ドキュメント」節（L54-62、5リンク）と `docs/README.md`（全 9 ディレクトリ一覧）の重複は **役割分担として妥当**（README は「最初に読む5点」への厳選、docs/README.md は全体構成）。L56 で相互リンクも張られている。**ここは変更不要**。
- 132行は多すぎるとは言えないが、**優先度の高い情報が後半にある配置**が読者導線上の実害。
