# req_trace（与件・要件充足レンズ）— README.md 突合結果

- 与件 §6（ドキュメント要件）の 3 点＝①セットアップ手順 ②設計上の判断・工夫した点・こだわったポイント ③ AI 利用の方法と範囲。
- `NFR-29`〜`NFR-32` / `AC-11`（`prd.md:367-370,457,541`）が README を対象要件として明示。
- `minimum-requirements-checklist.md` §6（D-1〜D-4）は全項目 ✅ 判定だが、これは「書いてあるか」の充足チェックであり、本レンズは「第三者が追える厚みになっているか」を別軸で検証する。

## 突合結果（項目ごと）

### ① セットアップ手順（README.md:10-41）
- **判定: 充足（軽微な改善余地あり）**。`npm ci` / `npm run dev` / `npm test` / `npm run test:e2e` / `npm run lint` / `npm run format` / `npm run check` を明記（README.md:14-22）。環境変数は 8 変数を表で「用途・未設定時の挙動」付きで記載（README.md:30-39）。第三者が値を推測せず追える形になっている。
- **改善提案**: README.md:28 に「⚠️ 本リポジトリに `.env.example` は存在しない（追加候補として Issue 化を検討する）」という **未解決 TODO の文言がドキュメント本文に残ったまま** になっている。第三者向け成果物としては、①実際に Issue を起票してリンクする ②今回のスコープでは対応しない判断を確定させて「検討する」という宙ぶらりんの言い回しを削る、のどちらかに倒すべき（README 内の「セットアップ」小節・加筆または削除の対象）。

### ② 設計上の判断・工夫した点・こだわったポイント（README.md:64-86, 99-119）
- **判定: NFR-30 の必須要件（`AR-5` を含める）は充足**。「設計上の判断」節に `D-21`（常設 dev 環境を持たない）と `AR-5`（与件対象外の認証を上乗せ）の 2 本が ADR リンク付きで記載されている（README.md:68-86）。
- **主要指摘（争点 C の中心）**: 与件 §6 が求める語は「設計上の判断」「**工夫した点**」「**こだわったポイント**」の 3 つだが、現行の「設計上の判断」節はどちらも「なぜ与件の期待から外れたか／なぜ上乗せしたか」という **弁明・スコープ判断型の 2 件のみ**で構成されている。「工夫した点・こだわった点」として第三者に響く実装判断（例: `ADR 0009` Hidden Gem スコア定義＝被依存数に対する star の残差、`ADR 0008` ページネーション選定の理由、`ADR 0005` Cache Port の YAGNI 例外化、`ADR 0011` i18n 自前実装）は ADR 索引表（README.md:103-119）に **タイトル 1 行のみ**で、本文への昇格がない。
  - ADR 索引だけで「充足」と見なせるかは選択が分かれる（読み手が索引を全部開けば分かる vs README 本文で厚みを示すべき）ため、**この 1 点はブラッシュアップ方針として要合意**（争点 C の主論点として提起する）。
  - 選択肢 A: 「設計上の判断」節に 3 件目として「工夫した点」枠を新設し、`ADR 0009`（Hidden Gem スコア定義）を 1 項目、既存の 2 件と同じ粒度（背景 + 却下案 + ADR リンク）で加筆する。
  - 選択肢 B: 節タイトルを維持しつつ ADR 索引表の該当行（0005/0008/0009/0011）に一言だけ実装意図を添えて「索引で足りる」形に軽く強化する。
  - 推奨: 選択肢 A（NFR-30 の文言「工夫した点・こだわったポイント」は現状ゼロ件のため、索引の一言追記だけでは要件の語义を満たしたと言い切れない）。

### ③ AI 利用の方法と範囲（README.md:88-97, `NFR-31`）
- **判定: 充足**。「AI を利用した範囲と方法」節がスプリント自走・TDD・セルフレビュー・PR 自律化・人間判断領域（A-1〜A-6 / SD-3）・定期運用の 6 点を要約し、`CLAUDE.md` / `docs/rules/` への参照リンクも明記。与件 §6 の「利用方法と範囲」を第三者が追える形で満たしている。追加指摘なし。

### `NFR-32`（ADR 記録・README.md:99-119）
- **判定: 充足**。15 本の ADR を索引し、`tools/check_adr_coverage.py` で `prd.md` §12 との転記整合を機械検証している旨も明記（README.md:101）。索引の妥当性は `docs/adr/` の見出しと目視突合し一致を確認済み（README.md:105-119 と `docs/adr/000N-*.md` の見出し行）。

### 与件 §7 受け入れ基準（README 関連項目）
- 「README にセットアップ手順と設計上の判断が記載されている」（`minimum-requirements.md:135` 相当・`AC-11`）は現状の記載で**最低限は充足**と判定できる（`NFR-29`/`30`/`31` いずれも記載あり）。ただし ② で指摘した「工夫した点・こだわったポイント」の薄さは、与件文言に照らすと「書いてあるが厚みが要件の語彙を十分に代表していない」グレーゾーンであり、AC-11 を「形式充足」から「趣旨充足」に引き上げるならブラッシュアップ対象。
