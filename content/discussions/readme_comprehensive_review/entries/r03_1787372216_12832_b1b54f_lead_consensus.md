## 2. 対立の決着

### 争点 C（「工夫した点・こだわったポイント」の厚み）: **1 件だけ本文昇格する**

`req_trace` は「与件 §6 の要求語彙のうち『工夫した点・こだわったポイント』が実質ゼロ件（現行 2 件は弁明・スコープ判断型）」と主張し、`reader_flow` は「分量より到達コストが問題。増やすなら埋没を悪化させるな」と反論した。**両者は round 2 で `ADR 0009`（Hidden Gem スコア定義）1 件のみの昇格で一致** した（`req_trace` は 3〜4 行、`reader_flow` は 8〜10 行を許容 → 中間の 5〜8 行で確定）。`docs_consistency` も「5 ファイル追加より工夫した点の厚みが本質」と同調。

- **却下**: ADR 0005 / 0007 / 0008 / 0011 の本文昇格（`req_trace` 自身が比較して退けた。弁明トーン・前提知識が要る・独自性が薄い・行数超過）
- **配置**: 「設計上の判断」節の **先頭**（節タイトルへの適合度と、目次から飛んだ読者が最初に工夫点を見る導線）

### 争点 A/F（目次と分量）: **1 行のインライン目次のみ。AI 節の圧縮はしない**

`reader_flow` は自ら 6 項目の箇条書き目次を撤回し **1 行のインラインリンク** に縮小、それに伴い「AI 節を 5→3 項目に圧縮する」提案も **撤回** した（`NFR-31` を犠牲にする価値がないため）。`fact_check` が発見した随伴リスク（圧縮すると `minimum-requirements-checklist.md` の `D-3` 行が静かに陳腐化する）も、圧縮しないことで消える。GitHub の自動アウトラインとの重複という反論は「見出しの先に何があるか分からない」問題には効かない点で部分的に退けられた。

### 争点（docs 追加）: **`domain-model.md` 1 件のみ**

`docs_consistency` は 5 ファイル追加を提案したが round 2 で **`reader_flow` の役割分担論（README は厳選、全体構成は `docs/README.md`）に譲歩** した。ただし `domain-model.md` は「実装時の 3 正本」のうち `application-architecture.md` だけが README にあって片方が欠ける **非対称な欠落** のため、既存文への追記（+0〜1 行）で解消することで一致。

### 争点（デプロイ節）: **新設しない**

`fact_check` の M-3 は、① `NFR-29` の対象 3 カテゴリ（依存インストール・環境変数・起動・テスト実行）に含まれない（`req_trace`）② `preview:*` / `deploy` を叩くのは人間コントリビュータではなくセッション（`reader_flow`）③ ADR 0002 への導線は既存（F-7）の 3 点で **要件外の任意加点** に格下げ。節は作らず、既存セルへの語句追加に留める。
