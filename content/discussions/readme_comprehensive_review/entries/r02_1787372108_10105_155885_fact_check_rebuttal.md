## fact_check ラウンド2: 3 争点の決着

### 争点1: ADR 索引の見出し一致（docs_consistency との対立）— 決着

**再確認した事実**（`docs/adr/*.md` 全 15 本の H1 と `tools/check_adr_coverage.py` を再読）:

- ADR 本体の H1 は例外なく `# ADR NNNN: {タイトル}` の形式（プレフィックスあり）。README の表セルは `{タイトル}` のみ（プレフィックスなし）。**この生の事実自体は docs_consistency の指摘どおり正しい**。
- ただし `check_adr_coverage.py` の `adr_title()`（36-39行目）は正規表現 `r"#\s*ADR\s*\d{4}:\s*(.+)$"` で **プレフィックスを剥がした後の文字列** を「タイトル」として定義し、`check_readme_lists_all_adrs()` はその「タイトル」が README に含まれるかだけを検査する。つまり **この機械ゲート自身が「見出し ≠ 転記対象」「タイトル（プレフィックス抜き）＝転記対象」という定義を採用している**。README の現状（プレフィックス抜きで転記）はこの機械ゲートの定義に完全準拠しており、ゲートは Green のまま通る。
- 加えて README の ADR 列（103-119行目 1 列目）には既に `[0001](...)` のようにリンクと番号が独立して存在するため、タイトル列に `ADR 0001:` を再掲すると同一表内で番号が二重表示される。プレフィックスを外している設計は意図的な冗長排除であり、欠落ではない。

**結論（自分の r1 投稿の訂正を含む）**:
- 自分が r1 で書いた「ADR 本体の H1 見出しと **一字一句一致**」という表現は不正確だった。正しくは「ADR 本体の H1 から `ADR NNNN: ` プレフィックスを除いた **タイトル文字列** と一字一句一致」である。ここは docs_consistency の指摘どおり **concede**（自分の言葉遣いの精度不足）。
- 一方で、これを README 側の「矛盾」「不一致」として扱うことには同意しない。`check_adr_coverage.py` 自身の定義（＝この項目の唯一の機械的な正本）と一致している以上、**README の現状記載は正しい**。修正が要るとすれば「そのまま転記」という言葉が「プレフィックス込みで一言一句」と誤読されうる点だけであり、これは docs_consistency 自身も「影響度: 低」「形式上の不一致」と格付けており評価は一致している。
- **決着**: README 101/103 行目は「各 ADR の見出しから `ADR NNNN: ` を除いたタイトルを転記」に一言足すことを推奨（任意・低優先度）。ADR 索引自体に critical な誤りは無い。docs_consistency の「⚠️ 形式上の不一致 15 件」は severity を上げる指摘ではなく wording 明確化の話として合意する。

### 争点2: C-1（`SESSION_ENCRYPTION_KEY` の未設定時挙動）— critical を維持する

想定される反論「本番では OAuth env 自体が未供給なので実害がない」「README は仕様を書く場所でデプロイ状態を書く場所ではない」を自己検証したが、**両方とも C-1 を弱めない**。

1. **「本番では実害がない」への反論**: C-1 が問題にしているのは *現在の本番状態* ではなく、README の「環境変数」節（NFR-29 のセットアップ手順そのもの）が **これから環境変数を設定する人**（フォーク先の運用者・将来の自分・本番へ OAuth を有効化しようとするセッション）に対して誤った期待を与える点。具体的には「OAuth 3 変数を揃えれば README の記載どおりログイン導線が出る」と読めるが、実際は `SESSION_ENCRYPTION_KEY` を含む計 4 変数の AND 条件（`src/composition/auth.ts:33-35` で確認済み）。**本番が今どうであるかとは独立に成立する記述バグ** であり、「今は実害が無い」は「将来 OAuth 3 変数だけ設定して『ボタンが出ない』とハマる人が出ない」ことを何も保証しない。
2. **「README は仕様を書く場所」への反論は、むしろ critical を補強する**: その通りで、C-1 はまさに「仕様（＝各環境変数の未設定時の挙動）の記載」が実装と食い違っているという指摘であり、デプロイ状態の話は一切していない。この反論は論点のすり替えにならず、むしろ「README は仕様を正確に書くべき場所である」という前提を認めるなら、その仕様記述自体が不正確である C-1 は是正対象として残る。
3. `NFR-29`（README にセットアップ手順＝必要な環境変数を記載する）の対象そのものであり、この節の正確性は与件充足に直結する。

**結論**: critical を維持する。格下げしない。修正は 1 文で足りる軽微な修正（39 行目の挙動説明を「（4 変数すべてが揃って初めてログイン導線が表示される。本行のみ欠落してもログイン導線ごと静かに無効化される）」に補う）なので、重大度と修正コストの低さは両立する。

### 争点3: reader_flow 提案1（AI 節 5→3 項目への圧縮）— NFR-31 / 与件§6 充足への影響を事実面から評価

**まず事実訂正**: reader_flow は「5 項目の箇条書き」と書いているが、README 92-97 行目を数え直すと **6 項目**（スプリント単位の自走 / TDD 主体 / セルフレビュー / PR 作成・マージの自律化 / 人間が判断する領域 / 定期運用）。件数の言及が 1 件ずれている。

**機械ゲートへの影響**: `check_adr_coverage.py` の `check_readme()`（80-83行目）は `re.search(r"^#{2,3} .*AI", readme, ...)` で **見出し文字列に「AI」を含む `##`/`###` 見出しが存在するか** しか見ておらず、箇条書きの項目数・内容は一切検査していない。**3 項目へ圧縮しても機械ゲート（`npm run check` に組込み済み）は Green のまま**。ここは reader_flow の提案を妨げない。

**与件 §6 への影響**: 原文は「開発にAIを利用した場合は、その利用方法と範囲」とだけ要求しており、項目数の下限は無い。3 項目（スプリント自走 / TDD 主体・セルフレビュー / 人間判断領域）に「方法」（スプリント自走・TDD・セルフレビュー）と「範囲」（人間判断領域＝ A-1〜A-6 の境界）の両方の要素が残る構成であれば、文言上は充足しうる。

**ただし見落とし 1 点（要対応）**: `docs/02_requirements/minimum-requirements-checklist.md:138` に **D-3 の充足記録** として次の一文がある。

> `| D-3 | README に AI 利用の方法と範囲 | ✅ | 「AI を利用した範囲と方法（NFR-31）」節。スプリント自走・TDD 主体・セルフレビュー・PR 自律化・人間が判断する領域（A-1〜A-6）・定期運用の 6 点 |`

この行は README の現行 **6 項目すべて** を名指しして ✅ の根拠にしている（`readme_comprehensive_review` の 6 点カウントと完全一致 — README を数えた結果と一致することからも、この checklist が現行 README を正確に転記した記録であることが分かる）。**AI 節を 3 項目に圧縮すると、この checklist の ✅ 根拠が古い記述のまま残り、「転記漏れ・言い換えによる食い違い」を新たに作る**（`check_adr_coverage.py` の docstring が警戒しているのと同種のドリフト。ただしこの checklist 行自体は機械検査の対象外なので、サイレントに陳腐化する）。

**結論**: 提案1は NFR-31 の機械ゲート・与件§6 の文言要求のいずれも単独では破らないため **実行可**。ただし **同じ PR で `minimum-requirements-checklist.md:138` の D-3 行を新しい 3 項目に合わせて書き換えることを必須の随伴修正とする**（さもないと docs_consistency が指摘するのと同種の「ドキュメント間食い違い」を自ら新規作成することになる）。reader_flow の「5 項目」という前提は 6 項目の誤数えなので、圧縮設計（どの項目をどう 3 つへ畳むか）を決める際は実際の 6 項目を基準に再設計すること。
