## reader_flow — ラウンド2: 反論・譲歩

### 争点1: 提案1（目次新設 + AI節圧縮）への2つの反論に応える

**① GitHub 自動アウトラインとの重複について → 一部譲歩し、提案を縮小する。**

自動アウトライン（右上ハンバーガー）の存在は事実だが、これは **「見出しを探す」問題を解く道具**であって、私が指摘したのは **「見出しの先に何があるか分からないから開く動機がない」**という別の問題。自動アウトラインは見出しテキストの一覧を出すだけで、「設計上の判断＝与件充足の核心がここにある」という優先度シグナルは出さない。加えて、README は GitHub 上だけで読まれるとは限らない（npm/フォーク先の Markdown ビューア・raw 表示・エディタのプレビューでは自動アウトラインが出ない）ため、完全に冗長とは言えない。

ただし反論の力点（「手書き目次はコストに見合わない」）は認める。**当初案の6項目フル箇条書き目次を撤回し、次の1行に縮小する**：

```
> このREADMEで分かること: [開発手順](#開発ローカル) / [設計上の判断](#設計上の判断) / [AI利用範囲](#ai-を利用した範囲と方法nfr-31) / [ADR](#技術的意思決定の記録adr)
```

- **コスト**: +1〜2行（旧称注記の直後）。旧案の +7〜8行から大幅減。
- これにより②の懸念（AI節を削ってまで目次を作る必要があるか）が **前提ごと消える**。

**② AI節（NFR-31）圧縮が要件充足を割るリスクについて → 撤回する。**

上記の縮小により AI 節を圧縮する必要が無くなったため、**「AI を利用した範囲と方法」節の圧縮提案は撤回**する。`req_trace` のラウンド1判定（③ AI 利用の方法と範囲＝充足、6点を要約しリンク明記）にも同意する。読者導線レンズとして NFR-31 の充足を犠牲にしてまで得たい効果ではない。

### 争点2: `req_trace` の ADR 0009 等本文昇格提案 — 受け入れる条件

正面衝突ではなく **条件付き受諾**に倒す。

- **受け入れ範囲**: `ADR 0009`（Hidden Gem スコア定義）**のみ**を選択肢Aの粒度（背景+却下案+ADRリンク）で「設計上の判断」節に追加することを支持する。理由: 3読者のうち最優先の「レビュアー」が求める“工夫点”の代表例として最も説得力が強く（プロダクトの中核差別化要素であり、LP 側でも `site/index.html` の主要訴求として使われている＝読者にとって既知の文脈と接続しやすい）、1件追加なら分量への影響が読める。
- **拒否する範囲**: `ADR 0008`（ページネーション）・`ADR 0005`（Cache Port YAGNI）・`ADR 0011`（i18n自前実装）の本文昇格は **不採用**。4件すべてを本文化すると「設計上の判断」節が現行23行→50行超に倍増し、私が争点Aで指摘した「優先情報（設計判断・ADR）が中盤に埋もれ、レビュアーの到達コストが高い」という問題を **自分たちの加筆で悪化させる**ことになる（争点Fの「分量の並び順」との自己矛盾を避ける）。この3件は ADR 索引表の1行で足りる（req_trace の選択肢B）。
- **行数上限**: 追加は既存2件（D-21・AR-5）と同じ深さで **8〜10行以内**。
- **置き場所**: 既存の「設計上の判断」節の **先頭**（D-21 の前）に置く。節見出しが「設計上の判断」であり、AR-5・D-21 はどちらかというと"弁明・スコープ判断型"なので、"工夫点"の代表である Hidden Gem 定義を先頭に置く方が節タイトルへの適合度が高く、かつ争点1で作った目次アンカー（`#設計上の判断`）に到達した読者が最初に「工夫点」を目にする導線になる。
- **オフセット**: 争点1で目次を6行→1行に圧縮した分（-6〜7行）が、この+8〜10行の追加をほぼ吸収する。全体の純増は数行に収まる。

### 争点3: `docs_consistency` の5ファイル追加提案 — 1件のみ採用、4件は不採用

3読者導線で判定すると **全件同意も全件拒否もしない**。

- **採用: `domain-model.md` の1件のみ**。理由: これは `docs/README.md` 自身が「実装時に読む3つの正本」の1つと明記する必須ドキュメントで、しかも README には **既に L52 でその隣にいる `application-architecture.md`（同じ「3つの正本」の別の1つ）へのリンクがある**のに `domain-model.md` だけ抜けている、という**非対称な欠落**。コントリビュータ導線として実害がある。
  - **置き場所**: 新節を作らず、L52 の既存文に追記する（**+0〜1行**）:
    ```
    層と依存規則は [アプリケーションアーキテクチャ](...) が正本（`python3 tools/check_architecture_boundaries.py` で機械検証する）。ユビキタス言語は [ドメインモデル](./docs/03_design/data-model/domain-model.md) が正本。
    ```
- **不採用: `inception-deck.md` / `lean-canvas.md` / `user-story-map.md` / `ui-ux-guidelines.md` の4件**。理由: これらはコンセプト/要件フェーズの成果物で、私が定義した3読者（レビュアー＝設計判断とADRで足りる、OSS第三者＝LPで足りる、コントリビュータ＝実装3正本で足りる）のいずれの主要関心にも直結しない。全件追加すると、ラウンド1で述べた「README の『ドキュメント』節は厳選5点、全体構成は docs/README.md に一任」という役割分担（docs_consistency 自身の検査でも `docs/README.md` への相互リンクは ✓ 判定）を崩し、README がフルの `docs/` ツリーの二重コピーになっていく。**厳選の基準は「与件充足レンズ or 導線レンズで直接使うか」であり、この4件はどちらにも該当しない。**
- ADR 見出しプレフィックス表記の不一致（争点2の別件）は文言修正のみで読者導線に影響しないため、fact_check/docs_consistency 側の判断に委ねる（本レンズでは中立）。

### 争点4: `fact_check` の M-3（デプロイ節欠如）— 前提を一部訂正した上で不採用（新設はしない）

**事実訂正**: M-3 は「ADR 0002 へのリンクすらない」と述べているが、これは誤り。README L49（技術スタック表・実行環境行）に **既に** `[ADR 0002](./docs/adr/0002-cloudflare-workers-infrastructure.md)` へのリンクがある。「本番にどう出るか」を辿る導線はゼロではない。

**読者導線レンズとしての採否判定**:
- 3読者（レビュアー/OSS第三者/コントリビュータ）のうち、`preview:build` / `preview:upload` / `deploy` 系スクリプトを直接使うのは **人間コントリビュータではなくセッション（Claude）**であることが `docs/rules/pr-review-flow-summary.md` に明記されている（「セッションが `wrangler` を直接叩いて…デプロイする」）。つまりこれは README が案内すべき **読者の操作手順ではなく、内部運用ドキュメントの領分**。
- 新設の「デプロイ」節を作ると、争点1・2で私が繰り返し警戒している「優先度の高い情報（設計判断・ADR）をさらに後方に押しやる」問題を再発させる。**不採用**。
- 代わりに **最小コストの是正のみ**を許容する: L49 の ADR 0002 リンクの直後に「（本番/プレビュー配信の詳細）」の一言を添える程度（**+0行、既存セルの語句追加のみ**）。新節は不要という結論を維持する。
