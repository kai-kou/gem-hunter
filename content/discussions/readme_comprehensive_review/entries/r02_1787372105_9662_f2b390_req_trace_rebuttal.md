# req_trace（与件・要件充足レンズ）— round 2 rebuttal / concession

## 論点1: 選択肢 A（工夫した点の本文昇格）vs `reader_flow`（圧縮優先）は本当に正面衝突するか

**部分的に譲歩し、部分的に反論する。**

- **反論（衝突ではない部分）**: `reader_flow` 自身の指摘（ラウンド1・91-94 行）を読むと、彼らが問題視しているのは「132 行という **分量**」ではなく「**優先度の高い情報（設計上の判断・ADR）が後半に埋もれていて到達コストが高いこと**」であり、本人も明言している（「132 行は多すぎるとは言えないが、優先度の高い情報が後半にある配置が読者導線上の実害」）。彼らの解決策は **提案1: 冒頭 TOC の新設** であり、TOC が入れば「設計上の判断」節の到達コストは行数と無関係に **O(1)（1 クリック）** になる。したがって TOC 導入後は、「設計上の判断」節自体が 3〜4 行増えても `reader_flow` が問題にした「埋もれ」は再発しない。**選択肢 A と `reader_flow` の核心的懸念（到達性）は TOC によって既に分離されており、正面衝突ではない。**
- **譲歩（衝突する部分）**: ただし「総行数」そのものは共有資源であり、`reader_flow` の会計（TOC +7〜8 行、AI 節 -5〜6 行、リンク文言 +1〜2 行、旧称移動 ±0 ＝ 純増 +3〜4 行）に無制限に上乗せするのは公正でない。ここは譲歩し、**選択肢 A の粒度を D-21/AR-5 と同じフル粒度（背景+却下案+ADR リンクで各 9 行）から、1〜3 行の圧縮バレットへ縮小する**（論点2で具体化）。

**総行数の具体化**:
- ベース 132 行 → `reader_flow` の 3 提案適用後 ≈ **135〜136 行**
- 選択肢 A（縮小版・論点2 で 1 件のみ・3〜4 行）を追加 → ≈ **138〜140 行**
- **削る節**: 追加で他節を削る必要はない（TOC が到達性問題を解決済みのため、`reader_flow` が要求していたのは「削って詰める」ことそのものではなく「優先情報への到達短縮」であり、それは TOC 単独で達成済み）。132 行から 138〜140 行への 6〜8 行（約 5%）増は、`reader_flow` 自身が「132 行は多すぎるとは言えない」と評価している基準に照らして許容範囲と判断する。

**結論**: 与件 §6 / `NFR-30` の観点では **内容充足（工夫した点をゼロ件から埋める）を優先** し、`reader_flow` の懸念は「TOC 導入」で担保する。「両方やる」を採用し、上記の行数変化で決着とする。

## 論点2: 昇格させるなら何件・どれか（最大2件 → 反論して1件に絞る）

**1 件（`ADR 0009`: Hidden Gem スコア定義）のみを推奨し、「最大2件」の上限を使い切らない。**

理由（他候補との比較）:
- `ADR 0007`（DB を持たない）: 「工夫」というより **制約・インフラ判断**（Cloudflare Workers 環境の帰結）に近く、第三者が読んで「こだわり」と感じにくい。
- `ADR 0008`（ページネーション）: 与件 `FR-7` の選択肢の一つを採っただけの **標準的トレードオフ** で、独自性が薄い。すでに `minimum-requirements-checklist.md` の FR-7 行でも「ADR 0008」として言及済みであり、README 本文での重複昇格の価値は低い。
- `ADR 0005`（Cache Port の YAGNI 例外）: アーキテクチャ内部の話で、非エンジニアの第三者（採用担当者等）には文脈（YAGNI・Port/Adapter）の前提知識が要り、1〜3 行では成立しない（説明にさらに行数が要る＝論点1の行数予算と衝突する）。
- `ADR 0011`（i18n 自前実装）: 「なぜ `next-intl` を使わなかったか」という否定形の説明になり、`D-21`/`AR-5` と同じ「弁明型」のトーンに寄ってしまう（与件が求める「工夫・こだわり」は肯定的な創意の提示であるべき）。
- **`ADR 0009`（Hidden Gem スコア）**: 「被依存数に対する star の残差」という **1 文で完結する独自の定義** であり、プロダクト名（`gem-hunter` / Hidden Gem）そのものに直結する最も象徴的な工夫。前提知識なしで第三者に伝わり、**3 行で成立する**（① 何を定義したか ② なぜ単純な star 数ではないか＝こだわりの理由 ③ ADR リンク）。

**「全部載せる案」への反論**: 論点1 の行数予算（+3〜4 行が上限）に対し、4 件をフル昇格させると +30 行超になり `reader_flow` の懸念を実際に的中させてしまう。3 行程度の要約でも 4 件なら +12〜16 行必要で、それでも予算超過。**1 件・3 行が、与件の要求語彙（工夫した点・こだわり）をゼロから埋めるという最小十分な変更であり、これ以上は分量の観点で正当化できない。**

## 論点3: `reader_flow` 提案1（AI 利用範囲を 5→3 項目に圧縮）は `NFR-31` を割るか

**条件付きで可。無条件の 3 項目圧縮には反対する。**

- `NFR-31` は与件 §6 の「AI を利用した **方法と範囲**」を求めている。現行 6 項目（README.md:92-97）のうち、「**人間が判断する領域**（`A-1`〜`A-6` / `SD-3`）」の項目だけが「**範囲**」（＝ AI がどこまでやり、どこはやらないか）を明示している。残り 5 項目（スプリント自走・TDD・セルフレビュー・PR 自律化・定期運用）はすべて「**方法**」の説明であり、互いに圧縮・統合しても意味の欠落は小さい。
- **判定**: 「人間が判断する領域」の項目を **残したまま**、残り 5 項目を 2 項目程度へ統合するなら `NFR-31` を割らない（3 項目 = 方法 2 項目 + 範囲 1 項目という構成にする）。もし圧縮の過程で「人間が判断する領域」の項目そのものが削られる、あるいは他項目に埋没して独立した文として読めなくなるなら、それは与件文言の「範囲」を欠落させることになり `NFR-31` の趣旨充足を割る。
- **結論**: `reader_flow` の提案1 は「**方法系5項目→2項目、範囲系1項目は独立維持**」という条件を明記した上で採用可。無条件の「5→3」という数合わせだけで実施すると、統合時に範囲の項目が方法の記述に混ざって読み取りにくくなるリスクがあるため、この条件を PR 実装時のガードとして明記すべき。

## 論点4: `fact_check` の M-3（README にデプロイ節が無い）は `NFR-29` の範囲内か

**範囲外＝要件外の親切さの話であり、与件充足の欠落ではない。**

- `NFR-29`（`prd.md:367`）の文言は「README にセットアップ手順を記載する」で、対応する範囲は「**依存インストール・必要な環境変数・起動・テスト実行コマンド**」の 3 カテゴリのみと明示されている。「デプロイ」（`preview:build` / `preview:upload` / `deploy` 系・`ADR 0002` への導線）はこの列挙に **含まれない**（起動＝ `npm run dev` であり本番デプロイとは別概念、テスト実行＝ `npm test` / `test:e2e` で充足済み）。
- 与件 §6 の原文（`minimum-requirements.md:118`）も同じ3カテゴリの列挙であり、デプロイ手順を求める文言は無い。
- **結論**: `fact_check` の M-3 は自ら「critical ではない」「改善候補」と分類している通り、要件充足レンズとしても **NFR-29 の範囲外**（読者親切さの改善提案）と判定する。本 Issue のブラッシュアップ方針には含めてよいが、**与件充足の欠落としては扱わない**（`AC-11` の判定には影響しない）。別 Issue 化するほどの重さでもなく、README 加筆の「任意加点」枠として扱うのが妥当。
