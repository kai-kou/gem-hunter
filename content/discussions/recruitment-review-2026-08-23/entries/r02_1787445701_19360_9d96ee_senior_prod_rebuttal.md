## 1. スコープ拡張（senior_req 争点2）への評価 — 反論寄りの立場確定

**立場**: A 軸ではなく **F 軸に一本化して反映する**（senior_req の「争点2は A 軸で扱うべきか点数化しないべきか」という提起への回答）。

- senior_req の A=28（過剰実装の視認性低下で-2）には **反論** する。A 軸は与件の定義どおり「FR-1〜7 + 状態表示の充足」であり、11 項目が実コードで確認できた以上、視認性コストはA軸の減点根拠にしない方が公正。視認性コストと「指示範囲を守れているか」は本質的に同じ論点（スコープ管理）で、F 軸の「スコープ管理」項目が受け皿として存在する以上、二重に評価軸を割く必要はない。
- 私の process/scope レンズから見ると、スコープ拡張自体は **F 軸で明確な減点要因**（採用課題という文脈では「指示範囲内で完遂する」ことも評価対象であり、Gem Index・OAuth・i18n・LP・日次ダイジェスト・AI ハーネス一式は与件 11 項目に対して桁違いの実装量）。ただし「主体性」の加点余地（`AR-5` で対象外機能を実際に避けている自己制約の遵守）も認め、**F 軸を全滅点にはしない**。
- **結論**: A 軸はスコープ論を含めない（req の -2 を撤回提案）。F 軸でのみスコープ管理を評価し、5点満点中3点（後述）とする。

## 2. senior_arch の争点3減点提案（二重計上の解消）— 一本化を提案

**立場**: **同意**。arch の指摘どおり、現状 3 名とも同じ欠陥（CI 不在 + Prettier 未接続）を複数軸に分散して減点しており、二重計上になっている。私自身も round1 で C（-5相当）と D（-1）の両方に同じ欠陥を計上していた。**これは私自身の誤りとして撤回する（concession）**。

**一本化の提案**: **C 軸に完全集約する**。理由は、ルーブリックの軸定義そのものが C を「テスト（…コマンド1つ・CI実行可能性）20点」と明記しており、「CI で自動実行できる状態」も「Lint/フォーマッタで機械的に検証できる状態」も同じ性質（機械的品質ゲートの実効性）の問題だから、性質の異なる D（信頼性・セキュリティ・a11y等の実物の非機能特性）や B（設計品質そのもの）に按分する必然性がない。

- C: CI 不在（-4〜5・arch案採用）+ Prettier 未接続（125ファイルFAIL、うち実アプリコード35ファイル）を合わせて **-5** に統一。
- B: arch が計上した Prettier 由来の -2 は **撤回を提案**（同じ欠陥の二重計上のため）。B は Prettier 未接続を除いた設計・アーキテクチャ品質のみで再評価してほしい。
- D: 私が計上した -1 は **撤回する**。D 軸はセキュリティ・信頼性・a11y・レスポンシブの実物の実装品質でフルスコアに戻す。

## 3. 「32分マージ・人間関与は A-1〜A-6 のみ」の扱い — スコアに反映せず面接懸念に留める（立場を軟化）

**立場**: 自分の round1 の主張を **一部撤回・限定** する。他2名は提出物の品質そのもの（実コード・実テスト・実測値）を実物で確認しており、その評価軸（成果物の客観的品質）とは矛盾しない。私が指摘したのは「成果物の質」ではなく「候補者本人の技術力をこの成果物からどこまで読み取れるか」という **別の問い** であり、これをスコア（100点満点のルーブリック）に落とし込むと、実際には確認しようがない未知数を減点するという二重の不公正になりかねない。

- **決定**: この論点は **得点化しない**。`concerns`（面接で確認すべき懸念）に明記し、`critical`（致命的問題）には入れない。
- ただし「AI 利用申告の妥当性」自体は F 軸のルーブリックが明示的に要求する評価項目なので、**申告が誠実で裏付けが取れること自体は F 軸のプラス材料として残す**（README の記述と実際の PR ログが矛盾しない、という事実は評価してよい）。「本人の技術力が測れない」という不確実性は、点数ではなく `conditions`（条件付き合格なら面接で技術力を直接確認すること）として扱うのが最も公正。

## 4. 撤回・緩和する自分の指摘（concession）

- **Watcher = `subscribers_count`**: round1 で「与件の言葉が `watchers_count` を期待していた可能性」を保留扱いにしたが、senior_req が `repository-detail.test.tsx` の実テストで「Star数と同じ値にならないことを検証済み」と確認した（GitHub API の `watchers_count` が `stargazers_count` のミラーである事実は私も把握していた）。**この論点は撤回する**。A 軸の減点理由から完全に外してよい。
- **`next/image` 不使用**: round1 で「与件の画像最適化を素朴に満たさない」と留保したが、`avatars.githubusercontent.com` への直参照 + GitHub 側のサイズパラメータ（`?s=80`）+ 明示 `width`/`height` による CLS 防止という代替策は、Cloudflare Workers という実行環境の制約下では技術的に妥当な等価実装と判断を改める。**A 軸の減点要因からは外し、コメント（工夫点）に格下げする**。
- **telemetry/cost-data ブランチの86件の自動コミット**（senior_arch が新規提示）: これは私が round1 で挙げた「Issue/PR番号が440まで進みスコープが甚大」という指摘を裏付ける追加証拠として **取り込む**（反論ではなく補強）。F 軸のスコープ管理・運用オーバーヘッド評価にそのまま反映する。
