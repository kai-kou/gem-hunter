## 1. 争点 3 の減点幅（C -4 / B -2）と A 軸との二重減点について

**反論（一部）**。

- ルーブリック上、「CI で自動実行できる状態」は与件 §5（テスト要件）＝**C 軸**の対象、「Lint/フォーマッタで機械的に検証できる状態」は与件 §4.4 保守性（非機能）＝**D 軸**の対象であり、どちらも A 軸（§2〜3・FR/技術要件/状態表示）の採点項目には含まれない。私自身も round 1 で A=28 とした際、この論点は D 軸（12/15）側で減点しており、A 軸では減点していない。**A 軸との二重減点は起きていない**と判断する。
- 一方で **B 軸 -2 には反論する**。senior_arch が挙げた「実アプリコード 35 ファイルが Prettier 未整形」は、フォーマット（空白・引用符スタイル）の機械的未検証であって、`src/domain`/`src/usecases`/`src/infrastructure` の層分割・ACL・エラー型設計（B 軸が測る「アーキテクチャ・型安全」）の質そのものを損なう事実ではない。同じ根拠事実（prettier 未接続）を C（CI/テスト実効性）・D（保守性ゲート）に加えて B にも計上すると、1 つの構造的欠陥を 3 軸で数えることになり過剰減点になる。**B 軸の -2 は撤回し 20 点満点中 18→18 のままだが、根拠から prettier を外すことを提案する**（層/ACL/エラー型の実装品質自体は 18/20 のままで妥当）。
- C 軸の -4 には同意する。「コマンド 1 つで実行できる」（`npm run check`）とは別に「CI で自動実行できる状態」という与件の字面要件を GitHub Actions 不在（`.github/workflows` 実測ゼロ）が満たしていないのは事実であり、テストの質（908 件・E2E 21 本）が高いことと、その実行が push/PR 契機で自動化されていないことは別の問題。

## 2. YAGNI 違反（`GemIndexSortOrder` 残存 / `AuthPort` 本番無効）について

**同意（senior_arch の元の結論）+ 一部留保**。

- `AuthPort`（本番 env 未供給時は常時無効）は round 1 で自分が読んだ README（`README.md:41-44, 105`）でも確認済みの事実だが、これは **YAGNI 違反ではない**と考える。YAGNI が問題にするのは「使われていない先回り抽象化」であり、`AuthPort` は `app/api/auth/{login,callback,logout}/route.ts` で実際に使われ、テストも存在する（round 1 で `route.test.ts` の存在を確認済み）。本番で無効化されているのは「機能フラグ的に env 未供給時は安全側に倒す」という運用判断であり、コードが死んでいるわけではない。**争点 4 での senior_arch の結論（「過剰の主因はアーキテクチャでなくスコープ拡張」）に同意する**。
- `GemIndexSortOrder` の残存については、round 1 で自分が実際に読んだファイル（`sort-order.ts` 本体は未読）に含まれておらず、この場で再読もしない方針のため **確認も反証もできない**。断定は避け、事実であれば「与件外機能（Gem Index）を撤去した際の消し残し」であり、争点 4 と同じくスコープ拡張の副産物としてアーキテクチャ軸（B）でなく E/F 軸（保守性の残骸・整理不足）で軽微に扱うのが妥当と考える。

## 3. PR 高速自己マージ・人間関与が A-1〜A-6 のみという事実の扱い

**同意（スコア軸への算入は F 軸に限定すべき）**。

- ルーブリック F は「エンジニアリングプロセス（スコープ管理・PR/コミットの質・**保守可能性・AI 利用の申告の妥当性**）」と明記されており、この論点は面接送りにする性質のものではなく**明示的に F 軸の採点対象**である。README の NFR-31 節（自分が round 1 で読んだ `README.md:107-116`）が「人間の判断領域は A-1〜A-6 と仕様解釈の分岐のみ」と自己申告しており、この申告自体は誠実（虚偽記載ではない）だが、採用課題として「候補者本人の技術判断」を提出物から読み取れないという senior_prod の指摘は妥当。
- ただし **A〜E 軸（成果物の機能・品質・テスト・非機能・ドキュメント）を割り引く理由にはならない**。成果物としての品質は実測（908 テスト・zod/ACL・OAuth のセキュリティ実装等）で確認済みであり、「誰が書いたか」は成果物の出来を変えない。F 軸に限定して反映し、かつ `dissent`/`conditions`（面接で本人に判断範囲を確認すべき）として lead に明示提案する。

## 4. 争点 2（スコープ拡張の是非）: 3 名の立場の食い違い

- senior_arch は「過剰はアーキテクチャでなくスコープの帰結」とし A 軸をほぼ据え置き（26/30、保留気味）、実質ニュートラル寄り。
- senior_prod は「スコープ逸脱が甚大」と F 軸を強く減点（2/5）し、マイナス寄り。
- 私は round 1 で「与件 11 項目の視認性を下げるコスト」を A 軸に軽く反映（30→28）しつつ、`AR-5` 等の自己制約の遵守を評価してプラス材料とバランスさせる中間的立場を取った。

**この場での整理案**: スコープ拡張そのものを複数軸で重複減点しない。① A 軸は「11 項目を満たしているか」の**充足判定**に純化し、視認性コストは点数化せず `concerns`（懸念事項）へ記述で残す（A を 28→29 へ戻すことを提案）。② F 軸は senior_prod の指摘（自己完結マージ + スコープ逸脱の運用オーバーヘッド）を反映し軽めに減点する。③ 強み（`strengths`）としてスコープ拡張下でも与件の下限を守り切った実装力・ドキュメント整合を明記する。この整理なら 3 名の立場は「どの軸で表現するか」の違いに収斂でき、対立点として残す必要はないと考える。
