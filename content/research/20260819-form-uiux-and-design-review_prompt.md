# Deep Research プロンプト

## 調査テーマ

Web アプリの入力フォーム（検索フォーム）の操作性を高めるための、2026 年時点の UI/UX トレンド・ノウハウ・ベストプラクティスと、開発プロセスに「デザイン観点のレビュー」を組み込むための運用ノウハウ・既存のスキル/エージェント定義資産を調査する。

対象アプリの前提: Next.js（App Router / RSC 主体）+ Tailwind CSS v4 + shadcn/ui（Radix UI ベース）で作る GitHub リポジトリ検索アプリ。現状は検索入力欄とボタンがいずれも高さ 32px（`h-8`）・フォント 14px で、モバイルで押しにくく iOS でフォーカス時ズームが起きる。

## 調査項目

- 入力欄・ボタンの推奨寸法（高さ・パディング・フォントサイズ）の一次情報。Material Design 3 / Apple HIG / GOV.UK Design System / MOJ Design System / GitHub Primer / shadcn/ui の各実寸ガイダンスを比較し、「デスクトップ最小」「モバイル最小」を数値で確定できる材料を集める
- WCAG 2.2 の Target Size (Minimum) 2.5.8（24×24 CSS px）と Target Size (Enhanced) 2.5.5（44×44 CSS px）の正確な要件・例外条項（間隔の例外・インライン例外等）、および 2.5.8 を満たすだけでは実操作性が不足するケース
- iOS Safari の 16px 未満フォントでの自動ズーム挙動、`maximum-scale` を使わずに回避する正しい実装（フォントサイズ / `text-size-adjust` 等）と、それが a11y（拡大の抑止禁止）に抵触しない条件
- 2026 年の検索フォーム UI のトレンドとベストプラクティス（入力欄とボタンの関係、モバイルでの縦積み/横並び、クリアボタン、`type="search"` の扱い、キーボード種別、オートコンプリート、送信時のフィードバック、レイアウトシフト回避）
- Tailwind CSS v4 + shadcn/ui で上記を満たす実装パターン（レスポンシブなサイズ出し分け、タッチターゲットの疑似要素拡張、フォーカスリング、`size` variant の設計、デザイントークン化）
- デザインレビュー / デザイン QA をレビュー工程に組み込む運用ノウハウ（実施タイミング、チェックリストの粒度、判定の出し方、開発者レビューとの役割分担、失敗パターン）
- AI エージェントによるデザインレビューの実践例と公開資産（Anthropic 公式の Agent Skills、Claude Code のコミュニティ製 design-review エージェント/スキル、Playwright 等で実画面を見て判定させる手法、視覚回帰テストとの併用）。実際に流用できる定義の構造（役割・観点リスト・出力形式）を具体的に抽出する

## 出力要件

- docs/rules/research-rules.md の品質基準（情報ランク A/B/C・official_names・5〜7 セクション・出典 8 件以上）に従う
- 🔴 実装指針にそのまま落とせる「判定できる数値」（px 値・比率・しきい値）と、その出典 URL を必ずセットで示す
- 推奨が資料間で食い違う場合は、食い違い自体を明示し、どの条件でどちらを採るかを提示する
