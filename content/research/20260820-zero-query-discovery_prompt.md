# リサーチプロンプト: キーワード入力に依存しない OSS 発見体験（zero-query discovery）の UI/UX

- **ID**: `20260820-zero-query-discovery`
- **作成日**: 2026-08-20 JST
- **依頼元**: Issue #218（MVP 後の開発方針決定）

## 0. 背景（プロダクト文脈）

`gem-hunter` は「star の多さでは埋もれてしまう、実際に使われている OSS を個人開発者が見つけられるようにする」検索プラットフォーム。MVP（キーワード検索 → 一覧 → 詳細 → 復帰）は完成済み。

次の段階として、**ユーザーがキーワードを思いつかなくても、リマインド的に「これ良さそう」というリストが提示される体験**を作りたい。初期コンセプトでは「セレンディピティ・レコメンド（週刊ダイジェスト）」「Gem Score（過小評価度）」として構想されていたが、UI/UX の具体像が無い。

### 動かせない制約（提案はこの中で成立すること）

| 制約 | 内容 |
|---|---|
| データベースを持たない | 状態は `localStorage` / Cookie / URL / 静的データ配信（バッチ生成した JSON 等）のみ。DB 導入は最後の手段 |
| ログイン必須にしない | GitHub OAuth は任意で、ログインしてもレート枠が変わるだけ。機能差を作らない |
| サーバーに個人データを持たない | IP・検索キーワード・閲覧履歴・ユーザー識別子をサーバー側に記録しない（ログ出力も禁止） |
| 実行基盤 | Cloudflare Workers（Free 枠: p95 CPU 10ms・バンドル 3MB gzip）+ Next.js（OpenNext アダプタ） |
| 健全性スコアを自作しない | OpenSSF `criticality_score` / Scorecard 等の既存指標に依存する |
| 被依存数のデータ源 | Ecosyste.ms（CC BY-SA 4.0・出典表示義務あり）。GitHub API では取得できない |
| アクセシビリティ | Lighthouse Accessibility 100・キーボードのみで完走可能が必須ゲート |

## 1. 調査の目的

「キーワードを入力しない発見体験」を実現する UI/UX パターンを、**2025〜2026 年の最新事例と研究知見**から網羅的に集め、上記制約下で採用可能なものを評価できる状態にする。

## 2. 解空間の軸（この 5 軸で網羅すること・特定の軸に偏らないこと）

1. **発見のトリガー**: 時間（定期配信）/ 文脈（ユーザーの技術スタック・依存関係）/ 偶然（ランダム・シャッフル）/ 他者（ソーシャル・キュレーション）/ 状態（前回訪問からの差分）
2. **状態の置き場所**: URL / `localStorage` / Cookie / 静的配信データ / クライアント側計算 / 外部購読（RSS・メール・Webhook）
3. **提示の器**: 無限フィード / 定期ダイジェスト / カードスタック（スワイプ）/ ダッシュボード / 通知・購読 / 埋め込みウィジェット / CLI・IDE 拡張 / MCP サーバー
4. **パーソナライズの深さ**: 全員同じ（匿名）/ ローカル履歴による弱い個人化 / 明示的な購読設定 / 入力ファイル（`package.json` 等）による推論
5. **推薦の質の目的関数**: 関連度 / 新規性（novelty）/ 多様性（diversity）/ セレンディピティ / 過小評価度（underrated-ness）

## 3. 調査項目（セクション構成の目安）

1. **zero-query / query-less discovery の UI パターンの現在地（2025〜2026）**
   - 検索窓に依存しない発見体験の代表的パターンと、それぞれが解いている問題
   - 「フィード疲れ」「無限スクロール離れ」に対する反動として何が起きているか（有限性の設計・"daily" 制約・締切のある UI）
   - Wordle 型の「1 日 1 回・有限」体験、Product Hunt / Hacker News / Arc Max / Perplexity Discover / Hugging Face Daily Papers 等の実装差
2. **OSS・開発者向けディスカバリー製品の事例研究**
   - GitHub Explore / Trending、OpenSauced、Ecosyste.ms、libraries.io、npm trends、Openbase（終了）、awesome リスト、Bytes/JavaScript Weekly 等のニュースレター
   - 何が成功し、何が失敗したか（特に「新規性の枯渇」「同じものが上位に居座る」問題への対処）
   - 開発者が実際に OSS を発見している経路の調査データ（Stack Overflow / JetBrains / GitHub Octoverse 等の年次調査があれば）
3. **AI エージェント時代の発見体験の変化（2025〜2026）**
   - LLM / コーディングエージェントがライブラリ選定を代行し始めたことで、人間向け発見 UI に何が求められるか
   - MCP サーバー・エージェント向けデータ提供という「UI ではない提示面」の可能性
   - AI 生成スロップ・偽 star 問題と、信頼できる指標の提示方法
4. **セレンディピティ推薦の設計原則（研究知見）**
   - recommender systems におけるセレンディピティ / novelty / diversity の定義と評価指標
   - フィルターバブル回避、探索と活用のバランス（exploration-exploitation）
   - コールドスタート（ユーザー情報がゼロ）での推薦手法。特に **ログイン不要・DB なし** で成立するもの
5. **ログイン不要・DB レスでパーソナライズする実装パターン**
   - `localStorage` / Cookie / URL に状態を持たせた個人化の実例と限界（端末間非同期をどう UI で伝えるか）
   - 静的に事前計算したデータ配信（JSON / エッジキャッシュ）でどこまで「個人化に見える」体験を作れるか
   - ユーザーが `package.json` / `requirements.txt` を貼る・アップロードする形の文脈入力（サーバーに保存しない前提）の UX 事例
   - プライバシー配慮を訴求点にしている製品の UI 上の伝え方
6. **「過小評価度」のような独自スコアを提示する UI/UX**
   - スコアの説明可能性（なぜこれが推薦されたかを示す UI）、信頼を得るための出典表示
   - 指標が 1 つの数値に潰れることへの批判と、代替の提示方法（レーダー・複数軸・バッジ）
   - スコアが操作（gaming）される懸念への対処
7. **アクセシビリティとパフォーマンスの観点での注意点**
   - フィード / カードスタック / 無限スクロール系 UI のアクセシビリティ上の既知の問題と回避策（WCAG 2.2）
   - エッジ実行・低 CPU 予算下でのフィード生成の現実的な手法
